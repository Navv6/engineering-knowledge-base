## 0. 한눈에 보기 (입문)

### 한 줄 요약
컴퓨터는 모든 수를 0과 1(2진수)로, 그것도 **정해진 칸 수 안에** 저장한다. 그래서 정수는 너무 크면 넘치고, 0.1 같은 소수는 정확히 담기지 않아 아주 작은 오차가 생긴다. 돈이나 ID처럼 오차가 있으면 안 되는 값은 저장 방식을 따로 골라야 한다.

### 쉬운 설명
1을 3으로 나누면 0.3333…이 끝없이 이어진다. 종이에 소수점 아래 다섯 자리까지만 쓸 수 있다면 0.33333으로 끊어야 하고, 이걸 세 번 더하면 0.99999가 되어 1이 아니다.

컴퓨터도 똑같은 일을 겪는다. 다만 컴퓨터는 10진수가 아니라 **2진수**를 쓰는데, 2진수에서는 **0.1이 1/3처럼 끝없이 이어지는 수**다. 그래서 0.1을 정해진 칸에 맞춰 반올림해 저장하고, 0.1 + 0.2를 하면 0.30000000000000004가 나온다. 계산기가 고장 난 것이 아니라 "칸 수가 정해진 기록 방식"의 성질이다.

정수에도 한계가 있다. 자동차 주행거리계가 999999km 다음에 000000으로 돌아가듯, 칸 수를 넘는 정수는 넘쳐서 엉뚱한 값이 된다(**오버플로**, overflow).

실무에서 기억할 것:
- **돈:** 소수(float)로 계산하지 말고 원·센트 단위 정수나 DECIMAL(정확한 10진 소수) 형식을 쓴다.
- **ID·코드:** 숫자처럼 보여도 계산할 일이 없으면 **문자열**로 다룬다. 앞자리 0이 사라지거나 큰 수가 바뀌는 사고를 막는다.
- **비교:** 소수끼리는 `==`로 비교하지 말고 "차이가 아주 작으면 같다"로 비교한다.

### 내 프로젝트에서는
- **Preflight — 엑셀 값으로 행 식별:** 엑셀 원본은 브라우저에서 SheetJS로 파싱하고, 행 번호 대신 **원본 값으로 행을 식별**하도록 바꿨다(ADR-03, 포트폴리오 기재). 엑셀은 숫자 칸을 부동소수점으로 저장하므로, 품목 코드처럼 숫자로 된 식별자가 숫자로 읽히면 앞자리 0이 사라지거나(001234 → 1234) 아주 긴 코드의 끝자리가 바뀔 수 있다. 식별 키를 문자열로 정규화하는 것이 안전하다. 실제로 Preflight에서 이런 문제가 있었는지는 기록이 없어 점검 질문으로 남긴다(10절).
- **DeepVi:** 재무 데이터를 PostgreSQL에 저장했다(README 기재). 금액 칸이 `numeric`인지 `double precision`인지는 기록이 없다. 금액 합계를 정확히 맞춰야 한다면 `numeric`이 맞다(8절).
- **STT 평가:** WER 0.5001, RTF 0.2493처럼 소수 넷째 자리까지 기록했다. 이런 지표는 근사값이라 부동소수점으로 충분하고, 보고할 때 자리수를 정해 반올림하는 것이 맞다.

### 먼저 알면 좋은 것
- 지수와 로그(MATH-BASE-002): $2^{10} = 1024$, 지수 표기 $1.5 \times 10^{3}$
- 파일 형식과 문자 인코딩(CS-DATA-001): 모든 데이터가 결국 바이트라는 관점

## 1. 핵심 요약

- **2진수:** 컴퓨터는 수를 0과 1의 자리(비트)로 저장한다. $n$비트로 표현할 수 있는 값은 $2^n$가지.
- **정수:** 부호 있는 정수는 **2의 보수**로 저장한다. 8비트는 −128~127, 32비트는 −2,147,483,648~2,147,483,647. 범위를 넘으면 **오버플로**.
- **부동소수점(IEEE 754):** 수를 $\pm 1.xxx_2 \times 2^{e}$ 꼴로 저장. 배정밀도(double, 64비트)는 부호 1 + 지수 11 + 가수 52비트, 10진 유효숫자 약 15~17자리.
- **반올림 오차:** 0.1처럼 2진수로 끝나지 않는 수는 근사값으로 저장된다. 오차는 계산을 거듭하면 쌓인다.
- **안전한 정수 한계:** double은 $2^{53} = 9{,}007{,}199{,}254{,}740{,}992$까지만 모든 정수를 정확히 표현한다. JavaScript의 `Number`가 double이라 큰 ID가 바뀔 수 있다.
- **선택 기준:** 근사로 충분한 측정값·지표는 float, 돈은 정수(최소 단위)나 DECIMAL, ID·코드는 문자열.

## 2. 개념과 등장 배경

초기 컴퓨터는 제조사마다 소수를 저장하는 방식이 달라, 같은 프로그램이 기계마다 다른 결과를 냈다. 1985년 IEEE 754 표준이 부동소수점 형식과 반올림 규칙을 통일했고, 윌리엄 카핸(William Kahan)이 표준 제정을 이끈 공로로 1989년 튜링상을 받았다. 지금은 CPU, GPU, 프로그래밍 언어, 데이터베이스 대부분이 이 표준을 따른다(현재판은 IEEE 754-2019).

1991년 데이비드 골드버그(David Goldberg)의 논문 "What Every Computer Scientist Should Know About Floating-Point Arithmetic"은 부동소수점 오차의 원리를 정리한 고전으로 지금도 널리 읽힌다.

## 3. 직관적 설명 및 기초 이론

### 2진수 읽기

10진수 $253 = 2 \times 10^2 + 5 \times 10^1 + 3 \times 10^0$이듯, 2진수 $1101_2 = 1 \times 2^3 + 1 \times 2^2 + 0 \times 2^1 + 1 \times 2^0 = 8 + 4 + 0 + 1 = 13$이다.

소수점 아래도 같다. $0.101_2 = 1 \times 2^{-1} + 0 \times 2^{-2} + 1 \times 2^{-3} = 0.5 + 0.125 = 0.625$.

### 왜 0.1은 끝나지 않는가

10진수에서 분모가 2와 5로만 이루어진 분수(1/2, 1/4, 1/5, 1/8)는 유한 소수다. 2진수에서는 분모가 **2로만** 이루어진 분수(1/2, 1/4, 1/8)만 유한 소수다. $0.1 = 1/10$은 분모에 5가 있어서 2진수로 끝나지 않는다.

$$
0.1 = 0.0\,0011\,0011\,0011\,\ldots_2
$$

반대로 0.5, 0.25, 0.125, 0.75는 2진수로 정확히 표현된다.

### 과학적 표기법

부동소수점은 과학적 표기법과 같은 생각이다. $6{,}020{,}000 = 6.02 \times 10^{6}$처럼 **유효숫자**와 **지수**를 따로 적으면, 아주 큰 수와 아주 작은 수를 같은 칸 수로 다룰 수 있다. 대신 유효숫자 칸 수가 정해져 있어 **상대적 정밀도**가 일정하다. 큰 수일수록 표현할 수 있는 값 사이의 간격이 넓어진다.

## 4. 엄밀한 정의와 작동 원리

### 2의 보수 정수

$n$비트 부호 있는 정수에서 가장 왼쪽 비트의 자리값을 $-2^{n-1}$로 본다. 8비트 $1111\,1111_2 = -128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = -1$. 범위는 $-2^{n-1}$ ~ $2^{n-1} - 1$이다. 덧셈 회로 하나로 양수·음수를 같이 계산할 수 있어 쓰인다. $127 + 1$을 8비트로 계산하면 $1000\,0000_2 = -128$이 된다(오버플로).

### IEEE 754 배정밀도

64비트를 부호 $s$(1비트), 지수 $E$(11비트), 가수 $f$(52비트)로 나눠, 정규화된 수를

$$
x = (-1)^{s} \times 1.f_2 \times 2^{E - 1023}
$$

로 해석한다. 앞자리 1은 항상 1이라 저장하지 않으므로 실제 정밀도는 53비트다. 특수값: $E$가 모두 0이면 0과 비정규수, 모두 1이면 무한대(Inf)와 NaN(Not a Number).

| 형식 | 전체 | 지수 | 가수 | 10진 유효숫자 |
|---|---|---|---|---|
| 단정밀도(float32) | 32 | 8 | 23 | 약 7자리 |
| 배정밀도(float64) | 64 | 11 | 52 | 약 15~17자리 |
| 반정밀도(float16) | 16 | 5 | 10 | 약 3자리 |

### 반올림과 기계 엡실론

계산 결과는 표현 가능한 가장 가까운 값으로 반올림된다(기본: 가장 가까운 값, 동률이면 짝수 쪽). 1과 그다음 표현 가능한 수의 차이를 **기계 엡실론** $\varepsilon = 2^{-52} \approx 2.22 \times 10^{-16}$이라 하고, 한 번의 연산에서 상대 오차는 최대 $\varepsilon / 2$다.

### 안전한 정수

가수가 53비트이므로 $2^{53}$까지의 정수는 모두 정확히 표현되지만, 그 위에서는 간격이 2 이상이 된다. JavaScript에서 `2**53 + 1`은 `9007199254740992`로 나온다. `Number.MAX_SAFE_INTEGER`는 $2^{53} - 1$이다.

### 오차가 커지는 연산

- **누적:** 작은 오차가 반복 덧셈으로 쌓인다(6절 예제 2).
- **큰 수 + 작은 수:** $10^{16} + 1$은 $10^{16}$이다. 작은 쪽이 간격보다 작아 사라진다.
- **비슷한 수의 뺄셈(상쇄):** 앞자리가 같은 두 수를 빼면 유효숫자가 대부분 사라져 상대 오차가 커진다.

## 5. 수식 및 기호 설명

| 기호 | 읽기 | 뜻 |
|---|---|---|
| $1101_2$ | 2진수 1101 | 아래 첨자 2는 2진수라는 표시 |
| $s, E, f$ | 부호, 지수, 가수 | IEEE 754의 세 부분 |
| $1.f_2$ | 일 점 에프 | 맨 앞 1이 생략된 2진 유효숫자 |
| $\varepsilon$ | 엡실론 | 기계 엡실론, double에서 $2^{-52}$ |
| NaN | 낸 | 정의되지 않은 결과(0/0 등). 자기 자신과도 같지 않다 |
| Inf | 무한대 | 범위를 넘은 결과(1/0 등) |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 13과 0.625를 2진수로

- 13: 2로 나눈 나머지를 거꾸로 읽는다. 13 → 6 나머지 1, 6 → 3 나머지 0, 3 → 1 나머지 1, 1 → 0 나머지 1. 거꾸로 $1101_2$.
- 0.625: 2를 곱해 정수 부분을 차례로 읽는다. 0.625 × 2 = 1.25 → 1, 0.25 × 2 = 0.5 → 0, 0.5 × 2 = 1.0 → 1. $0.101_2$로 끝난다.
- 0.1: 0.2 → 0, 0.4 → 0, 0.8 → 0, 1.6 → 1, 1.2 → 1, 0.4 → 0, 0.8 → 0, 1.6 → 1, … 0.4부터 반복되어 끝나지 않는다.

### 예제 2. 0.1을 계속 더하기

0.1을 10번 더하면 `0.9999999999999999`, 100번 더하면 `9.99999999999998`이 나온다(오차 약 $1.95 \times 10^{-14}$). 매번 반올림된 값에 반올림된 0.1을 더해 오차가 쌓인다. 금액을 **10원 단위 정수**처럼 최소 단위 정수로 더하면(10을 100번 더해 1000, 표시할 때만 나눔) 오차가 전혀 없다.

### 직접 해보기

```runjs
// @title 0.1을 n번 더할 때 오차가 생기는 횟수
// @label 기대값과 달라진 단계 수
// @param n | 더하는 횟수 | 1 | 100 | 10 | 1
// @param useInt | 정수(최소 단위)로 계산(0 = 소수, 1 = 정수) | 0 | 1 | 0 | 1
// @expect n=10, useInt=0 => 4
// @expect n=100, useInt=0 => 89
// @expect n=10, useInt=1 => 0
let sum = 0, cents = 0, bad = 0;
const rows = [];
for (let k = 1; k <= n; k++) {
  sum += 0.1;          // 소수로 0.1씩
  cents += 10;         // 1/100 단위 정수로 10씩 (0.1 = 10/100)
  const v = useInt ? cents / 100 : sum;
  const ok = v === k / 10;
  if (!ok) bad++;
  if (k <= 10 || k === n) rows.push([k, String(v), ok ? '같음' : '다름']);
}
table(rows, ['단계 k', '누적값', 'k/10과 비교']);
log('0.1 + 0.2 =', 0.1 + 0.2, ' / 2**53 + 1 =', 2 ** 53 + 1);
result(bad);
```

### 예제 3. 큰 ID가 바뀌는 사고

JSON `{"id": 1234567890123456789}`를 JavaScript로 읽으면 `1234567890123456800`이 된다. 19자리 정수는 $2^{53}$(16자리)을 넘어 가장 가까운 double로 반올림되기 때문이다. 그래서 많은 API가 큰 ID를 문자열(`"id": "1234567890123456789"`)로 보낸다(REST API 설계, SE-API-001).

### 예제 4. 반올림 표시의 함정

`(1.005).toFixed(2)`는 `"1.01"`이 아니라 `"1.00"`이다. 1.005는 실제로 1.00499999999999989…로 저장되기 때문이다. 금액 반올림 규칙이 중요한 곳(세금, 정산)에서는 DECIMAL 형식과 반올림 규칙을 명시한다.

## 7. 시각화와 해석

수직선 위에 double로 표현 가능한 값들을 점으로 찍으면, 0 근처에서는 촘촘하고 멀어질수록 간격이 2배씩 넓어진다. $[1, 2)$ 구간의 간격은 $2^{-52}$, $[2^{52}, 2^{53})$ 구간의 간격은 1, 그 위는 2다. "상대 오차는 일정하고 절대 오차는 값에 비례한다"는 성질이 그림으로 보인다. 지수 축(로그 축)으로 그리면 각 구간이 같은 폭이 된다(지수와 로그, MATH-BASE-002).

## 8. 기술 비교 및 선택 기준

| 데이터 | 권장 형식 | 이유 |
|---|---|---|
| 측정값, 확률, 점수, 임베딩 | float64(또는 float32) | 근사로 충분, 빠름, 메모리 효율 |
| 돈, 정산, 세금 | 최소 단위 정수(원, 센트) 또는 DECIMAL/NUMERIC | 합계가 정확해야 함 |
| 개수, 수량 | 정수(범위 확인) | 오차 없음. 32비트 범위(약 21억)를 넘을지 확인 |
| ID, 코드, 전화번호, 우편번호 | 문자열 | 계산 안 함, 앞자리 0·자릿수 보존 |
| 매우 큰 정수 | 64비트 정수(BIGINT), JS에서는 BigInt나 문자열 | $2^{53}$ 초과 시 double 손실 |

PostgreSQL의 `numeric`은 정확한 10진 계산(속도는 느림), `real`/`double precision`은 IEEE 754 부동소수점이다. 공식 문서는 금액처럼 정확성이 필요하면 `numeric`을 쓰라고 안내한다. 머신러닝은 반대로 정밀도를 **낮춰** 속도와 메모리를 얻는다. float16·bfloat16·8비트 양자화가 그 예다(미세조정과 LoRA, AI-FT-001).

## 9. 실무 사례

- **엑셀 숫자:** 엑셀은 숫자를 double로 저장하고 15자리까지만 유효숫자로 다룬다. 16자리 카드번호나 긴 주문번호를 숫자 칸에 입력하면 끝자리가 0으로 바뀐다. 텍스트 칸으로 지정해야 한다.
- **소수 비교:** 테스트에서 `expect(a).toBe(0.3)` 대신 허용 오차 비교(`toBeCloseTo`)를 쓴다. 이 학습 사이트의 '직접 해보기'도 결과 비교에 허용 오차 $10^{-6}$을 쓴다.
- **집계 순서:** 대량의 float를 더할 때 순서에 따라 결과가 미세하게 달라진다. 병렬 집계(여러 작업자가 나눠 더함) 결과가 실행마다 마지막 자리에서 다를 수 있다.
- **센서·로그 시간:** 초 단위 시각을 float32로 저장하면 정밀도가 약 7자리라 큰 타임스탬프의 밀리초가 사라진다. 정수 밀리초나 64비트를 쓴다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 비표준 xlsx 정규화:** ExcelJS·SheetJS가 모두 읽지 못한 ERP 파일을 보정하는 정규화 모듈을 만들었다. 점검 질문: 이 정규화 단계에서 품목 코드·워크센터 코드처럼 숫자로 보이는 식별자를 문자열로 고정하는가? 엑셀에서 숫자 칸이었던 코드는 앞자리 0이 이미 사라진 채 올 수 있어, 자릿수 규칙으로 복원할지도 정해야 한다.
- **Preflight — 원본 값으로 행 식별(ADR-03):** 행 식별 키에 숫자 칸이 포함되면 "같은 값"의 판단이 표현 방식에 따라 흔들릴 수 있다(1234 vs "1234" vs 1234.0). 키를 만들 때 문자열로 정규화하고 반례 테스트(ADR-02처럼)를 두면 안전하다.
- **Preflight — 지표 계산:** 준수율 같은 비율은 float로 계산해도 되지만, 화면과 보고서의 반올림 자리수와 방식을 한곳에서 정하면 "화면 87.5%, 보고서 87.4%" 같은 불일치를 막는다.
- **DeepVi — 재무 수치:** 재무 데이터를 PostgreSQL에 저장했다. 점검 질문: 매출·자산 같은 금액 칸의 타입은 무엇인가? 합계·비율 검증이 원 단위로 맞아야 한다면 `numeric`, 지표 계산용이면 `double precision`도 충분하다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 부동소수점은 부정확하다.** 정확히 표현되는 수(0.5, 정수 $2^{53}$ 이하)는 정확하고, 오차는 정해진 규칙대로 생긴다. "예측 가능한 근사"다.
- **오해: double이면 돈도 괜찮다.** 한 번은 괜찮아 보여도 합계·반올림에서 원 단위 차이가 생긴다.
- **오해: DECIMAL이 항상 낫다.** 정확하지만 느리고, 1/3 같은 수는 DECIMAL도 정확히 담지 못한다. 과학 계산·머신러닝에는 맞지 않는다.
- **NaN 전파:** NaN이 하나 섞이면 합계·평균이 모두 NaN이 된다. `NaN === NaN`은 거짓이라 일반 비교로 찾을 수 없고 `Number.isNaN`으로 확인한다.
- **언어마다 다름:** Python의 `int`는 크기 제한이 없지만 `float`는 double이다. JavaScript는 `Number` 하나(double)와 `BigInt`가 있다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 2진수 1011을 10진수로, 10진수 0.75를 2진수로 바꾸면?</summary>

**정답.** $1011_2 = 8 + 0 + 2 + 1 = 11$. $0.75 = 0.5 + 0.25 = 0.11_2$.

**해설.** 0.75는 분모가 4(2의 거듭제곱)라 2진수로 정확히 끝난다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 8비트 부호 있는 정수에서 127에 1을 더하면 어떻게 되며, 왜 그런가?</summary>

**정답.** −128이 된다. 결과 비트 $1000\,0000_2$에서 맨 왼쪽 비트의 자리값이 $-128$이기 때문이다(2의 보수, 오버플로).

**해설.** 언어에 따라 오류를 내거나(검사하는 경우), 조용히 돌아가거나, 정의되지 않은 동작이 된다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 주문 금액을 JavaScript에서 원 단위 소수(예: 1234.5원)로 계산하다가 합계가 1원씩 틀리는 문제가 생겼다. 어떻게 고치겠는가?</summary>

**정답.** 금액을 최소 단위(예: 0.1원 단위면 10배 한 정수)로 바꿔 정수로 계산하고, 표시할 때만 나눈다. DB는 `numeric`(DECIMAL)으로 저장하고, 반올림 규칙(어느 단계에서, 어떤 방식으로)을 한곳에 정한다. 금액이 $2^{53}$을 넘을 수 있으면 BigInt나 서버 측 DECIMAL 계산을 쓴다.

**해설.** 오차의 원인은 0.1 같은 소수를 2진 부동소수점으로 다루는 데 있다. 단위를 바꿔 정수 문제로 만든다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 엑셀 업로드 기능에서 품목 코드 "000123"이 DB에 "123"으로 저장되는 문제가 보고되었다. 원인과 대책은?</summary>

**정답.** 엑셀 칸이 숫자 형식이거나 파서가 숫자로 해석해 앞자리 0이 사라졌다. 대책: 파서에서 해당 칸을 문자열로 읽도록 지정(raw 텍스트 또는 표시 문자열 사용), 코드 자릿수 규칙이 있으면 정규화 단계에서 복원, DB 칸은 문자열 타입, 그리고 "000123" 같은 반례를 테스트에 추가한다.

**해설.** 식별자는 계산하지 않으므로 처음부터 끝까지 문자열로 다루는 것이 원칙이다(CS-DATA-001, DE-DQ-001).

</details>
