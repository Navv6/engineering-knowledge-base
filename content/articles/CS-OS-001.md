## 0. 한눈에 보기 (입문)

### 한 줄 요약
**프로세스**는 실행 중인 프로그램 하나(자기만의 메모리를 가진 방), **스레드**는 그 방 안에서 일하는 사람이다. **동시성**은 여러 일을 번갈아 진행하는 것이고, 같은 것을 동시에 건드릴 때 생기는 문제를 다루는 것이 동시성 프로그래밍의 핵심이다.

### 쉬운 설명
식당 주방을 떠올리자.

- **프로세스 = 주방 하나.** 주방마다 냉장고와 도구가 따로 있다. 옆 주방 냉장고는 함부로 못 연다(메모리 분리). 한 주방에 불이 나도 옆 주방은 멀쩡하다.
- **스레드 = 한 주방의 요리사들.** 같은 냉장고와 도마를 함께 쓴다(메모리 공유). 협업이 빠르지만, 두 사람이 마지막 달걀 하나를 **동시에** 집으려 하면 문제가 생긴다.
- **동시성:** 요리사 한 명이 국을 끓이는 동안 기다리지 않고 채소를 썬다. 한 사람이 여러 일을 번갈아 한다.
- **병렬성:** 요리사 여러 명이 정말로 같은 순간에 각자 일한다. CPU 코어가 여러 개일 때 가능하다.

가장 흔한 버그는 "두 사람이 같은 것을 동시에 고치는" 데서 나온다. 재고 장부에 두 요리사가 동시에 "달걀 10개 → 9개"라고 쓰면, 실제로는 2개를 썼는데 장부엔 9개가 남는다.

### 내 프로젝트에서는
- **이 학습 사이트에서 실제로 경쟁 상태를 고쳤다.** 화면을 옮길 때 3D 시각화를 비동기로 불러오는데, 불러오기가 늦게 끝나면 **이미 떠난 화면의 3D 장면이 메모리에 남아** 페이지가 무거워지는 문제가 있었다. 화면이 바뀔 때마다 번호(route token)를 1씩 올리고, 늦게 도착한 작업은 자기 번호가 현재 번호와 다르면 스스로 정리하게 고쳤다(`src/app.js`, 6절 예제 3).
- **Preflight는 엑셀을 브라우저에서 파싱한다.** 원본 파일을 밖으로 보내지 않으려고 파싱을 브라우저에서 하고 결과값만 서버에 보낸다(포트폴리오 기재). 큰 파일을 화면과 같은 스레드에서 파싱하면 그동안 화면이 멈춘다. 이럴 때 쓰는 것이 웹 워커(별도 스레드)다. Preflight가 워커를 썼는지는 기록이 없으니 점검 질문으로 남긴다.
- **PostgreSQL은 접속마다 프로세스를 하나씩 만든다.** 공식 문서가 "process per user" 모델이라고 설명한다. DeepVi와 Preflight 모두 PostgreSQL을 썼으니, 동시 접속이 많아지면 접속 수 자체가 서버 자원을 쓴다는 점을 알아 두면 좋다(커넥션 풀이 필요한 이유).

### 먼저 알면 좋은 것
- 특별한 선행 지식은 필요 없다. 트랜잭션과 ACID(DE-DB-002)의 갱신 손실을 읽었다면 6절 예제 1이 더 쉽다.

## 1. 핵심 요약

- **프로세스:** 독립된 주소 공간(메모리)을 가진 실행 단위. 격리가 강하고 생성·전환 비용이 크다.
- **스레드:** 한 프로세스 안의 실행 흐름. 메모리를 공유하므로 통신이 싸지만 동기화가 필요하다.
- **동시성 vs 병렬성:** 동시성은 여러 작업이 겹친 기간에 진행되는 구조, 병렬성은 실제로 같은 순간에 실행되는 것.
- **경쟁 상태:** 결과가 실행 순서(타이밍)에 따라 달라지는 버그. 공유 데이터를 고치는 구간(임계 구역)을 잠금이나 원자적 연산으로 보호한다.
- **교착 상태:** 서로가 가진 자원을 기다리며 아무도 진행하지 못하는 상태. 잠금 순서를 통일해 막는다.
- **이벤트 루프:** 스레드 하나가 I/O 완료 알림을 받아 콜백을 처리하는 방식(Node.js, 브라우저). 기다림이 많은 일에 강하지만, 무거운 계산은 루프를 막으므로 워커로 뺀다.
- **암달의 법칙:** 병렬화할 수 없는 부분이 전체 속도 향상의 상한을 정한다.

## 2. 개념과 등장 배경

초기 컴퓨터는 한 번에 프로그램 하나만 실행했다(일괄 처리). 1960년대 시분할 시스템은 CPU를 짧은 시간 조각으로 나눠 여러 사용자의 프로그램을 번갈아 실행했고, 이때 각 프로그램을 보호하기 위해 **프로세스**와 독립된 메모리 공간 개념이 자리 잡았다. 에츠허르 다익스트라는 1965년 상호 배제 문제와 세마포어를 제시했고, "식사하는 철학자" 문제로 교착 상태를 설명했다.

1990년대에는 하나의 프로그램 안에서 여러 일을 가볍게 나눠 하는 **스레드**가 보편화되었다. 2000년대 중반 CPU 클럭 속도 향상이 한계에 부딪히고 멀티코어가 표준이 되면서, 성능을 얻으려면 병렬 프로그래밍이 필수가 되었다. 한편 웹 서버처럼 "대부분의 시간을 네트워크·디스크를 기다리는" 프로그램에서는 스레드를 수천 개 만드는 대신, 스레드 하나로 수많은 연결을 처리하는 **이벤트 루프** 방식(nginx, Node.js)이 널리 쓰이게 되었다.

## 3. 직관적 설명 및 기초 이론

### 프로세스 vs 스레드

| 항목 | 프로세스 | 스레드 |
|---|---|---|
| 메모리 | 각자 분리 | 같은 프로세스 안에서 공유 |
| 생성·전환 비용 | 큼 | 작음 |
| 통신 | 파이프, 소켓, 공유 메모리 등 별도 장치 | 그냥 같은 변수를 읽고 씀 |
| 하나가 죽으면 | 다른 프로세스는 영향 적음 | 같은 프로세스 전체가 위험 |
| 예 | 브라우저 탭별 프로세스, PostgreSQL 접속별 프로세스 | 한 프로그램 안의 작업 스레드 |

### 일의 종류에 따른 선택

| 일의 성격 | 병목 | 잘 맞는 방식 |
|---|---|---|
| I/O 대기형(API 호출, DB 조회, 파일 읽기) | 기다림 | 비동기(이벤트 루프), 스레드 |
| CPU 계산형(엑셀 파싱, 이미지 처리, 음성 인식 추론) | 계산 | 여러 코어에서 병렬(프로세스, 워커 스레드), GPU |

### 경쟁 상태의 뿌리

"값 읽기 → 계산 → 쓰기"가 한 번에 일어나지 않기 때문이다. 두 실행 흐름이 이 세 단계 사이에 끼어들면 한쪽 결과가 사라진다. DB의 갱신 손실(DE-DB-002)과 완전히 같은 구조다.

## 4. 엄밀한 정의와 작동 원리

### 문맥 전환

운영체제 스케줄러는 실행 중인 스레드를 잠시 멈추고 레지스터 값 등 상태(문맥)를 저장한 뒤 다른 스레드를 실행한다. 프로세스 사이 전환은 메모리 주소 공간까지 바꿔야 해서 더 비싸다. 스레드가 수천 개면 전환 비용과 스레드별 메모리(스택)가 부담이 된다.

### 임계 구역과 상호 배제

공유 데이터를 고치는 코드 구간을 **임계 구역**이라 한다. 한 번에 하나의 스레드만 들어가도록 **잠금**(mutex)을 건다. 잠금은 원자적 하드웨어 명령(비교 후 교환 등) 위에 만들어진다. 숫자 하나 증감 같은 간단한 경우는 원자적 연산 자체를 쓴다.

### 교착 상태의 네 조건

다음 네 조건이 **모두** 성립할 때 교착이 생길 수 있다(코프먼 조건).

1. 상호 배제: 자원을 한 번에 하나만 쓸 수 있다.
2. 점유와 대기: 자원을 쥔 채 다른 자원을 기다린다.
3. 비선점: 남이 쥔 자원을 빼앗을 수 없다.
4. 순환 대기: A는 B가 쥔 것을, B는 A가 쥔 것을 기다린다.

하나만 깨면 된다. 실무에서 가장 쉬운 방법은 **모든 코드가 잠금을 같은 순서로 얻게** 해서 순환 대기를 없애는 것이다. 대기 관계를 그래프로 그리면 교착은 그래프의 **순환**이다(MATH-GRAPH-001).

### 이벤트 루프

Node.js 공식 문서는 이벤트 루프를 "JavaScript가 단일 스레드임에도 가능한 한 운영체제 커널에 작업을 넘겨 논블로킹 I/O를 수행하게 해 주는 것"으로 설명한다. 루프는 완료된 I/O의 콜백을 차례로 실행한다. 콜백 하나가 오래 걸리면(무거운 계산) 그동안 다른 모든 요청이 기다린다. 그래서 CPU 계산은 워커 스레드(Node.js `worker_threads`, 브라우저 Web Worker)나 별도 프로세스로 뺀다.

### 암달의 법칙

프로그램에서 병렬화 가능한 비율이 $p$, 코어 수가 $n$이면 이론적 최대 속도 향상은

$$
S(n) = \frac{1}{(1 - p) + \dfrac{p}{n}}
$$

$n$을 아무리 늘려도 $S \le \dfrac{1}{1 - p}$다.

## 5. 수식 및 기호 설명

| 기호 | 뜻 |
|---|---|
| $p$ | 병렬화 가능한 작업 비율(0~1) |
| $n$ | 코어(작업자) 수 |
| $S(n)$ | 코어 $n$개일 때 속도 향상 배수 |
| $\dfrac{1}{1 - p}$ | 코어가 무한히 많을 때의 상한 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 경쟁 상태 재현 (카운터)

공유 변수 `count = 10`. 스레드 A와 B가 각각 `count = count - 1`을 한다. 이 한 줄은 실제로 세 단계다.

| 순서 | 스레드 A | 스레드 B | count |
|---|---|---|---|
| 1 | 읽기: 10 | | 10 |
| 2 | | 읽기: 10 | 10 |
| 3 | 계산: 9 | | 10 |
| 4 | 쓰기: 9 | | 9 |
| 5 | | 계산: 9 | 9 |
| 6 | | 쓰기: 9 | **9 (정답 8)** |

이 순서가 **가끔만** 일어나기 때문에 경쟁 상태는 재현이 어렵고 테스트를 통과하기 쉽다. 고치는 방법: 잠금으로 세 단계를 한 덩어리로 묶거나, 원자적 감소 연산을 쓰거나, DB라면 `UPDATE ... SET count = count - 1`처럼 DB에 맡긴다(DE-DB-002 예제 1).

### 예제 2. 교착 상태 재현

| 순서 | 스레드 A | 스레드 B |
|---|---|---|
| 1 | 잠금 X 획득 | |
| 2 | | 잠금 Y 획득 |
| 3 | 잠금 Y 요청 → 대기 | |
| 4 | | 잠금 X 요청 → 대기 |
| 5 | 영원히 대기 | 영원히 대기 |

**해결:** 모든 코드가 "X 먼저, 그다음 Y" 순서로만 잠그게 한다. 그러면 B도 X부터 요청하므로 A가 끝날 때까지 기다렸다가 진행한다. DB에서도 두 트랜잭션이 행을 반대 순서로 잠그면 교착이 생기고, PostgreSQL은 이를 감지해 한쪽을 오류로 중단시킨다.

### 예제 3. 비동기 경쟁: 이 사이트의 route token

상황: 사용자가 설명집 화면 A를 열면 3D 시각화를 비동기로 불러온다(`mountViz`). 불러오기가 끝나기 전에 화면 B로 옮겼다.

| 순서 | 일어나는 일 |
|---|---|
| 1 | 화면 A 진입, 시각화 불러오기 시작 |
| 2 | 사용자가 화면 B로 이동, 화면 A의 정리 작업 실행 |
| 3 | 화면 A의 시각화 불러오기가 **뒤늦게** 끝남 |
| 4 | (고치기 전) 3D 장면이 만들어져 메모리에 남음. 정리 대상 목록에는 없어서 계속 쌓임 |

고친 방식(실제 코드를 단순화):

```javascript
let routeToken = 0;
function onRouteChange() { routeToken++; disposeAll(); }

const tok = routeToken;               // 시작할 때 번호를 기억
mountViz(el).then((v) => {
  if (tok !== routeToken) v.dispose(); // 그사이 화면이 바뀌었으면 스스로 정리
  else disposers.push(() => v.dispose());
});
```

스레드가 하나뿐인 JavaScript에서도 **비동기 작업의 완료 순서**가 바뀌면 경쟁 상태가 생긴다. 해결의 핵심은 "결과를 쓰기 직전에, 이 결과가 아직 유효한지 확인"하는 것이다. 검색창에서 이전 검색 응답이 늦게 도착해 최신 결과를 덮어쓰는 버그도 같은 구조다.

### 예제 4. 암달의 법칙

작업의 80%를 병렬화할 수 있다($p = 0.8$).

- 4코어: $S = 1 / (0.2 + 0.8/4) = 1 / (0.2 + 0.2) = 2.5$배
- 16코어: $S = 1 / (0.2 + 0.05) = 4$배
- 무한 코어: $S \le 1 / 0.2 = 5$배

코어를 4배(4 → 16) 늘렸는데 속도는 1.6배(2.5 → 4)만 좋아졌다. 병렬화가 안 되는 20%를 줄이는 것이 코어를 늘리는 것보다 효과적일 수 있다.

## 7. 시각화와 해석

동시성 버그는 6절처럼 **실행 흐름별로 열을 나눈 시간표**로 그리면 가장 잘 보인다. 열이 실행 흐름(스레드, 비동기 작업), 행이 시간 순서다. "읽기와 쓰기 사이에 다른 열의 쓰기가 끼어드는 줄"을 찾으면 경쟁 상태, "서로 상대 열이 쥔 것을 기다리는 줄"을 찾으면 교착이다.

## 8. 기술 비교 및 선택 기준

| 상황 | 권장 |
|---|---|
| 외부 API·DB를 많이 기다림(웹 서버, RAG 서비스) | 비동기 I/O(이벤트 루프) 또는 스레드 풀 |
| 브라우저에서 무거운 계산(대용량 엑셀 파싱) | Web Worker로 화면 스레드와 분리 |
| 서버에서 CPU 계산을 여러 코어로 | 여러 프로세스, 워커 스레드, 작업 대기열 |
| 공유 숫자 증감 | 원자적 연산 또는 DB의 원자적 UPDATE |
| 여러 자원 잠금 | 잠금 순서 통일, 잠금 시간 최소화 |
| 장애 격리가 중요 | 프로세스 분리 |

## 9. 실무 사례

- **웹 서버:** 요청마다 스레드를 만들면 동시 접속이 늘 때 메모리가 바닥난다. 스레드 풀이나 비동기 방식으로 제한된 자원으로 많은 요청을 처리한다.
- **DB 커넥션 풀:** PostgreSQL은 접속마다 백엔드 프로세스를 만들기 때문에, 애플리케이션은 접속을 재사용하는 풀을 둔다.
- **LLM API 호출:** 여러 요청을 동시에 보내면 전체 시간이 줄지만, 제공사의 속도 제한을 넘지 않도록 동시 실행 수를 제한한다.
- **음성 인식 추론:** GPU 하나를 여러 요청이 나눠 쓸 때 묶음(batch) 처리로 처리량을 높이고, 대신 개별 요청 지연이 늘어나는 절충이 생긴다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 코드에서 옮긴 것이다.

- **이 학습 사이트 — 비동기 경쟁 수정:** 늦게 끝난 시각화 불러오기를 route token으로 정리하고, 3D 렌더링 반복을 화면 밖이면 멈추고 초당 30프레임으로 제한해 메모리 폭증과 페이지 다운을 고쳤다(HANDOFF.md 기록). 경쟁 상태(예제 3)와 자원 관리의 실제 사례다.
- **Preflight — 브라우저 파싱:** 엑셀 원본은 브라우저에서 파싱하고 파싱한 값만 서버에 저장하며, ExcelJS·SheetJS가 못 읽는 비표준 ERP 파일을 보정하는 정규화 모듈을 만들었다. 파일이 크면 파싱이 화면 스레드를 오래 막을 수 있다. 점검 질문: 파싱을 Web Worker로 분리했는가? 아니라면 큰 파일에서 화면이 멈추지 않는가?
- **Preflight — 재업로드 멱등성:** 같은 파일을 두 번 올려도 결과가 같다. 사용자가 버튼을 두 번 누르거나 두 사람이 같은 파일을 거의 동시에 올리는 **동시 요청** 상황에서도 안전하려면 DB 수준의 유니크 제약이 함께 있어야 한다(DE-DB-002).
- **STT — RTF와 스트리밍:** RTF(음성 길이 대비 처리 시간)는 한 요청의 처리 속도이고, 여러 요청을 동시에 처리할 때의 처리량과 지연은 별개다. 포트폴리오에도 "RTF와 별개로 스트리밍 응답 지연은 추가 검증이 필요하다"고 적혀 있다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 스레드를 늘리면 빨라진다.** CPU 계산은 코어 수 이상으로 늘려도 소용없고, 전환 비용과 잠금 경쟁으로 오히려 느려질 수 있다.
- **오해: JavaScript는 단일 스레드라 경쟁 상태가 없다.** 비동기 작업의 완료 순서에 따른 경쟁은 흔하다(예제 3).
- **오해: 테스트를 통과했으니 동시성 버그가 없다.** 타이밍에 따라 가끔만 일어나 재현이 어렵다. 설계(공유 상태 줄이기, 원자적 연산)로 막는 것이 우선이다.
- **잠금의 비용:** 잠금 범위가 넓으면 병렬성이 사라지고, 좁으면 버그가 생기기 쉽다.
- **공유를 줄이는 설계:** 데이터를 복사해 넘기거나(메시지 전달), 변경 불가능한 데이터를 쓰면 잠금 자체가 필요 없어진다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 프로세스와 스레드의 가장 중요한 차이와, 그 차이가 낳는 장단점은?</summary>

**정답.** 스레드는 같은 프로세스의 메모리를 공유하고 프로세스는 분리되어 있다. 스레드는 통신이 싸고 빠르지만 공유 데이터 동기화가 필요하고 하나의 오류가 전체에 퍼질 수 있다. 프로세스는 격리가 강해 안전하지만 생성·통신 비용이 크다.

**해설.** PostgreSQL이 접속마다 프로세스를 쓰는 것, 브라우저가 탭을 프로세스로 나누는 것은 격리를 택한 예다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 작업의 90%를 병렬화할 수 있을 때 코어 10개의 이론적 속도 향상은?</summary>

**정답.** $1 / (0.1 + 0.9/10) = 1 / 0.19 \approx 5.26$배.

**해설.** 코어가 무한해도 최대 10배다. 순차 부분 10%가 상한을 정한다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. Node.js 서버에서 업로드된 엑셀을 파싱하는 동안 다른 사용자의 요청이 모두 느려졌다. 원인과 해결은?</summary>

**정답.** 파싱이 CPU 계산이라 이벤트 루프를 오래 막아, 그동안 다른 콜백이 실행되지 못했다. 파싱을 워커 스레드나 별도 프로세스(작업 대기열)로 옮기거나, 브라우저에서 파싱해 결과만 받는 구조로 바꾼다.

**해설.** 이벤트 루프는 기다림이 많은 일에 강하고 계산이 많은 일에 약하다. Preflight는 파싱을 브라우저에서 하는 구조를 택했다(그 이유는 원본 파일을 밖으로 보내지 않기 위해서였다).

</details>

<details class="qa" data-type="applied"><summary>Q4. 검색창에 글자를 칠 때마다 API를 호출하는데, 가끔 이전 검색어의 결과가 화면에 남는다. 원인과 해결은?</summary>

**정답.** 응답 도착 순서가 요청 순서와 달라, 늦게 도착한 이전 검색 응답이 최신 결과를 덮어쓴 비동기 경쟁 상태다. 요청마다 번호를 매겨 최신 번호의 응답만 반영하거나, 이전 요청을 취소(AbortController)한다. 입력이 멈춘 뒤에만 호출(디바운스)하면 요청 수 자체도 줄어든다.

**해설.** 이 사이트의 route token(예제 3)과 같은 해법이다. 결과를 쓰기 직전에 유효성을 확인한다.

</details>
