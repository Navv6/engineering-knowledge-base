## 0. 한눈에 보기 (입문)

### 한 줄 요약
**테스트**는 "프로그램이 약속대로 동작하는가"를 자동으로 확인하는 장치이고, **유지보수**는 고치거나 기능을 더할 때 기존 약속이 깨지지 않게 지키는 일이다. 테스트가 있어야 겁먹지 않고 코드를 고칠 수 있다.

### 쉬운 설명
자동차 정비소를 떠올리자.

- 부품 하나(브레이크 패드)만 따로 검사하는 것이 **단위 테스트**다. 빠르고 싸다.
- 브레이크와 바퀴를 연결해 함께 움직이는지 보는 것이 **통합 테스트**다.
- 실제로 차를 몰고 도로를 한 바퀴 도는 것이 **E2E(처음부터 끝까지) 테스트**다. 가장 현실적이지만 느리고 비싸다.

정비 후 "고친 곳 말고 다른 데가 망가지지 않았나"를 확인하는 것이 **회귀 테스트**다. 소프트웨어에서 버그 대부분은 새 기능보다 **고치다가 다른 곳을 망가뜨려서** 생긴다.

### 내 프로젝트에서는
- **Preflight는 업무 규칙 단위 시험 704개와 실제 DB 점검 64개를 둔다**(2026-11-20 저장소 기준, 포트폴리오 기재). 판정 규칙을 DB·브라우저 없이 순수 함수로 시험하기 때문에 수백 개가 빠르게 돈다.
- **반례 테스트로 실제 버그를 막았다.** 품목 기준 중복 제거가 두 사출처에 나눠 맡긴 정상 데이터를 지운 문제가 있었다. 판정 키에 워크센터를 넣고, 그 상황을 재현하는 **반례 테스트**를 추가했다(ADR-02). 같은 버그가 다시 생기면 테스트가 먼저 실패한다.
- **이 학습 사이트에서도 '게이트 누수'가 실제로 있었다.** 검증이 실패했는데 명령을 `&&`로 잘못 엮어 커밋이 그대로 올라간 적이 있다(AI-ANN-001 작성 때). 지금은 검증·단위·E2E 각각의 종료 코드를 확인한 뒤에만 커밋한다(6절 예제 4).

### 먼저 알면 좋은 것
- 상태 머신(CS-GEN-001): 전이표 전체를 시험하는 예가 나온다.
- 집합과 명제논리(MATH-DM-001): 조건 조합 수 $2^n$을 쓴다.

## 1. 핵심 요약

- **테스트 층:** 단위(빠름, 많이) → 통합(중간) → E2E(느림, 적게). 아래층이 넓은 피라미드 모양이 일반적인 권장이다.
- **좋은 테스트 케이스 설계:** 동등 분할(같은 동작을 할 입력끼리 묶어 대표값 하나), 경계값(경계 바로 앞·위·뒤), 반례(과거 버그·예외 상황).
- **순수 함수로 판정 로직을 분리**하면 DB·네트워크 없이 빠르고 안정적으로 시험할 수 있다.
- **커버리지**는 "실행된 코드 비율"이지 "검증된 동작 비율"이 아니다. 100%여도 틀린 기대값이면 버그가 통과한다.
- **품질 게이트:** 검증이 실패하면 다음 단계(커밋·배포)가 **반드시 멈추도록** 연결한다. 종료 코드(0 = 성공)가 그 신호다.
- **유지보수:** 레거시 코드를 고칠 때는 먼저 현재 동작을 고정하는 테스트를 쓰고 나서 고친다.

## 2. 개념과 등장 배경

초기 소프트웨어 개발에서 테스트는 개발이 끝난 뒤 별도 팀이 수동으로 하는 단계였다. 1979년 글렌포드 마이어스(Glenford Myers)의 『The Art of Software Testing』은 "테스트는 오류를 찾으려고 프로그램을 실행하는 과정"이라는 관점과 동등 분할·경계값 분석 같은 설계 기법을 정리했다.

1990년대 후반 익스트림 프로그래밍과 켄트 벡(Kent Beck)의 단위 테스트 프레임워크(SUnit, JUnit) 이후, 개발자가 직접 자동 테스트를 쓰는 문화가 퍼졌다. 2000년대에는 커밋마다 테스트를 자동 실행하는 **지속적 통합(CI)**이 보편화되었다. 2004년 마이클 페더스(Michael Feathers)는 "테스트가 없는 코드가 곧 레거시 코드"라고 정의하며, 기존 코드를 안전하게 고치는 방법을 정리했다. 대규모 조직의 경험은 『Software Engineering at Google』(2020)에 정리되어 있다.

## 3. 직관적 설명 및 기초 이론

### 테스트 층별 비교

| 층 | 무엇을 | 속도 | 실패 원인 찾기 | 현실감 | 예 |
|---|---|---|---|---|---|
| 단위 | 함수·모듈 하나 | 밀리초 | 쉬움 | 낮음 | 판정 함수, 계산식 |
| 통합 | 모듈 + DB·외부 연결 | 초 | 중간 | 중간 | 실제 DB에 저장·조회 |
| E2E | 사용자 화면 흐름 전체 | 수 초~분 | 어려움 | 높음 | 브라우저로 클릭해 결과 확인 |

### 테스트의 기본 꼴: 준비 → 실행 → 확인

```javascript
import test from 'node:test';
import assert from 'node:assert/strict';

test('완료 → 진행 중은 검토로 보낸다', () => {
  // 준비(Arrange): 입력을 만든다
  const from = '완료', to = '진행 중';
  // 실행(Act)
  const result = decide(from, to);
  // 확인(Assert): 기대값과 비교
  assert.equal(result, 'review');
});
```

기대값은 **명세(업무 규칙)**에서 와야 한다. 코드를 돌려 나온 값을 그대로 기대값으로 적으면, 버그도 "정답"으로 굳어 버린다.

## 4. 엄밀한 정의와 작동 원리

### 동등 분할과 경계값

입력 범위를 "같은 방식으로 처리될 구간"으로 나누고, 각 구간에서 대표값 하나와 경계값을 고른다. 규칙이 "점수 $s$가 $s \ge 4$이면 A등급"이라면:

| 구간 | 대표값 | 경계값 |
|---|---|---|
| $s < 4$ | 2 | 3 |
| $s \ge 4$ | 6 | 4 |

버그는 `>=`를 `>`로 잘못 쓰는 식으로 **경계에서** 가장 많이 생긴다. $s = 4$를 시험하지 않으면 이 버그를 놓친다.

### 조합 폭발

참·거짓 조건이 $n$개면 조합은 $2^n$개다. $n = 3$이면 8개라 전수 시험이 가능하지만 $n = 20$이면 약 100만 개다. 조건이 많을 때는 모든 **쌍**의 조합이 한 번 이상 나오게 고르는 쌍별(pairwise) 테스트, 위험도가 높은 조합 우선 같은 전략을 쓴다. 상태 4개짜리 전이표는 $4 \times 4 = 16$개라 전수 시험이 맞다(CS-GEN-001).

### 커버리지

$$
\text{줄 커버리지} = \frac{\text{테스트 중 실행된 줄 수}}{\text{전체 실행 가능한 줄 수}}
$$

분기 커버리지는 if의 참·거짓 두 갈래가 모두 실행되었는지 본다. 커버리지는 "한 번도 실행되지 않은 코드"를 찾는 데 유용하지만, 실행된 코드의 **결과를 제대로 확인했는지**는 알려 주지 않는다.

### 테스트 대역(test double)

DB·외부 API처럼 느리거나 불안정한 의존성은 가짜(stub, mock, fake)로 바꿔 단위 테스트를 빠르게 한다. 다만 가짜가 진짜와 다르게 동작하면 테스트는 통과하는데 운영에서 실패한다. 그래서 진짜 DB로 하는 통합 점검을 일부 남긴다. Preflight가 순수 함수 시험(704개)과 **실제 DB 점검**(64개)을 함께 둔 이유다.

## 5. 수식 및 기호 설명

| 표현 | 뜻 |
|---|---|
| $2^n$ | 참·거짓 조건 $n$개의 조합 수 |
| $s \ge 4$ | 경계값 4를 포함하는 조건 |
| 줄 커버리지 | 실행된 줄 ÷ 전체 줄 |
| 종료 코드 0 | 명령 성공(유닉스 관례). 0이 아니면 실패 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 경계값으로 버그 잡기

명세: "버핏 점수 4점 이상이고 린치 점수 1점 이하면 유형 1". 구현:

```javascript
const isType1 = (b, l) => b > 4 && l <= 1;   // 버그: >= 대신 >
```

| 입력 $(b, l)$ | 명세 기대 | 구현 결과 | 결과 |
|---|---|---|---|
| (6, 0) 대표값 | 참 | 참 | 통과 |
| (2, 0) 대표값 | 거짓 | 거짓 | 통과 |
| **(4, 1) 경계값** | 참 | **거짓** | **실패 → 버그 발견** |

대표값만 시험했다면 통과했을 버그다. (예시 코드이며 DeepVi 코드가 아니다. 조건은 DeepVi 포트폴리오의 분류 조건에서 가져왔다.)

### 예제 2. 반례 테스트 (Preflight ADR-02의 구조)

버그 상황: 같은 품목을 두 사출처에 나눠 맡긴 정상 데이터 2건이 "품목 기준 중복"으로 판정되어 1건이 지워졌다.

1. **재현:** 품목 같음 + 워크센터 다름인 행 2개를 입력으로 만든다.
2. **실패 확인:** 고치기 전 코드에서 테스트가 실패(1건만 남음)하는 것을 본다. 실패를 먼저 보는 이유는 테스트가 정말 그 버그를 잡는지 확인하기 위해서다.
3. **수정:** 판정 키에 워크센터를 포함한다.
4. **통과 확인:** 2건이 모두 남는다. 이 테스트는 계속 남아 회귀를 막는다.

포트폴리오에는 "판정 키에 워크센터를 포함하고 반례 테스트를 추가했다"까지 기재되어 있다. 위 1~4 순서는 일반적인 반례 테스트 절차로 재구성한 것이다.

### 예제 3. 대장과 실제 DB 대조 (메타 테스트)

Preflight는 표·칸·계산식 대장을 코드에서 자동 생성해 실제 DB와 칸 단위로 대조한다. 그런데 스키마 파서가 일부 문법을 못 읽어 **한 달간 18개 칸이 대장에서 빠져 있었다**(포트폴리오 기재). 교훈: 검사 도구 자체도 틀릴 수 있다. "대장 칸 수 = DB 칸 수"처럼 검사 도구의 결과를 다른 경로로 한 번 더 맞춰 보는 점검이 필요하다.

### 예제 4. 게이트 누수와 종료 코드

이 사이트에서 실제로 있었던 일의 단순화:

```bash
node scripts/validate.mjs | grep "통과" ; git commit -m "..."
```

검증이 실패해도 `;` 뒤의 커밋이 실행된다. 비슷한 형태로 실패를 놓친 경우가 있었다. 고친 방식:

```bash
node scripts/validate.mjs; V=$?
if [ $V -eq 0 ]; then
  npm run test:unit; U=$?
  if [ $U -eq 0 ]; then git commit -m "..."; fi
fi
```

각 단계의 **종료 코드**를 변수에 받아 0일 때만 다음으로 간다. 파이프(`|`)로 출력을 걸러 보면 파이프 앞 명령의 실패가 가려질 수 있다는 점도 주의한다(bash의 `set -o pipefail`로 막을 수 있다).

## 7. 시각화와 해석

테스트 층을 피라미드로 그리면 아래(단위)가 넓고 위(E2E)가 좁다. 이 사이트의 현재 모양:

| 층 | 개수 | 하는 일 |
|---|---|---|
| 콘텐츠 검증 | 설명집 전체 | 필수 절, 출처, 수식 문법, 문항 형식, 선행 관계 순환 |
| 단위 테스트 | 18 | 검색, 일정 계산, 간격 반복, 통계 함수 등 |
| E2E | 38 | 실제 브라우저로 화면 이동, 저장, 3D 실패 대체 문구 |

Preflight는 704(단위) : 64(실제 DB) 비율로, 아래층이 훨씬 두꺼운 전형적인 피라미드다.

## 8. 기술 비교 및 선택 기준

| 상황 | 권장 |
|---|---|
| 업무 판정 규칙(조건이 많음) | 순수 함수로 분리 + 표 기반 단위 테스트 다수 |
| DB 제약·마이그레이션 | 실제 DB(개발 서버 또는 임시 DB)로 통합 점검 |
| 핵심 사용자 흐름 3~10개 | E2E로 소수만 |
| 버그 수정 | 재현 테스트 먼저, 그다음 수정 |
| 레거시 코드 수정 | 현재 동작 고정 테스트(characterization test) 먼저 |
| LLM 출력처럼 정답이 하나가 아닌 경우 | 형식 검사(JSON 스키마) + 근거 포함 여부 + 표본 사람 평가 |

## 9. 실무 사례

- **CI:** 저장소에 푸시하면 테스트가 자동으로 돌고, 실패하면 병합을 막는다.
- **배포 게이트:** 개발 서버를 거치지 않은 변경은 운영 배포를 거부한다.
- **데이터 품질 테스트:** 행 수, NULL 비율, 합계가 지난번과 크게 다르면 경고한다. 코드가 아니라 **데이터**에 대한 테스트다.
- **LLM 응용:** 테스트용 질문 세트를 만들어 답이 근거 문서에서 나오는지, 정해진 JSON 형식을 지키는지 반복 확인한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 시험 구성:** 업무 규칙 단위 시험 704개(판정 규칙을 순수 함수로) + 실제 DB 점검 64개. 세 업무(샘플조달·시사출·CT)가 같은 판정 엔진을 쓰므로, 엔진 시험이 세 업무를 함께 지킨다.
- **Preflight — 배포 게이트:** 개발/운영 서버를 분리하고 개발을 거치지 않은 변경은 배포 스크립트가 거부하며, DB 변경은 더하기만 해서 되돌려도 데이터가 남게 했다(11.10). 유지보수에서 "되돌릴 수 있음"을 설계로 보장한 사례다.
- **Preflight — 재업로드 멱등성:** 같은 파일을 두 번 올려도 행·검토 건이 늘지 않는다. "같은 입력 두 번 → 결과 같음"은 그 자체로 좋은 테스트 케이스다.
- **DeepVi — 프롬프트 테스트:** 테스트용 프롬프트로 답변이 보유한 기업 데이터를 근거로 나오는지 확인했다(정량 평가 지표는 기재 없음). 다음 단계는 질문 세트와 기대 근거를 고정해 회귀 테스트로 만드는 것이다.
- **STT 평가 — 평가 파이프라인 검증:** Riva Offline 평가에서 출력이 중간에 잘리는 문제를 발견해 Streaming 방식으로 바꿨다. 평가 도구가 조용히 틀린 결과를 낼 수 있다는 점에서 예제 3과 같은 교훈이다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 커버리지 100%면 버그가 없다.** 실행만 하고 확인을 안 했거나 기대값이 틀리면 통과한다.
- **오해: E2E만 있으면 된다.** 느리고 깨지기 쉬우며(화면 문구 하나만 바뀌어도 실패), 실패 원인 찾기가 어렵다.
- **깨지기 쉬운 테스트:** 구현 세부(내부 함수 호출 순서)를 검사하면 리팩토링만 해도 실패한다. **겉으로 보이는 동작**을 검사한다.
- **불안정한(flaky) 테스트:** 시간·네트워크·실행 순서에 따라 가끔 실패하는 테스트는 신뢰를 무너뜨린다. 원인을 고치거나 격리한다.
- **비용:** 테스트도 유지보수 대상이다. 가치가 낮은 중복 테스트는 정리한다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 규칙이 "수량이 1 이상 100 이하일 때만 허용"이다. 경계값 테스트로 어떤 입력을 고르겠는가?</summary>

**정답.** 0, 1, 100, 101(필요하면 2, 99도).

**해설.** 경계 바로 바깥(0, 101)은 거부, 경계 자체(1, 100)는 허용되어야 한다. 부등호 실수는 경계에서만 드러난다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 줄 커버리지 95%인 코드에서 버그가 나왔다. 어떻게 가능한가?</summary>

**정답.** 해당 줄이 실행은 되었지만 결과를 확인하지 않았거나, 기대값 자체가 틀렸거나, 버그가 나머지 5%에 있었거나, 특정 입력 조합(경계)에서만 드러나는 버그였을 수 있다.

**해설.** 커버리지는 "실행 여부"만 잰다. 검증의 질은 기대값과 케이스 설계가 결정한다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 테스트가 하나도 없는 3년 된 정산 코드를 고쳐야 한다. 무엇부터 하겠는가?</summary>

**정답.** 먼저 현재 동작을 그대로 기록하는 테스트(실제 입력 몇 건 → 현재 출력)를 만들어 고정한다. 그다음 작은 단위로 고치면서 테스트가 계속 통과하는지 확인하고, 의도적으로 바꾸는 동작만 기대값을 갱신한다.

**해설.** 페더스의 레거시 코드 접근이다. 현재 동작이 틀렸더라도 일단 고정해야 "의도한 변경"과 "실수로 바뀐 것"을 구분할 수 있다.

</details>

<details class="qa" data-type="applied"><summary>Q4. CI 스크립트가 `run_tests | tee log.txt` 후 배포한다. 테스트가 실패했는데 배포가 되었다. 원인과 해결은?</summary>

**정답.** 파이프라인의 종료 코드는 기본적으로 마지막 명령(tee)의 것이라 테스트 실패가 가려진다. `set -o pipefail`을 켜거나, 테스트 종료 코드를 따로 받아 0일 때만 배포하게 한다.

**해설.** 이 사이트에서 실제로 비슷한 게이트 누수가 있었다(6절 예제 4). 게이트는 "실패하면 확실히 멈추는지"를 일부러 실패시켜 시험해 봐야 한다.

</details>
