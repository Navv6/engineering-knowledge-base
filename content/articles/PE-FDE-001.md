## 0. 한눈에 보기 (입문)

### 한 줄 요약
**FDE**(Forward Deployed Engineer, 현장 배치 엔지니어)는 고객의 현장에 들어가 실제 업무와 데이터를 보고, 그 자리에서 쓸 수 있는 해결책을 설계하고 만들어 정착시키는 엔지니어다. 핵심 능력은 코딩보다 **"진짜 문제와 제약을 찾아내는 것"**이다.

### 쉬운 설명
맞춤 양복점을 떠올리자.

- **기성복 디자이너(제품 개발자):** 많은 사람에게 맞을 표준 치수를 정해 대량으로 만든다.
- **맞춤 재단사(FDE):** 손님을 직접 만나 치수를 재고, 어디서 입을지 묻고, 가봉해서 입혀 보고 고친다. 손님이 "편한 옷"이라고 했을 때 그게 "어깨가 넓은 옷"인지 "신축성 있는 원단"인지 알아내는 것이 실력이다.

FDE의 일은 대체로 이런 순서다.

1. 현장에서 사람들이 **실제로 어떻게 일하는지** 본다(말과 실제가 다를 때가 많다).
2. 요청("대시보드 만들어 주세요")을 **문제**("매주 엑셀을 손으로 옮기느라 실수가 난다")로 바꾼다.
3. 바꿀 수 없는 **제약**(보안, 예산, 기존 시스템, 사람)을 찾는다.
4. 작게 만들어 써 보게 하고, 고치고, 정착시킨다.
5. 왜 그렇게 결정했는지 **기록**을 남긴다.

### 내 프로젝트에서는
- **Preflight가 FDE식 작업의 교과서적 예다.** 사내 제조 업무(샘플조달·시사출·CT) 현장의 도구로, 아래 결정들이 모두 현장 제약에서 나왔다(포트폴리오 기재).
  - **클라우드 불가 → 사내 서버 운영**, 설치·백업·복원을 PowerShell 스크립트로 정리.
  - **원본 파일을 밖으로 보내지 않기 → 브라우저에서 엑셀 파싱**, 파싱한 값만 서버로.
  - **ERP가 내보내는 비표준 xlsx → 정규화 모듈** 직접 개발(ExcelJS·SheetJS 모두 읽지 못함).
  - **팀 엑셀에 줄이 끼면 값이 밀림 → 행 번호 대신 원본 값으로 행 식별.**
  - **종이 기록을 엑셀로 옮겨 적던 일 → 반출 화면에서 누르는 순간 재고 차감·KPI 집계**(정성 비교).
- **결정을 ADR로 남겼다.** "품목 기준 중복 제거가 정상 데이터를 지움 → 판정 키에 워크센터 포함(ADR-02)", "빠진 행은 지우지 않고 업무 단계로 관리(ADR-05)"처럼 번호 붙은 결정 기록이 있다.
- **STT 평가 보고서도 솔루션 선택 작업이었다.** 정확도 중심(NeMo)과 실시간(Riva Streaming) 후보를 나누고, 추가 검증이 필요한 항목(스트리밍 응답 지연)을 명시했다(포트폴리오 기재). "무엇을 아직 모르는지"를 적는 것도 설계 문서의 일부다.

### 먼저 알면 좋은 것
- 목적함수와 제약조건(OR-OPT-001): "무엇을 최대화하고, 무엇은 반드시 지켜야 하나"로 문제를 쓰는 습관
- 관계형 데이터 모델링(DE-MODEL-001): 현장 데이터를 표로 정리하는 법

## 1. 핵심 요약

- **FDE의 역할:** 고객 현장에서 문제 발견 → 해결책 설계·구현 → 정착 → 제품 팀에 현장 지식 전달. 제품 엔지니어링과 컨설팅 사이.
- **요청 ≠ 문제.** "무엇을 만들어 달라"를 "어떤 일이 왜 어렵고, 해결되면 무엇이 달라지나"로 바꾼다.
- **제약을 먼저.** 보안·네트워크·기존 시스템·데이터 형식·예산·사람의 습관. 늦게 발견할수록 비싸다.
- **성공 기준을 숫자나 관찰 가능한 행동으로.** "편해진다"가 아니라 "주간 수기 입력 0건".
- **결정 기록(ADR):** 상황, 결정, 결과(대가)를 짧게 남긴다. 다음 사람이 "왜 이렇게 했지?"를 묻지 않게.
- **작게, 빨리, 현장에서.** 처음부터 완벽한 설계보다 실제 데이터로 돌아가는 작은 버전으로 숨은 문제를 드러낸다.

## 2. 개념과 등장 배경

현장 배치 엔지니어라는 직무명은 데이터 분석 플랫폼 회사 팔란티어(Palantir)가 고객 조직에 엔지니어를 보내 자사 플랫폼으로 문제를 풀게 하는 역할로 널리 알렸다. 이후 기업용 소프트웨어, 특히 데이터·AI 회사들이 비슷한 직무를 만들었다. 제품을 판 뒤 고객이 실제로 쓰게 만드는 일이 제품 자체만큼 중요해졌기 때문이다.

LLM 시대에 이 직무가 다시 주목받는 이유는, AI 기능의 가치가 **고객의 데이터와 업무 흐름에 얼마나 잘 붙느냐**에 달려 있기 때문이다. 모델은 같아도 어떤 데이터를 연결하고, 어떤 검증을 두고, 누가 어떤 화면에서 쓰는지에 따라 결과가 완전히 달라진다(AI-NATIVE-001). 요구사항 공학(Wiegers & Beatty), 아키텍처 결정 기록(Nygard, 2011) 같은 오래된 실무 지식이 이 직무의 기초 도구다.

## 3. 직관적 설명 및 기초 이론

### 요청을 문제로 바꾸는 표

| 들은 말 | 숨은 질문 | 바꿔 쓴 문제 |
|---|---|---|
| "대시보드가 필요해요" | 그걸 보고 무엇을 결정하나요? | 지연 건을 주 1회 회의에서야 알아 대응이 늦다 |
| "자동화해 주세요" | 지금 누가, 얼마나 자주, 무엇을 손으로 하나요? | 팀원이 매일 종이 기록을 엑셀로 옮기며 오타가 난다 |
| "AI로 분석해 주세요" | 지금 어떤 판단을 사람이 하고 있나요? 틀리면 무슨 일이? | 기업 분석 코멘트를 쓰는 데 시간이 걸리고 근거가 흩어져 있다 |

### 좋은 현장 질문의 특징 (The Mom Test의 원칙)

- 미래의 의견("이런 기능 쓰시겠어요?")보다 **과거의 사실**("지난주에 이 일을 어떻게 하셨어요?")을 묻는다.
- 칭찬과 막연한 동의는 정보가 아니다.
- 상대가 이미 돈·시간을 쓰고 있는 문제가 진짜 문제다.

### 제약의 종류

| 종류 | 예 | 놓치면 |
|---|---|---|
| 보안·정책 | 클라우드 금지, 파일 외부 반출 금지 | 구조 전체를 다시 설계 |
| 기존 시스템 | ERP가 비표준 파일만 내보냄 | 데이터 수집 단계에서 막힘 |
| 운영 | 전담 IT 인력 없음, 사내 서버 | 배포·백업이 안 돼 방치 |
| 사람 | 엑셀 사용 습관, 현장 노트북 | 아무도 안 씀 |
| 데이터 품질 | 행이 끼고 빠짐, 같은 품목 여러 사출처 | 조용히 틀린 결과 |

## 4. 엄밀한 정의와 작동 원리

### 문제 정의서의 최소 구성

1. **배경:** 누가, 어떤 업무에서, 무엇이 어렵나(관찰한 사실).
2. **목표:** 해결되면 달라지는 것(관찰 가능한 결과).
3. **제약:** 반드시 지켜야 할 조건(하드)과 가능하면 지킬 조건(소프트). OR-OPT-001의 하드·소프트 제약과 같은 구분이다.
4. **성공 기준:** 측정 방법과 기준값. 측정이 어려우면 정성 비교라도 명시.
5. **범위 밖:** 이번에 하지 않는 것.
6. **모르는 것:** 추가 검증이 필요한 가정.

### 가중치 의사결정표

후보 $j$의 점수를 기준 $i$의 가중치 $w_i$와 점수 $s_{ij}$로 합한다:

$$
\text{점수}_j = \sum_{i} w_i \, s_{ij}, \qquad \sum_i w_i = 1
$$

단, 하드 제약을 어기는 후보는 점수와 상관없이 **먼저 탈락**시킨다. 가중합은 하드 제약을 통과한 후보끼리만 비교한다. 가중치는 이해관계자와 함께 정하고 기록한다.

### ADR (Architecture Decision Record)

Nygard가 제안한 짧은 형식:

| 항목 | 내용 |
|---|---|
| 제목 | 번호 + 결정 한 줄 (예: ADR-05 빠진 행은 삭제하지 않고 업무 단계로 관리) |
| 상황 | 어떤 힘(제약, 요구, 문제)이 작용했나 |
| 결정 | 무엇을 하기로 했나 |
| 결과 | 그 결과 좋아지는 것과 **치르는 대가** |
| 상태 | 제안, 채택, 대체됨 |

결정을 바꿀 때는 기존 ADR을 지우지 않고 "대체됨"으로 표시한 뒤 새 ADR을 쓴다. 결정의 역사 자체가 기록이 된다.

## 5. 수식 및 기호 설명

| 기호 | 뜻 |
|---|---|
| $w_i$ | 기준 $i$의 가중치(합 1) |
| $s_{ij}$ | 후보 $j$가 기준 $i$에서 받은 점수 |
| $\sum_i w_i s_{ij}$ | 후보 $j$의 가중 합계 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 가중치 의사결정표 (설명용)

현장 업무 도구의 배포 방식을 고른다. 하드 제약: **원본 파일을 외부로 보내지 않는다.**

| 후보 | 하드 제약 |
|---|---|
| A. 외부 클라우드 SaaS | 위반 → **탈락** |
| B. 사내 서버 + 웹 앱 | 통과 |
| C. 각자 PC에 설치하는 프로그램 | 통과 |

남은 후보를 가중합으로 비교(점수 1~5):

| 기준 | 가중치 | B | C |
|---|---|---|---|
| 데이터 일관성(한곳에 모임) | 0.4 | 5 | 2 |
| 운영 부담(설치·업데이트) | 0.3 | 4 | 2 |
| 초기 구축 속도 | 0.2 | 3 | 4 |
| 네트워크 없이 동작 | 0.1 | 2 | 5 |
| **합계** | 1.0 | $2.0 + 1.2 + 0.6 + 0.2 = 4.0$ | $0.8 + 0.6 + 0.8 + 0.5 = 2.7$ |

B 채택. 이 표를 ADR의 "상황"에 붙이면 왜 B인지가 남는다. 가중치를 바꾸면 결론이 뒤집힐 수 있으므로(예: 네트워크 없이 동작이 0.5로 중요하면) 가중치 합의가 핵심이다. 숫자는 설명용이며, Preflight가 실제로 이런 표를 썼다는 기록은 없다. Preflight가 사내 서버를 택한 사실과 이유(클라우드 없이 운영)는 포트폴리오에 기재되어 있다.

### 예제 2. 데이터 품질 문제를 일찍 드러내기

Preflight에서 실제로 나온 문제들을 "처음에 물었다면 좋았을 질문"으로 바꿔 보자(문제와 해결은 포트폴리오 기재, 질문은 재구성).

| 나중에 드러난 문제 | 초기에 할 질문 |
|---|---|
| 화면용 12개 필드만 저장했는데 미결 목록·준수율에 다른 정보가 필요해짐 → ERP 원본 전체 보존으로 변경 | "이 데이터로 앞으로 어떤 집계를 하게 될까요? 원본은 보존해도 되나요?" |
| 엑셀 행 번호로 식별하다 줄이 끼어 값이 밀림 → 원본 값으로 식별 | "이 파일은 누가 어떻게 고치나요? 행을 끼우거나 정렬하나요?" |
| 품목 기준 중복 제거가 두 사출처 정상 데이터를 지움 → 워크센터 포함 | "같은 품목이 여러 곳에서 동시에 진행될 수 있나요?" |
| '지금 목록'만 세면 지난주 숫자가 바뀜 → 세는 범위 명시 | "지난 기간 숫자가 나중에 바뀌어도 괜찮은가요?" |

이런 질문은 대개 **실제 데이터 몇 주치를 놓고** 함께 볼 때 나온다. 작게 만들어 실제 데이터를 흘려 보는 것이 가장 빠른 요구사항 수집이다.

### 예제 3. 성공 기준 쓰기

| 막연한 목표 | 관찰 가능한 기준 |
|---|---|
| 업무가 편해진다 | 종이 기록을 엑셀로 옮겨 적는 일이 없어진다(Preflight 샘플창고 반출, 정성 비교로 기재) |
| 데이터가 정확해진다 | 같은 파일을 두 번 올려도 행·검토 건이 늘지 않는다(재업로드 멱등성) |
| 안전하게 배포한다 | 개발 서버를 거치지 않은 변경은 배포 스크립트가 거부한다 |
| 화면이 보기 좋다 | 글자 11px 이상, 대비 4.5:1 이상, 누르는 곳 28px 이상을 전 화면에 적용 |

오른쪽 열은 모두 Preflight 포트폴리오에 기재된 실제 기준이다. 정량 수치가 없는 항목은 "정성 비교"라고 정직하게 밝힌 점도 좋은 습관이다.

## 7. 시각화와 해석

솔루션 설계를 한 장으로 보여 줄 때는 **현재 흐름**(누가, 무엇을, 어떤 도구로, 어디서 손으로 옮기나)과 **바뀐 흐름**을 나란히 그린다. 손으로 옮기는 화살표, 같은 정보를 두 번 입력하는 지점, 실수가 생기는 지점에 빨간 표시를 하면, 무엇을 자동화해야 하는지가 이해관계자에게 바로 전달된다.

## 8. 기술 비교 및 선택 기준

| 질문 | 판단 |
|---|---|
| 기존 도구(엑셀 + 약간의 매크로)로 충분한가? | 충분하면 새 시스템을 만들지 않는다 |
| 구매할 제품이 있는가? | 핵심 업무가 아니면 구매, 차별화 요소면 구축 |
| 현장에 운영할 사람이 있는가? | 없으면 설치·백업·복원을 스크립트로, 구조는 단순하게 |
| 데이터가 밖으로 나갈 수 있는가? | 아니면 사내 배포, 브라우저 처리 |
| AI가 필요한가? | 규칙으로 되는 판정은 규칙으로. AI는 규칙으로 안 되는 부분에만 |

## 9. 실무 사례

- **데이터 플랫폼 도입:** 고객사의 흩어진 데이터 원천을 연결하고, 첫 번째 업무 사례 하나를 끝까지 동작시켜 가치를 보인 뒤 확장한다.
- **AI 기능 도입:** 사내 문서 Q&A를 만들 때, 권한(누가 어떤 문서를 볼 수 있나)과 평가 질문 세트를 먼저 정한다.
- **현장 피드백의 제품화:** 여러 고객에서 반복되는 맞춤 작업을 제품 기능으로 올리도록 제품 팀에 전달한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 제약 주도 설계:** 사내 서버 운영과 PowerShell 설치·백업·복원, 브라우저 파싱, 비표준 ERP 파일 정규화, 원본 값 기반 행 식별, 업무 단계 관리(ADR-05), 위험 변경만 검토, 업로드 단위 되돌리기, 개발/운영 분리와 더하기만 하는 DB 변경, 접근성 기준. 하나하나가 현장 제약에 대한 응답이다.
- **Preflight — 공통 엔진과 어댑터:** 세 업무가 같은 판정 엔진을 쓰고 업무마다 어댑터와 정책만 다르다. 비슷한 현장 요구를 공통 핵심 + 현장별 설정으로 나누는 것은 FDE가 맞춤 작업을 제품화할 때 쓰는 기본 구조다.
- **DeepVi — 운영 범위의 정직한 기록:** 시연과 주변 사용자 테스트까지 진행했고, 상시 운영할 배포 서버 여건이 되지 않아 공개 서비스로 열지 않았다. 어디까지 했는지 명확히 밝히는 것은 고객과의 신뢰에서 중요하다.
- **STT — 선택과 남은 검증:** 4개 모델을 같은 조건으로 비교하고 용도별 후보를 제시하며, 스트리밍 지연은 추가 검증이 필요하다고 적었다. 후보 비교 + 결정 + 미확인 사항은 ADR의 구성과 같다.
- **면접 대비:** FDE 직무 면접에서는 "현장 제약 때문에 설계를 바꾼 경험"을 묻는 경우가 많다. Preflight의 12개 필드 → 원본 보존 전환, 행 번호 → 원본 값 식별 전환은 "처음 판단, 발견한 문제, 바꾼 결정, 대가"로 말하기 좋은 사례다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: FDE는 영업 지원 개발자다.** 고객 요청을 그대로 구현하는 사람이 아니라, 문제를 재정의하고 때로는 "만들지 말자"고 판단하는 사람이다.
- **오해: 맞춤 개발은 많을수록 좋다.** 고객마다 다른 코드가 쌓이면 유지보수가 불가능해진다. 공통화할 부분을 계속 찾는다.
- **현장 관찰의 한계:** 관찰자가 있으면 사람들은 평소와 다르게 일한다. 실제 데이터와 로그로 교차 확인한다.
- **가중치 표의 함정:** 원하는 결론에 맞춰 가중치를 조정하기 쉽다. 가중치를 먼저 합의하고 점수를 매긴다.
- **기록 비용:** 모든 결정에 ADR을 쓸 필요는 없다. 되돌리기 어렵거나 나중에 "왜?"라는 질문이 나올 결정에만 쓴다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. ADR에 꼭 들어가야 할 세 가지 요소와, '결과' 항목에 좋은 점만 적으면 안 되는 이유는?</summary>

**정답.** 상황(작용한 제약과 문제), 결정, 결과. 결과에는 치르는 대가(포기한 것, 새로 생긴 위험)도 적어야 나중에 결정을 재검토할 때 무엇과 무엇을 맞바꿨는지 알 수 있다.

**해설.** 예: ADR-05(빠진 행을 지우지 않음)의 대가는 데이터가 계속 쌓이고, 단계 관리 규칙이 필요해진다는 것이다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 가중치 의사결정표에서 하드 제약은 어떻게 다뤄야 하는가?</summary>

**정답.** 가중합 점수에 넣지 않고, 먼저 하드 제약을 어기는 후보를 탈락시킨 뒤 남은 후보끼리 가중합으로 비교한다.

**해설.** 하드 제약 위반을 점수로 상쇄할 수 있게 두면, 다른 기준 점수가 높은 위반 후보가 뽑히는 오류가 생긴다(OR-OPT-001의 하드·소프트 제약 구분).

</details>

<details class="qa" data-type="judgment"><summary>Q3. 고객사 현장 담당자는 "엑셀을 그대로 쓰고 싶다"고 하고, 관리자는 "새 시스템으로 바꾸라"고 한다. FDE로서 어떻게 접근하겠는가?</summary>

**정답.** 두 사람의 진짜 목표를 각각 확인한다(담당자: 익숙한 입력 방식 유지, 관리자: 집계 정확성과 가시성). 그다음 엑셀을 입력 창구로 유지하면서 업로드해 정합성 검사·집계를 시스템이 맡는 식으로 둘 다 충족하는 설계를 찾고, 작은 범위로 시험 운영해 결과로 합의한다.

**해설.** Preflight가 팀 엑셀과 ERP 파일을 업로드받아 누적 병합하는 구조는 기존 습관을 유지하면서 데이터를 모으는 방식이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 고객이 "AI로 품질 이상을 자동 감지하고 싶다"고 한다. 첫 2주 동안 무엇을 하겠는가?</summary>

**정답.** 현재 이상을 누가 어떻게 발견하고 무엇을 하는지 관찰하고, 과거 이상 사례와 데이터(측정값, 기록)를 모아 품질을 확인한다. 성공 기준(놓치면 안 되는 이상의 종류, 허용 가능한 거짓 경보 수)을 합의하고, 단순한 통계 기준(관리도 등)으로 기준선을 먼저 만들어 AI가 필요한지 판단한다.

**해설.** 통계적 공정관리(STAT-SPC-001)로 충분한 경우가 많다. 기준선 없이 AI부터 만들면 개선 여부를 판단할 수 없다.

</details>
