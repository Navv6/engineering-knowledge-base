## 0. 한눈에 보기 (입문)

### 한 줄 요약
**규칙 엔진과 정책 분리**는 "무엇을 판정하는가(업무 규칙)"를 "어떻게 실행하는가(코드)"에서 떼어 내, 규칙은 표나 설정으로 관리하고 코드는 그 규칙을 읽어 일관되게 적용하게 하는 설계다. 규칙이 자주 바뀌거나, 비슷한 업무가 여러 개일 때 특히 강력하다.

### 쉬운 설명
식당 메뉴판을 떠올리자.

- **나쁜 방식:** 요리사마다 가격을 머릿속에 외우고 있다. 가격이 바뀌면 모든 요리사에게 일일이 알려야 하고, 누군가는 옛 가격으로 받는다.
- **좋은 방식:** 가격은 메뉴판(정책) 한 장에 적고, 계산대(엔진)는 메뉴판을 보고 계산한다. 가격이 바뀌면 메뉴판만 고친다.

업무 시스템도 같다. "변경 폭이 10% 넘으면 검토"라는 규칙이 코드 다섯 군데에 흩어져 있으면, 기준을 15%로 바꿀 때 한 군데를 빠뜨린다. 규칙을 한곳(표)에 모으고, 엔진이 그 표를 읽어 판정하게 하면 이런 실수가 사라진다.

### 내 프로젝트에서는
- **Preflight가 바로 이 구조다.** 샘플조달·시사출·CT 세 업무가 **같은 판정 엔진**을 쓰고, 업무마다 다른 것은 **어댑터와 정책뿐**이다(포트폴리오 기재). 엔진은 "칸 비교 → 위험도 판정 → 검토 대기열"을 공통으로 하고, 업무별 차이(어느 칸이 중요한지, 무엇이 위험한지)는 정책으로 분리했다.
- **판정 규칙을 순수 함수로 두고 704개 단위 시험으로 지킨다.** 판정 규칙을 DB·브라우저 없이 순수 함수로 시험한다(업무 규칙 단위 시험 704개, 2026-11-20 저장소 기준, 포트폴리오 기재). 엔진과 정책이 분리되어 있어 규칙만 따로 시험할 수 있다.
- **출처 우선순위도 정책이다.** 완료일이 여러 곳에서 오면 사람 > 파일 > 시스템 순으로 덮지 않는다(포트폴리오 기재). 이런 충돌 해결 규칙을 명시적인 정책으로 두면 업무가 늘어도 일관되게 적용된다.
- **DeepVi의 지표 판정 기준값은 코드 안에 있다.** 부채비율 50/100/150 같은 기준이 화면 코드의 if문에 직접 적혀 있다(저장소 `pages/stream.py`, AI-TREE-001). 지표별 기준을 표(정책)로 빼면 업종별 기준을 쉽게 추가할 수 있다(적용 아이디어).

### 먼저 알면 좋은 것
- 집합과 명제논리(MATH-DM-001): 조건, 겹침, 우선순위 규칙
- 소프트웨어 테스트와 유지보수(SE-TEST-001): 순수 함수, 표 기반 시험
- 의사결정나무와 앙상블(AI-TREE-001): 사람이 만든 규칙 나무

## 1. 핵심 요약

- **분리:** 엔진(규칙을 읽고 적용하는 코드) ↔ 정책(조건·기준값·결과를 담은 데이터). 정책은 업무 담당자가 읽을 수 있는 형태로.
- **결정표:** 조건 열 × 규칙 행 × 결과 열. 모든 조합을 한눈에 보고 겹침·빈틈을 찾는다.
- **충돌 해결:** 첫 번째 일치(우선순위), 가장 구체적인 규칙 우선, 모두 적용 후 합치기(가장 엄격한 결과) 등 방식을 명시한다.
- **설명 가능성:** 판정마다 "어느 규칙, 어떤 입력 값 때문에"를 기록한다. 검토자·감사에 필수.
- **버전 관리:** 정책도 코드처럼 버전·변경 이력·시험이 필요하다. 어느 판정이 어느 정책 버전으로 났는지 남긴다.
- **시험:** 판정을 순수 함수(입력 → 결과)로 만들고 결정표의 각 행·경계값을 시험 케이스로.

## 2. 개념과 등장 배경

1970~80년대 전문가 시스템(MYCIN 등)은 "만약 ~이면 ~이다" 형태의 규칙 수백~수천 개로 전문가의 판단을 흉내 냈다. 1982년 찰스 포지(Charles Forgy)의 **Rete 알고리즘**은 많은 규칙과 사실을 효율적으로 맞춰 보는 방법으로, 이후 상용 규칙 엔진의 기반이 되었다. 1990~2000년대에는 보험 심사, 대출 승인, 가격 정책처럼 규칙이 자주 바뀌는 업무에서 비즈니스 규칙 관리 시스템(BRMS)이 쓰였다.

2003년 에릭 에반스(Eric Evans)의 『도메인 주도 설계』는 업무 규칙을 도메인 모델과 정책 객체로 분리하는 설계를 정리했고, 2015년 OMG의 **DMN**(Decision Model and Notation)은 결정표와 결정 모델을 업무 담당자와 개발자가 함께 쓰는 표준 표기로 만들었다. 오늘날에는 무거운 규칙 엔진 대신 "설정 파일 + 작은 판정 함수 + 표 기반 시험"으로 같은 원칙을 가볍게 구현하는 경우가 많다.

## 3. 직관적 설명 및 기초 이론

### 흩어진 규칙 vs 분리된 규칙

| | 흩어진 if문 | 엔진 + 정책 |
|---|---|---|
| 규칙 위치 | 화면·API·배치 곳곳 | 정책 한곳 |
| 변경 | 코드 수정·배포 | 정책 수정(시험 후 반영) |
| 업무 추가 | 코드 복사·수정 | 정책 추가 |
| 판정 이유 | 추적 어려움 | 규칙 ID로 기록 |
| 시험 | 화면·DB와 얽혀 어려움 | 순수 함수로 표 기반 시험 |

### 결정표

조건을 열로, 규칙을 행으로 놓고 각 칸에 조건 값을 적는다. "–"는 상관없음.

| 규칙 | 사람이 고친 칸인가 | ERP 값이 바뀌었나 | 이전 단계 | 새 단계 | 결과 |
|---|---|---|---|---|---|
| R1 | 예 | 예 | – | – | 검토 |
| R2 | – | – | 완료 | 진행 중 | 검토 |
| R3 | 아니오 | 예 | – | – | 자동 반영 |
| R4 | – | 아니오 | – | – | 변화 없음 |

(Preflight 포트폴리오에 기재된 검토 규칙을 결정표 형태로 옮긴 설명용 예시이며, 실제 정책 전체가 아니다.)

## 4. 엄밀한 정의와 작동 원리

### 규칙과 판정

규칙 $r$은 조건 $c_r(x)$(입력 $x$에 대한 논리식, MATH-DM-001)와 결과 $a_r$의 쌍이다. 입력 $x$에 대해 일치하는 규칙 집합 $M(x) = \{r : c_r(x) = \text{참}\}$.

- $|M(x)| = 0$: **빈틈** — 어떤 규칙도 맞지 않음. 기본 결과(예: 검토)를 정해 둔다.
- $|M(x)| > 1$: **겹침** — 충돌 해결 방식이 필요.

### 충돌 해결 방식

| 방식 | 동작 | 주의 |
|---|---|---|
| 첫 번째 일치(우선순위) | 순서상 처음 맞는 규칙 | 순서가 곧 규칙이므로 문서화 필요 |
| 가장 구체적인 규칙 | 조건이 더 많이 지정된 규칙 우선 | 구체성 정의가 모호할 수 있음 |
| 가장 엄격한 결과 | 일치한 결과 중 가장 보수적인 것(검토 > 자동) | 안전하지만 검토가 늘 수 있음 |
| 모두 수집 | 일치한 모든 규칙의 이유를 함께 기록 | 결과 합치는 규칙 필요 |

예: 위 결정표에서 "사람이 고친 칸, ERP 값 바뀜, 완료 → 진행 중"이면 R1과 R2가 모두 맞는다. 둘 다 "검토"라 충돌은 없지만, 검토 사유로는 두 규칙을 모두 기록하는 것이 좋다.

### 완전성 점검

조건이 $k$개의 이진 조건이면 조합은 $2^k$개다(MATH-DM-001). 결정표의 규칙들이 모든 조합을 덮는지(빈틈 없음), 서로 다른 결과로 겹치는 조합이 없는지 기계적으로 검사할 수 있다. 조건 4개면 16개 조합을 전부 나열해 각 조합이 어느 규칙에 걸리는지 표로 확인한다.

### 판정 기록

판정마다 (입력 요약, 일치한 규칙 ID 목록, 결과, 정책 버전, 시각)을 남긴다. 검토자는 "왜 검토로 왔는지"를 바로 보고, 정책을 바꾼 뒤 판정이 어떻게 달라졌는지 비교할 수 있다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| $c_r(x)$ | 규칙 $r$의 조건(참/거짓) |
| $a_r$ | 규칙 $r$의 결과 |
| $M(x)$ | 입력 $x$에 맞는 규칙들 |
| 빈틈 / 겹침 | 맞는 규칙 0개 / 2개 이상 |
| 정책 버전 | 판정에 쓴 규칙 묶음의 버전 |
| 어댑터 | 업무별 입력을 엔진이 이해하는 공통 형태로 바꾸는 부분 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 결정표로 빈틈 찾기

조건 두 개(사람이 고친 칸인가 A, ERP 값이 바뀌었나 B)의 조합 4가지를 위 결정표 R1·R3·R4로 확인:

| A | B | 맞는 규칙 | 결과 |
|---|---|---|---|
| 예 | 예 | R1 | 검토 |
| 예 | 아니오 | R4 | 변화 없음 |
| 아니오 | 예 | R3 | 자동 반영 |
| 아니오 | 아니오 | R4 | 변화 없음 |

4개 조합이 모두 정확히 하나의 결과로 덮인다(R2는 단계 조건을 따로 보는 규칙). 조건이 하나 늘 때마다 조합이 두 배가 되므로, 표로 기계적으로 점검하는 습관이 중요하다.

### 예제 2. 엔진 + 정책 코드 구조 (설명용)

```javascript
// 정책(데이터): 업무마다 다르게
const policy = {
  version: '2026-11-26',
  rules: [
    { id: 'R1', when: (x) => x.humanEdited && x.erpChanged, then: 'review' },
    { id: 'R2', when: (x) => x.from === '완료' && x.to === '진행 중', then: 'review' },
    { id: 'R3', when: (x) => !x.humanEdited && x.erpChanged, then: 'apply' },
  ],
  default: 'no-change',
  resolve: 'strictest',            // review > apply > no-change
};

// 엔진(코드): 모든 업무 공통, 순수 함수
function decide(x, policy) {
  const hits = policy.rules.filter((r) => r.when(x));
  if (hits.length === 0) return { result: policy.default, rules: [], version: policy.version };
  const order = ['review', 'apply', 'no-change'];
  const result = hits.map((r) => r.then).sort((a, b) => order.indexOf(a) - order.indexOf(b))[0];
  return { result, rules: hits.map((r) => r.id), version: policy.version };
}
```

`decide`는 DB도 화면도 없이 입력만으로 결과를 내므로, 결정표의 행마다 시험 케이스를 만들 수 있다. 결과에 규칙 ID와 정책 버전이 함께 나와 판정 이유가 남는다. Preflight의 실제 코드가 아니라 구조 설명용이다.

### 예제 3. 시험 케이스 수 세기

조건 3개(사람 수정, ERP 변경, 역방향 단계 전이)의 모든 조합 $2^3 = 8$가지 + 경계값(빈 값, 같은 값 재업로드) 몇 개면 이 정책의 거의 모든 경우를 덮는다. 업무가 세 개면 정책별로 같은 표를 돌린다. Preflight가 704개 단위 시험을 둔 것은 이런 조합과 반례(ADR-02 같은 과거 사고 재현)를 쌓은 결과로 볼 수 있다(시험 구성의 세부는 기재 없음).

## 7. 시각화와 해석

결정표 자체가 가장 좋은 시각화다. 업무 담당자와 함께 표를 보며 "이 조합에서는 어떻게 되어야 하나요?"를 묻는 것이 요구사항 확인의 가장 빠른 방법이다(PE-FDE-001). 판정 기록을 규칙별로 세어 막대로 그리면 어느 규칙이 검토를 많이 만드는지, 그중 승인 비율이 높은(불필요한 검토) 규칙이 무엇인지 보인다(AI-EVAL-001의 정밀도).

## 8. 기술 비교 및 선택 기준

| 방식 | 적합 | 주의 |
|---|---|---|
| 코드 안 if문 | 규칙이 적고 거의 안 바뀜 | 흩어지면 관리 불가 |
| 설정 파일·DB 표 + 작은 엔진 | 대부분의 업무 시스템(Preflight 방식) | 정책도 시험·버전 관리 |
| DMN 결정표 도구 | 업무 담당자가 직접 규칙 편집 | 도구 학습, 표현력 한계 |
| 본격 규칙 엔진(Rete 계열) | 규칙 수천 개, 사실 간 복잡한 연결 | 디버깅·성능 예측 어려움 |
| 머신러닝 모델 | 규칙으로 표현하기 어려운 패턴 | 설명·감사 어려움(AI-TREE-001) |
| 온톨로지 추론 | 개념 계층과 함께 규칙 적용 | 열린 세계 가정 주의(KE-RDF-001) |

## 9. 실무 사례

- **보험·대출 심사:** 심사 기준을 결정표로 관리하고, 기준 변경 시 과거 신청 표본으로 영향(승인율 변화)을 미리 시뮬레이션한다.
- **가격·할인 정책:** 프로모션 규칙을 데이터로 두고 기간·대상·우선순위를 명시한다.
- **데이터 품질 규칙:** 칸별 검증 규칙을 정책 표로 관리해 적재 단계에서 적용한다(DE-DQ-001).
- **LLM 출력 검증:** 금지 표현·필수 근거 같은 출력 규칙을 정책으로 분리해 모델이 바뀌어도 같은 검증을 적용한다(AI-PROMPT-001).

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`, DeepVi 저장소 `pages/stream.py`)에서 옮긴 것이다.

- **Preflight — 공통 엔진 + 정책:** 세 업무가 같은 판정 엔진을 쓰고 업무마다 어댑터와 정책만 다르다. 판정 규칙은 순수 함수로 704개 단위 시험, 실제 DB 점검 64개. 출처 우선순위(사람 > 파일 > 시스템)와 위험 변경 검토 규칙도 정책이다. 점검 질문(기록 없음): 판정 결과에 일치한 규칙 ID와 정책 버전을 남기는가? 정책을 바꿀 때 과거 업로드로 영향을 시뮬레이션할 수 있는가?
- **Preflight — 반례 시험:** 품목 기준 중복 제거가 정상 데이터를 지운 사고 후 판정 키를 고치고 반례 시험을 추가했다(ADR-02). 정책 변경마다 과거 사고를 재현하는 시험을 남기는 것은 규칙 시스템 유지의 핵심 습관이다.
- **DeepVi — 하드코딩된 기준:** 부채비율·이자보상배율·자기자본비율의 기준값이 화면 코드의 if문에 있다. `{지표, 기준값들, 단계 이름}` 정책 표로 빼면 업종별 기준 추가와 시험이 쉬워진다(적용 아이디어). 질문 분류의 정규식 패턴도 같은 방식으로 정책화할 수 있다(CS-REGEX-001).

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 정책을 데이터로 빼면 시험이 필요 없다.** 정책 변경도 동작을 바꾸므로 코드처럼 시험·검토·버전 관리가 필요하다.
- **오해: 규칙 엔진을 도입하면 해결된다.** 규칙이 서로 얽히면 엔진이 있어도 이해하기 어렵다. 결정표로 단순하게 유지하는 것이 먼저다.
- **과도한 일반화:** 모든 것을 설정으로 만들면 설정 자체가 새로운 프로그래밍 언어가 되어 디버깅이 어려워진다(Fowler의 DSL 논의).
- **우선순위 숨김:** 첫 번째 일치 방식에서 순서가 문서화되지 않으면, 규칙 추가가 기존 결과를 조용히 바꾼다(MATH-DM-001 Q3).
- **업무 담당자 편집의 위험:** 비개발자가 직접 규칙을 바꾸게 하려면 시험 환경·검증·승인 절차가 함께 있어야 한다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 이진 조건 4개로 이루어진 결정표가 빈틈 없이 모든 경우를 덮는지 확인하려면 몇 개 조합을 검사해야 하나?</summary>

**정답.** $2^4 = 16$개.

**해설.** 각 조합이 정확히 하나의 결과(또는 정해진 충돌 해결 결과)로 이어지는지 확인한다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 판정 결과에 규칙 ID와 정책 버전을 함께 기록해야 하는 이유 두 가지는?</summary>

**정답.** ① 검토자·감사가 판정 이유를 바로 확인할 수 있고, ② 정책을 바꾼 뒤 어떤 판정이 어느 버전 기준이었는지 구분해 영향을 분석·되돌릴 수 있다.

**해설.** 설명 가능성과 재현 가능성. Preflight의 업로드 단위 되돌리기와 같은 발상이다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 비슷한 업무 화면 다섯 개가 각자 판정 로직을 복사해 쓰고 있고, 기준이 화면마다 조금씩 다르다. 어떻게 정리하겠는가?</summary>

**정답.** 다섯 화면의 판정 로직을 결정표로 정리해 공통 규칙과 업무별 차이를 구분하고, 공통 판정 엔진(순수 함수) + 업무별 정책으로 재구성한다. 기존 동작을 고정하는 시험(현재 결과 기록)을 먼저 만들고, 차이가 의도인지 실수인지 업무 담당자와 확인한 뒤 옮긴다.

**해설.** Preflight의 공통 엔진 + 어댑터·정책 구조, SE-TEST-001의 레거시 코드 접근(현재 동작 고정 후 수정)을 합친 방법이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 지표별 판정 기준(부채비율 50/100/150 등)을 업종마다 다르게 적용해야 한다. 정책을 어떻게 설계하겠는가?</summary>

**정답.** `(지표, 업종, 기준값 목록, 단계 이름, 비교 방향, 정책 버전)` 형태의 정책 표를 두고, 업종별 행이 없으면 기본 행을 쓰게 한다. 판정 함수는 (지표 값, 지표, 업종, 정책) → (단계, 사용한 정책 행)을 반환하는 순수 함수로 만들고, 업종별 경계값과 빈 값을 시험한다.

**해설.** DeepVi의 하드코딩된 기준값을 정책으로 분리하는 방향이다(AI-TREE-001 Q4의 경계값 시험과 함께).

</details>

## 14. 참고 자료

출처는 아래 패널에 있다. 결정표 표준은 DMN, 규칙 매칭 알고리즘은 Forgy(1982), 설정과 DSL의 균형은 Fowler(2010), 정책 분리는 Evans(2003)를 따랐다. 3절 결정표와 6절 코드는 Preflight 포트폴리오에 기재된 규칙을 바탕으로 한 설명용 예시이며 실제 정책·코드가 아니다. DeepVi 기준값은 저장소에서 직접 확인했다.
