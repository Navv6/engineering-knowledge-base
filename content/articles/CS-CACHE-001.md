## 0. 한눈에 보기 (입문)

### 한 줄 요약
**캐시**는 "자주 쓰는 것을 가까운 곳에 복사해 두는 것"이다. 느린 곳(DB, 외부 API, 먼 서버)에 매번 가지 않아 빨라지지만, 복사본이 원본과 달라질 수 있다는 대가가 있다. 컴퓨터 과학의 오래된 농담처럼 **"어려운 건 캐시 무효화와 이름 짓기"**다.

### 쉬운 설명
도서관에서 공부한다고 하자.

- 자주 보는 책은 **책상 위**(캐시)에 둔다. 손만 뻗으면 된다.
- 가끔 보는 책은 **서가**(원본 저장소)에 있다. 일어나서 찾으러 가야 한다.
- 책상이 좁으면 새 책을 올릴 때 한 권을 치워야 한다. **가장 오래 안 본 책**을 치우는 게 보통 합리적이다(LRU).
- 문제는 서가의 책이 **개정판으로 바뀌었는데** 책상 위엔 옛날 판이 있는 경우다. 언제 바꿔 올지 정하는 것이 **무효화**다.

### 내 프로젝트에서는
- **이 학습 사이트는 "미리 계산해 두기"를 쓴다.** 수식(KaTeX)과 본문(마크다운)을 페이지를 열 때마다 변환하지 않고, **빌드할 때 한 번** HTML로 바꿔 넣는다(`scripts/lib.mjs`의 `katex.renderToString`). 원본(설명집 파일)이 바뀌면 다시 빌드한다. 무효화 시점이 "빌드"로 명확한 캐시다.
- **DeepVi의 벡터 저장도 미리 계산한 결과다.** 매일 수집한 뉴스를 임베딩해 Pinecone에 저장했다(포트폴리오 기재). 질문할 때마다 수천 개 뉴스를 다시 임베딩하지 않고, 저장해 둔 벡터를 검색한다. 뉴스 원문이 바뀌거나 임베딩 모델을 바꾸면 다시 계산해야 한다.
- **PostgreSQL도 내부에 캐시가 있다.** DeepVi·Preflight가 쓴 PostgreSQL은 자주 읽는 데이터 페이지를 메모리(shared_buffers, 공식 문서 기준 기본값은 보통 128MB)에 둔다. 같은 조회를 반복하면 두 번째가 빠른 이유다.

### 먼저 알면 좋은 것
- 네트워크와 HTTP 기초(CS-NET-001): RTT, CDN, HTTP 헤더

## 1. 핵심 요약

- **왜 빠른가 — 지역성:** 최근에 쓴 것은 곧 다시 쓰고(시간 지역성), 근처 데이터를 함께 쓴다(공간 지역성).
- **평균 접근 시간:** $T = h\,t_{\text{hit}} + (1 - h)\,t_{\text{miss}}$. 적중률 $h$가 조금만 올라도 크게 빨라진다.
- **교체 정책:** LRU(가장 오래 안 쓴 것 제거), LFU(가장 덜 쓴 것), FIFO, TTL 만료.
- **일관성 전략:** TTL(일정 시간 뒤 만료), 명시적 무효화(원본 변경 시 삭제), 버전이 붙은 키(내용이 바뀌면 새 키).
- **쓰기 방식:** cache-aside(앱이 읽을 때 채움), write-through(쓸 때 캐시·원본 동시), write-back(캐시에 먼저 쓰고 나중에 원본).
- **위험:** 오래된 값, 캐시 폭주(만료 순간 요청이 원본에 몰림), 사용자별 데이터의 공유 캐시 노출, 캐시와 원본의 불일치.

## 2. 개념과 등장 배경

1960년대 IBM System/360 Model 85(1968)는 빠른 소용량 메모리를 CPU와 주기억장치 사이에 둔 **캐시**를 상용 컴퓨터에 처음 도입했다. CPU 속도가 메모리보다 훨씬 빨라지면서 레지스터 → L1·L2·L3 캐시 → 메모리 → 디스크로 이어지는 **메모리 계층**이 표준이 되었다. 1966년 벨라디(Belady)는 "가장 나중에 쓸 것을 버리는" 이론상 최적 교체 정책을 보였고, 실제로는 미래를 알 수 없어 LRU 같은 근사를 쓴다.

같은 원리가 모든 계층으로 퍼졌다. 웹 브라우저 캐시, 1990년대 후반 등장한 CDN, 웹 서비스 앞단의 메모리 캐시(memcached 2003년, Redis 2009년), DB 버퍼 캐시, 그리고 최근에는 LLM API의 프롬프트 캐싱과 임베딩 캐시까지. "느리고 비싼 계산·조회의 결과를 재사용한다"는 아이디어는 같다.

## 3. 직관적 설명 및 기초 이론

### 계층별 대략적 속도 감각

| 위치 | 대략의 접근 시간 |
|---|---|
| CPU 캐시 | 나노초(ns) 단위 |
| 메모리(RAM) | 수십~백 나노초 |
| 같은 데이터센터 안 네트워크 왕복 | 수백 마이크로초 |
| SSD 읽기 | 수십~수백 마이크로초 |
| 다른 대륙 서버 왕복 | 100밀리초 이상 |

(하드웨어마다 다르며 자릿수 감각만 보는 값이다.) 한 계층 내려갈 때마다 수십~수천 배 느려지므로, 위 계층에서 찾을 확률을 높이는 것이 성능의 핵심이다.

### 캐시가 맞는 곳, 안 맞는 곳

| 잘 맞음 | 잘 안 맞음 |
|---|---|
| 읽기가 쓰기보다 훨씬 많음 | 매번 다른 요청(적중률 낮음) |
| 계산·조회가 비쌈(LLM, 외부 API, 무거운 집계) | 값이 계속 바뀌고 정확성이 중요(재고 차감 직전 값) |
| 조금 오래된 값이 허용됨 | 사용자마다 다른 민감 정보(공유 캐시 위험) |

## 4. 엄밀한 정의와 작동 원리

### 평균 접근 시간

$$
T_{\text{avg}} = h \cdot t_{\text{hit}} + (1 - h) \cdot t_{\text{miss}}
$$

$t_{\text{miss}}$는 원본 조회 시간(캐시 확인 비용 포함)이다. 미스 비용이 클수록 적중률의 작은 차이가 크게 작용한다.

### LRU

용량이 가득 찼을 때 **가장 오래전에 사용된** 항목을 버린다. 해시 테이블(키 → 위치)과 이중 연결 리스트(사용 순서)를 함께 쓰면 조회·갱신·제거를 모두 $O(1)$에 할 수 있다(CS-ALG-001).

### 무효화 전략

| 전략 | 방법 | 장점 | 단점 |
|---|---|---|---|
| TTL | 저장 후 $t$초 지나면 만료 | 단순 | 최대 $t$초 오래된 값 |
| 명시적 삭제 | 원본을 바꿀 때 캐시 키 삭제 | 신선함 | 삭제를 빠뜨리면 영원히 틀림 |
| 버전 키 | 키에 버전·해시 포함(`style.a1b2.css`) | 무효화가 필요 없음 | 옛 항목이 공간 차지 |
| 이벤트 기반 | 변경 이벤트를 받아 갱신 | 빠른 반영 | 구성 복잡 |

**버전 키** 방식은 원본 내용의 해시를 이름에 넣는다. 내용이 바뀌면 이름이 바뀌어 옛 캐시를 쓸 일이 없다. Git의 내용 주소(SE-GIT-001)와 같은 원리다.

### HTTP 캐시

서버가 응답 헤더 `Cache-Control: max-age=3600`을 주면 브라우저·CDN이 1시간 동안 재사용한다. `ETag`(내용 지문)를 주면 다음 요청에서 "바뀌었나?"만 물어 바뀌지 않았으면 `304 Not Modified`로 본문 없이 응답한다. 로그인한 사용자별 응답에는 `private` 또는 `no-store`로 공유 캐시 저장을 막는다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| $h$ | 적중률(hit ratio) |
| $t_{\text{hit}}$, $t_{\text{miss}}$ | 적중 시, 미스 시 응답 시간 |
| TTL | 유효 시간(time to live) |
| LRU | 가장 오래 안 쓴 것부터 제거 |
| 캐시 폭주 | 인기 항목 만료 순간 동시 요청이 원본에 몰리는 현상 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 적중률이 응답 시간을 바꾸는 정도

$t_{\text{hit}} = 1$ms, $t_{\text{miss}} = 100$ms.

| 적중률 $h$ | 평균 응답 시간 |
|---|---|
| 0.50 | $0.5 + 50 = 50.5$ms |
| 0.90 | $0.9 + 10 = 10.9$ms |
| 0.99 | $0.99 + 1 = 1.99$ms |

적중률을 90%에서 99%로 올리면 평균이 약 5.5배 빨라진다. 남은 미스가 평균을 지배하기 때문이다.

### 예제 2. LRU 따라가기

용량 2, 요청 순서 A, B, A, C, B.

| 요청 | 결과 | 캐시(오래된 → 최근) |
|---|---|---|
| A | 미스 | A |
| B | 미스 | A, B |
| A | **적중** | B, A |
| C | 미스, B 제거 | A, C |
| B | 미스, A 제거 | C, B |

적중 1/5. 용량이 3이면 마지막 B도 적중해 2/5가 된다. 작업 집합(자주 쓰는 항목 수)보다 캐시가 작으면 적중률이 급격히 떨어진다.

### 예제 3. LLM 답변 캐시 (설명용)

기업 분석 화면에서 같은 기업의 "회사 개요 요약"을 사용자들이 반복 요청한다. 요약 생성은 1회 3초, API 비용이 든다.

- 키: `(기업코드, 요약 종류, 원천 데이터 버전, 모델·프롬프트 버전)`
- TTL: 원천 데이터가 하루 한 번 갱신되면 다음 갱신까지
- 하루 1,000번 요청 중 100개 기업에 몰려 있다면, 생성 호출은 최대 100번으로 줄고 나머지 900번은 즉시 응답

키에 **프롬프트·모델 버전**을 넣지 않으면, 프롬프트를 고친 뒤에도 옛 답이 나온다. DeepVi는 기업 분석 코멘트·뉴스 요약에 GPT-4o와 Gemini Flash를 썼는데(README 기재), 생성 결과를 캐시했는지는 기재가 없다(적용 아이디어).

## 7. 시각화와 해석

캐시 크기를 가로축, 적중률을 세로축에 그리면(적중률 곡선) 처음엔 가파르게 오르다가 어느 지점부터 평평해진다. 평평해지기 시작하는 지점이 "작업 집합 크기"이고, 그 이상 캐시를 늘려도 효과가 작다. 운영 중에는 적중률과 미스 시 원본 부하를 시간 순으로 함께 그려, 배포나 캐시 초기화 직후 원본이 버티는지 확인한다(OPS-OBS-001, 준비 중).

## 8. 기술 비교 및 선택 기준

| 위치 | 예 | 적합 |
|---|---|---|
| 빌드 시 미리 계산 | 정적 사이트, 수식 렌더링 | 원본이 가끔 바뀌는 콘텐츠(이 학습 사이트) |
| 브라우저·CDN | HTTP 캐시 헤더 | 정적 파일, 공개 데이터 |
| 앱 프로세스 메모리 | 사전, LRU 라이브러리 | 서버 1대, 작은 데이터 |
| 공유 메모리 캐시 | Redis 등 | 서버 여러 대, 세션·계산 결과 |
| DB 내부 | shared_buffers, 실체화 뷰 | 반복 조회·무거운 집계 |
| 미리 계산한 결과 저장 | 임베딩 벡터, 일별 집계 테이블 | 비싼 계산(DeepVi 벡터) |

**판단:** 먼저 느린 원인을 측정하고(쿼리 자체가 비효율이면 인덱스가 먼저, DE-DB-001), 읽기 비율·허용 가능한 오래됨·무효화 방법을 정한 뒤 캐시를 둔다.

## 9. 실무 사례

- **정적 파일 버전 키:** `app.3f9a.js`처럼 내용 해시를 파일명에 넣고 1년 캐시. 배포하면 새 이름이라 즉시 반영된다.
- **캐시 폭주 방지:** 만료 직전에 한 요청만 원본을 다시 계산하게 잠그거나, 만료 시각을 무작위로 흩뜨린다.
- **LLM 프롬프트 캐싱:** 긴 시스템 지시문·문서처럼 매번 같은 앞부분을 제공사가 캐시해 비용과 지연을 줄이는 기능이 있다(제공사·버전마다 조건이 다름, 확인 필요).

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 코드에서 옮긴 것이다.

- **이 학습 사이트 — 빌드 시 렌더링:** 마크다운과 KaTeX 수식을 빌드 때 HTML로 바꾸고, 수식 글꼴도 페이지에 내장해 열 때 외부 요청을 줄였다. 원본 설명집이 바뀌면 빌드를 다시 해 게시한다. 3D 라이브러리는 CDN에서 받으므로 브라우저 캐시의 도움을 받는다.
- **DeepVi — 미리 계산한 벡터:** 매일 수집한 뉴스를 e5-large로 임베딩해 Pinecone news-ns에 저장하고 검색했다. 점검 질문(기록 없음): 같은 기사가 다시 수집되면 임베딩을 다시 계산했는가(기사 키 기반 건너뛰기)? 임베딩 모델을 바꾸면 전체를 다시 계산해야 한다는 점을 고려했는가?
- **DeepVi·Preflight — PostgreSQL 버퍼:** 자주 읽는 데이터 페이지가 shared_buffers에 머물러 반복 조회가 빨라진다. 성능을 잴 때 첫 조회(차가운 캐시)와 반복 조회(따뜻한 캐시)를 구분해야 공정하다.
- **Preflight — 집계 범위:** '지금 목록'만 세면 지난주 숫자가 바뀔 수 있어 세는 범위를 명시했다. 집계 결과를 캐시한다면, 이 범위 정의가 캐시 키와 무효화 조건이 된다(적용 아이디어).

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 느리면 캐시를 붙이면 된다.** 원인이 비효율적인 쿼리나 반복 호출이면 그것부터 고친다. 캐시는 문제를 가리기도 한다.
- **오해: 캐시는 성능만의 문제다.** 오래된 값은 정확성 문제이고, 사용자별 응답을 공유 캐시에 넣으면 보안 사고다.
- **차가운 시작:** 배포·재시작 직후 캐시가 비어 원본에 부하가 몰린다. 미리 채우기(warm-up)를 고려한다.
- **측정 착시:** 같은 요청을 반복해 성능을 재면 캐시 효과로 실제보다 빠르게 보인다.
- **메모리 비용:** 캐시가 커질수록 메모리를 쓰고, 정작 다른 작업이 느려질 수 있다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 적중 시 2ms, 미스 시 200ms일 때 적중률 95%의 평균 응답 시간은?</summary>

**정답.** $0.95 \times 2 + 0.05 \times 200 = 1.9 + 10 = 11.9$ms.

**해설.** 5%의 미스가 평균의 대부분(10ms)을 차지한다.

</details>

<details class="qa" data-type="concept"><summary>Q2. TTL 방식과 버전 키 방식의 차이는?</summary>

**정답.** TTL은 정해진 시간 뒤 만료되어 그동안은 오래된 값이 나올 수 있다. 버전 키는 내용이 바뀌면 키 자체가 바뀌어 옛 값을 쓰지 않으므로 무효화가 필요 없지만, 옛 항목이 공간을 차지한다.

**해설.** 정적 파일은 버전 키, 자주 바뀌는 조회 결과는 TTL + 명시적 삭제가 흔하다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 대시보드가 느려 집계 쿼리 결과를 10분 캐시하자는 제안이 나왔다. 무엇을 먼저 확인하겠는가?</summary>

**정답.** 쿼리가 느린 원인(인덱스 부족, 불필요한 전체 스캔)을 실행 계획으로 확인하고, 사용자가 10분 지연된 숫자를 받아들일 수 있는지, 데이터 변경 시 무효화가 필요한지, 사용자별 권한에 따라 결과가 다른지(공유 캐시 위험)를 확인한다.

**해설.** 캐시는 정확성·보안과의 맞교환이다. 원인 해결이 가능하면 그쪽이 우선이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. LLM으로 생성한 기업 요약을 캐시하려 한다. 캐시 키와 무효화 조건을 설계하라.</summary>

**정답.** 키: 기업 코드 + 요약 종류 + 원천 데이터 버전(또는 수집 날짜) + 모델 이름 + 프롬프트 버전. 무효화: 원천 데이터 갱신 시 새 버전 키로 자연 교체, 프롬프트·모델 변경 시 버전 증가. 생성 실패나 검증(스키마·근거) 불통과 결과는 캐시하지 않는다.

**해설.** 생성 결과에 영향을 주는 모든 입력이 키에 들어가야 오래되거나 엉뚱한 답이 나오지 않는다(AI-PROMPT-001의 검증과 함께).

</details>
