## 0. 한눈에 보기 (입문)

### 한 줄 요약
**AI 에이전트**는 LLM이 "다음에 무엇을 할지"를 스스로 정하고, 도구(검색, 파일, 명령 실행)를 써서 결과를 확인하며 목표까지 반복하는 프로그램이다. 핵심은 똑똑함보다 **상태를 어디에 두고, 언제 멈추고, 무엇으로 검증하는가**다.

### 쉬운 설명
요리를 맡기는 세 가지 방법을 비교해 보자.

- **한 번 물어보기(LLM 호출):** "김치찌개 레시피 알려 줘." 답을 받으면 끝이다.
- **정해진 순서대로 시키기(워크플로):** "재료 손질 → 볶기 → 물 붓기 → 간 보기" 순서를 사람이 정해 두고, 각 단계만 맡긴다.
- **목표만 주고 맡기기(에이전트):** "저녁 차려 줘." 냉장고를 열어 보고(도구), 재료가 없으면 메뉴를 바꾸고, 맛을 보고(확인) 다시 간을 맞춘다. 다음 행동을 **스스로** 정한다.

에이전트는 유연하지만, 잘못하면 냉장고만 계속 열었다 닫았다 할 수도 있다. 그래서 "몇 번까지 시도", "다 됐는지 확인하는 기준", "비싼 재료를 쓰기 전엔 물어보기" 같은 장치가 필요하다.

### 내 프로젝트에서는
- **DeepVi의 질문 처리는 워크플로였다.** 질문을 정규식으로 뉴스 / 재무·실적 / 거시 / 일반으로 분류하고(우선순위 meta → news → macro), 정해진 검색 체인(LangChain RetrievalQA + GPT-4o)으로 보냈다(저장소 코드). 다음 단계를 LLM이 아니라 **코드가 정한다.** 이것은 Anthropic이 말하는 워크플로 패턴 중 **라우팅**(routing)에 해당한다.
- **이 학습 사이트의 매일 갱신은 에이전트다.** 매일 05:44(KST)에 새 세션이 열리면, Claude가 절차서(AUTOMATION.md)를 읽고 다음 주제를 고르고, 글을 쓰고, 검증·테스트를 돌리고, 실패하면 고치거나 초안으로 남기고, 통과하면 커밋·게시한다. 단계 안에서의 판단은 LLM이 하지만, **검증 게이트와 실행 기록**(content/runs/*.json)이 바깥에서 붙잡고 있다.
- **STT 프로젝트의 로컬 LLM 검토도 같은 고민이었다.** 정해진 JSON 스키마(refusal_law, reject_reason_summary, citation_evidence[], final_summary) 유지·처리 시간·실패 대응을 기준으로 타당성을 검토했다(포트폴리오 기재). 에이전트의 출력을 다음 단계가 믿고 쓰려면 형식이 고정되어야 한다.

### 먼저 알면 좋은 것
- 상태 머신(CS-GEN-001): 에이전트 루프는 상태와 전이로 그릴 수 있다.
- RAG(AI-RAG-001): 검색은 에이전트가 가장 자주 쓰는 도구다.

## 1. 핵심 요약

- **구분:** LLM 호출(한 번) → 워크플로(코드가 정한 경로를 따라 LLM과 도구를 엮음) → 에이전트(LLM이 스스로 다음 행동과 도구 사용을 정함). Anthropic의 정의를 따랐다.
- **기본 루프:** 관찰 → 생각(다음 행동 결정) → 도구 호출 → 결과 관찰 → … → 종료. ReAct 논문이 추론과 행동을 번갈아 하는 이 방식을 정리했다.
- **상태 세 겹:** ① 대화 기록(모델이 보는 맥락), ② 작업 상태(지금 몇 단계, 무엇을 끝냈나), ③ 외부 저장소(파일, DB, git). 오래 가는 상태는 ③에 둔다.
- **안전 장치:** 반복 한도, 비용·시간 한도, 결과 검증(테스트·스키마), 되돌리기 어려운 행동 전 사람 확인.
- **원칙:** 가장 단순한 방법부터. 워크플로로 되면 에이전트를 쓰지 않는다.

## 2. 개념과 등장 배경

"에이전트"는 원래 고전 인공지능의 용어로, 환경을 **지각**하고 **행동**하는 주체를 말한다(Russell & Norvig). LLM이 등장한 뒤 이 용어는 "언어 모델이 도구를 써서 여러 단계 작업을 하는 시스템"을 가리키게 되었다.

2022년 ReAct 논문(Yao 외)은 모델이 생각(Thought)과 행동(Action), 관찰(Observation)을 번갈아 쓰게 하면 질문 답변과 의사결정 과제에서 성능과 해석 가능성이 좋아짐을 보였다. 2023년 Toolformer(Schick 외)는 모델이 계산기·검색 같은 API를 언제 부를지 스스로 배우게 했다. 이후 주요 LLM API가 도구 호출(function calling, tool use)을 기본 기능으로 넣었고, 2024년 말 Anthropic은 실제 구축 경험을 바탕으로 "워크플로와 에이전트를 구분하고, 단순한 조합 가능한 패턴부터 시작하라"는 지침을 공개했다.

## 3. 직관적 설명 및 기초 이론

### 누가 다음 단계를 정하는가

| 방식 | 다음 단계 결정 | 예측 가능성 | 유연성 | 예 |
|---|---|---|---|---|
| 단일 호출 | 없음 | 높음 | 낮음 | 요약 한 번 |
| 워크플로 | 코드 | 높음 | 중간 | DeepVi 라우팅 + 검색 체인 |
| 에이전트 | LLM | 낮음 | 높음 | 코드 수정 에이전트, 이 사이트의 매일 갱신 |

### Anthropic이 정리한 워크플로 패턴

- **프롬프트 체이닝:** 단계를 나눠 앞 출력이 다음 입력. 단계 사이에 검사(gate)를 둘 수 있다.
- **라우팅:** 입력을 분류해 전문화된 경로로 보낸다.
- **병렬화:** 여러 호출을 동시에 돌려 합치거나 투표한다.
- **오케스트레이터-워커:** 중심 LLM이 작업을 나눠 하위 LLM에 맡긴다.
- **평가자-최적화자:** 한 LLM이 만들고 다른 LLM이 평가해 고친다.

### 에이전트 루프를 상태 머신으로

$$
\text{계획} \rightarrow \text{도구 실행} \rightarrow \text{결과 확인} \rightarrow
\begin{cases}
\text{완료} & \text{기준 충족} \\
\text{계획} & \text{미충족이고 한도 이내} \\
\text{사람 확인 대기} & \text{위험한 행동 또는 한도 초과}
\end{cases}
$$

상태 머신(CS-GEN-001)으로 그려 두면 "어느 상태에서 멈출 수 있는가", "빠져나올 수 없는 상태는 없는가"를 점검할 수 있다.

## 4. 엄밀한 정의와 작동 원리

### 도구 호출 한 번의 흐름

1. 애플리케이션이 모델에 **도구 목록**(이름, 설명, 입력 형식 JSON 스키마)과 대화를 보낸다.
2. 모델이 답 대신 "도구 X를 이 인자로 불러 달라"는 **구조화된 요청**을 낸다.
3. 애플리케이션이 실제로 도구를 실행한다. **모델은 직접 실행하지 않는다.** 권한 검사와 실행은 애플리케이션 책임이다.
4. 결과를 대화에 붙여 다시 모델에 보낸다.
5. 모델이 더 부를 도구가 없다고 판단하면 최종 답을 낸다.

### 상태의 세 층

| 층 | 무엇 | 수명 | 문제 |
|---|---|---|---|
| 대화 기록(컨텍스트) | 지금까지의 메시지, 도구 결과 | 한 세션 | 길어지면 비용 증가, 앞부분이 잘리거나 요약됨 |
| 작업 상태 | 현재 단계, 완료 목록, 시도 횟수 | 한 작업 | 대화에만 있으면 세션이 끊길 때 사라짐 |
| 외부 저장소 | 파일, DB, git 커밋, 실행 기록 | 영구 | 일관성 유지 필요 |

**원칙:** 세션이 끊겨도 이어서 할 수 있어야 하는 정보는 외부 저장소에 쓴다. 이 사이트의 예약 실행은 매번 **새 세션**에서 시작하므로, "오늘 이미 실행했는가"를 대화 기억이 아니라 `content/runs/`의 오늘 날짜 기록으로 판단한다(AUTOMATION.md 1절). 같은 이유로 진행 상황과 결정을 HANDOFF.md에 남긴다.

### 비용 감각

반복 $n$회 동안 매번 이전 대화 전체를 다시 보내면, 입력 토큰 총량은 대략

$$
\sum_{i=1}^{n} (c_0 + i \cdot r) = n c_0 + r \frac{n(n+1)}{2}
$$

이다($c_0$: 고정 맥락, $r$: 한 번에 늘어나는 양). $n$의 제곱에 비례해 늘어나므로(MATH-BASE-003의 합 공식), 긴 루프는 중간 요약이나 상태 외부화가 필요하다. 실제 비용은 캐싱 등 API 기능에 따라 달라진다.

## 5. 수식 및 기호 설명

| 표현 | 뜻 |
|---|---|
| $c_0$ | 매 호출마다 들어가는 고정 맥락(지시문, 도구 설명) |
| $r$ | 반복 한 번에 늘어나는 대화 양 |
| $\frac{n(n+1)}{2}$ | 1부터 $n$까지의 합 |
| JSON 스키마 | 도구 입력·출력의 형식 명세 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 같은 기능을 워크플로와 에이전트로

과제: "삼성전자 최근 이슈와 재무 상태를 요약해 줘."

**워크플로(DeepVi 방식에 가까움):**
1. 정규식이 '이슈' → 뉴스, '재무' → 재무로 판정(우선순위 규칙상 재무 경로가 먼저 선택될 수 있음)
2. 해당 검색 체인 실행 → 답변 생성

예측 가능하고 빠르지만, 두 가지를 동시에 묻는 질문은 한 경로만 탈 수 있다.

**에이전트:**
1. 모델: "뉴스 검색 도구를 부르자" → 결과 5건 관찰
2. 모델: "재무 API 도구를 부르자" → 수치 관찰
3. 모델: 둘을 합쳐 답변. 숫자는 도구 결과에서만 인용.

유연하지만 호출 횟수와 경로가 매번 달라질 수 있어, 로그와 검증이 더 필요하다. (DeepVi는 기업별 분석 화면 안에서만 질문할 수 있어 기업이 화면 맥락으로 정해졌다. 위 에이전트 흐름은 비교용 가정이다.)

### 예제 2. 이 사이트의 매일 갱신 루프

| 상태 | 하는 일 | 다음 상태 |
|---|---|---|
| 준비 | 저장소 받기, 빌드·단위 테스트 | 실패 → 실패 기록 / 성공 → 중복 확인 |
| 중복 확인 | 오늘 성공 기록이 있나 | 있으면 건너뜀 기록 / 없으면 주제 선택 |
| 주제 선택 | 선행 구멍 우선 규칙(next-candidates) | 작성 |
| 작성 | 설명집 작성 | 검증 |
| 검증 | 필수 절, 출처, 수식, 문항 | 실패 → 수정(최대 2회) → 그래도 실패면 초안 / 성공 → 테스트 |
| 테스트 | 빌드, 단위, E2E | 성공 → 기록·커밋·게시 |

"최대 2회 수정 후 초안으로 남김"이 반복 한도이고, 검증·테스트가 결과 확인 기준이다. 판단(주제 해석, 글쓰기, 오류 수정)은 LLM이 하지만 **성공 여부는 기계적 검사가 정한다.**

### 예제 3. 비용 계산

고정 맥락 $c_0 = 2{,}000$ 토큰, 반복마다 $r = 1{,}000$ 토큰 증가, $n = 10$회:

$$
10 \times 2000 + 1000 \times \frac{10 \times 11}{2} = 20000 + 55000 = 75000
$$

$n = 20$이면 $40000 + 1000 \times 210 = 250000$. 반복을 2배로 늘렸는데 입력량은 약 3.3배가 되었다.

## 7. 시각화와 해석

에이전트 실행 기록을 시간 순 표(단계, 도구, 입력 요약, 결과 요약, 소요 시간)로 남기면 디버깅이 쉬워진다. 같은 도구를 같은 인자로 반복 호출하는 줄이 보이면 루프에 갇힌 것이다. 이 사이트의 실행 기록(content/runs)은 생성·건너뜀·오류 목록과 메모를 남기는 최소한의 형태다.

## 8. 기술 비교 및 선택 기준

| 질문 | 예 → 권장 |
|---|---|
| 단계와 순서를 미리 알 수 있는가? | 예 → 워크플로 |
| 입력 종류가 몇 가지로 나뉘는가? | 예 → 라우팅 |
| 다음 행동이 중간 결과에 따라 크게 달라지는가? | 예 → 에이전트 검토 |
| 결과를 자동으로 검증할 수 있는가(테스트, 스키마, 대조)? | 아니오 → 에이전트는 위험. 사람 검토 비중을 높인다 |
| 되돌리기 어려운 행동(삭제, 결제, 외부 발송)이 있는가? | 예 → 그 직전에 사람 확인 |

## 9. 실무 사례

- **코딩 에이전트:** 파일 읽기·수정·테스트 실행 도구로 버그를 고친다. 테스트 통과가 종료 기준이 된다.
- **고객 지원:** 주문 조회, 환불 정책 검색 같은 도구를 쓰되 환불 실행은 사람 승인.
- **데이터 분석:** SQL 실행 도구로 질의를 만들고 결과를 확인하며 고친다. 읽기 전용 권한으로 제한한다.
- **MCP(Model Context Protocol):** 도구와 데이터 원천을 표준 방식으로 모델에 연결하는 개방형 규약이다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 절차서에서 옮긴 것이다.

- **DeepVi — 라우팅 워크플로:** 정규식 분류(우선순위 meta → news → macro) → 검색 체인(뉴스 k=5, 기업 k=5, 메타 k=3) → GPT-4o(temperature 0.3) 답변, 출처 문서 반환(return_source_documents=True). 확장 아이디어(기록 없음): 분류 규칙이 놓치는 복합 질문만 LLM 분류로 넘기는 2단 라우팅.
- **DeepVi — 출처 표시:** 뉴스 답변에 기사 제목·날짜·링크를 붙였다. 에이전트에서도 "도구 결과를 근거로 인용"은 검증 가능성을 높이는 기본 장치다.
- **STT — 구조화 출력:** 로컬 LLM의 JSON 스키마 유지와 실패 대응을 평가 기준에 넣었고, LLM 후처리의 과교정 문제가 있어 필요한 부분만 고치도록 정책을 제한했다(포트폴리오 기재). 에이전트에게 주는 권한과 범위를 좁히는 것과 같은 방향이다.
- **이 학습 사이트 — 예약 에이전트:** 새 세션, 절차서 기반 판단, 외부 상태(git, 실행 기록, HANDOFF), 검증 게이트, 반복 한도(수정 2회), 게시 전 E2E. 실제로 검증 게이트가 새는 사고가 한 번 있었고(SE-TEST-001 6절), 이후 종료 코드 기반으로 고쳤다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 에이전트가 워크플로보다 항상 낫다.** 예측 가능성·비용·디버깅에서 불리하다. 단계를 알 수 있으면 워크플로가 낫다.
- **오해: 모델이 도구를 실행한다.** 모델은 요청만 낸다. 실행과 권한은 애플리케이션이 쥔다.
- **오류 누적:** 단계마다 성공률이 0.95여도 10단계 연속이면 $0.95^{10} \approx 0.60$이다(STAT-PROB-001의 곱셈 규칙, 단계 독립 가정). 중간 검증이 필요한 이유다.
- **대화 기록 의존:** 맥락이 길어지면 앞부분이 요약·삭제될 수 있다. 중요한 결정은 외부 파일로 남긴다.
- **프롬프트 주입:** 도구가 가져온 웹 페이지나 문서 속 문장이 지시처럼 작동할 수 있다. 외부 데이터는 지시가 아니라 데이터로 다루고, 위험한 행동은 사람 확인을 거친다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 워크플로와 에이전트를 한 문장으로 구분하라.</summary>

**정답.** 워크플로는 LLM과 도구를 코드로 미리 정한 경로에 따라 엮은 것이고, 에이전트는 LLM이 스스로 다음 행동과 도구 사용을 결정하며 진행하는 것이다.

**해설.** Anthropic의 구분이다. 실무 시스템은 둘을 섞는 경우가 많다(큰 흐름은 워크플로, 한 단계 안은 에이전트).

</details>

<details class="qa" data-type="concept"><summary>Q2. 단계 성공률 0.9인 작업을 5단계 연속 수행하면 전체 성공률은? (단계는 독립이라 가정)</summary>

**정답.** $0.9^5 \approx 0.59$.

**해설.** 확률의 곱셈 규칙이다. 단계를 줄이거나 중간에 검증·재시도를 넣어야 전체 성공률이 올라간다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 매일 아침 자동으로 보고서를 만들어 팀 채널에 올리는 에이전트를 만든다. 설계에 꼭 넣을 장치 세 가지는?</summary>

**정답.** ① 결과 검증(형식·필수 항목·숫자 출처 대조)과 실패 시 게시 중단, ② 실행 기록과 중복 실행 방지(오늘 이미 올렸는지 외부 기록으로 확인), ③ 외부 발송 같은 되돌리기 어려운 행동의 범위 제한 또는 사람 확인. 반복·비용 한도도 함께 둔다.

**해설.** 이 사이트의 매일 갱신 절차(검증 게이트, content/runs 기록, 게시 전 테스트)가 같은 구조다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 에이전트가 같은 검색 도구를 같은 질의로 8번 연속 호출하고 있다. 원인 후보와 대책은?</summary>

**정답.** 원인 후보: 도구 결과가 비었거나 오류인데 모델이 그 의미를 이해하지 못함, 종료 기준이 불명확함, 도구 설명이 모호함. 대책: 도구가 명확한 오류 메시지를 돌려주게 하고, 같은 호출 반복을 감지해 중단하거나 다른 전략을 요구하며, 반복 한도와 종료 기준을 명시한다.

**해설.** 실행 기록을 표로 보면 이런 패턴이 바로 드러난다(7절).

</details>
