## 0. 한눈에 보기 (입문)

### 한 줄 요약
**데이터 품질 관리**는 "이 데이터로 내린 판단을 믿어도 되는가"를 보장하는 일이다. 품질 문제는 대부분 에러 없이 조용히 생기므로, **규칙을 명시하고(제약), 들어올 때 검사하고(검증), 정기적으로 대조하고(대사), 애매한 것은 사람에게 보내는** 여러 겹의 장치가 필요하다.

### 쉬운 설명
식당의 재료 관리를 떠올리자.

- **완전성:** 주문한 재료가 다 왔나(빠진 칸, 빠진 행).
- **유효성:** 유통기한 칸에 날짜가 아니라 "몰라"라고 적혀 있지 않나(형식·범위).
- **유일성:** 같은 상자가 두 번 입고 처리되지 않았나(중복).
- **일관성:** 창고 장부와 주방 장부의 수량이 같은가(시스템 간 일치).
- **적시성:** 오늘 재료인데 어제 장부를 보고 있지 않나(신선도).
- **정확성:** 장부에 10kg라 적혔는데 실제로 10kg인가(현실과 일치).

가장 무서운 건 **멀쩡해 보이는 틀린 장부**다. 에러 메시지도 없고 숫자도 그럴듯한데, 그걸 믿고 주문을 넣으면 손해를 본다.

### 내 프로젝트에서는
- **Preflight는 품질 사고와 대응의 사례집이다**(모두 포트폴리오 기재).
  - **유일성 판정 키 오류:** 품목 기준 중복 제거가 두 사출처에 나눠 맡긴 **정상** 데이터를 지웠다 → 판정 키에 워크센터를 포함하고 반례 테스트 추가(ADR-02).
  - **식별 안정성:** 엑셀 행 번호로 행을 식별하다 줄이 끼면 사람이 고친 값이 옆 행으로 밀림 → 원본 값으로 식별.
  - **메타데이터 완전성:** 대장을 실제 DB와 칸 단위로 대조했는데, 스키마 파서가 일부 문법을 못 읽어 한 달간 18개 칸이 대장에서 빠져 있었다.
  - **집계 정의의 일관성:** '지금 목록'만 세면 지난주 숫자가 바뀔 수 있음을 발견하고, 모든 산출식에 세는 범위를 명시했다.
  - **출처 충돌:** 완료일이 여러 곳에서 오면 사람 > 파일 > 시스템 순으로, 덜 확실한 값이 더 확실한 값을 덮지 않게 했다.
- **DeepVi는 444개 기업의 여러 원천을 연결했다.** 재무·주가·뉴스·ESG·거시 데이터를 PostgreSQL에 저장했다(포트폴리오·README 기재). 여러 원천을 합칠 때는 기업 식별자 일치(일관성)와 수집 날짜(적시성)가 핵심 품질 과제다.

### 먼저 알면 좋은 것
- 데이터 파이프라인과 ETL(DE-PIPE-001): 적재, 대사, 멱등성
- 통계적 공정관리(STAT-SPC-001): 지표의 평소 흔들림과 이상 구분

## 1. 핵심 요약

- **품질 차원:** 완전성, 유효성, 유일성, 일관성, 적시성, 정확성. 문제를 차원으로 분류하면 검사 방법이 정해진다.
- **품질은 용도에 상대적:** 같은 데이터도 대략적 추세 보기에는 충분하고 정산에는 부족할 수 있다(Wang & Strong의 "소비자 관점").
- **방어의 층:** ① DB 제약(NOT NULL, CHECK, UNIQUE, FK) ② 적재 시 검증(형식, 범위, 참조) ③ 정기 점검과 대사 ④ 이상 감시(건수·분포 관리도) ⑤ 사람 검토 대기열.
- **식별과 판정 키:** 품질 사고의 상당수는 "무엇이 같은 것인가"를 잘못 정해서 생긴다.
- **정의의 품질:** 지표 산출식의 범위·기준 시점을 명시하지 않으면 데이터가 맞아도 숫자가 흔들린다.
- **표본 검사:** 정확성은 현실과 대조해야 해 전수 확인이 어렵다. 표본으로 오류율과 그 상한을 추정한다.

## 2. 개념과 등장 배경

"쓰레기가 들어가면 쓰레기가 나온다(garbage in, garbage out)"는 컴퓨터 초기부터의 격언이다. 1990년대 데이터 웨어하우스가 퍼지면서 여러 시스템의 데이터를 합칠 때 품질 문제가 본격적으로 드러났고, 1996년 왕(Wang)과 스트롱(Strong)은 데이터 사용자 설문으로 품질이 정확성 하나가 아니라 여러 차원(내재적, 맥락적, 표현적, 접근성)으로 이루어짐을 보였다.

이후 DAMA의 데이터 관리 지식 체계(DMBOK)가 데이터 품질 관리를 데이터 거버넌스의 핵심 영역으로 정리했다. 2010년대 후반에는 데이터 파이프라인에 테스트를 자동으로 붙이는 도구들과 "데이터 계약"(생산자와 소비자가 스키마·품질 기준을 약속), "데이터 관측성" 개념이 퍼졌다. AI 시대에는 학습·검색에 쓰이는 데이터의 품질이 모델 품질을 좌우하면서 다시 중요해졌다.

## 3. 직관적 설명 및 기초 이론

### 차원별 검사 방법

| 차원 | 질문 | 검사 예 |
|---|---|---|
| 완전성 | 있어야 할 값·행이 있나 | NULL 비율, 기대 행 수, 대장 대 실제 칸 대조 |
| 유효성 | 형식·범위·허용 값을 지키나 | CHECK 제약, 정규식, 날짜 범위 |
| 유일성 | 중복이 없나 | UNIQUE 제약, 업무 키 중복 집계 |
| 일관성 | 시스템·테이블 간 맞나 | 원천 대 결과 대사, 외래 키, 합계 대조 |
| 적시성 | 충분히 최신인가 | 최신 데이터 시각, 파일 기준 시각 |
| 정확성 | 현실과 맞나 | 표본 현장 확인, 다른 원천과 교차 검증 |

### 어디서 막을까

| 위치 | 장점 | 한계 |
|---|---|---|
| DB 제약 | 어떤 경로로 들어와도 막음 | 단순 규칙만, 여러 행에 걸친 규칙은 어려움 |
| 적재 시 검증 | 원천 문제를 입구에서 차단·보고 | 검증 로직 자체의 버그 |
| 정기 점검 | 누적·장기 문제 발견 | 발견이 늦음 |
| 사람 검토 | 애매한 경우 판단 | 비용, 피로 |

## 4. 엄밀한 정의와 작동 원리

### 품질 지표

$$
\text{완전성} = 1 - \frac{\text{누락 값 수}}{\text{기대 값 수}}, \qquad
\text{중복률} = \frac{\text{중복 행 수}}{\text{전체 행 수}}
$$

지표는 테이블·칸별로 매일 기록하고, 관리도(STAT-SPC-001)로 평소 범위를 벗어나는지 감시한다.

### 판정 키 설계

"같은 것"을 판단하는 키가 너무 좁으면 중복이 남고, 너무 넓으면 정상 데이터가 합쳐지거나 지워진다. 키 후보마다 다음을 확인한다.

1. 업무 규칙상 같은 키인데 다른 실체가 있을 수 있나(같은 품목, 다른 워크센터)
2. 키 값이 시간이 지나도 안정적인가(행 번호는 불안정)
3. 키 값에 표기 흔들림이 있나(공백, 대소문자 → 정규화)

### 표본으로 오류율 상한 추정 (3의 규칙)

무작위 표본 $n$개를 현실과 대조했는데 오류가 **0건**이었다. 오류율이 $p$라면 0건이 나올 확률은 $(1 - p)^n$이다. 이 확률이 5%가 되는 $p$를 95% 상한으로 보면

$$
(1 - p)^n = 0.05 \;\Rightarrow\; p \approx \frac{3}{n}
$$

($\ln 0.05 \approx -3$이고 작은 $p$에서 $\ln(1 - p) \approx -p$이기 때문.) 100건이 모두 맞아도 "오류율 0%"가 아니라 "95% 신뢰로 약 3% 이하"라고 말해야 한다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| 완전성, 중복률 | 누락·중복 비율 |
| 판정 키 | 같은 실체를 판단하는 칸 조합 |
| 대사 | 원천과 결과의 수량·합계 대조 |
| $n$ | 표본 크기 |
| $3/n$ | 오류 0건일 때 오류율의 대략적 95% 상한 |
| 데이터 계약 | 생산자·소비자 간 스키마·품질 약속 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 판정 키가 정상 데이터를 지우는 과정

| 품목 | 워크센터 | 수량 | 품목 키로 중복 제거 | 품목+워크센터 키 |
|---|---|---|---|---|
| P-100 | WC-1 | 500 | 남김 | 남김 |
| P-100 | WC-2 | 300 | **삭제(정상인데)** | 남김 |
| P-200 | WC-1 | 200 | 남김 | 남김 |
| P-200 | WC-1 | 200 | 삭제(진짜 중복) | 삭제 |

품목만으로 판정하면 총수량 1,200 중 300이 사라진다. Preflight가 겪은 문제와 같은 구조이며(ADR-02, 표의 숫자는 설명용), 판정 키에 워크센터를 넣고 두 번째 행 같은 상황을 반례 테스트로 고정했다.

### 예제 2. 표본 정확성 검사

ERP에서 가져온 완료일 300건을 무작위로 뽑아 현장 기록과 대조했다.

| 결과 | 해석 |
|---|---|
| 오류 0건 | 95% 상한 약 $3/300 = 1\%$ (정확 계산 0.99%) |
| 오류 6건 | 추정 오류율 2%, 표준오차 $\sqrt{0.02 \times 0.98 / 300} \approx 0.8\%$p |

100건만 봤다면 0건이어도 상한이 약 3%다. 정산처럼 엄격한 용도면 더 큰 표본이 필요하다.

### 예제 3. 메타데이터 대조

| 테이블 | 대장 칸 수 | 실제 DB 칸 수 | 차이 |
|---|---|---|---|
| A | 42 | 42 | 0 |
| B | 37 | 45 | **8** |

"대장 칸 수 = DB 칸 수" 같은 단순한 합계 대조가 파서 누락을 잡는다. Preflight가 대장을 실제 DB와 칸 단위로 대조해 한 달간 빠져 있던 18개 칸을 발견한 것이 이 종류의 검사다(표의 숫자는 설명용). 검사 도구 자체도 검사해야 한다.

## 7. 시각화와 해석

테이블 × 품질 차원 표에 매일의 통과·실패를 색으로 칠하면(초록·노랑·빨강) 어느 원천이 반복해서 문제를 일으키는지 보인다. 지표별로는 시간 순 그래프에 관리 한계를 그려, 오늘의 NULL 비율·중복률이 평소 범위인지 판단한다. 사고가 나면 "언제부터 나빠졌나"를 이 그래프로 찾는다.

## 8. 기술 비교 및 선택 기준

| 문제 | 1차 장치 | 보완 |
|---|---|---|
| 필수 값 누락 | NOT NULL 제약 | 적재 시 거부 보고 |
| 허용 값 밖 | CHECK·enum | 원천 쪽 수정 요청 |
| 중복 | UNIQUE + 올바른 판정 키 | 중복 제거 건수 감시, 반례 테스트 |
| 시스템 간 불일치 | 대사(행 수·합계) | 출처 우선순위 규칙 |
| 오래된 데이터 | 기준 시각 검사(파일 지문) | 신선도 알림 |
| 현실과 불일치 | 표본 현장 확인 | 사람 검토 대기열 |
| 지표 정의 흔들림 | 산출식에 범위·기준 시점 명시 | 지표 사전, 변경 이력 |

## 9. 실무 사례

- **데이터 계약:** 원천 팀이 칸 이름·형식을 바꾸기 전에 소비 팀과 합의하고, 계약 위반은 적재 단계에서 실패시킨다.
- **마스터 데이터 관리:** 거래처·품목처럼 여러 시스템이 공유하는 기준 정보를 한곳에서 관리해 일관성을 지킨다.
- **AI 학습·검색 데이터:** 중복 문서, 오래된 문서, 잘못된 라벨이 모델·RAG 품질을 떨어뜨린다. 문서 수집에도 같은 품질 검사를 적용한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 차원별 대응:** 유일성(판정 키에 워크센터 포함, ADR-02), 식별 안정성(원본 값 식별), 완전성(대장 대 DB 칸 대조, ERP 원본 전체 보존), 적시성(같은 파일·더 오래된 파일은 반영 전에 멈춤), 일관성(출처 우선순위, 재업로드 멱등성), 정의 품질(세는 범위 명시). 업무 규칙 단위 시험 704개와 실제 DB 점검 64개가 이 규칙들을 지킨다.
- **Preflight — 사람 검토:** 위험한 변경만 검토 대기열로 보내고 파일에서 빠진 행은 지우지 않는다. 자동으로 판단하기 애매한 품질 문제를 사람에게 넘기는 마지막 층이다.
- **DeepVi — 다원천 통합:** 재무·주가·뉴스·ESG·거시 데이터를 444개 기업에 연결했다. 점검 질문(기록 없음): 기업 식별자(종목 코드) 기준으로 원천 간 일치를 검사했는가? 뉴스 중복(같은 기사 재수집)과 오래된 재무 수치를 어떻게 걸렀는가?
- **STT — 정답 데이터 품질:** 정답의 특수 태그·불필요한 구두점 제거와 정규화를 했다. 평가 데이터의 정답 품질이 곧 평가 결과의 품질이다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 에러가 없으면 데이터가 맞다.** 품질 사고 대부분은 에러 없이 생긴다(예제 1, 3).
- **오해: 표본에서 오류가 없으면 오류율 0%.** 상한으로 말해야 한다(3의 규칙).
- **오해: 중복은 무조건 지운다.** "같아 보이는 정상 데이터"가 있다. 판정 키를 업무 규칙으로 검증한다.
- **과도한 거부:** 검증이 너무 엄격하면 정상 데이터까지 막혀 사람들이 우회한다. 거부 대신 검토 대기도 선택지다.
- **품질 비용:** 모든 칸을 완벽히 하려 하지 말고, 의사결정에 쓰이는 핵심 데이터부터 관리한다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 무작위 표본 50건을 현실과 대조해 오류가 0건이었다. 오류율에 대해 무엇이라 말할 수 있나?</summary>

**정답.** 95% 신뢰로 오류율이 대략 $3/50 = 6\%$ 이하라고 말할 수 있다. 0%라고 단정할 수는 없다.

**해설.** 3의 규칙. 상한을 1% 아래로 낮추려면 약 300건이 필요하다.

</details>

<details class="qa" data-type="concept"><summary>Q2. DB 제약과 적재 시 검증을 모두 두는 이유는?</summary>

**정답.** DB 제약은 어떤 경로로 들어오든 마지막에 막아 주고, 적재 시 검증은 원천 문제를 입구에서 찾아 무엇이 왜 거부됐는지 보고하며 여러 행에 걸친 복잡한 규칙도 검사할 수 있다. 서로의 빈틈을 메운다.

**해설.** 심층 방어. 둘 중 하나의 버그가 있어도 다른 하나가 잡는다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 지난주 보고한 실적 숫자가 이번 주에 다시 뽑으니 달라졌다는 문의가 왔다. 어떻게 조사하고 재발을 막겠는가?</summary>

**정답.** 산출식이 '지금 상태' 테이블만 보는지, 그 사이 행이 삭제·상태 변경되었는지 확인한다. 재발 방지로 산출식마다 세는 범위(지금 목록, 과거 기록, 원본 누적)와 기준 시점을 명시하고, 필요하면 이력·스냅숏 테이블에서 계산하며, 확정된 보고 수치는 따로 보관한다.

**해설.** Preflight가 실제로 같은 문제를 발견하고 세는 범위를 명시했다. 데이터가 맞아도 정의가 흔들리면 숫자가 흔들린다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 두 공장의 ERP 데이터를 합쳐 품목별 재고를 보려 한다. 품질 검사를 어떻게 설계하겠는가?</summary>

**정답.** 품목 코드 체계가 같은지 확인하고 대응표를 만든다(일관성). 판정 키를 품목 + 공장(+ 창고)으로 정하고 반례로 검증한다(유일성). 원천별 행 수·재고 합계를 대사하고(일관성), 파일 기준 시각을 확인하며(적시성), 음수 재고 같은 허용 범위를 검사한다(유효성). 표본 품목은 실사와 대조한다(정확성).

**해설.** 차원별로 질문을 던지면 검사 목록이 빠짐없이 나온다.

</details>
