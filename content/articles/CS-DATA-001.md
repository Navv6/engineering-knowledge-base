## 0. 한눈에 보기 (입문)

### 한 줄 요약
컴퓨터 파일은 결국 숫자(바이트)의 나열이고, **인코딩**은 "어떤 숫자가 어떤 글자인지"의 약속, **파일 형식**은 "숫자들을 어떤 구조로 늘어놓는지"의 약속이다. 약속이 어긋나면 한글이 깨지고, 날짜가 숫자로 바뀌고, 앞자리 0이 사라진다.

### 쉬운 설명
암호문을 떠올리자. "가=1, 나=2" 표로 쓴 편지를 "가=2, 나=1" 표로 읽으면 엉뚱한 글이 된다. 한글이 `媛◆`나 `◆궪◆꽦` 같은 이상한 글자로 깨지는 것(◆는 해석할 수 없는 자리에 나타나는 대체 문자)이 바로 이 상황이다. 쓴 사람(UTF-8)과 읽는 사람(CP949)의 약속이 달랐던 것이다.

파일 형식도 마찬가지다.
- **CSV:** 쉼표로 칸을 나눈 단순한 글자 파일. 누구나 읽지만 "이 칸이 숫자인지 글자인지" 정보가 없다.
- **XLSX:** 엑셀 파일. 사실은 여러 XML 문서를 압축(ZIP)한 묶음이다. 서식·수식·여러 시트를 담지만, 만드는 프로그램마다 미묘하게 다르게 쓸 수 있다.

### 내 프로젝트에서는
- **Preflight가 실제로 이 문제를 겪고 풀었다.** ERP가 내보낸 **비표준 xlsx** 파일을 ExcelJS와 SheetJS 모두 읽지 못해, 파일을 보정하는 **정규화 모듈**을 직접 만들었다(포트폴리오 기재). 엑셀 원본은 브라우저에서 파싱하고 파싱한 값만 서버에 저장한다. 어떤 부분이 비표준이었는지는 기재가 없다.
- **행 식별 문제도 파일 구조와 관련 있다.** 엑셀 행 번호로 행을 식별하다가 팀 엑셀에 줄 하나가 끼면 값이 옆 행으로 밀려, 원본 값으로 행을 식별하도록 바꿨다(포트폴리오 기재). 행 번호는 파일의 "위치"이지 데이터의 "정체"가 아니다.
- **DeepVi·STT도 한글 텍스트를 다뤘다.** DeepVi는 한국어 뉴스를, STT 평가는 한국어 정답 문장을 정규화했다(특수 태그·구두점 제거, 포트폴리오 기재). 한글 처리에서는 인코딩과 유니코드 정규화(같은 글자의 다른 표현)를 맞추는 것이 기본이다.

### 먼저 알면 좋은 것
- 특별한 선행 지식은 필요 없다. 16진수(0~9, a~f로 세는 수)를 처음 본다면 "바이트 하나는 00~ff의 두 자리로 적는다" 정도만 알면 된다.

## 1. 핵심 요약

- **유니코드:** 세상의 모든 글자에 번호(코드 포인트)를 붙인 표. "가"는 U+AC00.
- **UTF-8:** 코드 포인트를 1~4바이트로 저장하는 방식. 영문은 1바이트, 한글 음절은 3바이트. 웹·리눅스·현대 시스템의 기본.
- **CP949(EUC-KR 확장):** 한국 윈도우의 옛 기본 인코딩. 한글 2바이트. 오래된 엑셀·ERP가 CSV를 이 방식으로 내보내는 경우가 많다.
- **깨짐(mojibake):** 쓴 인코딩과 읽은 인코딩이 다를 때. 해결은 원래 인코딩으로 다시 읽기.
- **CSV:** 쉼표·따옴표·줄바꿈 규칙(RFC 4180), 타입 정보 없음, 구분자·인코딩이 지역마다 다름.
- **XLSX:** XML 묶음의 ZIP(Office Open XML). 셀 값·공유 문자열·스타일이 따로 저장되고, 날짜는 일련번호 숫자 + 서식으로 저장된다.
- **정규화 단계:** 인코딩 확인 → 구조 파싱 → 타입 결정(코드는 문자열, 날짜 변환) → 공백·전각/반각·유니코드 정규화 → 검증.

## 2. 개념과 등장 배경

1963년 영어 중심의 7비트 ASCII(128자)가 표준이 되었고, 각 나라는 남는 공간이나 2바이트 조합으로 자기 글자를 넣은 인코딩을 따로 만들었다. 한국은 KS X 1001(완성형 2,350자) 기반의 EUC-KR을 썼고, 마이크로소프트가 이를 확장해 한글 11,172자를 모두 담은 CP949(통합형)를 만들었다. 나라마다 인코딩이 달라 문서를 주고받으면 글자가 깨지는 일이 흔했다.

1991년 모든 문자를 하나의 번호 체계로 모은 **유니코드**가 시작되었고, 1992년 켄 톰프슨과 롭 파이크(Rob Pike)가 ASCII와 호환되면서 가변 길이로 저장하는 **UTF-8**을 설계했다. 웹에서 UTF-8 비율은 꾸준히 늘어 오늘날 대부분을 차지한다. 파일 형식 쪽에서는 2006년 엑셀의 XML 기반 형식(Office Open XML)이 ECMA-376 표준이 되었고, CSV는 오래 관례로만 쓰이다 2005년 RFC 4180으로 정리되었다.

## 3. 직관적 설명 및 기초 이론

### 같은 글자, 다른 바이트

| 글자 | 유니코드 번호 | UTF-8 바이트 | CP949 바이트 |
|---|---|---|---|
| A | U+0041 | `41` (1바이트) | `41` |
| 가 | U+AC00 | `ea b0 80` (3바이트) | `b0 a1` (2바이트) |

"삼성전자" 네 글자는 UTF-8로 12바이트, CP949로 8바이트다. UTF-8 바이트 `ea b0 80`을 CP949로 읽으면 앞 두 바이트가 다른 한자로 해석되어 `媛◆`처럼 보인다.

### XLSX 파일 안쪽

XLSX의 확장자를 `.zip`으로 바꿔 풀면 `xl/worksheets/sheet1.xml`(셀 위치와 값), `xl/sharedStrings.xml`(반복되는 글자열 목록), `xl/styles.xml`(서식) 같은 파일이 나온다. 셀에는 "공유 문자열 3번" 또는 숫자 "45000"과 "날짜 서식"이 따로 적힌다. 표준을 느슨하게 따르는 프로그램이 이 구조 일부를 다르게 쓰면 엑셀은 열어도 라이브러리는 못 읽는 일이 생긴다.

## 4. 엄밀한 정의와 작동 원리

### UTF-8 규칙

| 코드 포인트 범위 | 바이트 수 | 비트 패턴 |
|---|---|---|
| U+0000–U+007F | 1 | `0xxxxxxx` |
| U+0080–U+07FF | 2 | `110xxxxx 10xxxxxx` |
| U+0800–U+FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000–U+10FFFF | 4 | `11110xxx` + 이어지는 바이트 3개 |

한글 음절(U+AC00–U+D7A3)은 세 번째 줄에 해당해 3바이트다. 첫 바이트만 보면 몇 바이트짜리 글자인지 알 수 있고, ASCII 글자는 그대로라 영어 파일과 호환된다. 파일 맨 앞에 `ef bb bf`(BOM)를 붙여 "UTF-8입니다"라고 표시하기도 하는데, 엑셀은 BOM이 있는 CSV를 UTF-8로 인식하는 경우가 많고 일부 프로그램은 BOM을 글자로 읽어 첫 칸 이름이 깨진다.

### 유니코드 정규화

"가"는 완성형 한 글자(U+AC00)로도, 자모 두 개(ㄱ U+1100 + ㅏ U+1161)로도 표현할 수 있다. 눈에는 같아 보여도 바이트가 달라 비교·검색이 실패한다. NFC(합쳐진 형태)로 통일하는 것이 일반적이다. macOS에서 만든 파일 이름이 자모 분리형으로 저장되는 경우가 대표적이다.

### CSV 규칙과 함정

- 칸 안에 쉼표·따옴표·줄바꿈이 있으면 큰따옴표로 감싸고, 안의 큰따옴표는 두 번 쓴다(`"그는 ""네""라고"`).
- 타입 정보가 없어 "00123", "2026-11-26", "1E5"가 숫자·날짜로 자동 변환될 수 있다.
- 일부 지역 설정의 엑셀은 쉼표 대신 세미콜론을 구분자로 쓴다.

### 엑셀 날짜 일련번호

엑셀(1900 날짜 체계)은 날짜를 기준일로부터의 일수로 저장한다. 1900년을 윤년으로 잘못 취급한 역사적 버그 때문에, 1900년 3월 이후 날짜는 실무적으로 **1899-12-30을 0일로 보고** 일수를 더하면 맞는다. 일련번호 45000은 2023-03-15다. 시간은 소수 부분(0.5 = 정오)이다.

### 숫자 정밀도

컴퓨터의 실수(부동소수점)는 0.1을 정확히 표현하지 못해 $0.1 + 0.2 = 0.30000000000000004$가 된다. 엑셀은 유효숫자 15자리까지만 다루므로 16자리 이상의 카드번호 같은 값은 끝자리가 바뀐다. 코드·번호는 문자열로, 금액은 정수(원 단위)나 고정소수점(DB의 `numeric`)으로 다룬다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| U+AC00 | 유니코드 코드 포인트(16진수) |
| 바이트 `ea` | 8비트 값을 16진수 두 자리로 쓴 것 |
| BOM | 파일 맨 앞 인코딩 표시(UTF-8은 `ef bb bf`) |
| NFC / NFD | 유니코드 합친 형태 / 분리 형태 |
| 일련번호 | 엑셀이 날짜를 저장하는 일수 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 깨진 글자 되돌리기

UTF-8로 저장된 "삼성전자"(12바이트)를 CP949로 읽으면 `◆궪◆꽦◆쟾◆옄`처럼 보인다(python으로 재현). 해결:

1. 원본 파일을 UTF-8로 다시 읽는다 → 정상.
2. 깨진 글자를 이미 저장했다면, 그 글자열을 CP949로 다시 바이트로 바꾼 뒤 UTF-8로 읽으면 되돌릴 수 있는 경우도 있지만, 대체 문자(화면에 보통 마름모 안 물음표로 표시되며, 이 글에서는 ◆로 적는다)로 바뀐 부분은 정보가 사라져 복구할 수 없다.

교훈: 파일을 받으면 **처음에** 인코딩을 확인하고, 깨진 채로 저장하지 않는다.

### 예제 2. 날짜 일련번호 변환

ERP 파일의 납기 칸에 45000이라는 숫자가 있다.

$$
1899\text{-}12\text{-}30 + 45000\text{일} = 2023\text{-}03\text{-}15
$$

같은 방식으로 46000은 2025-12-09다. 이 칸에 날짜 서식이 빠져 있으면 라이브러리는 그냥 숫자 45000으로 읽는다. "이 칸은 날짜"라는 업무 지식으로 변환 규칙을 정해야 한다.

### 예제 3. 받은 파일의 정규화 단계 (설명용)

| 단계 | 하는 일 | 실패 시 |
|---|---|---|
| 1. 형식 확인 | 확장자가 아니라 내용으로 판별(ZIP 서명, 텍스트 여부) | 거부 + 사유 표시 |
| 2. 인코딩 | CSV면 UTF-8 → 실패 시 CP949 시도, BOM 제거 | 검토 요청 |
| 3. 구조 파싱 | 시트·머리글 행 찾기, 병합 셀 풀기 | 비표준 구조 보정 또는 거부 |
| 4. 타입 결정 | 코드 = 문자열, 날짜 = 일련번호·문자열 변환, 금액 = 정수 | 해당 칸 오류 목록 |
| 5. 값 정규화 | 앞뒤 공백, 전각/반각, NFC, 대소문자 | — |
| 6. 검증 | 필수 칸, 형식, 중복(DE-DQ-001) | 거부·검토 |

Preflight의 정규화 모듈이 이 중 어디를 맡았는지는 기재가 없다. 이 표는 일반적인 설계 예시다.

## 7. 시각화와 해석

파일을 16진수 보기(hex 뷰어)로 열면 바이트가 그대로 보인다. 첫 바이트들로 형식을 알 수 있다: `50 4b 03 04`("PK", ZIP 서명)면 XLSX·DOCX 같은 압축 형식, `ef bb bf`면 BOM이 붙은 UTF-8 텍스트. "확장자는 .xlsx인데 사실은 HTML 표"인 파일도 이렇게 찾을 수 있다(일부 오래된 시스템이 이런 파일을 내보낸다).

## 8. 기술 비교 및 선택 기준

| 형식 | 장점 | 단점 | 적합 |
|---|---|---|---|
| CSV | 단순, 어디서나 읽힘, 큰 데이터 | 타입·인코딩·구분자 정보 없음 | 시스템 간 대량 교환(UTF-8 고정) |
| XLSX | 서식·여러 시트·사람이 편집 | 구조 복잡, 생성 프로그램마다 차이 | 사람이 보고 고치는 업무 파일 |
| JSON | 구조·타입(일부) 표현 | 표 데이터에는 장황 | API 교환(SE-API-001) |
| Parquet 등 열 형식 | 타입 보존, 압축, 빠른 분석 | 사람이 직접 못 읽음 | 분석용 대량 저장 |

**원칙:** 사람이 편집하는 단계는 엑셀을 인정하되, 시스템에 들어오는 순간 정규화 단계를 거쳐 타입이 확정된 데이터로 바꾼다. DB는 UTF-8로 통일한다(PostgreSQL은 데이터베이스 생성 시 인코딩을 정한다).

## 9. 실무 사례

- **CSV 내보내기:** 한국 사용자가 엑셀로 열 CSV는 BOM이 붙은 UTF-8로 내보내면 깨짐이 줄어든다(엑셀 버전에 따라 다름, 확인 필요).
- **유전자 이름 사고:** 엑셀이 일부 유전자 기호(예: 날짜처럼 보이는 이름)를 날짜로 자동 변환해 연구 데이터가 손상된 사례가 보고되어, 일부 기호의 공식 이름이 바뀌기도 했다.
- **ERP 연동:** 인코딩·날짜·코드 형식 규칙을 문서로 합의하고, 위반 파일은 적재 전에 거부한다(데이터 계약).

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 비표준 xlsx 정규화:** ExcelJS·SheetJS 모두 읽지 못한 ERP 파일을 보정하는 정규화 모듈을 만들었다. 점검 질문(기록 없음): 비표준 부분이 무엇이었는지(ZIP 구조, XML 네임스페이스, 공유 문자열, 날짜 서식) 문서로 남겼는가? ERP 버전이 바뀌면 다시 깨질 수 있으니, 실제 ERP 파일 표본으로 회귀 테스트를 두었는가?
- **Preflight — 브라우저 파싱과 원본 보존:** 원본 파일은 밖으로 보내지 않고 파싱 값만 저장하며, 처음 12개 필드만 저장하다 ERP 원본 전체를 보존하는 구조로 바꿨다. 파싱 단계에서 타입이 잘못 정해지면(예제 2의 날짜, 앞자리 0) 저장된 값 자체가 틀리므로, 원본 값 보존은 나중에 다시 해석할 수 있게 해 준다.
- **Preflight — 행 식별:** 행 번호 대신 원본 값으로 식별. 원본 값 비교 전에 공백·전각/반각·유니코드 정규화를 하지 않으면 같은 값이 다르게 보일 수 있다.
- **STT — 정답 정규화:** 특수 태그·구두점 제거와 텍스트 정규화. 유니코드 정규화(NFC)와 숫자 표기 통일도 같은 단계에 속한다(AI-ASR-001 예제 3).

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 확장자가 형식을 정한다.** 확장자는 이름일 뿐이다. 내용(첫 바이트)으로 판별한다.
- **오해: 한글이 깨지면 데이터가 망가졌다.** 대부분 해석 문제다. 깨진 채로 다시 저장하는 순간 진짜 손상이 된다.
- **오해: 엑셀에서 보이는 값이 저장된 값이다.** 엑셀은 서식으로 보여 줄 뿐, 실제 값(일련번호, 15자리 정밀도)은 다를 수 있다.
- **자동 감지의 한계:** 인코딩 자동 감지는 추측이다. 짧은 파일은 틀리기 쉬우므로 합의된 인코딩을 쓴다.
- **정규화의 대가:** 공백 제거, 대소문자 통일이 실제로 다른 값을 같게 만들 수도 있다. 업무 규칙으로 확인한다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 한글 100자와 영문 100자로 된 텍스트를 UTF-8로 저장하면 몇 바이트인가?</summary>

**정답.** $100 \times 3 + 100 \times 1 = 400$바이트(BOM 제외).

**해설.** 한글 음절은 UTF-8로 3바이트, ASCII 영문은 1바이트다. CP949였다면 $100 \times 2 + 100 = 300$바이트다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 엑셀 일련번호 45001.5는 언제인가?</summary>

**정답.** 2023-03-16 정오(12:00).

**해설.** 45000이 2023-03-15이므로 45001은 다음 날, 소수 0.5는 하루의 절반(12시간)이다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 협력사가 매주 보내는 CSV가 어떤 주는 한글이 깨지고 어떤 주는 정상이다. 어떻게 해결하겠는가?</summary>

**정답.** 보내는 쪽의 내보내기 방법(프로그램·설정)이 매번 달라 인코딩이 바뀌는 것으로 보고, UTF-8로 고정하자고 합의한다. 받는 쪽은 인코딩을 확인해 합의와 다르면 거부·경고하고, 자동 감지에만 의존하지 않는다. 받은 원본은 그대로 보관한다.

**해설.** 기술보다 합의(데이터 계약)가 근본 해결이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. ERP 엑셀의 품목 코드 칸이 어떤 행은 "00123", 어떤 행은 123으로 읽힌다. 원인과 해결은?</summary>

**정답.** 일부 셀은 텍스트, 일부는 숫자로 저장되어 숫자 셀의 앞자리 0이 사라졌다. 품목 코드 칸은 항상 문자열로 읽고, 숫자로 읽힌 값은 업무 규칙(코드 자릿수)에 맞게 앞자리 0을 채워 정규화하며, 규칙에 맞지 않는 값은 검토로 보낸다. 원본 값도 보존한다.

**해설.** 같은 코드가 두 형태로 저장되면 판정 키·중복 검사가 깨진다(DE-DQ-001).

</details>
