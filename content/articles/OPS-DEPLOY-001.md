## 0. 한눈에 보기 (입문)

### 한 줄 요약
**배포**는 만든 프로그램을 실제 사용자가 쓰는 곳에 올리는 일이고, **환경 분리**는 "실험하는 곳(개발)"과 "실제로 일하는 곳(운영)"을 나눠 실수가 사용자에게 바로 닿지 않게 하는 방법이다. 좋은 배포의 조건은 **자동이고, 검사를 거치고, 되돌릴 수 있는 것**이다.

### 쉬운 설명
식당이 새 메뉴를 내놓는 과정을 떠올리자.

- **개발 환경 = 시험 주방.** 마음껏 실험하고 실패해도 손님은 모른다.
- **검증 환경 = 직원 시식회.** 실제 주방과 같은 도구로 만들어 맛과 시간을 확인한다.
- **운영 환경 = 실제 영업.** 손님이 먹는다. 여기서 실수하면 바로 불만이 나온다.

새 메뉴가 손님 반응이 나쁘면 **어제 메뉴로 바로 돌아갈 수 있어야**(롤백) 한다. 그런데 이미 재료를 바꿔 버렸다면(DB를 바꿔 버렸다면) 돌아가기 어렵다. 그래서 재료는 "새것을 추가만 하고, 옛것은 당분간 그대로" 두는 방식이 안전하다.

### 내 프로젝트에서는
- **Preflight는 이 원칙을 그대로 구현했다(11.10).** 개발/운영 서버를 분리하고, **개발을 거치지 않은 변경은 배포 스크립트가 거부**하며, **DB 변경은 더하기만 해서 되돌려도 데이터가 남게** 했다(포트폴리오 기재).
- **사내 서버 운영을 스크립트로 정리했다.** 클라우드 없이 사내 서버에서 운영하고, 설치·백업·복원을 PowerShell 스크립트로 정리했다(포트폴리오 기재). 전담 운영 인력이 없는 현장에서 "누가 해도 같은 결과"가 나오게 한 것이다.
- **DeepVi는 배포 여건이 결정을 바꾼 사례다.** 시연과 주변 사용자 테스트까지 진행했지만, 상시 운영할 배포 서버 여건이 되지 않아 공개 서비스로 열지 않았다(포트폴리오 기재).
- **이 학습 사이트도 배포 파이프라인이 있다.** 원본은 GitHub 저장소, 매일 예약 실행이 글을 쓰고 → 검증 → 단위 시험 → E2E 시험을 모두 통과해야 → 커밋·푸시 → 학습 페이지 게시. 하나라도 실패하면 게시하지 않는다.

### 먼저 알면 좋은 것
- 프로세스·스레드·동시성(CS-OS-001): 서버 프로그램이 프로세스로 실행된다는 것

## 1. 핵심 요약

- **환경:** 개발(자유롭게 실험) → 검증(운영과 같은 구성으로 확인) → 운영(실사용). 같은 코드가 설정만 바꿔 각 환경에서 돌아야 한다.
- **설정과 비밀 분리:** DB 주소, API 키는 코드에 넣지 않고 환경 변수·비밀 저장소로. 저장소에 비밀이 커밋되면 이력에 영원히 남는다.
- **재현 가능한 배포:** 설치·배포·백업·복원을 스크립트로. 컨테이너는 실행 환경까지 묶어 "내 PC에서는 되는데"를 줄인다.
- **배포 게이트:** 테스트·검증 통과, 개발 환경 경유, 승인 같은 조건을 자동으로 강제.
- **롤백 가능성:** 코드는 이전 버전으로, DB는 확장-축소(expand-contract) 방식으로 "더하기만" 해서 되돌려도 동작하게.
- **백업은 복원해 봐야 백업이다.** RPO(잃어도 되는 데이터 시간)와 RTO(복구에 걸려도 되는 시간)를 정하고 복원을 연습한다.

## 2. 개념과 등장 배경

과거에는 개발팀이 만든 프로그램을 운영팀이 받아 수작업으로 서버에 설치했고, 배포는 몇 달에 한 번 밤새 하는 큰 행사였다. 수작업은 실수가 잦고, 개발과 운영 사이의 벽은 "개발은 변경을, 운영은 안정을" 원하는 갈등을 낳았다.

2000년대 후반 **데브옵스**(DevOps) 운동이 이 벽을 허물자고 주장했고, 2010년 험블(Humble)과 팔리(Farley)의 『Continuous Delivery』는 "언제든 버튼 하나로 안전하게 배포할 수 있는 상태"를 목표로 빌드·테스트·배포를 자동화하는 파이프라인을 정리했다. 2011년 Heroku의 애덤 위긴스(Adam Wiggins)가 정리한 "The Twelve-Factor App"은 설정을 환경 변수로 분리하고 개발·운영 환경을 최대한 비슷하게 유지하라는 원칙을 널리 퍼뜨렸다. 2013년 Docker가 컨테이너를 대중화했고, 2016년 구글의 『Site Reliability Engineering』은 가용성 목표와 장애 예산 같은 운영 개념을 정리했다.

## 3. 직관적 설명 및 기초 이론

### 환경별 역할

| 환경 | 데이터 | 누가 | 목적 |
|---|---|---|---|
| 개발 | 가짜·익명화 데이터 | 개발자 | 기능 만들기, 빠른 실험 |
| 검증(스테이징) | 운영과 비슷한 데이터·구성 | 개발자, 시험 담당 | 배포 직전 최종 확인, 마이그레이션 시험 |
| 운영 | 실제 데이터 | 사용자 | 실제 업무 |

환경이 하나뿐이면 실험이 곧 사고가 된다. 환경이 다르게 생겼으면(운영만 다른 DB 버전) 검증이 의미가 없다. "나누되, 비슷하게"가 원칙이다.

### 설정을 코드 밖으로

```text
# 같은 코드, 다른 설정
개발: DATABASE_URL=postgres://dev-server/app   LOG_LEVEL=debug
운영: DATABASE_URL=postgres://prod-server/app  LOG_LEVEL=info
```

코드에 운영 DB 주소가 박혀 있으면 개발 중 실수로 운영 데이터를 바꿀 수 있다. API 키 같은 비밀은 환경 변수나 비밀 저장소에 두고, 저장소에는 절대 커밋하지 않는다.

## 4. 엄밀한 정의와 작동 원리

### 배포 파이프라인

1. 코드 변경 → 저장소에 커밋
2. 자동 빌드 → 단위 테스트 → 통합·E2E 테스트
3. 검증 환경 배포 → 확인(자동·수동)
4. 운영 배포 → 상태 확인(헬스 체크, 오류율)
5. 문제 시 롤백

각 단계는 앞 단계의 **성공을 조건으로** 실행된다(SE-TEST-001의 종료 코드 게이트).

### 배포 전략

| 전략 | 방법 | 장점 | 단점 |
|---|---|---|---|
| 한 번에 교체 | 서버를 멈추고 새 버전으로 | 단순 | 중단 시간, 롤백 느림 |
| 블루-그린 | 새 환경(그린)을 띄우고 트래픽을 한 번에 전환 | 즉시 롤백(블루로 다시 전환) | 자원 두 배 |
| 카나리 | 일부 사용자에게만 먼저 | 위험을 작게 확인 | 라우팅·관측 필요 |
| 롤링 | 서버를 하나씩 교체 | 중단 없음 | 두 버전이 동시에 돎 → 호환성 필요 |

### 확장-축소(expand-contract) DB 변경

칸 `due`를 `due_date`로 바꾸고 싶을 때:

1. **확장:** `due_date` 칸을 **추가**한다(옛 칸 유지).
2. **이중 쓰기:** 새 코드가 두 칸에 모두 쓰고, 기존 행의 값을 새 칸으로 채운다.
3. **전환:** 읽기를 새 칸으로 옮긴다. 이 단계까지는 언제든 옛 코드로 롤백해도 옛 칸이 살아 있다.
4. **축소:** 충분히 안정된 뒤 옛 칸을 지운다(이 단계만 되돌리기 어려우므로 마지막에 따로).

Preflight의 "DB 변경은 더하기만 해서 되돌려도 데이터가 남게"가 1~3단계의 원칙이다.

### 백업·복원과 RPO·RTO

PostgreSQL 공식 문서는 백업 방식을 크게 SQL 덤프(`pg_dump`), 파일 시스템 수준 백업, 연속 아카이빙(WAL 기반 시점 복구) 세 가지로 설명한다.

- **RPO**(복구 시점 목표): 장애 시 잃어도 되는 최대 데이터 기간. 매일 밤 덤프만 하면 RPO는 최대 24시간.
- **RTO**(복구 시간 목표): 장애부터 서비스 복구까지 걸려도 되는 최대 시간.

### 가용성 숫자

$$
\text{허용 중단 시간} = (1 - \text{가용성}) \times \text{기간}
$$

30일(43,200분) 기준: 99% → 432분(7.2시간), 99.9% → 43.2분, 99.99% → 약 4.3분. 9 하나를 더할 때마다 허용 중단이 10분의 1로 줄고, 드는 비용은 크게 는다.

## 5. 수식 및 기호 설명

| 용어 | 뜻 |
|---|---|
| 환경 변수 | 프로그램 밖에서 주입하는 설정 값 |
| 롤백 | 이전 버전으로 되돌리기 |
| 헬스 체크 | 서비스가 정상인지 자동 확인하는 요청 |
| RPO / RTO | 잃어도 되는 데이터 기간 / 복구 허용 시간 |
| 가용성 | 서비스가 정상 동작한 시간 비율 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 배포 게이트가 막는 사고

| 상황 | 게이트 없음 | 게이트 있음 |
|---|---|---|
| 개발자가 급하게 운영 서버에서 직접 코드 수정 | 반영됨, 개발 서버와 코드가 달라짐 | 배포 스크립트가 "개발 환경을 거치지 않음"으로 거부 |
| 테스트 1건 실패 | 모르고 배포 | 파이프라인 중단 |
| 마이그레이션이 옛 칸을 삭제 | 롤백 시 옛 코드가 칸을 못 찾아 장애 | 더하기만 하는 규칙으로 리뷰에서 걸림 |

첫 줄이 Preflight의 실제 장치다(포트폴리오 기재). 이 학습 사이트도 검증·단위·E2E 중 하나라도 실패하면 게시하지 않는다. 실제로 E2E 1건이 실패해 게시를 멈추고 시험을 고친 뒤 게시한 일이 있다(HANDOFF.md 기록).

### 예제 2. 백업 주기와 RPO

매일 02:00에 `pg_dump`. 목요일 17:00에 디스크가 망가졌다.

- 마지막 백업: 목요일 02:00 → 잃는 데이터: 02:00~17:00, **15시간**
- 이 업무에서 RPO가 1시간이어야 한다면? 매일 덤프로는 부족 → WAL 연속 아카이빙(시점 복구)이나 1시간 주기 백업 + 복제 필요
- 복원 연습: 덤프 크기가 20GB이고 복원에 40분 걸린다면 RTO가 30분인 업무에는 부족

"백업이 있다"가 아니라 "몇 시간치를 잃고, 몇 분 만에 복구할 수 있다"로 말해야 한다. Preflight가 백업과 **복원**을 모두 스크립트로 둔 것이 이 점에서 중요하다.

### 예제 3. 가용성 목표 정하기

사내 업무 도구가 평일 09~18시에만 쓰인다면 "24시간 99.99%"는 과한 목표다. 업무 시간(한 달 약 22일 × 9시간 = 198시간) 기준 99.5%면 허용 중단은 $198 \times 60 \times 0.005 \approx 59$분. 이런 목표라면 업무 시간 밖에 배포하고, 단일 서버 + 확실한 복원 절차가 비용 대비 합리적이다.

## 7. 시각화와 해석

배포 파이프라인은 왼쪽에서 오른쪽으로 흐르는 상자(빌드 → 시험 → 검증 → 운영)와 각 상자 사이의 문(게이트)으로 그린다. 문마다 "무엇을 확인하고, 실패하면 어디로 돌아가는지"를 적어 두면 팀 전체가 같은 규칙을 이해한다. 그래프로 보면 DAG(MATH-GRAPH-001)이고, 상태로 보면 상태 머신(CS-GEN-001)이다.

## 8. 기술 비교 및 선택 기준

| 상황 | 권장 |
|---|---|
| 사내 서버 한두 대, 운영 인력 없음 | 설치·배포·백업·복원 스크립트, 개발/운영 분리, 업무 시간 외 배포(Preflight 방식) |
| 클라우드, 서비스 여러 개 | 컨테이너 + CI/CD + 관리형 DB |

| 정적 사이트·문서 | 저장소 푸시 → 빌드 → 정적 호스팅(이 학습 사이트) |
| 데이터가 외부로 나가면 안 됨 | 온프레미스, 사내망 배포 |

## 9. 실무 사례

- **금요일 오후 배포 금지 규칙:** 문제를 대응할 사람이 없는 시간을 피한다. 자동 롤백이 있으면 덜 중요해진다.
- **기능 플래그:** 코드는 배포하되 기능은 설정으로 켜고 끈다. 배포와 출시를 분리해 위험을 줄인다.
- **비밀 유출 대응:** 저장소에 API 키가 커밋되면 이력을 지워도 이미 복제되었을 수 있으므로 **키를 즉시 폐기·재발급**한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 기록에서 옮긴 것이다.

- **Preflight — 환경 분리와 배포 게이트(11.10):** 개발/운영 서버 분리, 개발을 거치지 않은 변경은 배포 스크립트가 거부, DB 변경은 더하기만. 4절의 파이프라인 게이트와 확장-축소 방식의 실제 구현이다.
- **Preflight — 스크립트화된 운영:** 클라우드 없이 사내 서버에서 운영하고 설치·백업·복원을 PowerShell 스크립트로 정리했다. 점검 질문: 복원 스크립트로 실제 복원을 연습해 걸린 시간(RTO)을 재 보았는가? 백업 주기에 따른 RPO는 업무 요구에 맞는가?
- **Preflight — PostgreSQL 이전(08.15)과 누적 병합(08.16):** 큰 구조 변경을 단계적으로 진행한 기록이다.
- **DeepVi — 배포 여건:** 상시 운영할 배포 서버 여건이 되지 않아 공개 서비스로 열지 않았다. 외부 API 비용, 서버 비용, 운영 책임은 기술 선택만큼 중요한 배포 조건이다.
- **이 학습 사이트 — 정적 배포 파이프라인:** GitHub 저장소(원본) → 예약 실행이 작성 → 검증·단위·E2E → 커밋·푸시 → 아티팩트 게시. 실패 시 초안으로 남기고 게시하지 않는다(AUTOMATION.md).

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 백업이 있으니 안전하다.** 복원해 보지 않은 백업은 쓸 수 있는지 모른다.
- **오해: 롤백 버튼만 있으면 된다.** DB 스키마나 데이터가 바뀌었으면 코드 롤백만으로는 안 된다. 확장-축소로 설계해야 한다.
- **오해: 개발 환경에 운영 데이터를 복사하면 편하다.** 개인정보·영업 비밀이 개발 환경으로 새어 나간다. 익명화한다.
- **환경 차이:** OS, DB 버전, 설정이 다르면 검증이 의미 없다. 컨테이너나 같은 설치 스크립트로 맞춘다.
- **과잉 설계:** 사용자 열 명의 사내 도구에 쿠버네티스는 운영 부담이 이득보다 크다. 규모에 맞게 고른다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 가용성 99.9%인 서비스가 30일 동안 허용되는 중단 시간은?</summary>

**정답.** 약 43.2분.

**해설.** $43{,}200\text{분} \times 0.001 = 43.2$분. 99.99%면 약 4.3분이다.

</details>

<details class="qa" data-type="concept"><summary>Q2. RPO와 RTO의 차이를 예로 설명하라.</summary>

**정답.** RPO는 장애 시 잃어도 되는 데이터의 시간 범위(예: 최대 1시간치 입력까지), RTO는 서비스를 복구하는 데 걸려도 되는 시간(예: 30분 안에 복구)이다.

**해설.** 매일 밤 백업은 RPO 최대 24시간을 뜻한다. RTO는 복원 연습으로만 확인할 수 있다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 운영 DB의 칸 이름을 바꾸는 배포를 해야 한다. 롤백 가능성을 지키려면 어떻게 진행하겠는가?</summary>

**정답.** 확장-축소 방식으로 나눈다. ① 새 칸 추가, ② 새 코드가 두 칸에 모두 쓰고 기존 값 복사, ③ 읽기를 새 칸으로 전환하고 안정화 기간을 둔다(이때까지는 옛 버전으로 롤백 가능), ④ 별도 배포로 옛 칸 삭제.

**해설.** 한 번에 이름을 바꾸면 롤백한 옛 코드가 옛 칸을 찾지 못해 장애가 난다. Preflight의 "더하기만 하는 DB 변경"과 같은 원칙이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 클라우드를 쓸 수 없고 운영 담당자도 없는 공장에 업무 도구를 배포해야 한다. 무엇을 준비하겠는가?</summary>

**정답.** 사내 서버에 개발/운영 환경을 분리하고, 설치·배포·백업·복원을 한 줄로 실행되는 스크립트로 만들며, 배포 스크립트에 "개발 환경 시험 통과" 조건을 넣는다. 백업 주기와 복원 시간을 업무 요구(RPO·RTO)에 맞춰 정하고 복원을 실제로 연습해 문서화한다. 배포는 업무 시간 외에 한다.

**해설.** Preflight가 실제로 택한 방식과 같다. 사람이 바뀌어도 같은 결과가 나오게 하는 것이 핵심이다.

</details>
