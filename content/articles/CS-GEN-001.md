## 0. 한눈에 보기 (입문)

### 한 줄 요약
**상태 머신**은 "지금 어떤 상태인가"와 "무슨 일이 생기면 어느 상태로 바뀌는가"를 표로 못 박아 두는 설계 방법이다. 업무 흐름, 주문 처리, 신호등, AI 에이전트가 모두 상태 머신으로 정리된다.

### 쉬운 설명
택배를 떠올리자. 택배는 **접수 → 배송 중 → 배송 완료** 순서로 바뀐다. 중간에 **반송**될 수도 있다.

- 접수, 배송 중, 배송 완료, 반송이 **상태**다. 택배는 한 순간에 정확히 한 상태에만 있다.
- "기사가 물건을 실었다", "고객이 받았다" 같은 일이 **이벤트**다.
- 이벤트가 상태를 바꾸는 규칙(배송 중 + 고객 수령 → 배송 완료)이 **전이**다.

중요한 것은 **안 되는 전이**도 정해진다는 점이다. "배송 완료"된 택배가 갑자기 "접수"로 돌아가면 뭔가 잘못된 것이다. 상태 머신으로 정리해 두면 이런 이상한 변화를 바로 잡아낼 수 있다.

### 내 프로젝트에서는
- **Preflight의 업무 단계가 상태 머신이다.** 파일에서 빠진 행을 지우지 않고 완료·취소·드롭 같은 **업무 단계**로 관리했다(포트폴리오 기재, ADR-05). 행이 지워지는 대신 상태가 바뀌니 기록이 남고, 업로드 단위로 되돌릴 수도 있다.
- **"위험한 변경만 검토로"가 곧 위험한 전이 목록이다.** 포트폴리오에는 "완료였던 건이 다시 진행 중으로 옴 → 검토" 같은 규칙이 있다. 상태 머신 관점에서는 "완료 → 진행 중" 전이를 자동으로 허용하지 않고 사람 확인을 거치게 한 것이다.
- **동기화 파이프라인도 단계 상태를 가진다.** 파일 지문 확인 단계에서 "같은 파일이거나 더 오래된 파일"이면 반영 전에 멈춘다(포트폴리오 기재). 업로드 한 건이 "확인 중 → 반영 / 중단"으로 바뀌는 작은 상태 머신이다.

### 먼저 알면 좋은 것
- 집합과 명제논리(MATH-DM-001): 전이 조건은 논리식이다.
- 그래프 이론 기초(MATH-GRAPH-001): 상태 머신을 그리면 정점(상태)과 방향 간선(전이)으로 된 그래프가 된다.

## 1. 핵심 요약

- **구성 요소:** 상태 집합, 초기 상태, 이벤트(입력), 전이 규칙, (필요하면) 종료 상태.
- **핵심 성질:** 한 순간에 정확히 하나의 상태. 다음 상태는 "현재 상태 + 이벤트"로 정해진다.
- **전이표**로 정리하면 허용·금지·검토 필요 전이가 한눈에 보인다.
- **불리언 플래그 여러 개**(is_done, is_canceled …)로 상태를 표현하면 "완료이면서 취소" 같은 불가능한 조합이 생긴다. 상태 칸 하나 + 허용 값 제약이 안전하다.
- 유한 상태 기계(FSM)는 계산 이론의 기본 모델이기도 하다. 정규 표현식은 FSM으로 실행된다.
- 복잡해지면 계층 상태(statechart)로 확장한다.

## 2. 개념과 등장 배경

상태 머신은 1950년대에 회로와 계산을 설명하는 모델로 정리되었다. 조지 밀리(George Mealy, 1955)와 에드워드 무어(Edward Moore, 1956)가 출력이 언제 정해지는지에 따라 두 형식을 제안했고, 마이클 라빈과 데이나 스콧(1959)이 유한 오토마타 이론을 정리했다. 정규 표현식과 유한 오토마타가 같은 표현력을 갖는다는 클리니(Kleene)의 결과도 이 무렵이다.

소프트웨어 설계에서는 상태가 수십 개로 늘면 표가 폭발하는 문제가 있었다. 1987년 데이비드 하렐(David Harel)은 상태 안에 하위 상태를 두는 **statechart**를 제안했고, 이 개념이 UML 상태 다이어그램의 바탕이 되었다. 오늘날 결제·주문 시스템, UI 화면 흐름, 네트워크 프로토콜(TCP 연결 상태), 게임 캐릭터, 그리고 AI 에이전트의 작업 흐름이 상태 머신으로 설계된다.

## 3. 직관적 설명 및 기초 이론

### 전이표로 생각하기

행은 현재 상태, 열은 이벤트, 칸은 다음 상태다. 아래는 업무 단계를 단순화한 **설명용 예시**다(Preflight의 실제 상태 이름·규칙 전체가 아니다).

| 현재 상태 \ 이벤트 | 완료일 입력 | 취소 표시 | 파일에서 사라짐 | 다시 진행 중으로 들어옴 |
|---|---|---|---|---|
| 진행 중 | 완료 | 취소 | 드롭 후보(검토) | 진행 중 |
| 완료 | 완료 | 검토 | 완료 유지 | **검토** |
| 취소 | 검토 | 취소 | 취소 유지 | 검토 |
| 드롭 | 검토 | 취소 | 드롭 | 진행 중(복귀) |

칸마다 "자동 전이 / 검토 / 무시" 중 하나를 고르면 모든 경우가 빠짐없이 결정된다. 빈칸이 있으면 그 경우를 아무도 생각하지 않았다는 신호다.

### 그림으로 보면

상태를 동그라미, 전이를 화살표로 그리면 방향 그래프가 된다(MATH-GRAPH-001). 어떤 상태에서도 나갈 화살표가 없으면 **종료 상태**, 들어오는 화살표가 없는데 초기 상태도 아니면 **도달할 수 없는 상태**(죽은 코드)다.

## 4. 엄밀한 정의와 작동 원리

### 유한 상태 기계 (결정적)

다섯 가지로 정의한다:

$$
M = (Q, \Sigma, \delta, q_0, F)
$$

- $Q$: 상태의 유한 집합
- $\Sigma$: 입력(이벤트)의 유한 집합
- $\delta : Q \times \Sigma \to Q$: 전이 함수. 현재 상태와 입력이 주어지면 다음 상태가 **하나** 정해진다.
- $q_0 \in Q$: 초기 상태
- $F \subseteq Q$: 받아들임(종료) 상태 집합

입력 이벤트 열 $a_1, a_2, \dots, a_n$을 차례로 넣으면 $q_{i} = \delta(q_{i-1}, a_i)$로 상태가 바뀐다. 마지막 상태가 $F$에 있으면 그 입력 열을 "받아들인다"고 한다.

### 업무 시스템에서의 변형

- **부분 함수:** 모든 $(q, a)$ 조합에 전이가 정의되지 않을 수 있다. 정의되지 않은 조합은 **거부**(오류)로 처리한다.
- **가드(guard):** 전이에 조건을 붙인다. 예: "완료일 입력" 이벤트라도 `완료일 ≤ 오늘`일 때만 완료로.
- **액션:** 전이할 때 실행할 일. 예: 완료로 바뀔 때 KPI 집계 갱신, 이력 기록.
- **밀리 vs 무어:** 출력(액션)이 전이에 붙으면 밀리형, 상태에 붙으면 무어형이다.

### 정규 표현식과의 관계

정규 표현식은 결국 유한 상태 기계로 실행된다. 예를 들어 "숫자 하나 이상"을 뜻하는 `[0-9]+`는 "시작 → (숫자) → 숫자 읽는 중 → (숫자) → 숫자 읽는 중" 두 상태짜리 기계다. DeepVi가 질문을 정규식으로 분류한 것(저장소 코드)도 내부적으로는 이런 기계를 돌린 셈이다(파이썬 `re`는 백트래킹 방식이라 구현은 다르지만 표현하는 언어는 같다).

## 5. 수식 및 기호 설명

| 기호 | 읽는 법 | 뜻 |
|---|---|---|
| $Q$ | "상태 집합" | 가능한 모든 상태 |
| $\Sigma$ | "시그마, 입력 알파벳" | 가능한 모든 이벤트 |
| $\delta(q, a)$ | "델타 q a" | 상태 $q$에서 이벤트 $a$가 오면 갈 상태 |
| $Q \times \Sigma$ | "Q 곱 시그마" | (상태, 이벤트) 쌍의 집합 |
| $q_0$ | "큐 제로" | 초기 상태 |
| $F \subseteq Q$ | "F는 Q의 부분집합" | 종료 상태들 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 이벤트 열 따라가기

3절 전이표에서 시작 상태가 "진행 중"이고 이벤트가 [완료일 입력, 파일에서 사라짐, 다시 진행 중으로 들어옴] 순으로 오면:

| 단계 | 현재 | 이벤트 | 다음 |
|---|---|---|---|
| 1 | 진행 중 | 완료일 입력 | 완료 |
| 2 | 완료 | 파일에서 사라짐 | 완료 유지 |
| 3 | 완료 | 다시 진행 중으로 들어옴 | **검토** |

3단계에서 자동 반영을 멈추고 사람에게 묻는다. ERP 쪽 실수일 수도, 실제로 재작업이 생긴 것일 수도 있기 때문이다.

### 예제 2. 불리언 플래그의 함정

상태를 칸 두 개 `is_done`, `is_canceled`로 저장하면 조합은 $2^2 = 4$가지다.

| is_done | is_canceled | 의미 |
|---|---|---|
| F | F | 진행 중 |
| T | F | 완료 |
| F | T | 취소 |
| T | T | **?? 불가능한 상태** |

플래그가 $n$개면 조합은 $2^n$개인데 실제 의미 있는 상태는 그보다 적다. 대신 상태 칸 하나를 두고 허용 값을 제한한다:

```sql
ALTER TABLE task
  ADD CONSTRAINT task_stage_valid
  CHECK (stage IN ('진행 중', '완료', '취소', '드롭'));
```

CHECK 제약은 "불가능한 상태"를 막지만 "불가능한 전이"(완료 → 진행 중)까지는 막지 못한다. 전이 규칙은 애플리케이션의 판정 함수나 DB 트리거(이전 값 `OLD`와 새 값 `NEW`를 비교)로 검사한다.

### 예제 3. 전이 판정 함수

```javascript
const RISKY = new Set(['완료>진행 중', '취소>완료', '드롭>완료']);
const ALLOWED = new Set(['진행 중>완료', '진행 중>취소', '드롭>진행 중', ...RISKY]);

function decide(from, to) {
  if (from === to) return 'no-op';
  const key = `${from}>${to}`;
  if (!ALLOWED.has(key)) return 'reject';
  return RISKY.has(key) ? 'review' : 'apply';
}
```

판정이 DB나 화면과 분리된 **순수 함수**라서 모든 (from, to) 조합을 표로 넣어 시험하기 쉽다. 상태가 4개면 조합은 $4 \times 4 = 16$개뿐이다. Preflight가 판정 규칙을 DB·브라우저 없이 순수 함수로 시험한 방식(단위 시험 704개, 포트폴리오 기재)이 이런 구조다. 위 코드는 설명용이며 Preflight 코드가 아니다.

## 7. 시각화와 해석

전이표를 그래프로 그려 보면 세 가지를 바로 점검할 수 있다:

1. **도달 불가 상태:** 초기 상태에서 화살표를 따라 갈 수 없는 상태. BFS로 찾는다(MATH-GRAPH-001).
2. **빠져나올 수 없는 상태:** 종료 상태가 아닌데 나가는 화살표가 없는 상태. 업무가 영원히 멈춘다.
3. **위험한 화살표:** 색을 다르게 칠한 검토 필요 전이. 역방향(완료 → 진행 중) 화살표가 대부분 여기에 속한다.

이 사이트의 지식 지도처럼 화살표 그래프로 보는 것이 표보다 직관적일 때가 많다.

## 8. 기술 비교 및 선택 기준

| 방식 | 장점 | 단점 | 적합한 경우 |
|---|---|---|---|
| if-else 흩어진 코드 | 처음엔 빠름 | 규칙이 여러 곳에 흩어져 누락·모순 | 상태 2~3개 |
| 전이표(데이터) + 판정 함수 | 한 곳에서 관리, 전수 시험 쉬움 | 표 설계 필요 | 업무 흐름 대부분 |
| 계층 상태(statechart) 라이브러리 | 하위 상태·병렬 상태 표현 | 학습 비용 | UI, 복잡한 제어 |
| 워크플로 엔진(BPMN 등) | 시각적 설계, 운영 도구 | 무겁다 | 여러 팀·장기 프로세스 |

**판단:** 상태가 4개 이상이거나 "되돌아가는 전이"가 있으면 전이표로 옮기는 것이 좋다. 전이표는 문서이자 시험 데이터가 된다.

## 9. 실무 사례

- **주문·결제:** 결제 대기 → 결제 완료 → 배송 → 환불 같은 흐름. 결제 완료를 두 번 처리하지 않도록 전이를 한 번만 허용한다(멱등성).
- **TCP 연결:** LISTEN, SYN-SENT, ESTABLISHED, CLOSE-WAIT 등 표준에 정의된 상태 머신이다.
- **UI:** 로딩 중 / 성공 / 실패 / 비어 있음 상태를 명시하면 "로딩 표시와 오류 메시지가 동시에 뜨는" 버그가 사라진다.
- **AI 에이전트:** 계획 → 도구 실행 → 결과 확인 → 다음 행동 / 사람 확인 대기 같은 루프를 상태로 관리한다(AI-AGENT-001).

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 업무 단계(ADR-05):** 파일에서 빠진 행을 지우지 않고 완료·취소·드롭 단계로 관리하고, 위험한 변경만 검토 대기열로 보내며, 업로드 단위로 되돌릴 수 있다. 상태 머신의 세 요소(상태, 위험 전이, 이력)가 모두 있다.
- **Preflight — 재업로드 멱등성:** 같은 파일을 두 번 올려도 행·검토 건이 늘지 않는다. 상태 머신으로 말하면 "같은 이벤트를 다시 받아도 상태가 그대로"인 자기 전이(no-op)다.
- **Preflight — 출처 우선순위:** 완료일이 여러 곳에서 오면 사람 > 파일 > 시스템 순으로, 덜 확실한 값이 더 확실한 값을 덮지 않는다. 전이에 붙은 **가드 조건**이다.
- **점검 질문:** 세 업무(샘플조달·시사출·CT)가 같은 판정 엔진을 쓰고 업무마다 어댑터와 정책만 다르다(포트폴리오 기재). 업무마다 상태 이름이나 허용 전이가 다르다면, 그 차이가 정책 데이터(전이표)로 분리되어 있는가?

## 11. 가정·한계·흔한 오해·트레이드오프

- **상태 폭발:** 독립적인 측면(배송 상태 × 결제 상태 × 검수 상태)을 하나의 상태로 합치면 곱만큼 늘어난다. 측면별로 따로 두거나 계층 상태를 쓴다.
- **오해: CHECK 제약이면 충분하다.** 값의 범위만 막고 전이는 못 막는다(예제 2).
- **오해: 상태 머신은 프론트엔드 라이브러리 이야기다.** 업무 데이터의 단계 칸, 배치 작업 상태, 에이전트 루프 모두 같은 개념이다.
- **동시성:** 두 요청이 같은 행을 동시에 바꾸면 "진행 중 → 완료"와 "진행 중 → 취소"가 경쟁한다. 트랜잭션과 잠금, 또는 "현재 상태가 X일 때만 바꿔라" 같은 조건부 갱신이 필요하다(DE-DB-002).

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 결정적 유한 상태 기계에서 전이 함수 δ: Q × Σ → Q가 뜻하는 바를 말로 설명하라.</summary>

**정답.** 현재 상태와 들어온 입력 한 개가 정해지면 다음 상태가 정확히 하나 정해진다는 뜻이다.

**해설.** 업무 시스템에서는 모든 조합을 정의하지 않고, 정의되지 않은 조합을 오류나 검토로 처리하는 부분 함수 형태를 흔히 쓴다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 불리언 칸 3개로 상태를 표현하면 조합은 몇 개이고, 왜 위험한가?</summary>

**정답.** $2^3 = 8$개. 실제 의미 있는 상태가 4개라면 나머지 4개는 불가능한 상태인데 저장이 가능해진다.

**해설.** 상태 칸 하나와 허용 값 제약(CHECK, enum)으로 바꾸면 불가능한 상태를 원천 차단한다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 외부 시스템(ERP)이 보내 주는 상태 값을 그대로 덮어쓰고 있는데, 가끔 완료된 건이 진행 중으로 되돌아가 집계가 흔들린다. 어떻게 설계를 바꾸겠는가?</summary>

**정답.** 외부 값을 바로 덮지 않고 "현재 상태 → 외부가 말한 상태"를 전이로 보고 판정한다. 안전한 전이는 자동 반영하고, 역방향 같은 위험 전이는 검토 대기열로 보내며, 모든 전이를 이력으로 남겨 되돌릴 수 있게 한다.

**해설.** Preflight의 "완료였던 건이 다시 진행 중으로 옴 → 검토" 규칙이 이 설계다. 외부 데이터가 틀릴 수 있다는 가정이 핵심이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 업무 상태 4개짜리 전이 판정 함수를 어떻게 시험하겠는가?</summary>

**정답.** (현재 상태, 다음 상태) 16개 조합 전부에 대해 기대 결과(적용·검토·거부·변화 없음)를 표로 만들고, 표 전체를 반복문으로 시험한다. 같은 이벤트를 두 번 넣었을 때 결과가 같은지(멱등성)도 확인한다.

**해설.** 판정을 순수 함수로 분리하면 DB 없이 빠르게 전수 시험할 수 있다. 조합이 적을 때는 전수 시험이 가장 확실하다.

</details>
