## 0. 한눈에 보기 (입문)

### 한 줄 요약
**인증**은 "당신이 누구인지 확인", **인가**는 "당신이 무엇을 할 수 있는지 결정"이다. **OAuth**는 비밀번호를 넘기지 않고 다른 서비스에 "이 일만 해도 된다"는 출입증(토큰)을 발급하는 표준이고, **OpenID Connect**는 그 위에 "이 사람이 누구인지"를 알려 주는 층을 얹은 것이다.

### 쉬운 설명
호텔을 떠올리자.

- **체크인(인증):** 프런트에서 신분증을 보여 주고 본인임을 확인한다.
- **객실 카드(토큰):** 확인이 끝나면 카드를 받는다. 이후로는 신분증 없이 카드만 대면 된다. 카드에는 "302호, 체크아웃 날까지"처럼 쓸 수 있는 범위와 기한이 있다(인가).
- **발레파킹 키(OAuth):** 주차 직원에게 차 열쇠 전체가 아니라 "시동과 운전만 되고 트렁크는 안 열리는" 키를 준다. 비밀번호(전체 열쇠)를 넘기지 않고 필요한 권한만 위임한다.

"구글로 로그인"이 바로 이 구조다. 사이트는 사용자의 구글 비밀번호를 모른 채, 구글이 발급한 증명으로 사용자를 확인한다.

### 내 프로젝트에서는
- **이 학습 사이트는 "누가 보는지"를 아는 기능을 쓴다.** 학습 페이지(아티팩트)는 사용자 정보(user) 기능을 선언하고, 학습 기록을 사용자별 개인 경로에 저장한다. 페이지 자체는 비공개라 소유자만 열 수 있다. 인증은 플랫폼이 맡고, 페이지는 확인된 사용자 정보만 받는다(HANDOFF.md 기록). 인증을 직접 만들지 않고 신뢰할 수 있는 곳에 맡기는 구조다.
- **예약 실행의 권한은 저장소 단위로 위임되어 있다.** 첫 예약 실행에서 저장소 푸시가 거부(403)되었다가, 사용자가 저장소를 예약 작업의 소스로 연결한 뒤 해결되었다(HANDOFF.md). "로그인은 되어 있지만 이 자원에 대한 권한이 없음"(인가 실패)의 실제 사례다.
- **Preflight·DeepVi의 인증 방식은 포트폴리오에 기재가 없다.** Preflight는 사내 서버에서 운영되는 업무 도구라 사내 계정 연동(SSO) 여부, 역할별 권한(검토자/일반 사용자)을 점검해 볼 만하다.

### 먼저 알면 좋은 것
- 웹 보안 기초(SE-SEC-001): 접근 제어, 비밀번호 저장, 쿠키 설정
- REST API 설계(SE-API-001): 401과 403, 상태 없는 요청

## 1. 핵심 요약

- **인증 vs 인가:** 401(누구세요?) vs 403(안 됩니다). 인가는 모든 요청마다 서버가 확인한다(SE-SEC-001).
- **세션 방식:** 서버가 로그인 상태를 저장하고 브라우저는 세션 ID 쿠키만 가진다. 즉시 폐기 쉬움.
- **토큰 방식(JWT 등):** 서명된 토큰에 사용자·권한·만료를 담아 요청마다 보낸다. 서버는 서명만 검증하면 되지만, 만료 전 폐기가 어렵다.
- **JWT 구조:** `헤더.내용.서명`(각각 base64url). 내용은 **누구나 읽을 수 있다**. 서명이 위조를 막을 뿐 비밀을 지키지 않는다.
- **OAuth 2.0:** 자원 소유자(사용자)가 클라이언트(앱)에게 제한된 권한(scope)을 위임. 브라우저·모바일 앱은 **인가 코드 흐름 + PKCE**가 권장.
- **OpenID Connect(OIDC):** OAuth 위에 "로그인한 사람이 누구인지"를 담은 ID 토큰을 더한 인증 표준. SSO의 기반.
- **운영:** 짧은 접근 토큰 + 갱신 토큰, 폐기 목록, 최소 권한(scope), 토큰을 로그·URL에 남기지 않기.

## 2. 개념과 등장 배경

초기 웹은 사이트마다 아이디·비밀번호를 따로 만들고, 서버가 세션을 저장하는 방식이었다. 2000년대 중반 서비스끼리 연동이 늘면서(사진 서비스가 내 주소록에 접근 등) 사용자가 **다른 서비스의 비밀번호를 넘겨주는** 위험한 관행이 생겼다. 이를 막기 위해 2007년 OAuth 1.0이 만들어졌고, 2012년 OAuth 2.0(RFC 6749)이 표준이 되었다.

OAuth는 원래 "권한 위임" 표준이지 "로그인" 표준이 아니었는데, 많은 서비스가 이를 로그인에 변형해 쓰면서 보안 문제가 생겼다. 2014년 OpenID Connect가 OAuth 위에 표준화된 인증 층(ID 토큰)을 정의했다. 2015년 JWT(RFC 7519)가 토큰 형식으로, PKCE(RFC 7636)가 모바일·브라우저 앱의 코드 가로채기 방어로 표준화되었다. 기업 환경에서는 SAML과 OIDC 기반 SSO가 사내 시스템 로그인을 하나로 묶는다.

## 3. 직관적 설명 및 기초 이론

### 세션 vs 토큰

| | 세션 | 토큰(JWT) |
|---|---|---|
| 상태 저장 | 서버(세션 저장소) | 토큰 자체에 담김 |
| 요청마다 | 세션 ID 쿠키 → 서버가 조회 | 토큰 → 서버가 서명 검증 |
| 즉시 로그아웃·폐기 | 쉬움(세션 삭제) | 어려움(만료까지 유효, 폐기 목록 필요) |
| 여러 서버·서비스 | 공유 세션 저장소 필요 | 서명 키만 공유하면 됨 |
| 적합 | 일반 웹 앱, 사내 도구 | 서비스 간 API, 모바일 |

### OAuth 등장인물

| 역할 | 예 |
|---|---|
| 자원 소유자 | 사용자 |
| 클라이언트 | 사용자의 데이터에 접근하려는 앱 |
| 인가 서버 | 로그인·동의를 처리하고 토큰 발급(구글, 회사 SSO) |
| 자원 서버 | 실제 데이터를 가진 API |

## 4. 엄밀한 정의와 작동 원리

### JWT

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJ1c2VyLTE3Iiwicm9sZSI6InJldmlld2VyIiwiZXhwIjoxNzk4NzYxNjAwfQ . (서명)
```

가운데 부분을 base64url로 풀면 `{"sub":"user-17","role":"reviewer","exp":1798761600}`이 그대로 나온다(설명용 토큰을 python으로 만들어 확인). `exp`는 1970년 1월 1일부터의 초(유닉스 시각)로, 이 값은 2027-01-01 00:00 UTC다. 서명은 `헤더.내용`을 비밀 키(HS256) 또는 개인 키(RS256 등)로 서명한 값이라, 내용을 한 글자라도 바꾸면 검증에 실패한다.

**검증할 것:** 서명, 알고리즘(허용 목록만, `none` 거부), 만료(`exp`), 발급자(`iss`), 대상(`aud`).

### OAuth 2.0 인가 코드 흐름 + PKCE

1. 앱이 무작위 값 `code_verifier`를 만들고 그 해시 `code_challenge`를 준비한다.
2. 사용자를 인가 서버로 보낸다(`scope`, `code_challenge` 포함).
3. 사용자가 인가 서버에서 로그인·동의한다(앱은 비밀번호를 보지 않음).
4. 인가 서버가 앱으로 **인가 코드**(짧은 1회용)를 돌려준다.
5. 앱이 코드 + `code_verifier`를 인가 서버에 보내 **접근 토큰**(+ 갱신 토큰, OIDC면 ID 토큰)을 받는다.
6. 앱이 접근 토큰으로 자원 서버 API를 호출한다.

PKCE는 중간에 인가 코드를 가로챈 공격자가 `code_verifier`를 몰라 토큰으로 바꾸지 못하게 한다.

### 토큰 수명 설계

- **접근 토큰:** 짧게(예: 5~15분). 유출돼도 피해 시간이 짧다.
- **갱신 토큰:** 길게(예: 수일~수주), 안전하게 저장, 사용할 때마다 새것으로 교체(rotation)하고 재사용이 감지되면 전부 폐기.
- **폐기:** 로그아웃·권한 변경 시 갱신 토큰 폐기. 접근 토큰은 짧은 만료로 자연 소멸.

## 5. 수식 및 기호 설명

| 용어 | 뜻 |
|---|---|
| `sub` | 토큰의 주체(사용자 식별자) |
| `exp`, `iat` | 만료 시각, 발급 시각(유닉스 초) |
| `iss`, `aud` | 발급자, 대상 서비스 |
| scope | 위임된 권한 범위(예: `read:uploads`) |
| PKCE | 인가 코드 가로채기 방지 장치 |
| SSO | 한 번 로그인으로 여러 시스템 사용 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. JWT는 비밀이 아니다

위 설명용 토큰의 가운데 부분 `eyJzdWIiOi...`를 base64url로 풀면 사용자 ID와 역할이 그대로 보인다. 그래서 JWT 내용에 주민번호·이메일 같은 민감 정보를 넣으면 안 된다. 토큰이 브라우저 저장소, 로그, URL에 남으면 누구나 읽을 수 있다. 서명은 "변조 방지"이지 "암호화"가 아니다(암호화가 필요하면 JWE 같은 별도 형식).

### 예제 2. 토큰 수명과 피해 시간

접근 토큰이 유출되었다고 하자.

| 접근 토큰 만료 | 최대 악용 가능 시간 | 폐기 수단 없을 때 |
|---|---|---|
| 24시간 | 최대 24시간 | 하루 내내 위험 |
| 15분 | 최대 15분 | 갱신 토큰만 폐기하면 곧 차단 |

대신 만료가 짧으면 갱신 요청이 잦아진다. 15분 만료면 8시간 근무 동안 갱신 약 32번($8 \times 60 / 15$). 사내 도구라면 세션 방식으로 즉시 폐기하는 것이 더 단순할 수 있다.

### 예제 3. 권한 범위(scope) 설계 (Preflight 연습)

| 역할 | 허용 | 금지 |
|---|---|---|
| 조회자 | 업무 목록·대시보드 조회 | 업로드, 검토 승인 |
| 담당자 | 조회 + 파일 업로드 + 자기 업무 수정 | 검토 승인 |
| 검토자 | 조회 + 검토 대기열 승인·거부 | 배포 |
| 관리자 | 위 전부 + 되돌리기 | — |

토큰·세션에는 역할을 담고, 서버는 요청마다 "이 역할이 이 행동을 이 자원에 할 수 있나"를 확인한다. Preflight의 실제 역할 구성은 기재가 없으며, 이 표는 업무 흐름(업로드, 검토 대기열, 업로드 단위 되돌리기, 포트폴리오 기재)에서 만든 설계 연습이다.

## 7. 시각화와 해석

OAuth 흐름은 사용자·앱·인가 서버·자원 서버 네 개의 세로줄을 두고 화살표를 시간 순으로 그리는 시퀀스 다이어그램으로 이해한다(CS-NET-001 7절). 비밀번호가 오가는 화살표는 사용자 ↔ 인가 서버 사이에만 있고, 앱은 코드와 토큰만 받는다는 점이 그림에서 드러난다.

## 8. 기술 비교 및 선택 기준

| 상황 | 권장 |
|---|---|
| 사내 업무 도구(한 서버) | 회사 SSO(OIDC/SAML) 연동 + 서버 세션 + 역할 기반 인가 |
| 여러 서비스가 같은 사용자 공유 | OIDC 기반 SSO |
| 외부 앱이 사용자 데이터에 접근 | OAuth 2.0 인가 코드 + PKCE, 최소 scope |
| 서비스 간(사람 없음) API | 클라이언트 자격 증명 흐름, 짧은 토큰, 키 교체 |
| 직접 비밀번호 로그인 구현 | 가능하면 피함. 필요하면 느린 해시, 다요소 인증, 시도 제한(SE-SEC-001) |

**원칙:** 인증은 직접 만들지 말고 검증된 제공자·라이브러리에 맡기고, 인가(무엇을 할 수 있나)는 업무 규칙이므로 직접 설계·시험한다.

## 9. 실무 사례

- **사내 SSO:** 퇴사자 계정을 한 곳에서 막으면 모든 사내 시스템 접근이 끊긴다.
- **API 키 대신 OAuth:** 외부 연동 앱에 전체 API 키 대신 사용자별·범위별 토큰을 준다.
- **LLM 에이전트 도구 권한:** 에이전트가 쓰는 도구에 사용자 권한보다 좁은 scope의 토큰을 준다(AI-AGENT-001의 최소 권한).
- **DB 접속 인증:** PostgreSQL은 `pg_hba.conf`로 접속 주소·사용자·DB별 인증 방식을 정한다(공식 문서). 애플리케이션 계정은 필요한 테이블 권한만 준다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 기록에서 옮긴 것이다.

- **이 학습 사이트:** 비공개 아티팩트, 사용자 정보 기능과 사용자별 개인 저장 경로. 인증은 플랫폼이 담당하고 페이지는 결과만 받는다. 예약 실행은 저장소를 소스로 연결받아 푸시 권한을 얻는다(첫 실행의 403이 인가 실패 사례).
- **Preflight — 역할과 검토:** 위험한 변경만 검토 대기열로 보내고, 업로드 단위로 되돌릴 수 있다. 점검 질문(기록 없음): 검토 승인과 되돌리기는 누가 할 수 있는가? 서버가 매 요청 역할을 확인하는가? 사내 계정과 연동되어 있는가? 예제 3이 설계 출발점이 될 수 있다.
- **DeepVi — 외부 API:** GPT-4o·Gemini·Pinecone을 API 키로 호출했다. 사용자 로그인 기능은 기재가 없고, 공개 서비스로 열지 않았다. 공개했다면 사용자 인증과 사용량 제한(키 남용 방지)이 필요했을 것이다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: JWT는 암호화되어 안전하다.** 서명만 되어 있고 내용은 누구나 읽는다(예제 1).
- **오해: OAuth는 로그인 표준이다.** OAuth는 권한 위임 표준이고, 로그인(신원 확인)은 OIDC가 표준화했다.
- **오해: 토큰 방식이 항상 낫다.** 즉시 폐기가 중요한 사내 도구에는 세션이 더 단순하고 안전할 수 있다.
- **토큰 저장 위치:** 브라우저 저장소(localStorage)는 XSS에 취약하고, 쿠키는 `HttpOnly`·`Secure`·`SameSite` 설정과 CSRF 대비가 필요하다. 상황별 맞교환이다(세부 권장은 확인 필요).
- **알고리즘 혼동 공격:** 검증 시 허용 알고리즘을 고정하지 않으면 위조 토큰이 통과할 수 있다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. JWT의 세 부분과 각각의 역할은?</summary>

**정답.** 헤더(서명 알고리즘·형식), 내용(사용자·권한·만료 등 클레임), 서명(앞 두 부분이 변조되지 않았음을 증명).

**해설.** 헤더와 내용은 base64url로 인코딩되었을 뿐 누구나 읽을 수 있다.

</details>

<details class="qa" data-type="concept"><summary>Q2. PKCE가 막는 공격은?</summary>

**정답.** 인가 코드가 돌아오는 도중 가로채진 경우, 공격자가 그 코드로 토큰을 받는 것. 토큰 교환에 앱만 아는 `code_verifier`가 필요해 코드만으로는 쓸 수 없다.

**해설.** 비밀 키를 안전하게 보관할 수 없는 브라우저·모바일 앱(공개 클라이언트)에 특히 중요하다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 사내 업무 도구에 JWT를 24시간 만료로 쓰고 있다. 퇴사자 계정을 즉시 막아야 한다는 요구가 왔다. 어떻게 바꾸겠는가?</summary>

**정답.** 접근 토큰 만료를 짧게(분 단위) 줄이고 갱신 토큰을 서버에서 폐기할 수 있게 하거나, 서버 세션 방식으로 바꿔 즉시 삭제할 수 있게 한다. 회사 SSO와 연동해 계정 비활성화가 바로 반영되게 한다.

**해설.** 긴 만료의 자기 완결형 토큰은 폐기가 어렵다는 트레이드오프가 그대로 드러나는 상황이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. LLM 에이전트가 사용자를 대신해 사내 문서 API를 조회하게 하려 한다. 권한을 어떻게 설계하겠는가?</summary>

**정답.** 사용자가 동의한 범위의 짧은 토큰(조회 전용 scope)을 에이전트에 위임하고, 문서 API는 그 토큰의 사용자 권한으로만 결과를 돌려준다(사용자가 못 보는 문서는 에이전트도 못 봄). 쓰기·삭제·외부 발송은 별도 확인을 거치고, 토큰은 로그와 프롬프트에 남기지 않는다.

**해설.** 에이전트는 사용자보다 넓은 권한을 가지면 안 된다(최소 권한, AI-AGENT-001, SE-SEC-001).

</details>
