## 0. 한눈에 보기 (입문)

### 한 줄 요약
**프롬프트 설계**는 LLM에게 "무엇을, 어떤 자료로, 어떤 규칙 아래, 어떤 모양으로" 답하라고 명확히 전하는 일이고, **구조화 출력**은 답을 사람이 읽는 글 대신 프로그램이 바로 쓸 수 있는 정해진 형식(JSON 등)으로 받는 방법이다. 형식은 **지시만으로 믿지 말고 코드로 검사**한다.

### 쉬운 설명
새로 온 유능한 직원에게 일을 맡기는 메모를 떠올리자.

- 나쁜 메모: "이거 정리해 줘."
- 좋은 메모: "너는 품질팀 보조야(역할). 아래 회의록에서 결정 사항만 뽑아 줘(작업). 회의록은 이거야(맥락). 추측하지 말고 회의록에 없는 건 '없음'이라고 써(제약). 결과는 '결정 / 담당자 / 기한' 표로(형식). 예시는 이렇게(예시)."

LLM도 같다. 다만 직원과 달리 LLM은 **가끔 형식을 어긴다.** 표를 달라고 했는데 설명문을 덧붙이거나, 필수 칸을 빼먹는다. 그래서 결과를 받는 프로그램이 "칸이 다 있나, 형식이 맞나"를 검사하고, 틀리면 다시 요청하거나 사람에게 넘긴다.

### 내 프로젝트에서는
- **STT 프로젝트의 로컬 LLM 검토가 바로 구조화 출력 문제였다.** 로컬 LLM이 정해진 JSON 스키마(`refusal_law`, `reject_reason_summary`, `citation_evidence[]`, `final_summary`)를 유지하는지, 요약 품질, 처리 시간, 실패 대응을 기준으로 타당성을 검토했다(포트폴리오 기재, 운영 전환 아님). 형식 유지와 **실패 대응**이 평가 기준에 들어간 것은, 출력 검증과 재시도 설계가 필요하다는 판단이다.
- **LLM 후처리의 과교정을 지시로 통제했다.** 후처리가 원문의 말투·의미를 바꾸는 문제가 있어 문체와 의미를 유지하고 필요한 부분만 고치도록 정책을 제한했다(포트폴리오 기재). 프롬프트의 "제약" 부분을 강화한 사례다.
- **DeepVi는 질문 유형에 따라 다른 검색 체인을 탔다.** 정규식으로 질문을 분류한 뒤 RetrievalQA + GPT-4o(temperature 0.3)로 답했다(저장소 코드). 검색 결과(맥락)를 프롬프트에 넣는 RAG 구조이고, 뉴스 답변에는 기사 제목·날짜·링크를 출처로 붙였다.

## 1. 핵심 요약

- **구성:** 역할, 작업, 맥락(근거 자료), 제약(하지 말 것, 모를 때 행동), 출력 형식, 예시. 자료와 지시를 구분 표시(태그, 구분선)한다.
- **few-shot:** 예시 몇 개로 형식과 기준을 보여 준다(GPT-3 논문이 대규모 모델의 퓨샷 능력을 보고).
- **단계적 사고:** 복잡한 추론은 중간 단계를 거치게 하면 정확도가 오를 수 있다(chain-of-thought). 최종 출력과 분리해 받는다.
- **구조화 출력:** JSON 스키마로 필드·타입·필수 여부·허용 값을 정의. 일부 API는 스키마를 강제하는 기능을 제공한다(제공사·버전마다 다름, 확인 필요).
- **검증 루프:** 파싱 → 스키마 검사 → 업무 규칙 검사(근거가 실제 자료에 있는가) → 실패 시 오류 내용을 담아 재시도 → 한도 초과 시 사람에게.
- **평가:** 프롬프트를 바꾸면 고정된 평가 세트로 형식 준수율과 내용 품질을 다시 잰다. 작은 차이는 통계적으로 확인한다.

## 2. 개념과 등장 배경

2020년 GPT-3 논문(Brown 외)은 큰 언어 모델이 학습 없이도 프롬프트에 넣은 몇 개의 예시만으로 새 작업을 수행할 수 있음을 보이며 "프롬프트로 프로그래밍한다"는 생각을 퍼뜨렸다. 2022년 위(Wei) 등은 예시에 중간 추론 단계를 포함하면 산술·상식 추론 과제에서 큰 모델의 정확도가 크게 오른다는 **사고 사슬**(chain-of-thought) 프롬프팅을 보고했다.

LLM이 실제 시스템의 부품이 되면서 "사람이 읽는 답"보다 "프로그램이 받는 데이터"가 중요해졌다. 2023년 이후 주요 LLM API는 함수 호출(도구 사용)과 JSON 출력 모드를 도입했고, JSON 스키마를 주면 그 형식에 맞는 출력을 생성하도록 제한하는 기능도 등장했다. 프롬프트 설계의 초점도 "마법의 문구 찾기"에서 명확한 명세와 검증, 평가로 옮겨 갔다(AI-NATIVE-001의 컨텍스트 엔지니어링).

## 3. 직관적 설명 및 기초 이론

### 좋은 프롬프트의 구성

```text
[역할] 너는 제조 품질 문서를 정리하는 보조다.
[작업] 아래 <문서>에서 불량 원인과 조치를 추출한다.
[제약]
- <문서>에 없는 내용은 쓰지 않는다. 없으면 null.
- 원문 표현을 바꾸지 않고 인용한다.
[출력] 아래 JSON 스키마를 따르는 JSON 하나만 출력한다.
[예시] (입력 → 출력 한두 쌍)
<문서>
...
</문서>
```

자료를 태그로 감싸면 지시와 자료가 섞이지 않는다. 자료 안에 "앞의 지시를 무시해" 같은 문장이 있어도 데이터로 다루기 쉬워진다(프롬프트 주입 방어의 일부).

### 왜 예시가 효과적인가

LLM은 앞의 글과 이어지는 그럴듯한 다음 토큰을 만든다(AI-LLM-001). 예시가 있으면 "이 패턴을 이어 가라"는 신호가 강해진다. 다만 예시 3개가 모두 "불량 원인 = 금형"이면 모델이 그 답 쪽으로 치우칠 수 있다.

## 4. 엄밀한 정의와 작동 원리

### JSON 스키마

출력의 모양을 기계가 읽을 수 있게 정의한다. 아래는 STT 프로젝트의 필드 이름을 빌린 **설명용** 스키마다(타입·필수 여부는 가정이며 실제 정의는 기재 없음).

```json
{
  "type": "object",
  "required": ["refusal_law", "reject_reason_summary", "citation_evidence", "final_summary"],
  "properties": {
    "refusal_law": { "type": "string" },
    "reject_reason_summary": { "type": "string", "maxLength": 500 },
    "citation_evidence": {
      "type": "array",
      "items": { "type": "string" },
      "minItems": 1
    },
    "final_summary": { "type": "string" }
  },
  "additionalProperties": false
}
```

`required`는 필수 필드, `additionalProperties: false`는 정의되지 않은 필드 금지, `minItems`는 배열 최소 길이다. 검사기는 위반 위치와 이유를 알려 준다.

### 검증·재시도 루프

1. LLM 호출 → 응답 문자열
2. JSON 파싱 실패 → 오류 메시지를 붙여 재요청
3. 스키마 위반 → 어떤 필드가 왜 틀렸는지 붙여 재요청
4. 업무 규칙 검사: `citation_evidence`의 각 인용이 입력 자료에 실제로 있는가(문자열 포함·편집 거리 검사)
5. 최대 $k$번 실패 → 사람 검토 대기열

시도마다 성공 확률이 $p$이고 독립이라 가정하면, 최대 $k$번 재시도(총 $k+1$번)의 성공 확률은

$$
1 - (1 - p)^{k+1}
$$

평균 호출 수는 $\sum_{i=0}^{k} (1-p)^i$다.

### 프롬프트 변경의 평가

| 지표 | 계산 |
|---|---|
| 형식 준수율 | 스키마 통과 응답 ÷ 전체 |
| 근거 일치율 | 인용이 자료에 실제로 있는 응답 ÷ 전체 |
| 내용 품질 | 기준표 점수(사람 또는 검증된 LLM 평가자) |
| 비용·지연 | 평균 토큰 수, 응답 시간 |

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| $p$ | 한 번 호출에서 검증을 통과할 확률 |
| $k$ | 최대 재시도 횟수 |
| `required` | JSON 스키마의 필수 필드 목록 |
| `additionalProperties` | 정의 밖 필드 허용 여부 |
| few-shot | 예시 몇 개를 프롬프트에 넣는 방식 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 재시도가 신뢰도를 얼마나 올리나

한 번에 스키마를 통과할 확률 $p = 0.9$(설명용 가정, 시도는 독립 가정).

| 최대 재시도 $k$ | 성공 확률 | 평균 호출 수 |
|---|---|---|
| 0 | $0.9$ | 1 |
| 1 | $1 - 0.1^2 = 0.99$ | $1 + 0.1 = 1.1$ |
| 2 | $1 - 0.1^3 = 0.999$ | $1 + 0.1 + 0.01 = 1.11$ |

호출을 평균 11%만 더 쓰고 실패율을 10%에서 0.1%로 줄인다. 다만 실패가 **입력 때문에 반복되는** 경우(문서가 너무 길거나 이상함)에는 독립 가정이 깨져 재시도가 소용없다. 그래서 한도를 두고 사람에게 넘긴다.

### 예제 2. 지시 개선 전후 비교

같은 평가 문서 100건에서:

| 프롬프트 | 형식 준수 | 근거 일치 |
|---|---|---|
| A: "JSON으로 요약해" | 82/100 | 70/100 |
| B: 역할·제약·스키마·예시 2개 | 97/100 | 91/100 |

형식 준수율 차이 15%p는 100건 기준 표준오차(각각 약 3.8%p, 1.7%p)보다 훨씬 커서 우연으로 보기 어렵다(STAT-INF-002). 실패한 3건은 직접 읽어 원인(긴 문서, 표가 섞인 입력)을 찾고 평가 세트에 비슷한 사례를 추가한다. (숫자는 설명용이다.)

### 예제 3. 과교정을 막는 제약 쓰기

후처리 목표: STT 결과의 띄어쓰기·맞춤법만 고치기.

| 나쁜 지시 | 개선한 지시 |
|---|---|
| "자연스럽게 다듬어 줘" | "띄어쓰기와 맞춤법 오류만 고친다. 어휘, 어미, 존댓말 여부, 문장 순서는 바꾸지 않는다. 확실하지 않으면 원문을 유지한다." |
| (검사 없음) | 원문과 결과의 글자 단위 편집 거리 ÷ 원문 길이가 10%를 넘으면 원문 유지 + 검토 표시 |

"자연스럽게"는 LLM에게 "그럴듯하게 고쳐 써라"로 읽힌다. STT 프로젝트에서 겪은 과교정이 이런 종류다. 편집 거리 검사는 CS-ALG-003 참고. 10%는 설명용 기준값이다.

## 7. 시각화와 해석

프롬프트 실험 결과는 가로축 버전(A, B, C …), 세로축 형식 준수율·근거 일치율인 막대그래프로 그리고, 각 막대에 신뢰구간을 표시한다. 버전을 바꿀 때마다 같은 평가 세트를 쓰면 회귀(이전보다 나빠짐)를 바로 볼 수 있다. 실패 사례를 유형별로 세어 표로 두면 다음 개선 방향이 보인다.

## 8. 기술 비교 및 선택 기준

| 방법 | 장점 | 한계 | 적합 |
|---|---|---|---|
| 지시만(제로샷) | 짧고 싸다 | 형식·기준이 흔들림 | 단순 작업 |
| few-shot | 형식·기준 전달이 쉬움 | 토큰 증가, 예시 편향 | 형식이 까다로운 추출 |
| 단계적 사고 유도 | 복잡한 추론 정확도 향상 | 토큰·지연 증가 | 계산, 다단계 판단 |
| 스키마 강제 기능(API) | 형식 오류 크게 감소 | 내용 정확성은 별개, 지원 범위 다름 | 구조화 추출 |
| 도구 호출 | 정해진 인자 형식으로 행동 | 도구 설계 필요 | 에이전트(AI-AGENT-001) |
| 미세조정 | 일관된 형식·말투 | 데이터·비용, 갱신 어려움 | 대량 반복 작업 |

## 9. 실무 사례

- **문서 추출 자동화:** 송장·계약서에서 필드를 JSON으로 뽑고, 금액 합계 같은 업무 규칙으로 교차 검증한다.
- **분류기:** 문의 유형을 허용 값 목록(enum)으로만 답하게 하고, 목록 밖이면 "기타"로 보낸다.
- **요약의 근거 표시:** 요약 문장마다 원문 인용을 붙이게 하고, 인용이 원문에 실제로 있는지 코드로 확인한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **STT — 로컬 LLM 검토:** Qwen2.5-7B-Instruct, vLLM, JSON 스키마 4개 필드 유지·요약 품질·처리 시간·실패 대응 기준. 점검 질문(기록 없음): 스키마 위반률을 측정했는가? 위반 시 재시도와 사람 검토 경로를 어떻게 설계했는가? `citation_evidence`가 입력 자료에 실제로 있는지 검사했는가?
- **STT — 과교정 대응:** 문체와 의미를 유지하고 필요한 부분만 고치도록 후처리 정책을 제한했다. 6절 예제 3처럼 지시의 제약과 편집 거리 검사를 함께 쓰면 정책을 수치로 지킬 수 있다.
- **DeepVi — RAG 프롬프트:** 검색한 뉴스(k=5)·기업(k=5)·메타(k=3) 문서를 맥락으로 넣고 GPT-4o(temperature 0.3)로 답했다. 뉴스 답변에 기사 제목·날짜·링크를 붙였다. 테스트용 프롬프트로 답변이 보유한 기업 데이터를 근거로 나오는지 확인했다(정량 지표는 기재 없음). 다음 단계는 예제 2처럼 평가 세트로 수치화하는 것이다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 좋은 프롬프트 문구 하나면 된다.** 실제 품질은 맥락(근거 자료), 검증, 평가 세트가 좌우한다.
- **오해: 스키마를 통과하면 내용도 맞다.** 형식이 맞아도 값은 틀릴 수 있다. 근거 대조 같은 업무 규칙 검사가 필요하다.
- **오해: 예시를 많이 넣을수록 좋다.** 토큰과 비용이 늘고, 예시에 과적합해 다른 입력을 그 틀에 억지로 맞출 수 있다.
- **모델·버전 의존:** 같은 프롬프트도 모델을 바꾸면 결과가 달라진다. 모델을 바꿀 때 평가 세트를 다시 돌린다.
- **프롬프트 주입:** 입력 자료 안의 지시문이 모델 행동을 바꿀 수 있다. 자료를 구분 표시하고, 위험한 행동은 코드와 권한으로 막는다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 한 번 호출의 형식 통과율이 0.8일 때, 최대 2번 재시도하면 최종 성공 확률은? (독립 가정)</summary>

**정답.** $1 - 0.2^3 = 0.992$.

**해설.** 세 번 모두 실패할 확률 $0.2^3 = 0.008$을 1에서 뺀다. 입력 때문에 반복 실패하는 경우에는 이 계산이 맞지 않는다.

</details>

<details class="qa" data-type="concept"><summary>Q2. JSON 스키마의 `required`와 `additionalProperties: false`는 각각 무엇을 막는가?</summary>

**정답.** `required`는 필수 필드 누락을, `additionalProperties: false`는 정의하지 않은 필드가 끼어드는 것을 막는다.

**해설.** LLM이 필드 이름을 조금 바꿔(예: `summary` 대신 `final_summary_text`) 내는 실수를 잡아 준다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 팀원이 프롬프트를 고친 뒤 "몇 개 해 보니 더 좋아졌다"고 배포하려 한다. 어떻게 하자고 하겠는가?</summary>

**정답.** 고정된 평가 세트(대표 사례 + 과거 실패 사례)로 이전·새 프롬프트를 같은 조건에서 돌려 형식 준수율, 근거 일치율, 품질 점수, 비용을 비교한다. 차이가 표본 오차보다 큰지 확인하고, 나빠진 사례가 없는지 본다.

**해설.** 몇 개 시험은 우연과 구별이 안 된다. 프롬프트도 코드처럼 회귀 테스트한다(SE-TEST-001).

</details>

<details class="qa" data-type="applied"><summary>Q4. 상담 기록에서 '불만 유형'을 6개 중 하나로 분류하는 LLM 기능을 만든다. 프롬프트와 출력 설계를 어떻게 하겠는가?</summary>

**정답.** 6개 유형의 정의와 경계 사례를 지시에 쓰고, 유형별 예시를 고르게 넣는다. 출력은 `{"category": enum 6개 + "기타", "evidence": 원문 인용}` 스키마로 받고, 인용이 원문에 있는지 검사한다. 평가는 사람이 라벨을 단 표본으로 클래스별 정밀도·재현율을 잰다(AI-EVAL-001).

**해설.** 허용 값 목록과 근거 인용이 분류 결과를 검증 가능하게 만든다.

</details>
