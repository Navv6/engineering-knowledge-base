## 0. 한눈에 보기 (입문)

### 한 줄 요약
**컨텍스트 엔지니어링**은 "AI가 일할 때 책상 위에 무엇을 올려 둘지"를 설계하는 일이고, **하네스 엔지니어링**은 "AI가 일하는 작업장(도구, 권한, 검사 장치)"을 설계하는 일이다. AI를 똑똑하게 만드는 것이 아니라, AI가 **믿을 만하게 일하도록 환경을 만드는** 기술이다.

### 쉬운 설명
새로 온 유능한 직원에게 일을 맡긴다고 하자.

- **프롬프트 엔지니어링:** 지시문을 잘 쓰는 것. "보고서를 3쪽으로, 표 포함해서."
- **컨텍스트 엔지니어링:** 책상에 **필요한 서류만** 올려 두는 것. 서류를 1,000장 쌓아 주면 오히려 중요한 것을 놓친다. 필요하면 서랍(파일, 검색)에서 꺼내 보게 하고, 하루가 끝나면 인수인계 메모를 남기게 한다.
- **하네스 엔지니어링:** 작업장 자체를 설계하는 것. 쓸 수 있는 도구, 들어갈 수 없는 방(권한), 결과물을 자동으로 검사하는 장치(테스트), 위험한 일은 상사 결재.

AI 모델은 같아도 이 환경에 따라 결과의 질과 안정성이 크게 달라진다.

### 내 프로젝트에서는
- **이 학습 사이트가 바로 그 예다.** 매일 새 세션에서 시작하는 AI가 일관되게 일하도록 절차서(AUTOMATION.md, 컨텍스트), 진행 기록(HANDOFF.md, 구조화된 메모), 실행 기록(content/runs), 그리고 검증·단위·E2E 테스트(하네스)를 두었다. 글의 질은 모델이 정하지만, **공개 여부는 하네스가 정한다.**
- **DeepVi의 RAG는 컨텍스트 설계였다.** 뉴스 k=5, 기업 k=5, 메타 k=3개만 골라 GPT-4o에 넣었고, 재무 수치는 벡터 검색 대신 API 응답을 넣었다(저장소 코드). "무엇을 몇 개 넣을지"가 곧 컨텍스트 엔지니어링이다.
- **STT 평가는 하네스였다.** 같은 평가 데이터 6,000개(KsponSpeech eval_clean·eval_other 각 3,000개), 같은 정규화, 같은 지표(WER·CER·RTF + 의미 지표)로 모델 4종을 비교했다(포트폴리오 기재). 평가 조건을 고정해야 비교가 의미를 갖는다.

## 1. 핵심 요약

- **컨텍스트 엔지니어링:** 추론 시점에 모델이 보는 토큰(지시문, 도구 설명, 예시, 대화 기록, 검색 결과)을 고르고 관리하는 일. Anthropic은 "원하는 결과의 가능성을 최대화하는, 신호가 강한 **가장 작은** 토큰 집합"을 찾는 것이라고 정리했다.
- **왜 필요한가:** 컨텍스트가 길어질수록 정보를 정확히 떠올리는 능력이 떨어지는 현상(**context rot**)과, 긴 입력의 **중간**에 있는 정보를 덜 활용하는 현상(Lost in the Middle)이 보고되었다.
- **긴 작업 전략:** 압축(대화를 요약해 새 창으로), 구조화된 메모(파일에 진행 상황 기록), 하위 에이전트(깨끗한 창에서 좁은 일을 하고 요약만 반환), 필요할 때 불러오기(경로·링크만 들고 있다가 그때 읽기).
- **하네스 엔지니어링:** 모델 바깥의 실행 환경 설계. 도구 정의, 권한, 검증 루프(테스트·스키마), 평가 세트, 실행 기록, 사람 확인 지점. 용어는 아직 표준 정의가 없다.
- **평가:** 정답이 확실한 과제는 자동 검사(테스트 통과 등), 정답이 여럿인 과제는 기준표 + LLM 평가자 + 사람 표본 검토. LLM 평가자에는 위치·길이 편향이 있다.

## 2. 개념과 등장 배경

LLM 초기(2020~2022년)에는 지시문을 어떻게 쓰느냐가 결과를 크게 바꿨기 때문에 **프롬프트 엔지니어링**이 주목받았다. 모델이 도구를 쓰고 여러 단계를 오래 수행하게 되면서, 문제는 "지시문 한 개"보다 "매 단계에 모델이 보는 전체 정보"로 옮겨 갔다. 2025년 Anthropic은 이를 **컨텍스트 엔지니어링**으로 정리해, 컨텍스트를 수확 체감하는 유한한 자원("attention budget")으로 다뤄야 한다고 설명했다.

같은 시기 코딩 에이전트가 실제 저장소에서 일하게 되면서, 모델 성능만큼 **환경**(테스트, 도구, 권한, 피드백 루프)이 결과를 좌우한다는 경험이 쌓였다. SWE-bench(2024)는 실제 GitHub 이슈를 주고 저장소의 테스트 통과 여부로 채점하는데, 이처럼 "자동으로 확인 가능한 성공 기준"이 에이전트 개발과 평가의 중심이 되었다. 모델을 둘러싼 이 실행·검증 환경을 설계하는 일을 업계에서 **하네스 엔지니어링**이라 부르기 시작했다(용어의 범위는 쓰는 곳마다 조금씩 다르다).

## 3. 직관적 설명 및 기초 이론

### 컨텍스트의 구성 요소

| 요소 | 설계 질문 | 흔한 실수 |
|---|---|---|
| 시스템 지시문 | 원칙과 기준을 적절한 추상도로 썼나 | 경우마다 if문처럼 나열(취약) 또는 너무 막연 |
| 도구 설명 | 도구끼리 역할이 겹치지 않나, 입력이 명확한가 | 비슷한 도구가 여럿이라 모델이 헷갈림 |
| 예시 | 대표적이고 다양한가 | 엣지 케이스를 잔뜩 나열 |
| 검색 결과 | 관련성 높은 것만, 출처와 함께 | 많이 넣을수록 좋다고 생각 |
| 대화 기록 | 오래된 도구 결과를 정리했나 | 수만 토큰의 로그를 그대로 누적 |

### "많이 넣으면 좋다"가 틀린 이유

Lost in the Middle 연구(Liu 외)는 여러 문서 중 정답 문서의 위치를 바꿔 가며 실험했고, 정답이 입력의 **처음이나 끝**에 있을 때 성능이 가장 높고 **중간**에 있을 때 크게 떨어지는 U자 모양을 관찰했다. Anthropic도 needle-in-a-haystack류 실험에서 토큰이 늘수록 정확한 회상이 떨어지는 현상(context rot)이 여러 모델에서 나타난다고 설명한다. 정도는 모델마다 다르다.

### 하네스의 구성 요소

$$
\text{결과의 신뢰도} \approx \text{모델 능력} \times \text{컨텍스트 품질} \times \text{검증 장치의 엄격함}
$$

엄밀한 공식이 아니라 생각의 틀이다. 어느 하나가 0에 가까우면 전체가 무너진다. 특히 검증 장치는 모델이 틀렸을 때 **틀렸다는 것을 알아채는** 유일한 수단이다.

## 4. 엄밀한 정의와 작동 원리

### 긴 작업을 위한 네 가지 전략 (Anthropic 정리)

1. **압축(compaction):** 컨텍스트 한도에 가까워지면 대화를 요약하고 새 창을 요약으로 시작한다. 무엇을 남기고 버릴지가 핵심이다(결정 사항, 미해결 버그, 다음 할 일은 남기고 이미 처리한 도구 출력은 버림).
2. **구조화된 메모:** 에이전트가 컨텍스트 밖 파일에 진행 상황을 적고 나중에 다시 읽는다. 세션이 바뀌어도 이어 갈 수 있다.
3. **하위 에이전트:** 넓은 탐색을 별도 창의 하위 에이전트에 맡기고, 결과는 압축된 요약만 받는다. 주 에이전트의 컨텍스트가 깨끗하게 유지된다.
4. **필요할 때 불러오기(just in time):** 모든 데이터를 미리 넣지 않고 파일 경로·쿼리·링크 같은 가벼운 식별자만 들고 있다가, 필요할 때 도구로 읽는다. 대신 탐색 시간이 든다.

### 평가 하네스

| 과제 유형 | 채점 방식 | 예 |
|---|---|---|
| 정답이 하나 | 자동 대조 | 수식 계산, 분류 라벨 |
| 실행으로 확인 가능 | 테스트 통과 | 코드 수정(SWE-bench 방식) |
| 형식이 정해짐 | 스키마 검증 | JSON 필수 키, 출처 개수 |
| 정답이 여럿 | 기준표 + LLM 평가자 + 사람 표본 | 요약, 설명문 |

LLM을 평가자로 쓰는 연구(Zheng 외)는 강한 모델의 판단이 사람 판단과 높은 일치도를 보일 수 있지만, **위치 편향**(먼저 제시된 답 선호), **길이 편향**(긴 답 선호), **자기 선호 편향**이 있다고 보고했다. 그래서 답의 순서를 바꿔 두 번 평가하고, 사람 표본 검토로 보정한다.

### 평가 세트의 크기 감각

정답률을 $\hat{p}$로 추정할 때 표준오차는 $\sqrt{\hat{p}(1-\hat{p})/n}$이다(STAT-INF-001). $\hat{p} = 0.8$, $n = 50$이면

$$
\sqrt{\frac{0.8 \times 0.2}{50}} = \sqrt{0.0032} \approx 0.057
$$

95% 신뢰구간이 대략 $0.8 \pm 0.11$이다. 프롬프트를 바꿔 정답률이 0.80에서 0.84가 됐다고 해서 50문항으로는 개선이라 단정할 수 없다.

## 5. 수식 및 기호 설명

| 표현 | 뜻 |
|---|---|
| $\hat{p}$ | 평가 세트에서 관찰한 정답률 |
| $n$ | 평가 문항 수 |
| $\sqrt{\hat{p}(1-\hat{p})/n}$ | 정답률 추정의 표준오차 |
| $\pm 1.96 \times$ 표준오차 | 95% 신뢰구간의 폭(정규 근사) |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. RAG 컨텍스트 예산 짜기

컨텍스트에 쓸 수 있는 예산을 8,000토큰으로 잡았다고 하자(설명용 가정).

| 항목 | 토큰 | 비고 |
|---|---|---|
| 시스템 지시문 | 600 | 답변 규칙, 출처 표기 규칙 |
| 질문 | 100 | |
| 재무 API 요약 | 800 | 수치는 표로 압축 |
| 뉴스 5건 | 5 × 700 = 3,500 | 기사 전체 대신 관련 단락 |
| 답변 여유 | 1,500 | |
| 합계 | 6,500 | 예산 안 |

뉴스를 20건으로 늘리면 $20 \times 700 = 14{,}000$으로 예산을 넘고, 넘지 않더라도 중간에 놓인 기사를 덜 활용할 수 있다. DeepVi가 뉴스 k=5로 둔 것은 이런 균형의 한 선택이다(k를 정한 근거는 기록이 없다).

| 장치 | 실제 구현 | 막는 문제 |
|---|---|---|
| 콘텐츠 검증 | 필수 절, 출처 2개 이상, LaTeX 문법, 문항 형식, 순환 검사 | 형식 누락, 렌더링 깨짐 |
| 사실 제한 | 프로젝트 사실은 profile.json의 사용자 확인 항목만 인용 | 경력 사실 지어내기 |
| 단위·E2E 테스트 | 18 + 38건 | 기능 회귀, 화면 깨짐 |
| 종료 코드 게이트 | 각 단계 0일 때만 커밋 | 실패한 결과 공개 |
| 실행 기록 | content/runs/*.json | 중복 실행, 원인 추적 |
| 사람 확인 | 사용자가 내용·사실 오류를 지적하면 반영(예: DeepVi RAG 설명 수정) | 자동 검사로 못 잡는 사실 오류 |

마지막 줄이 중요하다. DeepVi RAG를 "벡터 검색이 없다"고 잘못 쓴 오류는 자동 검사를 모두 통과했고, **사용자 지적**으로 고쳐졌다. 하네스는 형식 오류는 잘 잡지만 사실 오류는 사람과 출처 대조가 필요하다.

## 7. 시각화와 해석

컨텍스트 구성을 막대 하나로 그려 보면(지시문 | 도구 설명 | 검색 결과 | 대화 기록 | 여유) 어떤 항목이 예산을 잡아먹는지 보인다. 긴 세션에서는 보통 대화 기록과 도구 출력이 막대 대부분을 차지하게 되고, 이것이 압축이 필요한 시점이다.

## 8. 기술 비교 및 선택 기준

| 상황 | 권장 전략 |
|---|---|
| 짧은 질문 답변 | 좋은 지시문 + 관련 검색 결과 몇 개 |
| 큰 저장소·문서 더미 탐색 | 필요할 때 불러오기 + 하위 에이전트 |
| 여러 시간·여러 세션에 걸친 작업 | 구조화된 메모(인수인계 파일) + 압축 |
| 결과를 자동 검증할 수 있음 | 검증 루프를 하네스에 넣고 자동 재시도 |
| 자동 검증이 어려움 | 기준표 + 사람 검토 비율 높이기 |

## 9. 실무 사례

- **코딩 에이전트:** 저장소에 프로젝트 규칙 파일(빌드 명령, 금지 사항)을 두어 매 세션 컨텍스트로 쓰고, 테스트를 하네스로 쓴다.
- **고객 지원 봇:** 정책 문서 전체 대신 질문 유형별 관련 조항만 검색해 넣고, 답변에 조항 번호 인용을 강제한다.
- **사내 문서 Q&A:** 평가 질문 100~200개와 기대 근거 문서를 고정해, 프롬프트나 검색 설정을 바꿀 때마다 회귀 평가한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 기록에서 옮긴 것이다.

- **DeepVi — 컨텍스트 선택:** 뉴스는 Pinecone 벡터 검색(e5-large, k=5), 재무 수치는 API 응답, 질문은 기업별 분석 화면 안에서만 가능해 기업이 화면 맥락으로 정해졌다. 기업 맥락을 화면이 고정해 준 덕분에 검색 범위가 좁혀졌다. 테스트용 프롬프트로 근거 기반 답변을 확인했지만 정량 지표는 기재가 없다. 다음 단계라면 질문 세트 + 기대 근거로 평가 하네스를 만드는 것이다.
- **STT — 평가 하네스:** 고정 데이터 6,000개, 텍스트 정규화, WER·CER·RTF + Semantic Similarity·SemWER@0.85. 0.85 임계값을 고른 이유는 기재되어 있지 않다. 이런 미기재 결정은 하네스 문서에 남겨야 다음 평가와 비교할 수 있다. Riva Offline 출력 잘림을 발견해 Streaming으로 바꾼 일은 "평가 도구 자체의 결함"을 하네스가 드러낸 사례다.
- **STT — LLM 후처리 범위 제한:** 과교정 문제로 필요한 부분만 고치도록 정책을 제한했다. 지시문(컨텍스트)으로 범위를 좁힌 것이다.
- **이 학습 사이트:** 6절 예제 3의 하네스 전체. 그리고 사실 오류는 사용자 피드백으로 고쳐졌다는 한계.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 컨텍스트 창이 크면 다 넣으면 된다.** 창이 커도 정보 활용이 균일하지 않다(context rot, 중간 손실).
- **오해: 프롬프트만 잘 쓰면 된다.** 긴 작업에서는 도구 설계, 메모, 검증이 더 큰 차이를 만든다.
- **압축의 위험:** 요약이 미묘하지만 중요한 정보를 버릴 수 있다. 결정 사항과 교훈은 파일로도 남긴다.
- **하네스의 한계:** 자동 검사는 "형식"과 "실행 가능성"을 잘 보지만 "사실"과 "적절성"은 놓친다.
- **평가 세트 과적합:** 같은 평가 세트로 계속 고치면 그 세트에만 맞춰진다. 새 문항을 주기적으로 추가하고 일부는 숨겨 둔다.
- **버전 의존:** 컨텍스트 한도, 캐싱, 도구 호출 형식은 모델과 API 버전마다 다르다(확인 필요).

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 프롬프트 엔지니어링과 컨텍스트 엔지니어링의 차이는?</summary>

**정답.** 프롬프트 엔지니어링은 주로 지시문을 잘 쓰는 일이고, 컨텍스트 엔지니어링은 지시문을 포함해 도구 설명, 예시, 검색 결과, 대화 기록 등 매 추론 시점에 모델이 보는 전체 정보를 고르고 관리하는 일이다.

**해설.** 여러 단계를 오래 수행하는 에이전트에서는 매 단계 컨텍스트가 바뀌므로 후자가 중요해진다.

</details>

<details class="qa" data-type="concept"><summary>Q2. Lost in the Middle 연구가 보여 준 현상과 실무 시사점은?</summary>

**정답.** 관련 정보가 긴 입력의 처음이나 끝에 있을 때보다 중간에 있을 때 모델 성능이 낮아지는 U자 경향. 시사점: 검색 결과를 많이 넣기보다 적게 고르고, 가장 중요한 정보를 앞이나 끝에 두며, 길이를 늘리는 것이 항상 이득은 아니라는 것.

**해설.** 정도는 모델마다 다르므로 자기 과제에서 직접 측정하는 것이 좋다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 프롬프트를 바꿨더니 평가 50문항 정답률이 80%에서 84%가 되었다. 개선이라고 보고해도 되는가?</summary>

**정답.** 단정하기 어렵다. 50문항이면 표준오차가 약 5.7%p라 4%p 차이는 우연 범위 안이다. 문항 수를 늘리거나, 같은 문항에서 두 프롬프트를 짝지어 비교하고, 어떤 문항이 바뀌었는지 직접 확인해야 한다.

**해설.** 평가 하네스도 통계적 불확실성을 고려해야 한다(STAT-INF-001).

</details>

<details class="qa" data-type="applied"><summary>Q4. 매일 새 세션에서 시작하는 AI 작업자가 어제의 결정을 자꾸 잊고 같은 실수를 반복한다. 어떻게 고치겠는가?</summary>

**정답.** 결정과 교훈을 대화가 아니라 저장소의 파일(절차서, 인수인계 문서, 실행 기록)에 남기고 매 세션 시작 때 읽게 한다. 반복되는 실수는 가능하면 자동 검사로 만들어 하네스에 넣는다(예: 수식 문법 검사).

**해설.** 구조화된 메모 + 검사 자동화. 이 사이트의 AUTOMATION.md, HANDOFF.md, 검증 게이트가 이 방식이다.

</details>
