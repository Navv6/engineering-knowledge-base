## 0. 한눈에 보기 (입문)

### 한 줄 요약
관계형 데이터 모델링은 데이터를 **여러 개의 표(테이블)로 나눠 담고, 표끼리 "번호(키)"로 연결**하는 설계 방법이다. 잘 나누면 같은 정보를 한 곳에만 적게 되어 틀릴 일이 줄어든다.

### 쉬운 설명
엑셀 한 시트에 주문을 이렇게 적었다고 해 보자.

| 주문번호 | 고객명 | 고객 전화 | 상품 | 수량 |
|---|---|---|---|---|
| 1 | 김민수 | 010-1111 | 노트북 | 1 |
| 2 | 김민수 | 010-1111 | 마우스 | 2 |

김민수의 전화번호가 바뀌면 **모든 줄을 찾아 고쳐야** 하고, 하나라도 빠뜨리면 같은 사람의 번호가 두 개가 된다. 그래서 표를 나눈다.

- **고객 표:** 고객번호, 이름, 전화 (사람마다 한 줄)
- **주문 표:** 주문번호, 고객번호, 상품, 수량

주문 표에는 전화번호 대신 **고객번호**만 적는다. 전화가 바뀌면 고객 표 한 줄만 고치면 끝이다. 표마다 줄을 하나로 콕 집는 번호를 **기본 키**, 다른 표의 줄을 가리키는 번호를 **외래 키**라고 부른다. 필요할 때는 두 표를 고객번호로 **이어 붙여(조인)** 한 번에 본다.

### 내 프로젝트에서는
Preflight의 설계 판단(포트폴리오 기재) 대부분이 이 단원의 질문이었다.

- **원본을 다 보존할까, 필요한 칸만 저장할까 (ADR-01):** 처음에는 화면에 필요한 12개 칸만 저장했는데, 미결 업무 목록·준수율 집계에 빠진 정보가 필요해졌다. 그래서 **ERP 원본 전체를 보존하고, 화면용 값은 거기서 가공**하는 방식으로 바꿨다. 데이터 모델링으로 말하면 **원본 테이블과 가공(파생) 데이터를 분리**한 것이다.
- **행을 무엇으로 콕 집을까 (ADR-03):** 엑셀 행 번호로 행을 구분했더니 줄 하나가 끼면 사람이 고친 값이 옆 행으로 밀렸다. 그래서 **원본 값으로 행을 식별**하게 바꿨다. 이것이 바로 "기본 키를 무엇으로 정하느냐"의 문제다. 행 번호처럼 바뀔 수 있는 값은 키가 될 수 없다.
- **빠진 행을 지울까 (ADR-05):** 파일에서 빠진 행을 지우지 않고 완료·취소·드롭 같은 **업무 단계로 표시**한다. 줄을 실제로 지우는 대신 상태 칸으로 표시하는 이 방식을 **논리 삭제**라 한다.
- **되돌릴 수 있게 (ADR-05):** 행의 전후 모습을 남겨 업로드 단위로 되돌린다. 이력을 별도로 쌓는 **이력(감사) 테이블** 설계다.
- **DeepVi:** 재무·주가·뉴스·ESG·거시지표를 PostgreSQL에 저장하고 기업 기준으로 조회했다. 기업이라는 공통 키로 여러 표를 잇는 구조다.

## 1. 핵심 요약

- **관계형 모델**은 데이터를 행(row)과 열(column)로 된 **테이블(relation)**들로 표현하고, 테이블 사이를 **키(key)** 값으로 연결한다(Codd, 1970).
- **기본 키(primary key):** 테이블에서 각 행을 유일하게 식별하는 열(또는 열 조합). 비어 있으면 안 되고 바뀌지 않아야 한다.
- **외래 키(foreign key):** 다른 테이블의 기본 키를 가리키는 열. DB가 "존재하지 않는 고객을 가리키는 주문"을 막아 준다.
- **정규화(normalization):** 같은 사실이 한 곳에만 저장되도록 테이블을 나누는 과정. 수정 누락(이상 현상)을 줄인다. 대신 조회할 때 조인이 늘어난다.
- 실무 설계는 정규화 원칙 위에 **원본 보존, 키 선택, 삭제 방식, 이력 관리** 같은 판단을 더한다.

## 2. 개념과 등장 배경

1960년대 데이터베이스는 데이터를 트리나 네트워크 모양의 포인터로 연결해 저장했다. 프로그램이 저장 구조를 직접 따라가야 해서, 구조를 조금만 바꿔도 프로그램을 다시 짜야 했다.

1970년 IBM의 에드거 F. 코드(Edgar F. Codd)는 데이터를 수학의 "관계(relation)", 즉 표로 보고, 사용자는 **무엇을** 원하는지만 말하면 시스템이 **어떻게** 찾을지 정하는 모델을 제안했다. 이 생각에서 SQL과 오늘날의 관계형 데이터베이스(PostgreSQL, MySQL, Oracle 등)가 나왔다. 저장 방식과 질문 방식을 분리한 것이 핵심이다.

## 3. 직관적 설명 및 기초 이론

| 용어 | 엑셀로 말하면 | 예 |
|---|---|---|
| 테이블(relation) | 시트 하나 | 고객 시트 |
| 행(row, tuple) | 한 줄 | 김민수의 정보 |
| 열(column, attribute) | 한 칸 제목 | 전화번호 |
| 기본 키 | 줄을 콕 집는 번호 | 고객번호 |
| 외래 키 | 다른 시트의 번호를 적어 둔 칸 | 주문 시트의 고객번호 |
| 조인(join) | 번호가 같은 줄끼리 옆으로 이어 붙이기 | 주문 + 고객 |

**정규화의 직관:** "한 가지 사실은 한 곳에만." 고객 전화번호는 고객 표에만, 상품 가격은 상품 표에만 둔다. 다른 표는 번호로 가리킨다.

## 4. 엄밀한 정의와 작동 원리

### 키

- **후보 키:** 행을 유일하게 식별할 수 있는 최소한의 열 조합. 여러 개일 수 있다.
- **기본 키:** 후보 키 중 하나를 골라 대표로 쓴 것. NULL(빈 값)을 허용하지 않는다.
- **자연 키(natural key):** 업무에 원래 있는 값으로 만든 키(예: 사업자등록번호, 품목코드 + 워크센터).
- **대리 키(surrogate key):** 의미 없는 일련번호나 UUID로 만든 키. 업무 값이 바뀌어도 키는 그대로다.

### 정규형 (자주 쓰는 3단계)

| 정규형 | 조건 | 위반 예 |
|---|---|---|
| 제1정규형(1NF) | 한 칸에 값 하나 | "상품" 칸에 "노트북, 마우스" |
| 제2정규형(2NF) | 키의 **일부**에만 딸린 열이 없음 | (주문번호, 상품) 키인데 "고객명"은 주문번호에만 딸림 |
| 제3정규형(3NF) | 키가 아닌 열에 딸린 열이 없음 | 주문 표의 "고객 전화"가 고객번호에 딸림 |

### 조인

주문과 고객을 고객번호로 잇는 SQL:

```sql
SELECT o.order_id, c.name, o.product, o.qty
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id;
```

### 제약 조건

DB가 규칙을 직접 지키게 할 수 있다. 사람이 실수해도 잘못된 데이터가 들어가지 않는다.

```sql
CREATE TABLE customers (
  customer_id  bigint PRIMARY KEY,
  phone        text NOT NULL
);
CREATE TABLE orders (
  order_id     bigint PRIMARY KEY,
  customer_id  bigint NOT NULL REFERENCES customers(customer_id),
  qty          int CHECK (qty > 0)
);
```

## 5. 수식 및 기호 설명

이 단원은 수식이 거의 필요 없다. 코드가 처음이라면 SQL 키워드만 읽으면 된다.

| 표기 | 뜻 |
|---|---|
| `PRIMARY KEY` | 기본 키 지정 |
| `REFERENCES t(col)` | 외래 키: t 테이블의 col을 가리킴 |
| `UNIQUE (a, b)` | a와 b 조합이 겹치지 않게 |
| `NOT NULL` | 빈 값 금지 |
| `CHECK (조건)` | 조건을 만족하는 값만 허용 |
| `JOIN ... ON` | 조건이 맞는 줄끼리 이어 붙이기 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 한 장짜리 표를 나누기

처음 표(주문번호, 고객명, 고객 전화, 상품, 상품 가격, 수량)를 3NF로 나눈다.

1. **고객:** (customer_id, 이름, 전화)
2. **상품:** (product_id, 상품명, 가격)
3. **주문:** (order_id, customer_id, 주문일)
4. **주문 항목:** (order_id, product_id, 수량) — 한 주문에 여러 상품이 들어가므로 따로 둔다. 기본 키는 (order_id, product_id).

전화번호, 가격은 이제 한 곳에만 있다.

### 예제 2. 엑셀 업로드를 받는 테이블 설계 (Preflight식 판단을 일반화)

매주 ERP 엑셀을 올려 현황을 관리한다고 하자.

| 판단 | 선택지 | 고려할 점 |
|---|---|---|
| 무엇을 저장? | 필요한 칸만 / 원본 전체 | 나중에 필요한 칸이 생기면 원본이 없을 때 복구 불가 |
| 행 식별 | 행 번호 / 원본 값 조합(자연 키) / 일련번호(대리 키) | 행 번호는 바뀜. 원본 값 조합은 업무 의미가 있지만 조합이 부족하면 서로 다른 행이 같은 키가 됨 |
| 빠진 행 | 지운다 / 상태로 표시 | 지우면 "완료인지 취소인지" 근거가 사라짐 |
| 변경 이력 | 덮어쓴다 / 이력 테이블에 전후 기록 | 되돌리기와 감사가 필요하면 이력 테이블 |

유니크 제약으로 키 중복을 DB가 막게 할 수 있다.

```sql
CREATE TABLE erp_rows (
  item_code    text NOT NULL,
  work_center  text NOT NULL,
  order_no     text NOT NULL,
  status       text NOT NULL DEFAULT 'active',  -- active / done / canceled / dropped
  raw          jsonb NOT NULL,                  -- 원본 행 전체 보존
  UNIQUE (item_code, work_center, order_no)
);
```

위 테이블은 설명을 위한 일반적인 예시이며, Preflight의 실제 스키마가 아니다.

### 예제 3. 조인 결과 세어 보기

고객 3명, 주문 5건(고객1: 2건, 고객2: 3건, 고객3: 0건).

- `JOIN`(내부 조인): 짝이 있는 줄만 → **5줄**
- `LEFT JOIN customers → orders`: 고객 기준, 주문 없는 고객도 한 줄(주문 칸은 비움) → 2 + 3 + 1 = **6줄**

## 7. 시각화와 해석

테이블 관계는 보통 ERD(개체-관계 다이어그램)로 그린다. 이 설명집 예제 1을 말로 그리면: 고객 1 ── N 주문 1 ── N 주문 항목 N ── 1 상품. "1 ── N"은 "한 고객이 여러 주문을 가진다"는 뜻이다. Knowledge Map 화면에서 이 개념이 B-Tree 인덱스와 트랜잭션의 선행 개념으로 연결된 것도 확인할 수 있다.

## 8. 기술 비교 및 선택 기준

| 선택 | 장점 | 단점 | 이럴 때 |
|---|---|---|---|
| 정규화 | 중복·수정 누락이 적다 | 조회 시 조인이 많다 | 쓰기가 많고 정확성이 중요한 업무 데이터 |
| 비정규화(일부 중복 허용) | 조회가 빠르고 단순 | 중복을 맞춰 줄 책임이 생김 | 대시보드·리포트용 읽기 전용 테이블 |
| 자연 키 | 업무 의미가 바로 보인다 | 업무 값이 바뀌거나 조합이 부족하면 문제 | 값이 안정적이고 조합이 확실할 때 |
| 대리 키 | 안정적, 짧다 | 중복 판정은 따로 유니크 제약이 필요 | 대부분의 테이블 기본값 |
| 물리 삭제 | 단순, 공간 절약 | 근거와 이력이 사라짐 | 개인정보 파기 등 실제로 지워야 할 때 |
| 논리 삭제(상태 칸) | 이력과 되돌리기 가능 | 조회마다 상태 조건을 붙여야 함 | 업무 이력이 중요한 데이터 |
| 관계형 테이블 | 제약·조인·트랜잭션 | 구조 변경에 마이그레이션 필요 | 정형 업무 데이터 |
| JSON 칸(jsonb) | 구조가 바뀌어도 그대로 저장 | 칸별 제약이 약함 | 원본 보존, 구조가 자주 바뀌는 외부 데이터 |

자주 쓰는 조합은 **대리 키를 기본 키로 두고, 자연 키 조합에는 UNIQUE 제약을 거는 것**이다. 안정성과 중복 방지를 둘 다 얻는다.

## 9. 실무 사례

- **주문·결제 시스템:** 고객, 상품, 주문, 주문 항목, 결제를 나누고 외래 키로 잇는다. 가격은 주문 시점 가격을 주문 항목에 따로 저장한다(나중에 상품 가격이 바뀌어도 과거 주문은 그대로여야 하므로). 이것은 의도된 중복이다.
- **분석용 데이터 웨어하우스:** 원천 시스템은 정규화하고, 분석용은 일부러 비정규화한 "사실 테이블 + 차원 테이블"(스타 스키마)을 만든다.
- **외부 데이터 수집:** 원본은 그대로(JSON 등) 보관하고, 정제한 값은 별도 테이블로 만든다. 원본이 있으면 가공 규칙이 바뀌어도 다시 만들 수 있다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 원본 보존(ADR-01):** 화면에 필요한 12개 필드만 저장하다가, 미결 업무 목록·준수율 집계에 빠진 정보가 필요해 ERP 원본 전체를 보존하고 필요한 값을 가공하는 방식으로 바꿨다. 8절의 "원본 테이블 + 가공 데이터" 분리다.
- **Preflight — 행 식별(ADR-03):** 행 번호로 식별하다 줄 삽입 시 수정값이 밀리는 문제를 겪고 원본 값으로 식별하게 바꿨다. 자연 키를 고른 사례다.
- **Preflight — 판정 키 확장(ADR-02):** 품목 기준 중복 제거가 두 사출처에 나눠 맡긴 정상 데이터를 지워 판정 키에 워크센터를 포함했다. 자연 키 조합이 부족하면 서로 다른 행이 같은 키가 된다는 8절의 단점이 실제로 나타난 경우다.
- **Preflight — 논리 삭제와 이력(ADR-05):** 빠진 행은 지우지 않고 업무 단계(완료·취소·드롭)로 관리하고, 행의 전후 모습을 남겨 업로드 단위로 되돌린다.
- **Preflight — DB 변경은 더하기만:** 개발/운영을 분리하고 DB 변경은 더하기만 해서 되돌려도 데이터가 남게 했다. 열을 지우거나 이름을 바꾸지 않고 추가만 하는 마이그레이션 원칙이다.
- **DeepVi:** 재무·주가·뉴스·ESG·거시지표를 PostgreSQL에 저장하고 FastAPI로 조회했다.
- 점검 질문: Preflight에서 자연 키 조합에 UNIQUE 제약을 걸었는지, 대리 키를 함께 두었는지는 포트폴리오에 없다. 면접에서 키 설계를 물으면 이 두 가지를 구분해 말할 수 있게 확인해 둔다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: "정규화는 많이 할수록 좋다."** 지나치게 나누면 조회마다 조인이 많아지고 이해하기 어려워진다. 업무용은 보통 3NF 근처에서 멈추고, 읽기 전용 리포트는 일부러 비정규화한다.
- **오해: "자연 키가 항상 낫다."** 사람 이름, 전화번호, 행 번호처럼 바뀌거나 겹칠 수 있는 값은 키로 부적합하다. 업무 값이 안정적이어도 조합이 충분한지 반례로 확인해야 한다(ADR-02).
- **논리 삭제의 비용:** 모든 조회에 `WHERE status = 'active'` 같은 조건을 빠뜨리지 않아야 한다. 빠뜨리면 지운 줄이 다시 보인다.
- **외래 키를 빼고 싶은 유혹:** 대량 적재 속도를 이유로 외래 키를 빼면, 존재하지 않는 대상을 가리키는 고아 데이터가 쌓일 수 있다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 기본 키와 외래 키의 차이를 주문·고객 예로 설명하라.</summary>

**정답.** 고객 표의 고객번호는 고객 한 명을 유일하게 가리키는 기본 키다. 주문 표의 고객번호는 그 주문이 어느 고객의 것인지 고객 표의 기본 키를 가리키는 외래 키다.

**해설.** 외래 키 제약을 걸면 존재하지 않는 고객번호로는 주문을 넣을 수 없다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 고객 3명 중 1명만 주문이 없고, 나머지 두 명이 각각 2건, 3건 주문했다. 고객 기준 LEFT JOIN 결과는 몇 줄인가?</summary>

**정답.** 6줄.

**해설.** 주문 있는 고객은 주문 수만큼(2 + 3 = 5줄), 주문 없는 고객은 주문 칸이 빈 한 줄이 나온다. 내부 조인이면 5줄이다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 매주 올리는 외부 엑셀 데이터를 저장할 때, 필요한 칸만 정제해 저장하는 방식과 원본을 함께 보존하는 방식 중 무엇을 고르겠는가?</summary>

**정답.** 원본을 함께 보존한다. 나중에 필요한 칸이나 계산 규칙이 바뀌어도 원본에서 다시 만들 수 있고, 숫자의 근거를 추적할 수 있다. 저장 공간이 더 드는 대가를 감수한다.

**해설.** Preflight가 12개 필드 저장에서 원본 전체 보존으로 바꾼 이유(ADR-01)와 같다. 화면·집계용 값은 원본에서 가공한 별도 데이터로 둔다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 업로드 판정 키를 "품목코드"로만 잡았더니 정상 데이터 일부가 중복으로 지워졌다. 어떻게 진단하고 고치겠는가?</summary>

**정답.** 같은 품목코드를 가진 행들 중 실제로 다른 행(예: 다른 사출처·워크센터에 나눠 맡긴 건)이 있는지 찾아, 그 행들을 구분하는 열을 키에 추가한다. 고친 뒤에는 그 반례를 테스트로 만들어 다시 생기지 않게 하고, DB에는 새 키 조합에 UNIQUE 제약을 건다.

**해설.** Preflight ADR-02에서 실제로 판정 키에 워크센터를 포함하고 반례 테스트를 추가한 사례다. 키는 "업무적으로 같은 것"의 정의라서 반례로 검증해야 한다.

</details>
