## 0. 한눈에 보기 (입문)

### 한 줄 요약
**Git**은 파일의 변경 기록을 "커밋"이라는 사진으로 남기고, 여러 사람이 각자 작업한 기록을 합칠 수 있게 해 주는 버전 관리 도구다. 핵심은 **언제든 과거로 돌아갈 수 있고, 누가 무엇을 왜 바꿨는지 남는다**는 것이다.

### 쉬운 설명
문서 파일 이름을 "보고서_최종.docx", "보고서_최종_진짜.docx", "보고서_최종_진짜_수정.docx"로 늘려 본 적이 있다면, Git이 해결하는 문제를 이미 알고 있다.

- **커밋:** 지금 상태를 사진 찍듯 저장하고 "무엇을 왜 바꿨나" 메모를 붙인다.
- **기록(히스토리):** 사진들이 줄줄이 이어진 앨범. 어느 사진으로든 돌아갈 수 있다.
- **브랜치:** 앨범을 복사해 "실험용" 줄기를 따로 만드는 것. 실험이 성공하면 원래 줄기에 합치고(**merge**), 실패하면 버린다.
- **원격 저장소(GitHub 등):** 앨범을 인터넷에 백업하고 팀원과 공유하는 곳. 올리기가 **push**, 받기가 **pull**이다.

### 내 프로젝트에서는
- **이 학습 사이트의 원본이 Git 저장소다.** 비공개 GitHub 저장소의 `main` 브랜치가 단일 기준이고, 설명집 한 편마다 커밋 하나를 남긴다(이 글 작성 시점에 커밋 57개). 매일 05:44 예약 실행도 저장소를 받아 → 글을 쓰고 → 검증·시험을 통과하면 커밋·푸시한다(AUTOMATION.md).
- **실수는 기록을 지우지 않고 "고친 커밋"으로 바로잡았다.** 수식 오류가 있는 설명집(AI-ANN-001)이 한 번 커밋·푸시되었을 때, 이력을 되감지 않고 다음 커밋("fix: 수식 안 가운뎃점 제거")으로 고쳤다. 절차서에는 "force push 금지, 거부되면 pull --rebase 후 다시 시험하고 푸시"라는 규칙이 있다(6절).
- **Preflight·DeepVi의 Git 사용 방식은 포트폴리오에 기재가 없다.** Preflight의 "개발을 거치지 않은 변경은 배포 스크립트가 거부" 규칙(포트폴리오 기재)은 보통 브랜치·커밋 기록과 함께 구현되는 장치라, 연결 방식을 점검해 볼 만하다.

### 먼저 알면 좋은 것
- 소프트웨어 테스트와 유지보수(SE-TEST-001): 커밋 전에 시험을 돌리는 게이트
- 그래프 이론 기초(MATH-GRAPH-001): 커밋 기록은 방향 그래프(DAG)다.

## 1. 핵심 요약

- **커밋:** 프로젝트 전체의 스냅숏 + 부모 커밋 참조 + 작성자·시각·메시지. 내용에서 계산한 **해시**(SHA-1, 최근 버전은 SHA-256도 지원)가 이름이다.
- **기록은 DAG:** 각 커밋이 부모를 가리키는 순환 없는 방향 그래프. merge 커밋은 부모가 둘이다.
- **브랜치 = 이름표:** 특정 커밋을 가리키는 포인터. 새 커밋을 만들면 이름표가 따라 움직인다. 만드는 비용이 거의 없다.
- **세 영역:** 작업 폴더 → (`git add`) → 스테이징 영역 → (`git commit`) → 저장소.
- **원격 동기화:** `fetch`(받기만) / `pull`(받아서 합치기) / `push`(올리기). 원격이 내가 모르는 커밋을 가지고 있으면 push가 거부된다.
- **되돌리기:** `revert`는 되돌리는 새 커밋을 추가(공유된 기록에 안전), `reset`은 이름표를 과거로 옮김(공유된 기록에 쓰면 위험). **force push는 남의 커밋을 지울 수 있다.**

## 2. 개념과 등장 배경

1970~80년대의 SCCS, RCS는 파일 하나씩 버전을 관리했고, 1990년대 CVS와 2000년 Subversion은 중앙 서버 하나에 기록을 모으는 방식이었다. 중앙 서버가 죽으면 아무도 커밋할 수 없었고, 브랜치를 만들고 합치는 일이 무겁고 위험했다.

2005년 리눅스 커널 팀이 쓰던 상용 도구 BitKeeper의 무료 사용이 끝나자, 리누스 토르발스(Linus Torvalds)가 약 몇 주 만에 Git의 첫 버전을 만들었다. 목표는 빠른 속도, 완전한 **분산**(모든 사람이 전체 기록을 가짐), 내용 해시로 무결성 보장, 가벼운 브랜치였다. 2008년 GitHub가 등장해 풀 리퀘스트(pull request) 기반 코드 리뷰를 대중화했고, 오늘날 Git은 소프트웨어뿐 아니라 문서·데이터·인프라 설정 관리의 표준이 되었다.

## 3. 직관적 설명 및 기초 이론

### 커밋 그래프

```text
A ← B ← C ← F   (main)
         ↖
           D ← E   (feature)
```

화살표는 "부모를 가리킨다". `main`과 `feature`는 각각 F와 E를 가리키는 이름표다. 두 줄기가 갈라진 지점 C가 **공통 조상**(merge base)이다.

### merge vs rebase

- **merge:** 두 줄기를 합친 새 커밋 M(부모 F, E)을 만든다. 기록이 "실제로 일어난 대로" 남는다.
- **rebase:** D, E를 F 위에 다시 쌓아 D′, E′를 만든다. 기록이 한 줄로 깔끔해지지만 **커밋 해시가 바뀐다**(새 커밋이다).

```text
merge:   A ← B ← C ← F ← M (main)        rebase:  A ← B ← C ← F ← D′ ← E′
                  ↖     ↙
                    D ← E
```

**원칙:** 아직 나만 가진 커밋은 rebase해도 되지만, 이미 공유(push)한 커밋은 rebase하지 않는다. 다른 사람이 옛 해시를 기준으로 작업하고 있기 때문이다.

## 4. 엄밀한 정의와 작동 원리

### 내용 주소 저장

Git은 파일 내용(blob), 폴더 구조(tree), 커밋을 모두 객체로 저장하고, 객체의 이름을 내용의 해시로 정한다. 내용이 한 글자라도 바뀌면 해시가 바뀌고, 커밋은 부모의 해시를 포함하므로 **과거 커밋 하나를 몰래 바꾸면 그 뒤 모든 커밋의 해시가 바뀐다.** 기록 위조를 감지할 수 있는 이유다(블록체인과 같은 원리의 해시 사슬).

### fast-forward와 push 거부

원격 `main`이 C를 가리키고 내가 C 위에 D를 만들었다면, 원격 이름표를 D로 옮기기만 하면 된다(fast-forward). 그런데 그 사이 다른 사람이 원격에 F를 올렸다면, 원격 이름표를 D로 옮기면 F가 기록에서 사라진다. 그래서 Git은 push를 **거부**한다. 해결: 원격 변경을 받아(`pull`, 또는 `pull --rebase`) 내 커밋을 그 위에 놓고, **다시 시험한 뒤** push한다.

### revert와 reset

| 명령 | 하는 일 | 기록 | 공유된 브랜치에서 |
|---|---|---|---|
| `git revert <커밋>` | 그 커밋의 변경을 되돌리는 **새 커밋** 추가 | 늘어남 | 안전 |
| `git reset --hard <커밋>` | 이름표를 과거 커밋으로 옮기고 작업 폴더도 맞춤 | 뒤 커밋이 이름표에서 떨어짐 | push하려면 force 필요 → 위험 |
| `git push --force` | 원격 이름표를 강제로 내 것으로 | 원격의 다른 커밋이 사라질 수 있음 | 원칙적으로 금지 |

`--force-with-lease`는 "원격이 내가 마지막으로 본 상태일 때만" 강제로 덮어 써서, 남의 새 커밋을 지우는 사고를 줄인다.

### 비밀 정보와 .gitignore

`.gitignore`에 적은 파일(환경 변수 파일, 빌드 결과 등)은 추적하지 않는다. 비밀 키를 한 번 커밋하면 이후 커밋에서 지워도 **과거 커밋에 남는다.** 이미 push했다면 기록 정리보다 **키 폐기·재발급**이 먼저다(OPS-DEPLOY-001).

## 5. 수식 및 기호 설명

| 용어 | 뜻 |
|---|---|
| 해시 | 내용에서 계산한 고정 길이 지문(SHA-1은 160비트, 16진수 40자) |
| `HEAD` | 지금 작업 중인 위치(보통 현재 브랜치) |
| merge base | 두 브랜치의 가장 가까운 공통 조상 |
| fast-forward | 이름표를 앞으로 옮기기만 하면 되는 합치기 |
| `origin/main` | 마지막으로 받아 온 원격 `main`의 위치 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 이 사이트의 커밋 순서

```bash
node scripts/validate.mjs; V=$?          # 1. 검증
npm run test:unit; U=$?                   # 2. 단위 시험 (V가 0일 때만)
git add -A                                # 3. 변경 담기
git commit -m "manual: SE-GIT-001 Git과 버전 관리"   # 4. 커밋
git push origin HEAD:main                 # 5. 원격 main으로 올리기
```

로컬 브랜치 이름과 상관없이 `HEAD:main`으로 지금 커밋을 원격 `main`에 올린다. 3~5는 1·2의 종료 코드가 0일 때만 실행된다(SE-TEST-001의 게이트).

### 예제 2. push가 거부될 때 (예약 실행과 수동 작업이 겹친 경우)

| 시점 | 예약 실행(원격) | 수동 작업(로컬) |
|---|---|---|
| 05:40 | | 원격 main = C를 받아 둠 |
| 05:49 | D를 커밋해 원격 main = D | |
| 06:10 | | C 위에 E를 커밋, push → **거부**(원격에 모르는 D가 있음) |
| 06:11 | | `git pull --rebase origin main` → E가 D 위로 옮겨져 E′ |
| 06:12 | | 빌드·시험 다시 실행 → 통과하면 push → 원격 main = E′ |

E′는 해시가 E와 다르다. 아직 push하지 않은 내 커밋이라 rebase해도 안전하다. 다시 시험하는 이유는 D와 E가 따로는 괜찮아도 합치면 깨질 수 있기 때문이다. force push로 해결하면 예약 실행의 D가 사라진다.

### 예제 3. 실수한 커밋을 고치는 두 가지 방법

이미 push한 커밋 X에 오류가 있다.

- **revert(또는 고친 커밋 추가):** X 뒤에 X를 되돌리거나 고치는 Y를 추가. 다른 사람·예약 실행이 X를 이미 받았어도 문제없다. 이 사이트가 AI-ANN-001 수식 오류를 고친 방식이다.
- **reset + force push:** 원격에서 X를 지운다. 그 사이 다른 커밋이 올라왔다면 함께 지워질 수 있고, X를 받은 사람의 저장소와 기록이 어긋난다.

## 7. 시각화와 해석

`git log --graph --oneline`은 커밋 그래프를 글자로 그려 준다. 선이 갈라지면 브랜치, 합쳐지면 merge다. 그래프 이론(MATH-GRAPH-001) 관점에서 커밋 기록은 DAG이고, merge base 찾기는 두 정점의 공통 조상 찾기, `git log A..B`는 "B에서는 도달 가능하지만 A에서는 도달할 수 없는 커밋"이라는 집합 차(MATH-DM-001)다.

## 8. 기술 비교 및 선택 기준

| 작업 방식 | 방법 | 적합 |
|---|---|---|
| 트렁크 기반 | 모두 main에 작고 자주 합침, 기능 플래그 사용 | 자동 시험이 탄탄한 팀 |
| 기능 브랜치 + 풀 리퀘스트 | 기능별 브랜치 → 리뷰 → 합침 | 대부분의 팀, 리뷰 문화 |
| 개발/운영 브랜치 분리 | develop에서 검증 후 main(운영)으로 | 배포 게이트를 브랜치로 표현할 때 |
| 1인 + 자동화 | main 직접 커밋, 커밋 전 시험 게이트 필수 | 이 학습 사이트처럼 작은 저장소 |

| 합치기 | 장점 | 단점 |
|---|---|---|
| merge | 실제 기록 보존, 안전 | 기록이 복잡해짐 |
| rebase | 한 줄의 깔끔한 기록 | 해시 변경, 공유 커밋에 쓰면 위험 |
| squash merge | 기능 하나 = 커밋 하나 | 중간 기록 사라짐 |

## 9. 실무 사례

- **코드 리뷰:** 풀 리퀘스트로 변경을 보이고, 자동 시험(CI)이 통과해야 합칠 수 있게 보호 규칙을 건다.
- **장애 원인 찾기:** `git bisect`는 "잘 되던 커밋"과 "깨진 커밋" 사이를 이진 탐색해 문제 커밋을 찾는다. 커밋 100개면 약 7번 시험으로 찾는다($\log_2 100 \approx 6.6$, CS-ALG-002).
- **설정·문서 관리:** 서버 설정, 데이터 파이프라인 SQL, 프롬프트도 Git으로 관리하면 "언제부터 바뀌었나"를 추적할 수 있다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 기록에서 옮긴 것이다.

- **이 학습 사이트:** 비공개 저장소 `main`이 단일 기준, 설명집 한 편 = 커밋 하나, 커밋 전 검증·시험 게이트, force push 금지, 거부 시 pull --rebase 후 재시험(AUTOMATION.md). 첫 예약 실행에서 푸시가 권한 문제로 거부(403)되었다가, 저장소를 예약 작업의 소스로 추가한 뒤 해결되었다(HANDOFF.md).
- **Preflight — 배포 게이트:** 개발을 거치지 않은 변경은 배포 스크립트가 거부한다. 점검 질문(기록 없음): 이 판단은 어떤 기준으로 하는가(개발 서버에 배포된 커밋 해시와 운영 배포 요청 커밋의 일치 등)? 커밋 해시로 "개발에서 시험한 바로 그 버전"임을 확인하면 규칙이 확실해진다.
- **Preflight — 업로드 단위 되돌리기(ADR-05):** 데이터 변경을 업로드 단위로 되돌리는 설계는, 코드 변경을 커밋 단위로 revert하는 것과 같은 발상이다. 지우지 않고 되돌리는 기록을 추가한다.
- **DeepVi — 팀 작업:** 기획·수집·백엔드·LLM·대시보드를 맡고 뉴스 분석과 재무건전성 평가는 팀원이 맡았다(포트폴리오 기재). 여러 사람이 같은 저장소에서 일할 때 브랜치·리뷰 방식이 필요하다(실제 방식은 기재 없음).

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 지운 파일은 기록에서도 사라진다.** 과거 커밋에 남는다. 비밀 정보는 키 폐기가 먼저다.
- **오해: force push로 깔끔하게 정리하면 된다.** 공유된 브랜치에서는 남의 커밋을 지울 수 있다. 꼭 필요하면 `--force-with-lease`와 팀 합의.
- **오해: Git이 백업을 대신한다.** 원격 저장소가 있어야 백업이고, DB 데이터·업로드 파일은 Git으로 관리하지 않는다(OPS-DEPLOY-001의 백업).
- **큰 파일:** 동영상·모델 가중치 같은 큰 파일은 저장소를 무겁게 한다. 별도 저장소나 대용량 파일 확장 기능을 쓴다.
- **merge 충돌:** 두 사람이 같은 줄을 바꾸면 Git은 자동으로 못 합친다. 작은 커밋을 자주 합치면 충돌이 작아진다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 과거 커밋 하나의 내용을 몰래 바꾸면 왜 들키는가?</summary>

**정답.** 커밋 이름은 내용의 해시이고 각 커밋은 부모의 해시를 포함하므로, 한 커밋이 바뀌면 그 커밋과 뒤의 모든 커밋 해시가 바뀐다. 다른 사람이 가진 기록과 해시가 달라져 바로 드러난다.

**해설.** 해시 사슬 구조 덕분에 분산 저장소끼리 무결성을 확인할 수 있다.

</details>

<details class="qa" data-type="concept"><summary>Q2. revert와 reset의 차이를 공유 브랜치 관점에서 설명하라.</summary>

**정답.** revert는 되돌리는 변경을 새 커밋으로 추가해 기록을 보존하므로 공유 브랜치에서도 안전하다. reset은 브랜치 이름표를 과거로 옮겨 이후 커밋을 기록에서 떼어 내므로, 공유 브랜치에 적용하려면 force push가 필요하고 다른 사람의 작업을 망가뜨릴 수 있다.

**해설.** 공유된 기록은 "추가만" 한다는 원칙은 DB의 더하기만 하는 변경(OPS-DEPLOY-001)과 같다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. push가 "non-fast-forward"로 거부되었다. 동료가 "force로 밀어"라고 한다. 어떻게 하겠는가?</summary>

**정답.** force push는 원격에 먼저 올라간 다른 사람의 커밋을 지울 수 있으므로 하지 않는다. 원격 변경을 받아(`pull --rebase` 또는 merge) 내 커밋을 그 위에 놓고, 충돌을 해결한 뒤 빌드·시험을 다시 돌리고 push한다.

**해설.** 6절 예제 2의 상황이다. 따로는 괜찮던 두 변경이 합쳐지면 깨질 수 있어 재시험이 필요하다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 실수로 API 키가 든 설정 파일을 커밋해 공개 저장소에 push했다. 무엇부터 하겠는가?</summary>

**정답.** 즉시 그 키를 폐기하고 새로 발급한다. 그다음 파일을 `.gitignore`에 넣고 비밀은 환경 변수·비밀 저장소로 옮기며, 필요하면 기록에서 해당 파일을 제거하는 정리 작업을 한다. 키가 쓰인 기록(사용 내역)을 점검한다.

**해설.** 공개된 순간 복제·수집되었을 수 있어, 기록을 지우는 것보다 키 무효화가 먼저다.

</details>
