## 0. 한눈에 보기 (입문)

### 한 줄 요약
LLM 응용은 "써 보니 괜찮다"로는 개선 여부를 알 수 없다. **고정된 평가 세트 + 명확한 채점 기준 + 버전 간 짝지은 비교**로 평가하고, LLM을 채점자로 쓸 때는 **그 채점자부터 사람과 비교해 검증**한다.

### 쉬운 설명
요리 대회를 떠올리자.

- **평가 세트 = 정해진 과제 목록.** 매번 다른 요리를 시키면 실력이 늘었는지 알 수 없다. 같은 과제로 비교해야 한다.
- **채점 기준표 = 맛, 모양, 시간, 위생 항목별 점수.** "맛있다/없다" 한 줄보다 항목별로 매기면 무엇이 문제인지 보인다.
- **심사위원 = 사람 또는 LLM.** LLM 심사위원은 빠르고 싸지만 버릇이 있다. 먼저 나온 요리를 좋아하거나, 양이 많은(긴 답) 요리에 점수를 후하게 주는 식이다. 그래서 먼저 사람 심사위원과 점수가 얼마나 비슷한지 확인한다.
- **같은 과제로 전후 비교:** 새 레시피(프롬프트)가 이전보다 나은지, 과제마다 짝지어 비교한다.

### 내 프로젝트에서는
- **DeepVi는 테스트용 프롬프트로 근거 기반 답변을 확인했다.** 답변이 보유한 기업 데이터를 근거로 나오는지 테스트용 프롬프트로 확인했고, 정량 평가 지표는 기재되어 있지 않다(포트폴리오 기재). 다음 단계는 질문 세트와 기대 근거를 고정해 "근거 충실도"를 숫자로 재는 것이다(6절).
- **STT 평가는 같은 조건 비교의 모범이다.** 같은 데이터 6,000개, 같은 정규화, 같은 지표로 모델 4종을 비교했고, WER·CER만으로 의미 보존을 판단하기 어려워 의미 지표(Semantic Similarity, SemWER@0.85)를 더했다(포트폴리오 기재). 자동 지표의 한계를 보완 지표로 메운 것이다.
- **STT 로컬 LLM 검토는 평가 기준을 먼저 정했다.** JSON 스키마 유지, 요약 품질, 처리 시간, 실패 대응을 기준으로 타당성을 검토했다(포트폴리오 기재). 평가 항목을 여러 축으로 나눈 기준표다.

### 먼저 알면 좋은 것
- 분류 평가 지표(AI-EVAL-001): 정밀도·재현율, 혼동행렬
- 가설검정과 p-value(STAT-INF-002): 짝지은 비교, 표본 크기
- LLM과 트랜스포머 작동 원리(AI-LLM-001): temperature, 환각

## 1. 핵심 요약

- **무엇을 잴까:** 정답 정확성, 근거 충실도(답이 제공된 자료에서 나왔나), 검색 품질(맞는 문서를 가져왔나), 형식 준수, 안전(금지 내용·개인정보), 지연·비용.
- **어떻게 잴까:** 정답이 정해진 것은 자동 대조, 형식은 스키마 검사, 실행 가능한 것은 테스트, 정답이 여럿인 것은 기준표 + 사람 또는 LLM 채점.
- **평가 세트:** 대표 사례 + 경계 사례 + 과거 실패 사례. 버전 관리하고, 일부는 숨겨 과적합을 막는다.
- **LLM 평가자:** 강한 모델은 사람과 높은 일치를 보일 수 있지만 위치·길이·자기 선호 편향이 보고되었다(Zheng 외 2023). 순서를 바꿔 두 번 채점하고, 사람 표본으로 일치도(카파)를 확인한다.
- **비교:** 같은 문항에서 짝지어 비교(맥니마 검정, 짝지은 부트스트랩). 작은 차이는 우연일 수 있다.
- **운영 평가:** 배포 후에도 실제 질문 표본을 주기적으로 채점해 품질 변화를 감시한다.

## 2. 개념과 등장 배경

전통적인 NLP는 정답과의 단어 겹침(BLEU, ROUGE)이나 분류 정확도로 평가했다. 생성형 LLM이 자유로운 문장을 만들면서 "정답이 하나가 아닌" 출력이 늘었고, 단어 겹침 지표는 의미 품질을 잘 반영하지 못했다. 2022년 HELM(Liang 외)은 정확도뿐 아니라 보정, 견고성, 공정성, 효율 등 여러 축으로 모델을 평가해야 한다고 정리했다.

2023년 Zheng 외는 GPT-4 같은 강한 모델을 채점자로 쓰는 **LLM-as-a-judge**를 체계적으로 분석해, 사람 판정과 높은 일치도를 보일 수 있지만 위치·길이·자기 선호 편향이 있음을 보고했다. 같은 해 RAGAS(Es 외)는 RAG 시스템을 정답 라벨 없이도 근거 충실도, 답변 관련성, 문맥 정밀도 같은 지표로 자동 평가하는 방법을 제안했다. 실무에서는 이런 자동 평가를 **회귀 테스트**처럼 프롬프트·모델·검색 설정을 바꿀 때마다 돌리는 것이 표준이 되었다.

## 3. 직관적 설명 및 기초 이론

### 평가 축과 방법

| 평가 축 | 질문 | 방법 |
|---|---|---|
| 정확성 | 답이 맞나 | 정답 대조, 사람 채점 |
| 근거 충실도 | 답의 주장이 제공 자료에 있나 | 주장별 근거 대조(LLM 또는 사람) |
| 검색 품질 | 맞는 문서를 가져왔나 | precision@k, recall@k(AI-RAG-001) |
| 형식 | 정해진 구조를 지켰나 | 스키마 검사(AI-PROMPT-001) |
| 안전 | 금지 내용·개인정보 없나 | 규칙 검사 + 표본 검토 |
| 효율 | 지연·비용 | 로그 집계(OPS-OBS-001) |

### 좋은 평가 세트의 조건

- **대표성:** 실제 사용자 질문 분포를 닮았다(실제 질문 표본에서 뽑기).
- **경계 사례:** 자료에 답이 없는 질문, 두 기업을 비교하는 질문, 오래된 정보를 묻는 질문.
- **과거 실패:** 한 번 틀린 사례는 평가 세트에 넣어 다시 틀리지 않는지 본다(SE-TEST-001의 회귀 테스트).
- **기대 결과의 기준:** 정답 문장 대신 "반드시 포함할 사실", "인용해야 할 문서", "하면 안 되는 말"로 정의하면 정답이 여럿인 문제도 채점할 수 있다.

## 4. 엄밀한 정의와 작동 원리

### 채점자 일치도: 코헨의 카파

두 채점자(사람, LLM)가 같은 문항에 합격/불합격을 매겼을 때, 관찰된 일치율 $p_o$와 우연히 일치할 확률 $p_e$로

$$
\kappa = \frac{p_o - p_e}{1 - p_e}
$$

$p_e = p_{J} p_{H} + (1 - p_{J})(1 - p_{H})$($p_J$, $p_H$: 각 채점자의 합격 비율). 단순 일치율은 "대부분 합격"인 데이터에서 저절로 높아지므로, 우연 일치를 뺀 카파를 본다. 대략 0.6 이상이면 상당한 일치로 보는 관례가 있지만 기준은 용도에 따라 정한다.

### 위치 편향 확인

두 답 A, B를 비교하게 할 때 (A, B) 순서와 (B, A) 순서로 두 번 물어, 두 번 모두 같은 답을 고른 비율(순서 일관성)을 잰다. 일관되지 않은 쌍은 "무승부"로 처리하거나 사람에게 넘긴다.

### 짝지은 비교: 맥니마 검정

같은 문항에서 버전 A, B의 합격 여부를 짝지으면, 결과가 갈린 문항 수만 중요하다: $b$ = A만 합격, $c$ = B만 합격.

$$
\chi^2 = \frac{(|b - c| - 1)^2}{b + c} \quad (\text{자유도 } 1)
$$

$b + c$가 작으면 이항분포로 정확한 p-value를 구한다(STAT-INF-002).

### 근거 충실도

답변을 주장 단위로 나누고, 각 주장이 제공된 자료로 뒷받침되는지 판정한 비율:

$$
\text{충실도} = \frac{\text{근거가 있는 주장 수}}{\text{전체 주장 수}}
$$

RAGAS 같은 도구는 이 판정에 LLM을 쓰므로, 판정 LLM 자체의 정확도도 표본으로 확인해야 한다.

## 5. 수식 및 기호 설명

| 기호 | 뜻 |
|---|---|
| $p_o$ | 두 채점자의 관찰 일치율 |
| $p_e$ | 우연히 일치할 확률 |
| $\kappa$ | 코헨의 카파(우연 보정 일치도) |
| $b$, $c$ | 짝지은 비교에서 결과가 갈린 문항 수 |
| $\chi^2$ | 맥니마 검정 통계량 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. LLM 채점자 검증 (설명용 숫자)

100문항을 사람과 LLM이 각각 합격/불합격으로 채점:

| | 사람 합격 | 사람 불합격 |
|---|---|---|
| LLM 합격 | 60 | 10 |
| LLM 불합격 | 8 | 22 |

- 관찰 일치율 $p_o = (60 + 22)/100 = 0.82$
- LLM 합격 비율 0.70, 사람 합격 비율 0.68 → $p_e = 0.70 \times 0.68 + 0.30 \times 0.32 = 0.476 + 0.096 = 0.572$
- $\kappa = (0.82 - 0.572)/(1 - 0.572) \approx 0.58$

일치율 82%는 높아 보이지만, 우연 일치를 빼면 카파 0.58로 "중간~상당" 수준이다. LLM이 합격시켰는데 사람이 불합격시킨 10건을 읽어 채점 기준을 고친 뒤 다시 잰다.

### 예제 2. 프롬프트 두 버전 비교

같은 80문항에서:

| | B 합격 | B 불합격 |
|---|---|---|
| A 합격 | 50 | 4 |
| A 불합격 | 12 | 14 |

A 합격률 $54/80 = 67.5\%$, B 합격률 $62/80 = 77.5\%$. 결과가 갈린 문항: $b = 4$(A만), $c = 12$(B만).

- 맥니마 $\chi^2 = (|4 - 12| - 1)^2 / 16 = 49/16 \approx 3.06$, p ≈ 0.08
- 정확한 이항 검정(16건 중 4건 이하, 양측): p ≈ 0.077

10%p 개선은 실무적으로 의미 있어 보이지만, 이 표본으로는 5% 기준에서 우연을 배제하기 어렵다. 문항을 늘리거나, B만 합격한 12건과 A만 합격한 4건을 읽어 차이의 성격을 확인한다.

### 예제 3. RAG 답변 평가표 (DeepVi형 질문, 설명용)

| 질문 | 기대 근거 | 검색에 포함? | 답의 주장 | 근거 있음 | 판정 |
|---|---|---|---|---|---|
| 최근 이 기업의 주요 이슈는? | 최근 뉴스 3건 | 3/3 | 4개 | 4/4 | 통과 |
| 지난 분기 영업이익은? | 재무 API 값 | API 응답 포함 | 1개 | 1/1 | 통과 |
| 경쟁사 대비 강점은? | (자료에 없음) | — | 2개 | 0/2 | **실패: 근거 없는 주장** |

세 번째 같은 "자료에 답이 없는 질문"이 평가 세트에 꼭 있어야 한다. 기대 행동은 "제공된 자료로는 답할 수 없음"이다. DeepVi는 질문이 기업 분석 화면 안에서만 가능하고 뉴스 답변에 출처를 붙였다(저장소 기재). 이런 평가표를 만들었다는 기록은 없다.

## 7. 시각화와 해석

버전별 평가 결과는 축(정확성, 충실도, 형식, 안전, 지연)마다 막대를 나란히 그리고 신뢰구간을 표시한다. 한 축이 좋아지고 다른 축이 나빠지는 맞교환(예: 답이 길어져 정확성은 오르고 지연·비용은 증가)이 한눈에 보인다. 문항별로 "이전 통과 → 이번 실패"인 사례 목록을 함께 두면 회귀를 바로 찾는다.

## 8. 기술 비교 및 선택 기준

| 채점 방식 | 장점 | 단점 | 적합 |
|---|---|---|---|
| 자동 대조(정답, 스키마, 테스트) | 빠르고 정확, 재현 가능 | 정답이 정해진 경우만 | 추출, 분류, 형식, 코드 |
| 단어 겹침 지표 | 싸다 | 의미 반영 약함 | 참고용 |
| 임베딩 유사도 | 의미를 어느 정도 반영 | 사실 오류에 둔감 | 의미 보존 대략 확인(STT 의미 지표) |
| LLM 채점 | 대량, 기준표 적용 가능 | 편향, 비용, 검증 필요 | 요약·설명 품질, 충실도 |
| 사람 채점 | 가장 신뢰 | 느리고 비쌈 | 기준 설정, 채점자 검증, 표본 감사 |

**조합 원칙:** 자동으로 잴 수 있는 것은 자동으로, 나머지는 LLM 채점 + 사람 표본 감사. 사람 라벨 일부로 LLM 채점자를 주기적으로 재검증한다.

## 9. 실무 사례

- **배포 전 게이트:** 프롬프트·모델 변경 PR마다 평가 세트를 돌려, 주요 지표가 기준 아래로 떨어지면 병합을 막는다(SE-TEST-001).
- **모델 교체:** 더 싼 모델로 바꿀 때 같은 평가 세트로 품질 손실을 재고, 비용 절감과 맞교환을 판단한다.
- **운영 감시:** 실제 질문을 매주 일부 뽑아 채점해 품질 변화(데이터 변화, 외부 API 모델 업데이트)를 감시한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **DeepVi — 근거 기반 확인:** 테스트용 프롬프트로 답이 보유 데이터를 근거로 나오는지 확인(정량 지표 없음). RetrievalQA는 출처 문서를 반환하도록(return_source_documents=True) 설정되어 있어, 예제 3처럼 "답의 주장이 반환된 문서에 있는가"를 자동·반자동으로 채점할 기반이 이미 있었다.
- **STT — 같은 조건 비교와 보완 지표:** 6,000개 고정 데이터·같은 정규화·같은 지표로 4종 비교, WER·CER에 의미 지표 추가. SemWER@0.85의 0.85를 고른 이유가 기재되어 있지 않은데, 사람이 "의미 보존됨/아님"을 라벨링한 표본과의 일치도(카파)로 임계값을 정당화할 수 있다.
- **STT — 로컬 LLM 기준표:** 스키마 유지·요약 품질·처리 시간·실패 대응. 이 네 축을 평가 세트와 함께 수치화하면(스키마 통과율, 품질 점수, p95 지연, 실패 처리율) 운영 전환 판단의 근거가 된다(운영 전환은 하지 않음).
- **이 학습 사이트 — 자동 검증 + 사람 피드백:** 형식·출처·수식 문법은 자동 검증하고, 사실 오류(예: DeepVi RAG 설명)는 사용자 지적으로 고쳤다. 자동 채점이 못 잡는 영역을 사람 검토가 메우는 구조다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 몇 개 써 보고 좋아졌으면 개선이다.** 고정 평가 세트와 짝지은 비교 없이는 우연과 구별이 안 된다(예제 2).
- **오해: LLM 채점이면 객관적이다.** 위치·길이·자기 선호 편향이 있다. 사람과의 일치도로 검증한다.
- **평가 세트 과적합:** 같은 세트로 계속 고치면 그 세트에만 맞춰진다. 숨겨 둔 세트와 새 실제 질문으로 확인한다.
- **지표 하나로 최적화:** 충실도만 높이면 "자료에 없어 답할 수 없음"만 반복하는 쓸모없는 시스템이 될 수 있다. 여러 축을 함께 본다.
- **외부 모델 변화:** API 모델이 업데이트되면 같은 프롬프트도 결과가 바뀐다. 정기 재평가가 필요하다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 두 채점자의 일치율이 90%인데 카파가 0.2로 낮게 나올 수 있는 이유는?</summary>

**정답.** 거의 모든 문항이 합격인 데이터에서는 두 채점자가 아무렇게나 "합격"을 매겨도 우연히 많이 일치한다. 카파는 이 우연 일치를 빼므로, 실제로 판별력이 있는 일치는 적다는 뜻이다.

**해설.** 불균형 데이터에서 정확도가 속이는 것과 같은 원리다(AI-EVAL-001).

</details>

<details class="qa" data-type="concept"><summary>Q2. 짝지은 비교에서 두 버전이 모두 합격하거나 모두 불합격한 문항은 왜 검정에 쓰이지 않는가?</summary>

**정답.** 두 버전의 차이에 대한 정보가 없기 때문이다. 차이는 결과가 갈린 문항(A만 합격, B만 합격)에서만 드러난다.

**해설.** 맥니마 검정은 갈린 문항 수 $b$, $c$만으로 계산한다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 팀이 RAG 챗봇 품질을 LLM 채점자 하나로만 재고 있고, 점수가 계속 오른다. 무엇을 점검하겠는가?</summary>

**정답.** 사람 라벨 표본으로 LLM 채점자의 일치도를 확인하고, 길이 편향(답이 길어져서 점수가 오르는지), 평가 세트 과적합(숨긴 세트·실제 질문에서도 오르는지), 채점 프롬프트 변경 이력을 점검한다. 자동으로 잴 수 있는 지표(검색 recall, 스키마 통과율)도 함께 본다.

**해설.** 측정 도구가 틀리면 개선처럼 보이는 착시가 생긴다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 기업 분석 Q&A의 평가 세트를 처음 만든다면 어떻게 구성하겠는가?</summary>

**정답.** 실제 질문 로그나 예상 질문에서 유형별(뉴스, 재무 수치, 거시, 일반)로 고르게 뽑고, 자료에 답이 없는 질문, 숫자 정확성이 중요한 질문, 과거 실패 사례를 포함한다. 각 문항에 기대 근거(문서·API 값)와 반드시 포함할 사실, 하면 안 되는 말(투자 권유 등)을 적는다. 일부는 숨겨 두고, 버전 관리한다.

**해설.** 정답 문장 대신 "기대 근거와 필수 사실"로 정의하면 생성형 답도 일관되게 채점할 수 있다.

</details>
