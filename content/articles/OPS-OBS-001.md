## 0. 한눈에 보기 (입문)

### 한 줄 요약
**모니터링**은 "시스템이 지금 괜찮은가"를 숫자로 지켜보는 것이고, **관측성**은 문제가 생겼을 때 "왜 그런가"를 로그·지표·추적으로 거슬러 찾을 수 있는 능력이다. 가장 위험한 장애는 에러가 아니라 **아무도 모르게 틀린 결과가 쌓이는 조용한 실패**다.

### 쉬운 설명
자동차 계기판을 떠올리자.

- **지표(metrics):** 속도계, 연료계, 엔진 온도. 숫자 몇 개로 지금 상태를 한눈에.
- **로그(logs):** 블랙박스 기록. "몇 시 몇 분에 무엇이 일어났나"의 상세한 사건 기록.
- **추적(traces):** 내비게이션 경로 기록. 요청 하나가 어떤 길(서비스, DB, 외부 API)을 거쳐 어디서 오래 걸렸나.
- **알림(alerts):** 경고등. 사람이 계기판을 계속 보지 않아도 문제가 생기면 알려 준다.

경고등이 너무 자주 켜지면(헛경보) 운전자는 무시하게 된다. 그래서 "정말 행동이 필요할 때만" 울리게 기준을 정하는 것이 중요하다.

### 내 프로젝트에서는
- **이 학습 사이트는 실행 기록을 남긴다.** 매일 예약 실행이 끝나면 `content/runs/<날짜시각>.json`에 시작·종료 시각, 상태(success/skipped/failed), 만든 설명집, 오류, 메모를 기록하고, 학습 설정 화면에 최근 실행이 표시된다. 같은 날 성공 기록이 있으면 새로 쓰지 않는 **중복 방지**에도 이 기록을 쓴다(AUTOMATION.md).
- **Preflight는 "조용한 실패"를 찾는 장치를 여럿 두었다.** 표·칸·계산식 대장을 실제 DB와 칸 단위로 대조해, 스키마 파서가 일부 문법을 못 읽어 **한 달간 18개 칸이 대장에서 빠져 있던** 문제를 발견했다. 실제 DB 점검 64개도 둔다(포트폴리오 기재). 에러가 나지 않는 문제를 찾는 것이 관측성의 핵심이다.
- **STT 평가도 결과 이상을 보고 원인을 찾았다.** Riva Offline 평가에서 출력이 중간에 잘리는 문제를 확인해 Streaming 방식으로 평가 파이프라인을 바꿨다(포트폴리오 기재). 지표(WER)가 이상할 때 원문(로그)을 확인하는 습관의 사례다.

### 먼저 알면 좋은 것
- 배포와 환경 분리(OPS-DEPLOY-001): 운영 환경, 가용성 숫자
- 통계적 공정관리(STAT-SPC-001): 평소 흔들림과 특별한 변화의 구분

## 1. 핵심 요약

- **세 신호:** 지표(숫자 시계열, 싸고 집계 쉬움), 로그(사건 기록, 자세하지만 많음), 추적(요청 경로별 소요 시간).
- **네 가지 황금 신호(SRE):** 지연 시간, 트래픽, 오류, 포화도(자원이 얼마나 찼나).
- **평균의 함정:** 응답 시간은 소수의 아주 느린 요청이 평균을 끌어올린다. p50(중앙값), p95, p99를 본다.
- **SLO와 오류 예산:** "요청의 99.9%가 성공" 같은 목표를 정하면, 남는 0.1%가 쓸 수 있는 실패 예산이다. 예산이 빨리 줄면 알림.
- **조용한 실패 감시:** 처리 건수, 데이터 신선도, 원천과 결과의 대사, 결과 분포 변화.
- **좋은 알림:** 사람이 행동해야 할 때만, 무엇을 할지 알 수 있게. 원인보다 **증상**(사용자 영향) 기준으로.

## 2. 개념과 등장 배경

초기 서버 운영은 로그 파일을 사람이 읽고, CPU·디스크 사용률 같은 자원 지표를 그래프로 보는 수준이었다(1990년대 MRTG, 2000년대 Nagios 등). 서비스가 여러 서버·여러 서비스로 쪼개지면서 "어느 부분이 느린가"를 찾기 어려워졌고, 2010년 구글의 Dapper 논문이 요청 하나를 여러 서비스에 걸쳐 따라가는 **분산 추적**을 소개했다.

2016년 구글의 『Site Reliability Engineering』은 서비스 수준 목표(SLO), 오류 예산, 네 가지 황금 신호를 정리해 운영의 공통 언어를 만들었다. 2010년대 후반에는 "미리 정한 질문(대시보드)에 답하는 모니터링"을 넘어 "예상하지 못한 질문에도 답할 수 있게 풍부한 데이터를 남기자"는 **관측성** 개념이 퍼졌고, 로그·지표·추적의 표준 수집 방식(OpenTelemetry)도 자리 잡았다.

## 3. 직관적 설명 및 기초 이론

### 세 신호 비교

| | 지표 | 로그 | 추적 |
|---|---|---|---|
| 형태 | 시각별 숫자 | 사건별 텍스트·구조화 기록 | 요청별 단계 소요 시간 트리 |
| 질문 | "얼마나, 추세는?" | "정확히 무슨 일이?" | "어디서 오래 걸렸나?" |
| 비용 | 낮음 | 높음(양이 많음) | 중간(표본 추출 흔함) |
| 예 | 분당 요청 수, 오류율, p95 지연 | 업로드 실패 사유, 예외 스택 | API → DB → LLM 호출별 시간 |

### 구조화된 로그

```json
{"time": "2026-11-25T05:49:01+09:00", "level": "info", "event": "upload_applied",
 "upload_id": 1043, "rows": 1220, "rejected": 12, "review": 3, "duration_ms": 2140}
```

문장 대신 키-값으로 남기면 "rejected가 평소보다 많은 업로드"를 바로 검색·집계할 수 있다. 비밀번호·개인정보는 로그에 남기지 않는다. (예시는 설명용이며 Preflight의 실제 로그 형식이 아니다.)

## 4. 엄밀한 정의와 작동 원리

### 백분위수

응답 시간을 작은 순으로 정렬했을 때 $p$% 지점의 값이 $p$번째 백분위수다. p95 = 200ms는 "요청의 95%가 200ms 이하"라는 뜻이다. 평균은 극단값에 끌려가지만 중앙값은 그렇지 않다(STAT-BASE-001).

### SLI, SLO, 오류 예산

- **SLI**(지표): 성공한 요청 비율, 300ms 안에 응답한 비율 등
- **SLO**(목표): "30일 동안 SLI ≥ 99.9%"
- **오류 예산:** $(1 - \text{SLO}) \times \text{전체 요청}$. 이 범위의 실패는 허용하고, 그 안에서 배포·실험을 한다.

**소진 속도**(burn rate) $=$ 실제 오류율 ÷ 허용 오류율. 1이면 기간이 끝날 때 딱 예산을 다 쓰는 속도, 10이면 10배 빠르게 쓰는 중이다. 소진 속도가 높은 상태가 지속될 때 알림을 보내면, 순간적인 흔들림에는 울리지 않고 진짜 문제에는 빨리 울린다.

### 조용한 실패를 잡는 검사

| 검사 | 질문 |
|---|---|
| 건수 | 오늘 처리 건수가 평소 범위인가(관리도, STAT-SPC-001) |
| 신선도 | 가장 최근 데이터 시각이 기대보다 오래되지 않았나 |
| 대사 | 원천 행 수 = 적재 + 거부 + 중복 제거인가(DE-PIPE-001) |
| 분포 | 결과 값 분포(예: 검토 대기 비율, 모델 출력 길이)가 급변하지 않았나 |
| 하트비트 | 정기 작업이 정해진 시각에 실행 기록을 남겼나 |

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| p50, p95, p99 | 50·95·99번째 백분위수 |
| SLI / SLO | 서비스 수준 지표 / 목표 |
| 오류 예산 | 목표 기간 동안 허용되는 실패 양 |
| burn rate | 오류 예산을 쓰는 속도(실제 ÷ 허용 오류율) |
| 포화도 | 자원 사용률(CPU, 메모리, 연결 수, 대기열 길이) |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 평균이 속이는 경우

응답 시간 10건(ms): 100, 110, 105, 120, 98, 102, 115, 108, **2000**, 111

- 평균: $2969 / 10 = 296.9$ms
- 중앙값(p50): 정렬하면 가운데 두 값 108과 110의 평균 109ms
- p90(최근접 순위): 정렬 후 9번째 값 120ms
- p95: 10건 중 $\lceil 9.5 \rceil = 10$번째 값 2000ms

평균 297ms는 대부분의 사용자(약 110ms)도, 느린 사용자(2초)도 대표하지 않는다. "보통은 빠르고 일부가 매우 느림"이라는 사실은 p50과 p95를 함께 볼 때 드러난다. 표본이 적으면 높은 백분위수는 값 하나에 좌우된다는 점도 함께 기억한다.

### 예제 2. 오류 예산

SLO 99.9%, 30일 동안 요청 100만 건 예상 → 오류 예산 $= 0.001 \times 1{,}000{,}000 = 1{,}000$건.

- 하루 평균 요청 약 33,333건, 허용 오류율 0.1%
- 어느 날 1시간 동안 오류율이 2%라면 소진 속도 $= 2\% / 0.1\% = 20$배. 그 시간의 요청이 약 1,389건이면 오류 약 28건 → 하루 동안 이 속도가 이어지면 약 667건으로 한 달 예산의 3분의 2를 하루에 쓴다 → 알림 대상
- 오류율 0.15%가 잠깐 나타나는 것(소진 속도 1.5)은 바로 깨울 일은 아니다

### 예제 3. 예약 실행 감시

이 학습 사이트의 매일 실행에 감시를 붙인다면:

| 신호 | 기준 | 판단 |
|---|---|---|
| 하트비트 | 06:30까지 오늘 날짜 실행 기록이 없음 | 실행 자체가 안 됨(예약·권한 문제) |
| 상태 | status = failed | 원인을 errors에서 확인 |
| 결과 | success인데 created 0개이고 skipped 사유 없음 | 조용한 실패 |
| 소요 시간 | 평소 4~6분인데 30분 | 무한 재시도, 네트워크 문제 의심 |

실제 실행 기록에는 시작·종료 시각, 상태, 생성·건너뜀·오류 목록이 있다. 위 기준은 그 기록으로 만들 수 있는 알림 설계 예시다(현재 자동 알림은 구성되어 있지 않다).

## 7. 시각화와 해석

대시보드 한 화면에 네 가지 황금 신호(요청 수, 오류율, p50·p95 지연, 자원 사용률)를 같은 시간축으로 놓으면, "요청이 늘자 p95가 튀고 오류가 따라 오른다" 같은 인과의 단서가 보인다. 배포 시각을 세로선으로 표시해 두면 배포가 원인인지 바로 판단할 수 있다. 일별 처리 건수는 관리도(STAT-SPC-001)로 그려 평소 흔들림과 이상을 구분한다.

## 8. 기술 비교 및 선택 기준

| 규모 | 권장 |
|---|---|
| 사내 도구, 서버 1~2대 | 구조화 로그 파일 + 일별 점검 스크립트 + 핵심 지표 몇 개 + 실패 시 메일·메신저 알림 |
| 여러 서비스 | 지표 수집·대시보드 + 중앙 로그 검색 + 분산 추적 |
| 데이터 파이프라인 | 실행 기록, 건수·신선도·대사 검사, 실패 알림 |
| LLM 기능 | 요청별 토큰 수·지연·비용, 검증 실패율, 표본 출력 검토 |

**알림 원칙:** ① 증상 기준(사용자 영향), ② 행동 가능(무엇을 할지 문서 연결), ③ 헛경보가 많으면 기준을 고친다(AI-EVAL-001의 정밀도).

## 9. 실무 사례

- **느린 쿼리 찾기:** PostgreSQL의 `log_min_duration_statement`를 250ms로 두면 250ms 이상 걸린 SQL이 모두 로그에 남는다(공식 문서 예시). 느린 화면의 원인을 쿼리 단위로 찾는다.
- **LLM 비용 감시:** 하루 토큰 사용량이 평소의 3배가 되면 반복 호출 버그나 루프에 빠진 에이전트를 의심한다(AI-AGENT-001).
- **사후 분석:** 장애 후 시간순 로그로 무슨 일이 있었는지 재구성하고, 비난 없이 원인과 재발 방지책을 문서로 남긴다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 기록에서 옮긴 것이다.

- **이 학습 사이트 — 실행 기록:** `content/runs/*.json`(시작·종료, 상태, created·skipped·errors, notes)을 남기고 화면에 표시하며 중복 실행 방지에 쓴다. 예제 3처럼 하트비트·결과 기준 알림을 붙일 수 있다.
- **Preflight — 대장 대조와 DB 점검:** 대장을 실제 DB와 칸 단위로 대조해 18개 칸 누락을 찾았고, 실제 DB 점검 64개를 둔다. 결과물 자체를 검사해 조용한 실패를 잡는 관측성의 좋은 사례다. 점검 질문: 이 점검을 정기적으로 자동 실행하고 실패 시 알림을 보내는가?
- **Preflight — 검토 대기열:** 위험한 변경만 검토로 보낸다. 하루 검토 건수와 승인 비율을 지표로 보면 규칙의 정밀도 변화나 ERP 쪽 이상(갑자기 검토가 폭증)을 일찍 알 수 있다(적용 아이디어).
- **STT — 지표 이상에서 원인으로:** Riva Offline 출력 잘림 발견 → Streaming 평가로 변경. 지표만 보지 않고 원문을 확인한 것이 핵심이었다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 에러가 없으면 정상이다.** 조용한 실패(0건 처리, 잘린 출력, 오래된 데이터)는 에러를 내지 않는다.
- **오해: 다 기록하면 된다.** 로그가 너무 많으면 비용이 커지고 정작 중요한 것을 못 찾는다. 개인정보가 섞이면 사고가 된다.
- **오해: 알림은 많을수록 안전하다.** 헛경보가 많으면 사람이 무시해 진짜 경보도 놓친다.
- **평균 지표:** 응답 시간은 백분위수로, 오류는 비율과 절대 건수로 함께 본다.
- **측정의 영향:** 지나친 계측은 그 자체로 성능을 떨어뜨린다. 추적은 표본 추출을 쓴다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 네 가지 황금 신호는 무엇인가?</summary>

**정답.** 지연 시간, 트래픽, 오류, 포화도.

**해설.** 구글 SRE 책이 사용자에게 보이는 시스템의 기본 감시 대상으로 제시한 것이다.

</details>

<details class="qa" data-type="concept"><summary>Q2. SLO 99.5%, 한 달 요청 20만 건이면 오류 예산은 몇 건인가?</summary>

**정답.** $0.005 \times 200{,}000 = 1{,}000$건.

**해설.** 이 범위 안의 실패는 목표 위반이 아니다. 예산을 쓰는 속도가 빠르면 알림을 보낸다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. CPU 사용률 80% 초과 시 알림이 하루에 열 번씩 울리는데 실제 문제는 거의 없다. 어떻게 바꾸겠는가?</summary>

**정답.** 원인 지표(CPU) 대신 사용자 증상(오류율, p95 지연, SLO 소진 속도) 기준으로 알림을 바꾸고, CPU는 대시보드에서 참고 지표로 둔다. 알림에는 대응 절차를 연결한다.

**해설.** CPU가 높아도 사용자가 괜찮으면 행동할 필요가 없다. 헛경보는 진짜 경보를 무디게 한다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 매일 새벽 ERP 파일을 받아 적재하는 작업에 어떤 감시를 붙이겠는가?</summary>

**정답.** ① 하트비트: 정해진 시각까지 실행 기록이 없으면 알림, ② 실패: 종료 코드·예외 시 알림, ③ 결과: 적재 행 수가 관리 한계를 벗어나면 경고, ④ 대사: 원천 = 적재 + 거부 + 중복 제거가 맞지 않으면 경고, ⑤ 신선도: 파일 기준 시각이 예상보다 오래되면 경고. 실행마다 구조화된 기록을 남긴다.

**해설.** Preflight의 파일 지문 확인(같은 파일·더 오래된 파일은 멈춤)도 신선도 검사의 한 형태다.

</details>
