## 0. 한눈에 보기 (입문)

### 한 줄 요약
**대기행렬 이론**은 "일이 들어오는 속도"와 "처리하는 속도"로 줄이 얼마나 길어지고 얼마나 기다리는지를 계산하는 방법이다. 핵심 교훈 두 가지: 쌓인 일 = 들어오는 속도 × 머무는 시간(**리틀의 법칙**), 그리고 처리 능력을 거의 다 쓰면 **기다리는 시간이 폭발적으로** 늘어난다.

### 쉬운 설명
은행 창구를 떠올려 보자. 손님이 한 시간에 8명 오고, 직원은 한 시간에 10명을 처리할 수 있다. 직원이 손님보다 빠르니 줄이 없을 것 같지만, 실제로는 줄이 생긴다. 손님이 고르게 오지 않고 몰려서 오기도 하고, 어떤 손님은 오래 걸리기 때문이다.

이때 직원이 바쁜 비율(**이용률**)은 8 ÷ 10 = 80%다. 놀라운 점은 이용률을 조금만 올려도 대기가 크게 늘어난다는 것이다(6절 예제 2).

| 이용률 | 평균 머무는 시간(이 예의 조건) |
|---|---|
| 50% | 12분 |
| 80% | 30분 |
| 90% | 60분 |
| 95% | 120분 |

그래서 "직원(서버, 작업자)이 놀지 않게 100% 가깝게 돌리자"는 생각은 대기 시간을 망친다. 여유가 있어야 갑자기 몰릴 때 버틴다.

**리틀의 법칙**은 더 단순하다. 하루에 일이 20건 들어오고 각 건이 평균 3일 머문다면, 언제 봐도 평균 60건이 쌓여 있다. 셋 중 둘을 알면 나머지 하나를 안다.

### 내 프로젝트에서는
- **Preflight — 검토 대기열:** 위험한 변경만 **검토 대기열**로 보내고, 운영 첫 업로드에서 검토 건이 몰리는 문제를 겪어 일괄 처리와 변경 상세를 다음 개선으로 정했다(포트폴리오 기재). 검토자(처리하는 사람)는 그대로인데 한 번에 많은 건이 도착한 **몰림**이다. 일괄 처리는 한 건당 처리 시간을 줄여 처리율 $\mu$를 높이는 대책이다(6절 예제 4, 10절).
- **STT 평가 — RTF:** RTF는 음성 길이 대비 처리 시간이다(포트폴리오 기재: NeMo Conformer CTC 0.0216, Riva Streaming 0.0566). RTF가 1보다 작으면 들어오는 음성보다 빨리 처리한다는 뜻으로, 이용률과 같은 개념이다. 다만 실시간 서비스의 대기는 평균 RTF만으로 정해지지 않고 요청이 몰리는 정도와 동시 처리 수에 달려 있다. 포트폴리오에도 "스트리밍 응답 지연은 추가 검증 필요"로 남아 있다.
- **DeepVi:** 매일 기업 뉴스를 수집해 벡터로 저장했다(저장소 기재). 수집 작업량과 처리 시간 기록은 없다.

### 먼저 알면 좋은 것
- 확률, 조건부확률, 확률분포(STAT-PROB-001): 평균과 무작위로 일어나는 사건
- 메시지 큐와 비동기 작업(SE-QUEUE-001): 소프트웨어의 대기열

## 1. 핵심 요약

- **기본 양:** 도착률 $\lambda$(단위 시간당 도착 수), 처리율 $\mu$(작업자 1명이 단위 시간에 처리할 수 있는 수), 이용률 $\rho = \lambda / (c\mu)$($c$는 작업자 수).
- **안정 조건:** $\rho < 1$. 아니면 줄이 끝없이 길어진다.
- **리틀의 법칙:** $L = \lambda W$. 분포와 상관없이 안정된 시스템이면 성립한다.
- **M/M/1(무작위 도착·무작위 처리·작업자 1명):** $W = \dfrac{1}{\mu - \lambda}$, $L = \dfrac{\rho}{1 - \rho}$. 이용률이 1에 가까워지면 급격히 커진다.
- **변동이 대기를 만든다:** 도착이나 처리 시간이 들쭉날쭉할수록 같은 이용률에서 대기가 길다.
- **줄 합치기:** 작업자마다 따로 줄을 서는 것보다 한 줄로 합쳐 여럿이 나눠 처리하는 편이 대기가 훨씬 짧다.

## 2. 개념과 등장 배경

1909년 덴마크 전화회사의 엔지니어 아그너 크라루프 얼랑(Agner Krarup Erlang)이 "전화 교환원과 회선을 몇 개 두어야 통화 대기가 적당할까"를 계산하면서 대기행렬 이론이 시작되었다. 지금도 콜센터 인력 계산에 쓰는 **얼랑 C 공식**에 이름이 남아 있다. 1953년 켄들(Kendall)은 대기 시스템을 "도착 분포/처리 분포/작업자 수"로 적는 표기법(M/M/1 등)을 만들었다.

1961년 존 리틀(John Little)이 $L = \lambda W$를 일반적으로 증명했다. 이후 대기행렬 이론은 공장 생산 라인, 병원 응급실, 컴퓨터 네트워크, 서버·데이터베이스 성능 설계의 기초가 되었다.

## 3. 직관적 설명 및 기초 이론

### 리틀의 법칙은 왜 항상 성립할까

물탱크로 생각하자. 물이 분당 $\lambda$리터 들어오고, 물 한 방울이 탱크에 평균 $W$분 머문다면, 탱크 안의 물은 평균 $\lambda \times W$리터다. 들어오는 방식이나 나가는 순서와 상관없이, 오래 관찰하면 들어온 양과 머문 시간의 곱이 쌓인 양과 같아진다. 그래서 어떤 분포를 가정하지 않아도 쓸 수 있는 강력한 법칙이다.

### 왜 이용률이 높으면 대기가 폭발하나

이용률 80%면 작업자가 쉬는 시간이 20%다. 몰림이 생기면 그 20%의 여유로 밀린 일을 따라잡아야 한다. 이용률 95%면 여유가 5%밖에 없어, 한 번 밀린 줄을 따라잡는 데 4배 더 오래 걸린다. 여유가 줄어드는 속도보다 대기가 늘어나는 속도가 훨씬 빠르다. 공식의 $1/(1 - \rho)$가 이 성질을 보여 준다.

## 4. 엄밀한 정의와 작동 원리

### 켄들 표기

A/S/c: 도착 시간 간격 분포 / 처리 시간 분포 / 작업자 수. M은 지수분포(기억 없음, 무작위 도착 = 포아송 과정), D는 일정한 값, G는 일반 분포.

### 리틀의 법칙

안정 상태에서 시스템 안 평균 개수 $L$, 도착률 $\lambda$, 평균 체류 시간 $W$에 대해

$$
L = \lambda W, \qquad L_q = \lambda W_q
$$

$L_q$, $W_q$는 처리 중인 것을 뺀 "줄에서 기다리는" 개수와 시간이다.

### M/M/1

$\rho = \lambda / \mu < 1$일 때

$$
L = \frac{\rho}{1 - \rho},\qquad W = \frac{1}{\mu - \lambda},\qquad W_q = \frac{\rho}{\mu - \lambda},\qquad P(\text{기다림}) = \rho
$$

$W = W_q + 1/\mu$(기다린 시간 + 처리 시간)이고, $L = \lambda W$로 리틀의 법칙과 맞는다.

### 변동의 영향 (M/G/1)

처리 시간 분포가 일반적이면 폴라체크-힌친 공식으로

$$
W_q = \frac{\rho}{1 - \rho}\cdot\frac{1 + C_s^2}{2}\cdot\frac{1}{\mu}
$$

$C_s$는 처리 시간의 변동계수(표준편차 ÷ 평균). 처리 시간이 일정하면($C_s = 0$) 지수분포($C_s = 1$)보다 기다림이 절반이다. 처리 시간이 들쭉날쭉할수록 대기가 길어진다.

### M/M/c (작업자 여러 명, 한 줄)

얼랑 C 공식으로 기다릴 확률 $P_W$를 구하고 $W_q = P_W / (c\mu - \lambda)$다. 계산은 6절 예제 3에서 한다.

## 5. 수식 및 기호 설명

| 기호 | 읽기 | 뜻 |
|---|---|---|
| $\lambda$ | 람다 | 도착률(시간당 도착 수) |
| $\mu$ | 뮤 | 작업자 1명의 처리율 |
| $c$ | 씨 | 작업자(서버) 수 |
| $\rho$ | 로 | 이용률 $\lambda / (c\mu)$ |
| $L$, $L_q$ | 엘 | 시스템 안 / 줄에서 기다리는 평균 개수 |
| $W$, $W_q$ | 더블유 | 평균 체류 시간 / 평균 대기 시간 |
| $C_s$ | 변동계수 | 처리 시간의 표준편차 ÷ 평균 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 리틀의 법칙으로 거꾸로 계산하기

검토 대기열에 평균 45건이 쌓여 있고, 하루에 15건씩 들어온다. 한 건이 들어와서 처리될 때까지 평균 며칠 걸리나? $W = L / \lambda = 45 / 15 = 3$일. 대기 시간을 일일이 기록하지 않아도 쌓인 건수와 유입량만으로 알 수 있다.

### 예제 2. 이용률과 대기 시간 (M/M/1)

처리율 $\mu = 10$건/시간(한 건 평균 6분).

| $\lambda$ | $\rho$ | $W = 1/(\mu - \lambda)$ | $W_q$ | $L$ |
|---|---|---|---|---|
| 5 | 0.5 | 1/5시간 = **12분** | 6분 | 1 |
| 8 | 0.8 | 1/2시간 = **30분** | 24분 | 4 |
| 9 | 0.9 | 1시간 = **60분** | 54분 | 9 |
| 9.5 | 0.95 | 2시간 = **120분** | 114분 | 19 |

이용률을 0.8에서 0.95로 15%포인트 올렸을 뿐인데 머무는 시간은 4배가 된다. 50만 건을 무작위로 만들어 시뮬레이션해 보면 각각 약 11.9분, 29.5분, 58.6분, 117.2분으로 공식과 거의 같다.

### 직접 해보기

```runjs
// @title 이용률을 올리면 대기 시간은 얼마나 늘어날까 (M/M/1)
// @label 평균 머무는 시간(분)
// @param lam | 시간당 도착 건수 λ | 1 | 9.8 | 8 | 0.1
// @param mu | 시간당 처리 능력 μ | 5 | 20 | 10 | 1
// @expect lam=8, mu=10 => 30
// @expect lam=9, mu=10 => 60
// @expect lam=5, mu=10 => 12
if (lam >= mu) {
  log('도착이 처리 능력 이상입니다(이용률 ≥ 100%). 줄이 끝없이 길어집니다.');
  result('무한대');
} else {
  const rho = lam / mu;
  const W = 60 / (mu - lam);          // 분
  const Wq = 60 * rho / (mu - lam);   // 분
  const L = rho / (1 - rho);
  table([['이용률 ρ', (rho * 100).toFixed(1) + '%'], ['평균 대기(줄에서) Wq', Wq.toFixed(1) + '분'], ['평균 처리 시간 1/μ', (60 / mu).toFixed(1) + '분'], ['평균 머무는 시간 W', W.toFixed(1) + '분'], ['평균 시스템 안 건수 L = λW', L.toFixed(2)]], ['항목', '값']);
  const grid = [0.5, 0.7, 0.8, 0.9, 0.95];
  bars(grid.map((r) => `ρ=${r}`), grid.map((r) => Number((60 / (mu - r * mu)).toFixed(1))));
  result(Math.round(W * 100) / 100);
}
```

### 예제 3. 줄을 합치면 얼마나 줄까

시간당 8건이 들어오고, 작업자 2명이 각각 시간당 5건을 처리한다(이용률 80%).

- **따로 줄(작업자마다 4건씩 배정):** 각각 M/M/1, $\lambda = 4$, $\mu = 5$. $W = 1/(5 - 4) = 1$시간 = **60분**.
- **한 줄(누구든 먼저 끝난 사람이 다음 건):** M/M/2. $a = \lambda/\mu = 1.6$, 얼랑 C로 기다릴 확률 $P_W = 0.711$, $W_q = P_W / (c\mu - \lambda) = 0.711 / 2 = 0.356$시간 ≈ 21.3분, $W = 21.3 + 12 = $ **33.3분**.
- **빠른 작업자 1명(시간당 10건):** M/M/1, $W = 1/(10 - 8) = $ **30분**.

같은 인력과 같은 이용률인데 줄을 합치기만 해도 머무는 시간이 60분에서 33분으로 줄어든다. 따로 줄은 한 사람이 밀릴 때 옆 사람이 놀 수 있기 때문이다. 콜센터, 은행이 번호표 한 줄을 쓰는 이유다.

### 예제 4. 몰림(버스트)

평소 하루 20건이 들어오고 검토자가 하루 25건을 처리한다(이용률 80%). 그런데 첫날 300건이 한꺼번에 들어오면, 하루 여유 5건으로 밀린 300건을 해소하는 데 $300 / 5 = 60$일이 걸린다(그동안 새로 들어오는 건도 처리해야 하므로). 처리율을 하루 40건으로 높이면(일괄 처리 도입) 여유가 20건이 되어 $300 / 20 = 15$일로 줄어든다. 몰림이 예상되면 **처리율을 일시적으로 높이거나(일괄 처리, 인력 추가), 들어오는 양을 나누는(단계적 도입)** 것이 대책이다.

## 7. 시각화와 해석

가로축 이용률, 세로축 평균 대기 시간으로 그리면 0.7까지는 완만하다가 0.9를 넘으며 거의 수직으로 솟는 "하키 스틱" 곡선이 나온다. 운영 대시보드에서는 대기열 길이와 유입량, 처리량을 같은 시간축에 그린다. 유입이 처리를 넘는 구간에서 대기열이 쌓이고, 처리가 유입을 넘어야 줄어든다. 평균보다 **백분위수(p95, p99) 대기 시간**을 함께 그려야 일부 사용자가 겪는 긴 대기가 보인다(로깅·모니터링·관측성, OPS-OBS-001).

## 8. 기술 비교 및 선택 기준

| 대책 | 효과 | 비용·주의 |
|---|---|---|
| 작업자(서버, 워커) 추가 | $c$ 증가로 이용률 감소 | 비용. 공유 자원(DB)이 병목이면 효과 없음 |
| 한 건 처리 시간 단축 | $\mu$ 증가 | 일괄 처리, 캐시(CS-CACHE-001), 알고리즘 개선 |
| 줄 합치기(공유 대기열) | 같은 인력으로 대기 단축 | 작업자 간 능력 차이, 전문성 분리 필요 시 제약 |
| 처리 시간 변동 줄이기 | $C_s$ 감소로 대기 단축 | 큰 작업을 쪼개기, 표준화 |
| 우선순위 대기열 | 중요한 일의 대기 단축 | 낮은 우선순위는 더 오래 기다림(굶주림) |
| 유입 제한·분산 | 몰림 완화 | 요청 거절, 사용자 경험 영향 |

## 9. 실무 사례

- **서버 용량 계획:** CPU 이용률 목표를 70% 안팎으로 잡는 관행은 대기 시간 곡선에서 나온다. 100% 가까이 쓰면 응답 시간이 급격히 나빠진다.
- **메시지 큐와 워커:** 큐 길이(L)와 유입량(λ)으로 처리 지연(W)을 리틀의 법칙으로 추정하고, 워커 수를 정한다(메시지 큐와 비동기 작업, SE-QUEUE-001).
- **DB 연결 풀:** 연결 수가 작업자 수 $c$다. 쿼리 하나가 느려지면(처리 시간 증가) 이용률이 올라 대기가 폭발한다. 느린 쿼리 하나가 전체 장애로 번지는 이유다(B-Tree와 데이터베이스 인덱스, DE-DB-001).
- **LLM 추론 서버:** 요청을 묶어 처리하면(배칭) 처리량이 늘지만 각 요청이 묶음을 기다리는 시간이 생긴다. 처리량과 지연의 트레이드오프다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 첫 업로드의 검토 몰림:** 위험한 변경만 검토 대기열로 보내는 구조에서 운영 첫 업로드 때 검토 건이 몰렸고, 일괄 처리와 변경 상세를 다음 개선으로 정했다. 예제 4처럼 몰림은 평소 이용률이 낮아도 생긴다. 점검 질문: 하루 평균 유입 건수(λ)와 검토자가 하루에 처리하는 건수(μ)를 기록하는가? 두 숫자가 있으면 리틀의 법칙으로 평균 대기 일수를 바로 알 수 있고, 새 업무(샘플조달·시사출·CT)를 추가할 때 검토 인력이 버틸지 미리 계산할 수 있다.
- **Preflight — 판정 기준과 유입량:** "위험한 변경"의 기준이 넓으면 유입 λ가 늘어 대기가 길어지고, 좁으면 문제를 놓친다. 판정 기준 조정이 곧 대기열 용량 조정이다.
- **STT — RTF와 동시 처리:** RTF 0.0216은 1초 음성을 약 0.02초에 처리한다는 뜻으로, 처리 장치 하나가 평균적으로 실시간 음성 약 46개 분량을 감당할 수 있는 계산이 된다($1/0.0216$). 그러나 실제 동시 사용자 수는 요청 몰림과 지연 목표(p95)로 정해야 하며, 포트폴리오에도 스트리밍 응답 지연은 추가 검증이 필요하다고 남아 있다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 처리 능력이 유입보다 크면 대기가 없다.** 변동이 있으면 대기가 생기고, 이용률이 높을수록 급격히 길어진다.
- **오해: 작업자를 100% 바쁘게 하는 것이 효율적이다.** 작업자 효율과 대기 시간은 반대로 움직인다. 목표는 대기 시간과 인력 비용의 균형이다.
- **모형의 가정:** M/M/1은 무작위 도착과 지수분포 처리 시간을 가정한다. 실제 업무는 몰림이 더 심하거나 처리 시간이 더 들쭉날쭉해, 공식보다 대기가 길 수 있다. 공식은 감을 잡는 용도로 쓰고 실제 측정값으로 확인한다.
- **리틀의 법칙의 조건:** 장기적으로 안정된 상태(유입과 처리가 균형)에서 성립한다. 줄이 계속 길어지는 중이면 평균이 의미가 없다.
- **평균의 함정:** 평균 대기 시간이 괜찮아도 일부는 아주 오래 기다린다. 백분위수를 함께 본다.

<details class="qa" data-type="concept"><summary>Q1. M/M/1에서 시간당 12건이 도착하고 시간당 15건을 처리한다. 이용률, 평균 머무는 시간, 평균 시스템 안 건수는?</summary>

**정답.** $\rho = 12/15 = 0.8$, $W = 1/(15 - 12) = 1/3$시간 = 20분, $L = \lambda W = 12 \times 1/3 = 4$건.

**해설.** $L = \rho/(1-\rho) = 0.8/0.2 = 4$로도 확인된다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 같은 M/M/1에서 도착률을 그대로 두고 처리율을 15에서 16으로 올리면 평균 머무는 시간은 몇 분이 되는가?</summary>

**정답.** $W = 1/(16 - 12) = 1/4$시간 = 15분. 처리 능력을 약 7% 높였는데 대기는 20분에서 15분으로 25% 줄었다.

**해설.** 이용률이 높을 때는 작은 능력 증가도 큰 효과를 낸다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 팀장이 "검토자 한 명이 하루 25건 처리할 수 있으니, 하루 24건까지 들어와도 괜찮다"고 한다. 어떻게 답하겠는가?</summary>

**정답.** 이용률 96%가 되어 평균 대기가 매우 길어진다(M/M/1 근사로 머무는 시간이 $1/(25 - 24) = 1$일, 하루 20건일 때 0.2일의 5배). 유입이 몰리는 날에는 며칠씩 밀린다. 목표 대기 시간을 먼저 정하고, 그에 맞는 이용률(보통 70~80%)이 되도록 인력이나 처리 방식, 판정 기준을 조정하자고 제안한다.

**해설.** "평균적으로 감당 가능"과 "대기가 짧다"는 다르다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 매일 새벽 수집 작업이 메시지 큐에 작업 1,000건을 넣고, 워커 하나가 건당 평균 6초 걸린다. 1시간 안에 다 끝내려면 워커가 몇 개 필요한가? 고려할 점은?</summary>

**정답.** 총 작업 시간 1,000 × 6초 = 6,000초. 1시간(3,600초) 안에 끝내려면 최소 6,000 / 3,600 ≈ 1.67, 즉 2개다. 그러나 처리 시간 변동, 실패 재시도, 외부 API 속도 제한, DB 같은 공유 자원 병목을 고려해 여유를 두고(예: 3개) 큐 길이와 처리 시간을 모니터링한다. 워커를 늘려도 공유 자원이 병목이면 빨라지지 않는다.

**해설.** 한꺼번에 들어오는 일괄 작업은 몰림 그 자체다. 총량 ÷ 처리율로 최소치를 구하고 변동과 병목에 여유를 둔다.

</details>
