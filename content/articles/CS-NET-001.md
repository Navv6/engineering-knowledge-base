## 0. 한눈에 보기 (입문)

### 한 줄 요약
인터넷 통신은 **주소 찾기(DNS) → 연결(TCP) → 암호화(TLS) → 요청과 응답(HTTP)** 순서로 이루어진다. 웹 페이지, API 호출, LLM 호출, DB 연결이 모두 이 위에서 돈다.

### 쉬운 설명
택배를 보내는 과정에 빗대 보자.

1. **DNS(주소 찾기):** "삼성전자 본사"라는 이름만 알 때 실제 주소(IP 주소)를 찾는다. 전화번호부에서 이름으로 번호를 찾는 것과 같다.
2. **TCP(연결):** 상대에게 "보낼게요" → "받을게요" → "그럼 보냅니다" 인사를 주고받아 통로를 연다. 물건이 빠지면 다시 보내고, 순서가 섞이면 바로잡아 준다.
3. **TLS(암호화):** 중간에서 누가 상자를 열어 봐도 내용을 못 알아보게 잠근다. 주소창의 자물쇠, `https`의 `s`다.
4. **HTTP(요청과 응답):** "이 페이지 주세요"(요청) → "여기 있습니다, 200 OK"(응답).

통신이 느린 이유 대부분은 **거리**다. 서울에서 미국 서버까지 신호가 한 번 왕복하는 데 100ms 이상 걸리고, 처음 연결할 때는 이 왕복을 여러 번 한다.

### 내 프로젝트에서는
- **Preflight는 사내 서버에서 브라우저로 쓰는 웹 앱이다.** 클라우드 없이 사내 서버에서 운영한다(포트폴리오 기재). 엑셀을 브라우저에서 파싱하고 **파싱한 값만** 서버로 보낸다. 원본 파일은 네트워크로 나가지 않는다. 네트워크 경계를 설계로 활용한 예다.
- **DeepVi는 HTTP API의 연결이었다.** FastAPI로 DB를 조회하고, GPT-4o·Gemini Flash와 Pinecone 같은 외부 서비스를 HTTPS로 호출했다(포트폴리오·저장소 기재). 외부 API 호출 하나하나에 네트워크 왕복 시간이 더해진다.
- **이 학습 사이트도 네트워크 실패를 대비했다.** 3D 시각화용 three.js를 외부 CDN에서 불러오는데, E2E 시험에 "CDN 실패 시에도 본문은 정상이고 대체 문구가 뜬다"는 항목이 있다. 이 사이트를 만드는 환경에서는 허용되지 않은 외부 사이트로의 연결이 프록시에서 막혀, 일부 표준 문서는 URL 대신 서지 정보로 출처를 적었다.

### 먼저 알면 좋은 것
- 특별한 선행 지식은 필요 없다. 프로세스·스레드·동시성(CS-OS-001)을 읽었다면 서버가 여러 요청을 동시에 처리하는 부분이 더 쉽다.

## 1. 핵심 요약

- **계층:** 응용(HTTP) / 보안(TLS) / 전송(TCP, UDP) / 네트워크(IP) / 링크(이더넷, 와이파이). 위 계층은 아래 계층을 믿고 쓴다.
- **DNS:** 이름 → IP 주소. 결과는 일정 시간 캐시된다(TTL).
- **TCP:** 연결 수립(3방향 핸드셰이크), 순서 보장, 재전송, 흐름·혼잡 제어. **UDP:** 보장 없이 빠르게(실시간 음성·영상, DNS 조회).
- **TLS 1.3:** 새 연결의 핸드셰이크에 1번 왕복. 인증서로 서버 신원 확인.
- **HTTP:** 메서드(GET, POST, PUT, PATCH, DELETE) + 경로 + 헤더 + 본문 → 상태 코드 + 헤더 + 본문. 상태가 없는(stateless) 프로토콜이라 로그인 상태는 쿠키·토큰으로 유지.
- **응답 시간 ≈ 왕복 횟수 × RTT + 데이터 크기 ÷ 대역폭 + 서버 처리 시간.** 작은 요청은 RTT가, 큰 파일은 대역폭이 지배한다.

## 2. 개념과 등장 배경

1969년 미국 국방부의 ARPANET이 패킷 교환 네트워크로 시작했다. 1974년 빈트 서프(Vint Cerf)와 밥 칸(Bob Kahn)이 서로 다른 네트워크를 잇는 TCP/IP를 설계했고, 1983년 ARPANET이 TCP/IP로 전환하면서 오늘날 인터넷의 기반이 되었다. 같은 해 폴 모커페트리스(Paul Mockapetris)가 DNS를 설계했다.

1989~1991년 CERN의 팀 버너스리가 HTML, URL, HTTP를 만들어 월드와이드웹을 시작했다. HTTP는 HTTP/1.1(1997년 첫 표준), 한 연결에서 여러 요청을 동시에 주고받는 HTTP/2(2015), UDP 기반 QUIC 위의 HTTP/3(2022)로 발전했다. 2022년 IETF는 HTTP의 의미를 버전과 무관하게 정리한 RFC 9110을 냈다. 암호화는 SSL을 거쳐 TLS로 발전해 2018년 TLS 1.3이 표준이 되었다.

## 3. 직관적 설명 및 기초 이론

### URL을 입력하면 일어나는 일

`https://api.example.com/companies/005930?fields=price`

| 단계 | 하는 일 | 왕복 |
|---|---|---|
| 1. DNS | `api.example.com`의 IP 주소 조회(캐시에 있으면 생략) | 0~1+ |
| 2. TCP | SYN → SYN-ACK → ACK로 연결 수립 | 1 |
| 3. TLS 1.3 | 암호 방식 합의, 인증서 확인, 키 교환 | 1 |
| 4. HTTP | `GET /companies/005930?fields=price` 요청 → 응답 | 1 |

URL 구조: 스킴(`https`) / 호스트(`api.example.com`) / 경로(`/companies/005930`) / 쿼리(`?fields=price`).

### HTTP 요청과 응답

```text
POST /uploads HTTP/1.1
Host: preflight.internal
Content-Type: application/json
Authorization: Bearer <토큰>

{"file_hash": "ab12...", "rows": [ ... ]}
```

```text
HTTP/1.1 201 Created
Content-Type: application/json

{"upload_id": 42, "review_count": 3}
```

(설명용 예시이며 Preflight의 실제 API가 아니다.)

### 상태 코드 읽기

| 코드 | 뜻 | 원인 후보 |
|---|---|---|
| 200 OK / 201 Created | 성공 / 생성됨 | |
| 301, 302, 307, 308 | 다른 주소로 이동 | 주소 변경, http → https |
| 400 Bad Request | 요청 형식 오류 | JSON 오류, 필수 값 누락 |
| 401 Unauthorized | 인증 안 됨 | 토큰 없음·만료 |
| 403 Forbidden | 인증은 됐지만 권한 없음 | 권한 설정, 허용되지 않은 저장소·호스트 |
| 404 Not Found | 자원 없음 | 주소 오타, 삭제됨 |
| 409 Conflict | 상태 충돌 | 중복 생성, 동시 수정 |
| 429 Too Many Requests | 요청 한도 초과 | 속도 제한(LLM API에서 흔함) |
| 500 / 502 / 503 / 504 | 서버 오류 / 중계 서버가 받은 응답 오류 / 일시적 불가 / 중계 서버 시간 초과 | 버그, 과부하, 뒤쪽 서버 장애 |

## 4. 엄밀한 정의와 작동 원리

### TCP의 신뢰성

데이터를 조각(세그먼트)으로 나눠 번호를 붙여 보낸다. 받는 쪽은 받은 번호를 알려 주고(ACK), 보내는 쪽은 일정 시간 안에 ACK가 없으면 다시 보낸다. **혼잡 제어**는 손실이 생기면 보내는 속도를 줄이고, 잘 되면 늘린다. 새 연결은 느리게 시작하므로(slow start), 짧은 연결을 많이 여는 것보다 연결을 재사용하는 것이 빠르다.

### TLS와 인증서

서버는 인증 기관(CA)이 서명한 인증서로 "이 공개키가 이 도메인의 것"임을 증명한다. 클라이언트는 신뢰하는 CA 목록으로 서명을 확인한다. 회사 프록시가 통신을 검사하는 환경에서는 회사 CA를 신뢰 목록에 추가해야 하는데, 이를 빠뜨리면 "인증서 확인 실패" 오류가 난다.

### HTTP 메서드의 성질

| 메서드 | 용도 | 안전(조회만) | 멱등 |
|---|---|---|---|
| GET | 조회 | 예 | 예 |
| PUT | 전체 교체 | 아니오 | 예 |
| DELETE | 삭제 | 아니오 | 예 |
| POST | 생성, 처리 요청 | 아니오 | 아니오 |
| PATCH | 일부 수정 | 아니오 | 보장 안 됨 |

멱등한 요청은 네트워크 오류 때 다시 보내도 안전하다. POST를 안전하게 재시도하려면 멱등 키를 쓴다(DE-DB-002).

### 응답 시간 모형

$$
T \approx k \times RTT + \frac{\text{크기}}{\text{대역폭}} + T_{\text{서버}}
$$

$k$는 필요한 왕복 횟수. 새 HTTPS 연결이면 TCP 1 + TLS 1 + 요청 1로 $k = 3$(DNS 제외), 연결을 재사용하면 $k = 1$이다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| RTT | 왕복 시간(round-trip time) |
| 대역폭 | 초당 보낼 수 있는 데이터 양(예: 100 Mbps = 초당 1억 비트) |
| $k$ | 필요한 왕복 횟수 |
| $T_{\text{서버}}$ | 서버가 처리하는 시간 |
| TTL | DNS 캐시 유효 시간 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 새 연결 vs 재사용

RTT 50ms, 응답 크기 작음, 서버 처리 20ms.

- 새 HTTPS 연결: $3 \times 50 + 20 = 170$ms
- 연결 재사용: $1 \times 50 + 20 = 70$ms

API를 10번 순서대로 부르면 새 연결은 1.7초, 재사용은 0.7초. HTTP 클라이언트의 연결 재사용(keep-alive, 커넥션 풀)이 중요한 이유다. DB 연결도 같다(CS-OS-001의 커넥션 풀).

### 예제 2. 지연이 지배하나, 대역폭이 지배하나

대역폭 100 Mbps, RTT 50ms(연결 재사용, $k = 1$).

| 응답 크기 | 전송 시간 = 크기 ÷ 대역폭 | 합계(서버 처리 제외) |
|---|---|---|
| 10 KB | $80{,}000 \text{비트} / 10^8 = 0.0008$초 | 약 51ms (RTT가 대부분) |
| 10 MB | $8 \times 10^7 / 10^8 = 0.8$초 | 약 850ms (대역폭이 대부분) |

작은 API 응답을 빠르게 하려면 왕복 횟수를 줄이고(요청 묶기, 가까운 서버), 큰 파일은 크기를 줄이는(압축, 필요한 칸만) 것이 효과적이다. Preflight가 원본 파일 대신 파싱한 값만 보내는 구조는 보안 목적이지만, 전송량도 줄인다.

### 예제 3. 순서대로 부를까, 동시에 부를까

DeepVi처럼 답변 하나에 뉴스 검색, 기업 정보 검색, 메타 검색이 필요하다고 하자(각각 200ms라고 가정).

- 순서대로: $200 \times 3 = 600$ms
- 동시에(비동기): 가장 느린 것 기준 약 200ms

서로 결과에 의존하지 않는 호출은 동시에 보낼 수 있다(CS-OS-001의 이벤트 루프). 다만 외부 API의 속도 제한(429)을 넘지 않게 동시 수를 제한한다. DeepVi는 질문 유형별로 하나의 검색 체인을 탔으므로(저장소 코드) 이 예는 확장 아이디어다.

### 예제 4. 오류 메시지로 원인 좁히기

| 증상 | 해석 |
|---|---|
| `getaddrinfo ENOTFOUND` | DNS 실패: 이름 오타, 내부 DNS에만 있는 이름 |
| `ECONNREFUSED` | IP는 찾았는데 그 포트에서 아무도 안 받음: 서버 꺼짐, 포트 오류 |
| 시간 초과(timeout) | 방화벽이 조용히 버림, 서버 과부하, 경로 문제 |
| 인증서 오류 | 인증서 만료, 이름 불일치, 프록시 CA 미설치 |
| 401 → 403 | 401은 "누구세요?", 403은 "누군지 알지만 안 됨" |

## 7. 시각화와 해석

통신 과정은 세로축을 시간, 가로에 클라이언트와 서버를 두고 화살표를 비스듬히 그리는 **시퀀스 다이어그램**으로 그린다. 화살표가 오가는 횟수가 왕복 수이고, 화살표의 기울기가 지연이다. 브라우저 개발자 도구의 네트워크 탭은 요청마다 DNS, 연결, TLS, 대기(서버 처리), 다운로드 시간을 막대로 보여 주어, 느린 원인이 어디인지 바로 알 수 있다.

## 8. 기술 비교 및 선택 기준

| 선택 | 언제 |
|---|---|
| HTTP/JSON API | 대부분의 웹·서비스 간 통신, 사람이 읽기 쉬움 |
| WebSocket, 서버 전송 이벤트(SSE) | 서버가 계속 밀어 줘야 할 때(실시간 알림, LLM 답변 스트리밍) |
| gRPC | 서비스 간 고성능 통신, 스트리밍, 엄격한 스키마 |
| UDP 기반 | 실시간 음성·영상처럼 약간의 손실보다 지연이 중요할 때 |
| 사내망 전용 | 데이터가 외부로 나가면 안 될 때(Preflight) |

## 9. 실무 사례

- **LLM API 호출:** 응답이 길면 스트리밍(SSE 등)으로 토큰을 받는 대로 보여 줘 체감 지연을 줄인다. 429를 받으면 지수적으로 기다렸다 재시도한다.
- **CDN:** 정적 파일을 사용자와 가까운 서버에 복제해 RTT를 줄인다. 이 사이트의 three.js도 CDN에서 받는다.
- **사내 시스템 연동:** 방화벽·프록시·내부 DNS 때문에 "내 PC에서는 되는데 서버에서는 안 되는" 문제가 흔하다. 4절·6절의 오류 구분이 진단의 출발점이다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)과 이 사이트의 기록에서 옮긴 것이다.

- **Preflight — 사내망과 데이터 경계:** 클라우드 없이 사내 서버에서 운영하고, 원본 파일은 브라우저에서 파싱해 값만 서버에 저장한다. 개발/운영 서버를 분리했다. 점검 질문: 사내망 안이라도 HTTPS를 쓰는가? 브라우저와 서버 사이에서 값이 바뀌지 않았음을 어떻게 보장하는가?
- **DeepVi — 외부 API 의존:** GPT-4o, Gemini Flash, Pinecone 같은 외부 서비스를 호출했다. 각 호출에 RTT와 서버 처리 시간이 더해지고, 속도 제한(429)·일시 장애(503)에 대비한 재시도가 필요하다. 상시 운영 서버 여건이 되지 않아 공개 서비스로 열지 않았다는 기록도 있다.
- **이 학습 사이트 — CDN 실패 대비와 네트워크 정책:** three.js CDN 실패 시 대체 문구를 띄우는 E2E 시험이 있다. 예약 실행 환경은 허용된 호스트만 접근할 수 있어, 표준 문서 일부는 서지 정보로만 출처를 넣었다. 첫 예약 실행에서 저장소 푸시가 권한 문제로 거부(403)되었다가 저장소를 예약 작업 소스에 추가한 뒤 해결된 기록이 있다(HANDOFF.md).

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 대역폭을 늘리면 빨라진다.** 작은 요청은 RTT가 지배한다. 거리와 왕복 횟수를 줄여야 한다.
- **오해: 401과 403은 같다.** 401은 인증(누구인가), 403은 권한(무엇을 할 수 있나)이다. 해결 방법이 다르다.
- **오해: 사내망이면 암호화가 필요 없다.** 내부자 위협과 잘못된 네트워크 설정을 고려하면 내부도 TLS를 쓰는 추세다.
- **시간 초과 설정:** 너무 짧으면 정상 요청이 실패하고, 너무 길면 장애가 길게 번진다. 재시도와 함께 설계한다.
- **재시도의 위험:** 멱등하지 않은 요청(POST)을 무작정 재시도하면 중복 처리가 생긴다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 처음 접속하는 HTTPS 사이트에 요청 하나를 보낼 때 필요한 왕복 횟수(DNS 제외, TLS 1.3 기준)와 각 왕복의 용도는?</summary>

**정답.** 3번. TCP 연결 수립 1번, TLS 핸드셰이크 1번, HTTP 요청·응답 1번.

**해설.** 연결을 재사용하면 이후 요청은 1번 왕복이면 된다. TLS 1.2는 핸드셰이크에 2번 왕복이 필요했다.

</details>

<details class="qa" data-type="concept"><summary>Q2. GET과 POST 중 네트워크 오류 후 자동 재시도하기에 안전한 것은? 이유는?</summary>

**정답.** GET. 조회만 하는 안전하고 멱등한 메서드라 여러 번 보내도 서버 상태가 바뀌지 않는다.

**해설.** POST는 같은 요청이 두 번 처리될 수 있어, 재시도하려면 멱등 키 같은 장치가 필요하다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 사내 서버에서 외부 LLM API를 부르는 기능이 개발 PC에서는 되는데 운영 서버에서는 시간 초과가 난다. 어떤 순서로 확인하겠는가?</summary>

**정답.** ① 운영 서버에서 DNS 조회가 되는지, ② 해당 호스트·포트로 연결이 되는지(방화벽, 프록시 필요 여부), ③ 프록시가 있다면 프록시 설정과 회사 CA 인증서 설치, ④ 응답이 오면 상태 코드(401/403/429)를 확인한다. 시간 초과는 보통 방화벽이 패킷을 조용히 버릴 때 난다.

**해설.** 계층 아래부터(이름 → 연결 → 암호화 → HTTP) 차례로 좁히는 것이 빠르다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 화면 하나를 그리는 데 API를 순서대로 8번 부르고, 각 호출이 RTT 80ms + 서버 40ms다. 어떻게 빠르게 하겠는가?</summary>

**정답.** 지금은 약 $8 \times 120 = 960$ms(연결 재사용 가정). 서로 의존하지 않는 호출은 동시에 보내고, 자주 함께 쓰는 데이터는 API 하나로 묶으며, 연결 재사용을 확인한다. 모두 독립이면 약 120ms까지 줄 수 있다.

**해설.** 작은 요청 여러 개는 RTT의 합이 지배한다. 왕복 횟수를 줄이는 것이 핵심이다.

</details>
