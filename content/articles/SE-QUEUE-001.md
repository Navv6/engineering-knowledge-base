## 0. 한눈에 보기 (입문)

### 한 줄 요약
**메시지 큐**(message queue)는 "지금 당장 끝낼 필요가 없는 일"을 쪽지로 적어 줄 세워 두는 곳이다. 일을 맡기는 쪽은 쪽지만 꽂고 바로 다음 일로 넘어가고, 일하는 쪽은 자기 속도대로 하나씩 꺼내 처리한다. 대신 **같은 쪽지가 두 번 처리될 수 있다**는 점을 항상 대비해야 한다.

### 쉬운 설명
분식집 주방의 **주문표 꽂이**를 떠올리자.

- 계산대 직원(**생산자**, producer: 일을 만들어 넣는 쪽)은 주문을 받으면 주문표를 꽂이에 꽂고 바로 다음 손님을 받는다. 떡볶이가 다 될 때까지 손님 앞에 서서 기다리지 않는다.
- 꽂이(**큐**, queue: 먼저 온 것부터 줄 서는 대기열)는 주문표를 순서대로 붙들고 있다.
- 요리사(**소비자**, consumer: 일을 꺼내 처리하는 쪽)는 하나씩 꺼내 요리한다. 손님이 몰리면 요리사를 한 명 더 붙이면 된다.

이렇게 "맡기고 나중에 처리"하는 방식을 **비동기**(asynchronous: 요청과 처리가 같은 순간에 묶여 있지 않음) 처리라고 한다. 좋은 점은 세 가지다.

1. **손님이 덜 기다린다.** 계산대는 주문표만 꽂으면 끝이다.
2. **몰려도 무너지지 않는다.** 점심에 주문이 한꺼번에 와도 꽂이에 쌓일 뿐, 주문을 놓치지 않는다.
3. **한쪽이 쉬어도 다른 쪽이 계속 일한다.** 요리사가 잠깐 자리를 비워도 계산대는 주문을 계속 받는다.

주의할 점도 있다. 요리사가 떡볶이를 다 만들었는데 "완료" 표시를 하기 직전에 넘어졌다고 하자. 다른 요리사는 주문표에 완료 표시가 없으니 **같은 떡볶이를 또 만든다.** 그래서 큐를 쓰는 시스템은 "같은 일이 두 번 와도 결과가 한 번 한 것과 같게"(이것을 **멱등**이라고 한다) 만들어 두는 것이 기본이다.

숫자로도 감을 잡을 수 있다. 1분에 주문이 12개 오는데 요리사 3명이 각자 1분에 3개씩, 합해서 9개를 만든다면 꽂이에는 1분마다 3개씩 쌓인다(12 − 9 = 3). 10분이면 30개가 밀린다. 요리사를 1명 더 붙여 1분에 12개를 만들어야 겨우 쌓이지 않는다.

### 내 프로젝트에서는
세 프로젝트 모두 **메시지 큐 제품(RabbitMQ, Kafka 등)을 썼다는 기록은 없다.** 다만 큐의 핵심 원리가 이미 들어가 있는 곳이 있다.

- **Preflight의 검토 대기열은 "사람이 소비자인 큐"다.** 동기화할 때 위험도를 판정해 **위험한 변경만 검토 대기열로 보내고**, 사람이 하나씩 꺼내 승인·거부한다(포트폴리오 기재). 판정 엔진(생산자)과 검토자(소비자)가 서로 기다리지 않고 각자 속도로 일하는 구조라는 점이 메시지 큐와 같다. 포트폴리오에는 "운영 첫 업로드에서 검토 건이 몰림"도 문제로 적혀 있는데, 이는 6절 예제 1의 "도착이 처리보다 빠르면 쌓인다"가 실제로 나타난 경우다.
- **Preflight의 재업로드 멱등성은 큐 소비자에게 꼭 필요한 성질이다.** 같은 파일을 두 번 올려도 행·검토 건이 늘지 않고, 파일 지문 확인 단계에서 같은 파일·더 오래된 파일은 반영 전에 멈춘다(포트폴리오 기재). 큐는 같은 메시지를 다시 보낼 수 있으므로, 큐 뒤의 처리기는 바로 이런 방식으로 중복을 막는다.
- **DeepVi는 매일 뉴스를 수집해 Pinecone에 벡터로 저장했다.** 수집 → 임베딩 → 저장으로 이어지는 흐름인데, 큐를 썼는지는 기록 없음. 기사 수가 늘거나 외부 API(GPT-4o, Gemini Flash) 호출이 느려질 때 단계 사이에 큐를 두면 한 단계가 막혀도 앞 단계가 멈추지 않는다(적용 아이디어).

## 1. 핵심 요약

- **구성:** 생산자(producer)가 메시지를 **브로커**(broker: 메시지를 받아 보관하고 넘겨 주는 중간 서버)에 넣고, 소비자(consumer)가 꺼내 처리한 뒤 **확인 응답**(ack, acknowledgement)을 보낸다. ack를 받은 메시지만 지워진다.
- **왜 쓰나:** 느린 일을 요청 경로에서 떼어 내 응답을 빠르게(비동기화), 몰리는 요청을 줄 세워 흡수(부하 평준화), 생산자·소비자가 서로의 장애에 덜 묶이게(결합도 낮춤).
- **두 모양:** 한 메시지를 소비자 **한 명**이 처리하는 작업 큐(point-to-point), 한 메시지를 **여러 구독자**가 각각 받는 발행·구독(publish/subscribe).
- **전달 보장:** 실무의 기본은 **최소 한 번**(at-least-once). 처리 후 ack 전에 죽으면 다시 온다. 그래서 소비자는 **멱등**해야 한다. "정확히 한 번"은 브로커만으로는 끝나지 않고, 소비자의 중복 제거와 함께 만들어진다.
- **용량 계산:** 도착률 $\lambda$가 처리 용량 $c\mu$보다 크면 대기열은 $(\lambda - c\mu)$의 속도로 끝없이 늘어난다. 평균 대기 수는 리틀의 법칙 $L = \lambda W$로 이어진다. 가동률이 100%에 가까울수록 대기 시간이 급격히 길어진다.
- **안전장치:** 재시도와 지수 대기(exponential backoff), 계속 실패하는 메시지를 따로 빼는 **데드 레터 큐**(DLQ), DB 변경과 메시지 발행을 함께 묶는 **아웃박스 패턴**, 순서가 필요하면 키 단위 순서 보장.

## 2. 개념과 등장 배경

프로그램끼리 메시지를 주고받는 방식은 크게 둘이다. 상대가 답할 때까지 기다리는 **동기 호출**(전화)과, 메시지를 맡겨 두고 각자 일하는 **비동기 메시징**(우편함)이다. 1980~90년대 은행·항공 예약 같은 대형 업무 시스템은 서로 다른 시스템을 잇기 위해 **메시지 지향 미들웨어**(MOM, message-oriented middleware)를 썼다. 상대 시스템이 잠시 꺼져 있어도 메시지를 잃지 않는 것이 핵심 요구였다.

2003년 호프(Gregor Hohpe)와 울프(Bobby Woolf)는 『Enterprise Integration Patterns』에서 메시지 채널, 점대점 채널, 발행·구독 채널, 데드 레터 채널, 멱등 수신자(idempotent receiver) 같은 패턴에 이름을 붙여 정리했다. 지금도 이 용어가 그대로 쓰인다.

2000년대 후반부터는 오픈소스 브로커가 널리 퍼졌다. RabbitMQ는 AMQP라는 메시징 프로토콜을 구현한 브로커로, 라우팅 규칙에 따라 메시지를 큐에 나눠 주는 데 강하다. 2011년 LinkedIn에서 나온 **Kafka**는 메시지를 지우지 않고 **추가만 하는 로그**(log: 순서대로 이어 붙이기만 하는 기록)로 저장해, 여러 소비자가 각자 읽은 위치를 기억하고 필요하면 과거부터 다시 읽게 했다. 클라우드에서는 관리형 큐 서비스가 흔해졌다. 한편 PostgreSQL은 9.5 버전부터 `SKIP LOCKED`를 제공해, 별도 브로커 없이 **DB 테이블을 큐로 쓰는** 방식도 실용적이 되었다.

AI 응용에서도 큐는 흔하다. 문서 임베딩, 음성 변환, LLM 일괄 호출처럼 "오래 걸리고, 외부 API 한도에 걸리고, 실패하면 다시 해야 하는" 일이 대표적인 큐 작업이다.

## 3. 직관적 설명 및 기초 이론

### 동기 처리와 비동기 처리 비교

파일 업로드 후 처리에 2분이 걸리는 화면을 생각하자.

| | 동기 처리 | 큐를 쓴 비동기 처리 |
|---|---|---|
| 요청 흐름 | 업로드 → (2분 처리) → 응답 | 업로드 → 작업 등록 → 즉시 "접수됨" 응답 → 소비자가 2분 처리 |
| 사용자가 기다리는 시간 | 2분 | 거의 없음(결과는 나중에 확인) |
| 처리 중 서버가 재시작되면 | 요청 실패, 사용자가 다시 올림 | 메시지가 큐에 남아 있어 다시 처리됨 |
| 동시에 100명이 올리면 | 서버 자원이 한꺼번에 소진될 수 있음 | 큐에 100건이 쌓이고 소비자 수만큼씩 처리 |
| 대가 | 단순함 | 상태 조회 화면, 중복 처리 대비, 운영할 부품 하나 추가 |

### 작업 큐와 발행·구독

- **작업 큐(point-to-point):** "이 파일 처리해 줘" 같은 **명령**. 소비자 여러 명이 같은 큐를 나눠 먹지만, 메시지 하나는 한 명만 처리한다. 소비자를 늘리면 처리량이 늘어난다.
- **발행·구독(publish/subscribe):** "업로드 1043이 반영됐다" 같은 **사건**(event). 알림 발송, KPI 재계산, 검색 색인 갱신처럼 관심 있는 쪽이 **각자 한 부씩** 받는다. 생산자는 누가 듣는지 몰라도 된다.

### 메시지 한 건의 일생

1. 생산자가 메시지를 보낸다. 브로커가 안전하게 저장한 뒤 "받았다"고 답한다(발행 확인).
2. 브로커가 메시지를 소비자 A에게 넘긴다. 이 순간 메시지는 "처리 중"으로 표시되고, 다른 소비자에게는 가지 않는다.
3. A가 처리를 마치고 ack를 보낸다. 브로커는 메시지를 지운다(또는 Kafka처럼 "여기까지 읽었다"는 위치만 앞으로 옮긴다).
4. A가 ack 없이 죽거나 연결이 끊기면, 브로커는 메시지를 다시 "대기"로 돌려 다른 소비자에게 넘긴다(재전달, redelivery).

4단계가 큐를 믿을 수 있게 만드는 핵심이면서, 동시에 **중복 처리의 원인**이다.

## 4. 엄밀한 정의와 작동 원리

### 전달 보장 세 가지

소비자가 "처리"와 "ack"를 어떤 순서로 하느냐에 따라 보장이 달라진다.

| 보장 | 소비자 순서 | 장애 시 | 결과 |
|---|---|---|---|
| 최대 한 번(at-most-once) | ack → 처리 | ack 후 처리 중 죽음 | 메시지 **유실** 가능, 중복 없음 |
| 최소 한 번(at-least-once) | 처리 → ack | 처리 후 ack 전에 죽음 | 유실 없음, **중복** 가능 |
| 정확히 한 번(exactly-once) | 처리 결과와 "처리함" 기록을 한 트랜잭션으로 | 어느 시점에 죽어도 | 효과가 정확히 한 번 |

네트워크 너머에서는 "상대가 처리했는데 답만 사라진 경우"와 "처리하지 못한 경우"를 구별할 수 없다(SE-API-001의 재시도 문제와 같다). 그래서 유실을 피하려면 다시 보내야 하고, 다시 보내면 중복이 생긴다. 실무의 결론은 **"최소 한 번 전달 + 멱등한 소비자 = 효과는 정확히 한 번"**이다. Kafka는 0.11 버전(2017년)부터 멱등 프로듀서와 트랜잭션을 제공해 Kafka 안에서 읽고 쓰는 범위의 정확히 한 번 처리를 지원하지만, 처리 결과를 외부 DB나 외부 API에 쓰는 부분까지 자동으로 보장해 주지는 않는다.

### 멱등한 소비자 만들기

- **처리 기록 테이블:** 메시지마다 고유 ID를 붙이고, 처리할 때 `processed_messages(message_id)`에 유니크 제약으로 기록한다. 업무 변경과 이 기록을 **같은 트랜잭션**에 넣으면, 두 번째 도착한 메시지는 유니크 위반으로 걸러진다(DE-DB-002).
- **자연스러운 멱등 연산:** "재고를 1 줄여라"(중복이면 두 번 줄어듦) 대신 "반출 기록 #881을 만들어라"(이미 있으면 무시)처럼, 결과 상태를 지정하는 연산으로 바꾼다.
- **내용 지문:** 같은 내용이면 같은 결과가 되도록 내용의 해시(지문)를 키로 쓴다. Preflight의 파일 지문 확인이 이 방식이다.

### 재시도, 지수 대기, 데드 레터 큐

일시적 실패(외부 API 429, 네트워크 끊김)는 다시 하면 성공한다. 하지만 바로 다시 하면 이미 힘든 상대를 더 몰아붙인다. 그래서 대기 시간을 1초, 2초, 4초, 8초…처럼 두 배씩 늘리는 **지수 대기**를 쓰고, 여러 소비자가 같은 순간에 몰리지 않도록 약간의 무작위 흔들림(jitter)을 더한다.

어떤 메시지는 몇 번을 해도 실패한다(형식이 깨진 파일, 코드 버그). 이런 **독이 든 메시지**(poison message)를 계속 재시도하면 큐 맨 앞을 막거나 소비자 자원을 계속 먹는다. 그래서 최대 횟수를 넘긴 메시지는 **데드 레터 큐**(DLQ, dead-letter queue)라는 별도 큐로 옮겨 사람이 보게 한다. RabbitMQ는 이를 데드 레터 익스체인지(dead letter exchange)로, 관리형 큐 서비스들도 비슷한 설정으로 제공한다(설정 방법은 제품별로 다르니 확인 필요).

### 순서

"먼저 넣은 것이 먼저 나온다(FIFO)"는 소비자가 하나일 때만 깔끔하게 성립한다. 소비자가 여럿이면 메시지 2가 메시지 1보다 먼저 끝날 수 있고, 재전달된 메시지는 뒤늦게 다시 처리된다. Kafka는 토픽을 **파티션**(partition: 토픽을 나눈 칸, 칸마다 순서가 있는 로그)으로 나누고, **같은 키**(예: 기업 코드, 업로드 ID)를 가진 메시지를 같은 파티션에 넣어 **키 단위로만** 순서를 보장한다. 전체 순서가 꼭 필요하면 병렬성을 포기해야 한다. 그래서 설계할 때 "정말 전체 순서가 필요한가, 같은 대상 안에서만 필요한가"를 먼저 묻는다.

### 아웃박스 패턴: DB 변경과 메시지 발행 묶기

"업로드를 DB에 반영하고, 반영됐다는 이벤트를 큐에 보낸다"를 두 단계로 하면 그 사이에서 죽을 때 둘이 어긋난다(DB에는 반영됐는데 이벤트 없음, 또는 그 반대). **아웃박스**(outbox) 패턴은 업무 변경과 함께 `outbox` 테이블에 보낼 메시지를 **같은 트랜잭션**으로 기록하고, 별도 프로세스가 outbox를 읽어 브로커로 보낸 뒤 "보냄" 표시를 한다. 이 전달도 중복될 수 있으므로 소비자는 여전히 멱등해야 한다.

### DB 테이블을 큐로 쓰기

이미 PostgreSQL이 있고 처리량이 크지 않으면 별도 브로커 없이 테이블로 충분할 수 있다. 소비자 여러 개가 같은 행을 집지 않게 하는 것이 핵심이다.

```sql
-- 소비자 하나가 작업 하나를 집는다 (트랜잭션 안에서)
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- 처리 후: UPDATE jobs SET status = 'done' WHERE id = :id; COMMIT;
```

PostgreSQL 공식 문서는 `SKIP LOCKED`가 즉시 잠글 수 없는 행을 건너뛰며, 일관되지 않은 데이터 보기를 주므로 일반 용도에는 맞지 않지만 **큐 같은 테이블에 여러 소비자가 접근할 때 잠금 경합을 피하는 데** 쓸 수 있다고 설명한다. 트랜잭션 안에서 처리하다 소비자가 죽으면 트랜잭션이 롤백되고 행 잠금이 풀려, `pending` 상태 그대로인 그 행을 다른 소비자가 다시 집는다. ack·재전달과 같은 효과다. 다만 오래 걸리는 처리 동안 트랜잭션과 잠금을 계속 쥐고 있는 것은 부담이므로, 실무에서는 "처리 중 + 시작 시각"을 기록하고 시간이 지나면 다시 집을 수 있게 하는 방식도 쓴다.

## 5. 수식 및 기호 설명

| 기호 | 읽기 | 뜻 | 예 |
|---|---|---|---|
| $\lambda$ | 람다 | 도착률: 단위 시간당 들어오는 메시지 수 | 분당 120건 |
| $\mu$ | 뮤 | 소비자 **한 명**의 처리율: 단위 시간당 처리하는 수 | 분당 30건 |
| $c$ | | 소비자(일꾼) 수 | 3명 |
| $\rho$ | 로 | 가동률: 처리 능력 중 실제로 쓰이는 비율, $\rho = \lambda / (c\mu)$ | 0.8 = 80% |
| $L$ | | 시스템 안(대기 + 처리 중)에 있는 평균 메시지 수 | 30건 |
| $W$ | | 메시지 하나가 시스템에 머무는 평균 시간 | 0.5분 |

**누적 속도.** 처리 용량은 $c\mu$이다. $\lambda > c\mu$이면 대기열은 단위 시간마다 $\lambda - c\mu$씩 늘어난다. 시간 $t$ 동안 쌓이는 양은 $(\lambda - c\mu)\,t$이다.

**비우는 시간.** 대기 $B$건이 쌓여 있고 도착이 $\lambda' < c\mu$로 줄었다면, 비우는 데 걸리는 시간은
$$
T_{\text{drain}} = \frac{B}{c\mu - \lambda'}
$$
이다. 비우는 동안에도 새 메시지가 계속 들어오므로 분모가 $c\mu$가 아니라 $c\mu - \lambda'$이다.

**리틀의 법칙(Little's law).** 안정된 시스템(오래 보면 들어오는 만큼 나가는 시스템)에서
$$
L = \lambda W
$$
가 성립한다. 도착 간격이나 처리 시간의 분포에 상관없이 성립하는 것이 강점이다(Little, 1961). 대기열 길이 $L$과 도착률 $\lambda$를 재면 평균 대기 시간 $W = L / \lambda$를 바로 추정할 수 있다.

**가동률과 대기 시간(심화).** 도착이 무작위(포아송 과정)이고 처리 시간이 지수분포인 소비자 1명 모형(M/M/1)에서는 평균 체류 시간이
$$
W = \frac{1}{\mu - \lambda}
$$
이다($\lambda < \mu$). 이 가정은 현실과 다를 수 있지만, "가동률이 1에 가까워지면 대기 시간이 폭증한다"는 모양은 대부분의 큐에서 나타난다.

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 몰림이 쌓이고 비워지는 시간

평소 분당 30건이 들어오는 업로드 처리 큐가 있다. 소비자 3명이 각자 분당 30건을 처리한다($c\mu = 3 \times 30 = 90$건/분). 월요일 아침 10분 동안 분당 120건이 몰렸다.

1. 몰리는 동안 누적 속도: $\lambda - c\mu = 120 - 90 = 30$건/분
2. 10분 뒤 대기: $30 \times 10 = 300$건
3. 이후 도착이 분당 30건으로 돌아오면 비우는 속도: $c\mu - \lambda' = 90 - 30 = 60$건/분
4. 비우는 시간: $T_{\text{drain}} = 300 / 60 = 5$분

몰림이 끝난 직후에 들어온 메시지는 앞의 300건을 기다려야 하므로, 처리량 90건/분 기준으로 약 $300 / 90 \approx 3.3$분 기다린다. 큐 덕분에 메시지는 하나도 잃지 않았지만, **결과가 늦게 나오는 시간**이 생겼다. 이 지연이 허용되는지가 소비자 수를 정하는 기준이다.

### 예제 2. 리틀의 법칙으로 대기 시간 추정

모니터링 화면에서 큐 안(대기 + 처리 중)의 메시지가 평균 30건이고, 도착률은 분당 60건이다.

$$
W = \frac{L}{\lambda} = \frac{30}{60} = 0.5\text{분} = 30\text{초}
$$

메시지 하나가 들어와서 처리가 끝날 때까지 평균 30초 걸린다는 뜻이다. 대기 시간을 직접 재기 어려울 때, 큐 길이와 도착률만으로 추정할 수 있다.

### 예제 3. 가동률 80%와 95%의 차이

소비자 1명이 초당 10건($\mu = 10$)을 처리하는 M/M/1 모형에서 도착률만 바꿔 본다.

| 도착률 $\lambda$ | 가동률 $\rho = \lambda/\mu$ | 평균 체류 $W = 1/(\mu - \lambda)$ | 평균 메시지 수 $L = \lambda W$ |
|---|---|---|---|
| 5 | 0.5 | $1/5 = 0.2$초 | 1 |
| 8 | 0.8 | $1/2 = 0.5$초 | 4 |
| 9 | 0.9 | $1/1 = 1$초 | 9 |
| 9.5 | 0.95 | $1/0.5 = 2$초 | 19 |

가동률이 0.8에서 0.95로 0.15 늘었을 뿐인데 체류 시간은 4배가 됐다. "평균 처리량이 도착률보다 크니 괜찮다"로 끝내지 않고 여유(보통 가동률을 넉넉히 낮게)를 두는 이유다.

### 예제 4. 지수 대기와 독이 든 메시지

재시도 대기를 1, 2, 4, 8, 16초로 두면 5번 재시도에 걸리는 대기 합은 $1+2+4+8+16 = 31$초다. 실패가 서로 독립이고 매번 10% 확률로 실패한다면 5번 모두 실패할 확률은 $0.1^5 = 0.00001$이다. 하지만 형식이 깨진 파일은 **매번 100% 실패**하므로 이 계산이 맞지 않는다. 실패는 독립이 아닐 때가 많다. 그래서 횟수를 넘기면 DLQ로 보내고, DLQ 건수를 경보로 감시한다(OPS-OBS-001).

### 예제 5. 처리 후 ack 전에 죽는 경우

반출 처리 소비자가 메시지 "반출 #881, 샘플 2개"를 받았다.

| 시점 | 일 | 멱등하지 않은 소비자("재고 −2") | 멱등한 소비자("반출 #881 기록, 이미 있으면 무시") |
|---|---|---|---|
| t1 | 재고 차감 커밋 | 재고 10 → 8 | 반출 #881 생성, 재고 8 |
| t2 | ack 보내기 전 소비자 재시작 | | |
| t3 | 브로커가 같은 메시지 재전달 | 재고 8 → **6 (틀림)** | #881 이미 있음 → 무시, 재고 8 |

최소 한 번 전달에서는 t2가 언젠가 반드시 일어난다고 보고 설계한다.

## 7. 시각화와 해석

큐를 운영할 때는 숫자 세 개를 시간 축으로 함께 본다.

- **대기열 길이**(backlog, lag): 계속 오르면 $\lambda > c\mu$라는 뜻이다. 몰림 뒤 내려오는 기울기가 비우는 속도($c\mu - \lambda'$)다.
- **가장 오래된 메시지의 나이:** 길이보다 사용자 체감에 가깝다. "업로드 후 결과가 나올 때까지 최대 몇 분"을 목표로 경보를 건다.
- **DLQ 건수:** 0이 정상이다. 늘기 시작하면 코드 버그나 입력 형식 변화를 의심한다.

대기열 길이 그래프가 톱니 모양(올랐다가 내려옴)이면 정상적인 몰림 흡수이고, 계단처럼 계속 오르기만 하면 용량 부족이나 소비자 장애다.

## 8. 기술 비교 및 선택 기준

| 방식 | 장점 | 단점 | 적합 |
|---|---|---|---|
| 프로세스 안의 비동기(async/await, 스레드 풀) | 부품 추가 없음, 가장 단순 | 프로세스가 죽으면 작업 유실, 서버 여러 대로 나누기 어려움 | 잃어도 되는 짧은 작업(CS-OS-001) |
| DB 테이블 큐(`SKIP LOCKED`) | 이미 있는 DB 사용, 업무 변경과 같은 트랜잭션으로 등록 가능 | 처리량 한계, 폴링·잠금 부하, DB에 부담 | 소규모 사내 시스템, 분당 수백~수천 건 수준(규모 기준은 환경마다 다름) |
| 메시지 브로커(RabbitMQ 등) | ack·재전달·DLQ·라우팅 기본 제공 | 운영할 서버 추가, 처리 후 메시지 사라짐(다시 읽기 어려움) | 작업 분배, 서비스 간 명령 전달 |
| 로그 기반(Kafka 등) | 높은 처리량, 보존 기간 동안 다시 읽기, 여러 소비자 그룹 | 운영 복잡도 큼, 파티션 설계 필요, 개별 메시지 단위 재시도는 직접 구현 | 이벤트 스트림, 데이터 파이프라인(DE-PIPE-001) |
| 관리형 클라우드 큐 | 운영 부담 적음 | 클라우드 의존, 비용, 제품별 제약 | 클라우드를 쓰는 서비스 |

**선택 질문:** ① 작업을 잃어도 되는가(안 되면 프로세스 밖 큐) ② 이미 DB가 있고 양이 적은가(테이블 큐부터) ③ 같은 사건을 여러 소비자가 각자 읽거나 나중에 다시 읽어야 하는가(로그 기반) ④ 운영할 사람이 있는가(없으면 부품을 늘리지 않는다).

## 9. 실무 사례

- **문서 임베딩 파이프라인:** 새 문서가 들어오면 "임베딩 작업"을 큐에 넣고, 소비자가 청크 분할 → 임베딩 API 호출 → 벡터 DB 저장을 한다. 임베딩 API의 속도 제한에 맞춰 소비자 수를 조절하고, 문서 ID + 내용 해시로 중복 저장을 막는다(AI-RAG-001, AI-EMB-001).
- **음성 일괄 변환:** 녹음 파일마다 변환 작업을 큐에 넣고 GPU 소비자 수만큼 병렬로 처리한다. 예를 들어 6,000개 파일을 개당 4초에 처리하는 소비자 4개로 돌리면 $6000 \times 4 / 4 = 6000$초 = 100분이 걸린다(설명용 숫자). 실패 파일은 DLQ로 모아 원인을 따로 본다.
- **알림·후속 처리:** "주문 완료" 사건을 발행하면 이메일 발송, 재고 갱신, 통계 집계가 각자 구독한다. 이메일 서버가 느려도 주문 응답은 늦어지지 않는다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다. 세 프로젝트 모두 메시지 큐 제품을 사용했다는 기록은 없다.

- **Preflight — 검토 대기열과 몰림:** 위험한 변경만 검토 대기열로 보내고, 업로드 단위로 되돌릴 수 있다. "운영 첫 업로드에서 검토 건이 몰림 → 일괄 처리와 변경 상세를 다음 개선으로 정함"이 문제로 기재되어 있다. 큐 관점에서 일괄 처리는 소비자 처리율 $\mu$를 높이는 방법이다. 점검 질문(기록 없음): 검토 대기열의 하루 도착 건수와 처리 건수, 가장 오래 기다린 건의 나이를 기록하는가?
- **Preflight — 멱등성과 지문:** 재업로드 멱등성, 파일 지문 확인(같은 파일·더 오래된 파일은 반영 전에 멈춤). 큐 소비자의 중복 방지 방법(4절 "내용 지문")과 같다.
- **Preflight — PostgreSQL 단일 DB와 사내 서버:** 클라우드 없이 사내 서버에서 운영하고 전 모듈을 PostgreSQL로 이전했다. 비동기 작업이 필요해진다면 브로커를 새로 운영하기보다 `SKIP LOCKED` 테이블 큐가 먼저 검토할 만한 후보다(적용 아이디어). 점검 질문(기록 없음): 업로드 처리는 요청 안에서 동기로 끝나는가? 처리 중 서버가 재시작되면 어떻게 되는가?
- **DeepVi — 매일 뉴스 수집과 벡터 저장:** 매일 수집한 기업 뉴스를 Pinecone 벡터로 저장했고, 기업 분석 코멘트·뉴스 요약에 GPT-4o와 Gemini Flash를 썼다. 점검 질문(기록 없음): 수집·임베딩·요약 중 한 단계가 실패하면 나머지가 어떻게 되었는가? 같은 기사가 두 번 저장되는 것을 무엇으로 막았는가?
- **STT 평가 — 6,000개 평가 데이터:** KsponSpeech eval_clean 3,000개 + eval_other 3,000개로 4개 모델을 평가했다. 작업 단위가 "파일 × 모델"로 나뉘는 전형적인 작업 큐 문제다. 실제 실행 방식은 기록 없음.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 큐를 쓰면 처리량이 늘어난다.** 큐는 몰림을 **늦게라도 처리**하게 할 뿐이다. 평균 도착률이 처리 용량보다 크면 큐는 끝없이 길어진다. 처리량은 소비자 수와 처리 속도가 정한다.
- **오해: 브로커가 "정확히 한 번"을 보장하니 중복 걱정이 없다.** 브로커 안의 보장과, 소비자가 외부 DB·API에 남기는 효과는 다르다. 소비자를 멱등하게 만드는 것이 기본이다.
- **오해: 큐는 순서대로 처리된다.** 소비자가 여럿이거나 재전달이 있으면 순서가 바뀐다. 순서가 필요한 범위(키)를 정하고 그 범위만 보장한다.
- **숨는 실패:** 동기 처리는 실패가 바로 사용자에게 보이지만, 비동기 처리는 실패가 큐 뒤에 숨는다. 대기열 길이, 가장 오래된 메시지의 나이, DLQ 건수를 감시하지 않으면 며칠 뒤에야 안다(OPS-OBS-001).
- **복잡도 비용:** 부품 하나, 상태 조회 화면, 재시도·중복 처리 코드가 늘어난다. 작업이 짧고 잃어도 되면 큐 없이 처리하는 편이 낫다.
- **무한 버퍼는 없다:** 큐도 디스크·메모리 한도가 있다. 한도에 가까우면 생산자를 늦추거나(배압, backpressure) 새 요청을 거절(429)해야 한다.
- **모형의 한계:** M/M/1 공식은 무작위 도착·지수분포 처리 시간 가정에 기댄다. 실제 큐는 몰림이 뭉쳐 오므로 공식보다 나쁠 수 있다. 리틀의 법칙은 분포 가정이 없지만 "안정된 시스템"의 장기 평균에 대한 식이라, 몰림이 진행 중인 순간에는 맞지 않는다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. 최소 한 번(at-least-once) 전달에서 중복이 생기는 구체적인 순간은 언제이고, 소비자는 무엇으로 대비하는가?</summary>

**정답.** 소비자가 처리를 끝내고(효과가 반영되고) ack를 보내기 전에 죽거나 연결이 끊기는 순간이다. 브로커는 ack를 못 받았으니 같은 메시지를 다시 넘긴다. 소비자는 메시지 ID를 처리 기록 테이블에 유니크 제약으로 남기고 업무 변경과 같은 트랜잭션에 묶거나, 결과 상태를 지정하는 연산으로 바꿔 멱등하게 만든다.

**해설.** ack를 먼저 보내면 중복은 없지만 처리 중 죽을 때 메시지를 잃는다(최대 한 번). 유실과 중복 중 하나를 고르는 문제이고, 대부분은 유실을 피하고 중복을 소비자에서 걸러 낸다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 큐 길이가 평균 120건이고 도착률이 분당 40건이다. 메시지 하나가 들어와서 처리가 끝날 때까지 평균 몇 분 걸리는가? 어떤 법칙을 썼고, 그 법칙이 맞으려면 무엇이 필요한가?</summary>

**정답.** $W = L / \lambda = 120 / 40 = 3$분. 리틀의 법칙 $L = \lambda W$를 썼고, 시스템이 안정적(장기적으로 들어오는 만큼 나감)이어야 하며 $L$과 $\lambda$가 같은 범위(대기 + 처리 중)와 긴 기간의 평균이어야 한다.

**해설.** 리틀의 법칙은 도착·처리 시간 분포를 가정하지 않아 실무에서 쓰기 좋다. 대기열이 계속 늘어나는 중이라면 안정 상태가 아니므로 그대로 쓰면 안 된다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 임베딩 작업 큐의 소비자가 같은 메시지에서 계속 예외를 내며 무한히 재시도하고 있고, 그 뒤의 작업들이 밀린다. 무엇이 문제이고 어떻게 고치겠는가?</summary>

**정답.** 몇 번을 해도 실패하는 독이 든 메시지(poison message)를 횟수 제한 없이 재시도하는 것이 문제다. 재시도에 지수 대기와 최대 횟수를 두고, 횟수를 넘기면 데드 레터 큐로 옮겨 나머지 작업이 계속 흐르게 한다. DLQ 건수에 경보를 걸고, DLQ의 메시지는 원인(입력 형식, 코드 버그)을 고친 뒤 다시 넣는다.

**해설.** 일시적 실패(429, 네트워크)와 영구적 실패(형식 오류)를 구분해야 한다. 영구적 실패는 재시도해도 성공 확률이 올라가지 않는다.

</details>

<details class="qa" data-type="judgment"><summary>Q4. PostgreSQL 하나로 운영하는 소규모 사내 시스템에서 "업로드 후 무거운 집계"를 비동기로 바꾸려 한다. Kafka를 도입하자는 의견과 DB 테이블 큐를 쓰자는 의견 중 무엇을 먼저 권하겠는가?</summary>

**정답.** DB 테이블 큐(`FOR UPDATE SKIP LOCKED`)를 먼저 권한다. 처리량이 작고, 운영할 부품이 늘지 않으며, 업로드 반영과 작업 등록을 같은 트랜잭션으로 묶을 수 있어 아웃박스 문제가 저절로 풀린다. 여러 소비자가 같은 사건을 각자 읽어야 하거나 처리량이 DB 한계를 넘을 때 브로커·로그 기반으로 옮긴다.

**해설.** Kafka의 강점(높은 처리량, 재읽기, 여러 소비자 그룹)은 이 상황에서 필요하지 않고 운영 비용만 커진다. 판단 기준은 기술의 유명함이 아니라 요구(유실 허용 여부, 처리량, 재읽기, 운영 인력)다.

</details>

<details class="qa" data-type="applied"><summary>Q5. 평소 분당 50건이 들어오고 소비자 1명이 분당 20건을 처리한다. 매일 오전 9시부터 15분 동안 분당 100건이 몰린다. 몰림이 끝난 뒤 10분 안에 대기열을 비우려면 소비자가 최소 몇 명 필요한가?</summary>

**정답.** 4명. 소비자 $c$명이면 용량은 $20c$건/분이다. 몰리는 동안 쌓이는 양은 $(100 - 20c) \times 15$, 이후 비우는 속도는 $20c - 50$. 조건은 $(100 - 20c) \times 15 / (20c - 50) \le 10$. $c = 3$이면 $(100-60) \times 15 = 600$건, 비우는 속도 $10$건/분 → 60분(불합격). $c = 4$면 $(100-80) \times 15 = 300$건, 비우는 속도 $30$건/분 → 10분(합격).

**해설.** 평소 도착률(50)만 보면 3명(용량 60)으로 충분해 보이지만, 몰림 뒤 비우는 속도는 용량에서 평소 도착률을 뺀 값이라 매우 느리다. 소비자 수는 "평균"이 아니라 "몰림과 허용 지연"으로 정한다.

</details>

## 14. 참고 자료

출처는 아래 패널에 있다. `SKIP LOCKED`의 동작과 "큐 같은 테이블에 여러 소비자가 접근할 때 잠금 경합을 피하는 데 쓸 수 있다"는 서술은 PostgreSQL 공식 문서(SELECT의 Locking Clause)를 직접 확인했다. RabbitMQ·Kafka 공식 문서는 이 환경에서 접속할 수 없어, 제품별 설정·버전 의존 세부(데드 레터 설정 방법 등)는 확인 필요로 남겼다. 패턴 이름은 Hohpe·Woolf(2003), 전달 보장과 로그 기반 메시징은 Kleppmann(2017) 11장, 리틀의 법칙은 Little(1961)을 따랐다. 예제의 숫자는 설명용이며 Preflight·DeepVi의 실제 측정값이 아니다.
