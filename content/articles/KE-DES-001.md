## 0. 한눈에 보기 (입문)

### 한 줄 요약
**온톨로지 설계**는 "이 분야에서 무엇이 존재하고(개념), 서로 어떤 관계인지"를 정하는 일이다. 좋은 설계는 세상을 완벽히 묘사하는 것이 아니라 **미리 정한 질문들(역량 질문)에 답할 수 있게** 만드는 것에서 시작한다.

### 쉬운 설명
도서관 분류 체계를 새로 만든다고 하자.

- 먼저 **이용자가 무엇을 찾는지** 묻는다. "어린이용 과학책은 어디 있어요?", "이 작가의 다른 책은?" 이것이 **역량 질문**이다.
- 그 질문에 답하려면 무엇이 필요한지 정한다. "책", "작가", "주제", "대상 연령"(개념)과 "쓰다", "다루다"(관계).
- 애매한 결정을 내린다. "어린이용"을 별도 분류로 둘까, 책의 속성(대상 연령 = 어린이)으로 둘까?
- 질문들을 실제로 던져 보고, 답이 안 나오면 고친다.

모든 것을 다 담으려 하면 끝나지 않는다. 질문이 범위를 정한다.

### 내 프로젝트에서는
- **온톨로지를 실제로 설계·구축한 기록은 없다.** 아래는 Preflight·DeepVi 도메인을 설계 **연습** 대상으로 쓴 것이다.
- **Preflight에는 온톨로지와 같은 구조적 결정이 이미 있다**(포트폴리오 기재). 샘플조달·시사출·CT 세 업무가 같은 판정 엔진을 쓰고 업무마다 어댑터와 정책만 다르다 → 상위 클래스 "업무"와 하위 클래스 세 개. 판정 키에 워크센터를 포함(ADR-02) → "업무를 식별하는 데 품목만으로는 부족하다"는 개념 정의의 수정. 빠진 행을 업무 단계(완료·취소·드롭)로 관리(ADR-05) → 상태를 클래스가 아니라 시간에 따라 바뀌는 속성으로 다루는 결정.
- **DeepVi의 질문 분류도 일종의 개념 체계다.** 질문을 뉴스 / 재무·실적 / 거시 / 일반으로 나눴다(저장소 코드). 범주가 겹치는 질문이 생기는 문제(CS-REGEX-001 예제 3)는 개념 체계를 설계할 때 "서로소인가, 겹쳐도 되는가"를 정하는 문제와 같다.

### 먼저 알면 좋은 것
- RDF·OWL·SPARQL(KE-RDF-001): 클래스, 속성, SPARQL 질의
- FDE와 솔루션 설계(PE-FDE-001): 현장 요구를 문제로 바꾸기

## 1. 핵심 요약

- **정의:** 온톨로지는 "공유된 개념화의 명시적 명세"(Gruber 1993의 정의를 따른 표현). 사람과 시스템이 같은 뜻으로 단어를 쓰게 하는 약속이다.
- **순서(Noy & McGuinness의 단계):** 범위와 역량 질문 → 기존 온톨로지 재사용 검토 → 용어 나열 → 클래스와 계층 → 속성(관계) → 속성 제약(정의역·치역·개수) → 개체 → 검증.
- **역량 질문:** "이 온톨로지로 답할 수 있어야 하는 질문" 목록. 설계의 범위이자 시험 문제(Grüninger & Fox).
- **핵심 판단:** 클래스 vs 속성 값 vs 개체, 하위 클래스 vs 분류 속성, 관계에 정보가 붙으면 관계 자체를 개체로(다항 관계).
- **시간·출처:** 바뀌는 사실은 시점과 함께, 추출된 사실은 출처와 함께(KE-KGB-001).
- **반복:** 역량 질문을 SPARQL로 바꿔 실제 데이터로 돌려 보고, 답이 안 나오면 고친다. 테스트 주도 개발과 같은 흐름이다.

## 2. 개념과 등장 배경

"온톨로지"는 원래 철학에서 "존재하는 것이 무엇인가"를 다루는 분야의 이름이다. 1990년대 초 인공지능 연구에서 지식 공유를 위해 이 말을 빌려 썼고, 1993년 토머스 그루버(Thomas Gruber)가 "개념화의 명시적 명세"라는 정의를 제시했다. 1995년 그뤼닝거(Grüninger)와 폭스(Fox)는 **역량 질문**으로 온톨로지의 요구사항을 정하고 평가하는 방법을 제안했다.

2001년 스탠퍼드의 노이(Noy)와 맥기니스(McGuinness)가 쓴 「Ontology Development 101」은 Protégé 도구와 함께 실무 입문서로 널리 읽혔다. 이후 METHONTOLOGY, NeOn 같은 체계적 방법론과, 자주 나오는 문제의 표준 해법을 모은 **온톨로지 설계 패턴**이 정리되었다. 오늘날에는 LLM이 용어 후보 추출과 초안 작성을 돕지만, 범위 결정과 개념 구분은 여전히 도메인 전문가와의 협업이 핵심이다.

## 3. 직관적 설명 및 기초 이론

### 클래스, 속성, 개체

| 구성 요소 | 뜻 | 예(Preflight 연습) |
|---|---|---|
| 클래스 | 같은 종류의 모임 | 업무, 시사출, 워크센터, 품목, 업로드 |
| 하위 클래스 | 더 구체적인 종류 | 시사출 ⊑ 업무 |
| 개체 | 클래스의 구체적인 하나 | 업무 #123, 워크센터 WC-2 |
| 객체 속성 | 개체와 개체의 관계 | 업무 —수행장소→ 워크센터 |
| 데이터 속성 | 개체와 값의 관계 | 업무 —납기→ 2026-12-01 |

### 자주 하는 판단

| 질문 | 기준 |
|---|---|
| 하위 클래스로 둘까, 속성 값으로 둘까? | 하위 클래스마다 다른 속성·규칙이 붙으면 클래스, 단순한 구분이면 속성 값 |
| 클래스로 둘까, 개체로 둘까? | 그 아래에 다시 여러 개가 속하면 클래스, 하나뿐인 구체적 대상이면 개체 |
| 관계로 둘까, 개체로 둘까? | 관계에 날짜·수량·출처 같은 정보가 붙으면 관계 자체를 개체로(다항 관계) |
| 바뀌는 성질은? | 시점과 함께 이력으로(상태, 담당자) |

## 4. 엄밀한 정의와 작동 원리

### 역량 질문에서 설계로

1. 현장 사용자와 함께 질문을 모은다(PE-FDE-001의 인터뷰).
2. 각 질문에서 명사(후보 클래스)와 동사(후보 관계)를 뽑는다.
3. 질문을 SPARQL 질의로 써 본다. 쓸 수 없으면 무언가 빠진 것이다.
4. 실제 데이터 일부로 질의를 돌려 기대한 답이 나오는지 확인한다.
5. 답이 안 나오는 질문, 너무 복잡해지는 질의를 보고 설계를 고친다.

### 다항 관계 패턴

"업무 #123을 워크센터 WC-2에서 수량 300으로 2026-11-20에 사출했다"는 두 대상 사이의 단순 관계로 담을 수 없다. 관계 자체를 개체(사건)로 만든다:

```text
:사출작업_9 a :사출작업 ;
    :대상업무 :업무123 ;
    :수행장소 :WC-2 ;
    :수량 300 ;
    :일자 "2026-11-20"^^xsd:date .
```

### 시간에 따라 바뀌는 상태

상태를 개체에 직접 덮어쓰면 이력이 사라진다. 상태 변경을 사건으로 남긴다:

```text
:상태변경_77 a :상태변경 ;
    :대상업무 :업무123 ;
    :이전상태 :진행중 ; :새상태 :완료 ;
    :시각 "2026-11-21T10:00:00"^^xsd:dateTime ;
    :출처 :사람입력 .
```

"현재 상태"는 가장 최근 상태변경에서 구한다(DE-SQL-001의 그룹별 최신 한 건과 같은 질의). 출처를 두면 Preflight의 "사람 > 파일 > 시스템" 우선순위 같은 규칙을 표현할 수 있다.

### 서로소와 완전성

같은 상위 클래스 아래 하위 클래스들이 겹치면 안 되는지(서로소), 모든 개체가 반드시 하나에 속해야 하는지(완전 분할) 정한다. OWL로 `owl:disjointWith`를 선언하면 둘 다에 속한 개체가 생길 때 불일치로 잡힌다(KE-RDF-001). 규칙 기반 분류의 겹침 문제(MATH-DM-001 예제 4)를 설계 단계에서 명시하는 것이다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| $C_1 \sqsubseteq C_2$ | $C_1$은 $C_2$의 하위 클래스 |
| 역량 질문(CQ) | 온톨로지가 답해야 할 질문 |
| 정의역 / 치역 | 속성의 주어 / 목적어가 속하는 클래스 |
| 다항 관계 | 셋 이상의 참여자·속성을 가진 관계(사건 개체로 표현) |
| 서로소 | 두 클래스에 동시에 속하는 개체가 없음 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 역량 질문으로 범위 정하기 (Preflight 연습)

| 번호 | 역량 질문 | 필요한 개념 |
|---|---|---|
| CQ1 | 납기가 지났는데 완료되지 않은 시사출 업무는? | 시사출, 납기, 상태 |
| CQ2 | 워크센터 WC-2에서 이번 주 처리할 업무는? | 워크센터, 수행장소, 일정 |
| CQ3 | 사람이 고친 완료일이 ERP 값과 다른 업무는? | 완료일, 출처, 값 비교 |
| CQ4 | 지난 업로드에서 검토로 간 변경과 그 사유는? | 업로드, 변경, 검토, 사유 |
| CQ5 | 같은 품목을 여러 워크센터에서 진행 중인 경우는? | 품목, 워크센터, 업무 식별 |

CQ5는 Preflight의 ADR-02(품목만으로 판정하면 정상 데이터가 지워짐)를 개념 수준에서 드러낸다. "업무 = 품목"이 아니라 "업무는 품목과 워크센터 등으로 식별된다"고 정의해야 CQ5에 답할 수 있다. 이 표는 포트폴리오 기재 사항에서 만든 설계 연습이며 Preflight의 실제 요구사항 문서가 아니다.

### 예제 2. CQ를 SPARQL 시험으로

CQ1을 질의로 쓰면:

```text
SELECT ?task WHERE {
  ?task a :시사출 ; :납기 ?due .
  FILTER(?due < "2026-11-26"^^xsd:date)
  FILTER NOT EXISTS { ?task :현재상태 :완료 }
}
```

이 질의를 쓰려고 하니 `:현재상태`가 필요하다는 것이 드러난다. 상태를 이력(상태변경 사건)으로만 두었다면 "현재 상태" 계산 규칙을 정해야 한다. 시험 데이터(완료 1건, 미완료 2건, 납기 안 지남 1건)를 넣고 기대 결과 2건이 나오는지 확인한다. 이렇게 CQ마다 질의와 기대 결과를 묶어 두면, 설계를 바꿀 때마다 회귀 시험으로 돌릴 수 있다(SE-TEST-001).

### 예제 3. 진척도

역량 질문 9개 중 현재 설계로 SPARQL을 쓸 수 있고 시험 데이터에서 기대 결과가 나오는 것이 7개라면, 진척도는 $7/9 \approx 78\%$다. 나머지 2개가 무엇을 요구하는지(새 클래스? 시간 표현?)가 다음 반복의 작업 목록이 된다.

## 7. 시각화와 해석

클래스 계층은 나무 그림으로, 속성은 클래스 사이의 이름 붙은 화살표로 그린다(개념도). 역량 질문 × 필요한 클래스·속성 표를 만들면, 어떤 개념이 많은 질문을 떠받치는지(핵심 개념), 어떤 개념은 어떤 질문에도 쓰이지 않는지(범위 밖일 가능성)가 보인다. 이 사이트의 지식 지도처럼 개념 그래프를 3D로 둘러보는 것도 탐색에는 도움이 된다.

## 8. 기술 비교 및 선택 기준

| 선택 | 언제 |
|---|---|
| 기존 표준 온톨로지 재사용(schema.org, 업계 표준) | 공통 개념(조직, 사람, 장소, 제품)과 외부 데이터 연동 |
| 자체 설계 | 업무 고유 개념(판정 규칙, 업무 단계) |
| 가벼운 분류 체계(SKOS류) | 용어 정리와 검색이 목적, 추론 불필요 |
| OWL 제약까지 | 자동 분류·불일치 검출이 필요할 때 |
| 관계형 스키마로 충분 | 질문이 정해져 있고 관계가 단순할 때(DE-MODEL-001) |

## 9. 실무 사례

- **제조 지식 그래프:** 설비·공정·품목·불량 유형을 온톨로지로 정의하고, 불량 원인 분석 질문(CQ)으로 범위를 정한다.
- **의료 용어:** 표준 의학 용어 체계를 재사용하고 병원 고유 코드를 연결한다.
- **기업 데이터 통합:** 부서마다 다른 "고객" 정의를 온톨로지로 조정해 같은 질문에 같은 답이 나오게 한다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다. 온톨로지를 구축한 기록은 없으므로 모두 설계 연습 또는 적용 가능성이다.

- **Preflight — 클래스 계층:** 세 업무가 같은 판정 엔진 + 업무별 어댑터·정책 → 상위 클래스 "업무"에 공통 규칙, 하위 클래스에 업무별 규칙.
- **Preflight — 식별 정의:** 판정 키에 워크센터 포함(ADR-02), 원본 값으로 행 식별 → "무엇이 같은 업무인가"의 정의를 고친 결정. 예제 1의 CQ5.
- **Preflight — 상태와 이력:** 빠진 행을 업무 단계로 관리(ADR-05), 출처 우선순위(사람 > 파일 > 시스템) → 4절의 상태변경 사건 + 출처 패턴.
- **DeepVi — 범주 설계:** 질문 범주(뉴스/재무/거시/일반)가 겹치는 문제 → 범주를 서로소로 정의할지, 여러 범주를 허용할지 먼저 정하는 설계 결정.
- **면접 대비:** "Preflight 도메인을 온톨로지로 설계한다면"을 CQ → 클래스 → 속성 → SPARQL 시험 순서로 설명하면 방법론을 보여 줄 수 있다. 실제 구축 경험과는 구분해서 말한다.

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 온톨로지는 클 수록 좋다.** 질문에 쓰이지 않는 개념은 유지 비용만 늘린다.
- **오해: 개념 정의는 개발자가 하면 된다.** 같은 단어의 업무상 뜻(예: "완료")은 현장이 정한다. 협업이 필수다.
- **클래스 남용:** 상태·색·크기 같은 값을 모두 하위 클래스로 만들면 계층이 폭발한다.
- **이름 붙이기:** 사람이 읽는 이름(label)과 바뀌지 않는 식별자를 분리한다. 이름은 바뀐다.
- **추론 비용:** 표현력 높은 OWL 제약은 계산 비용이 크다. 필요한 만큼만 쓴다(KE-RDF-001).

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. "주문 #5가 고객 김OO에게 2026-11-20에 상품 A 3개를 판매"를 표현하려면 단순 관계와 다항 관계 중 무엇이 적합한가?</summary>

**정답.** 다항 관계. 판매(또는 주문) 자체를 개체로 만들고 고객, 상품, 수량, 일자를 그 개체의 속성으로 단다.

**해설.** 두 대상 사이의 관계 하나로는 수량·일자 같은 정보를 붙일 곳이 없다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 역량 질문이 설계 과정에서 하는 두 가지 역할은?</summary>

**정답.** ① 범위를 정하는 요구사항(무엇을 담아야 하나), ② 완성도를 검증하는 시험(질의로 바꿔 답이 나오는지 확인).

**해설.** 역량 질문 → SPARQL 시험의 흐름은 테스트 주도 개발과 같다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 팀이 "모든 업무 상태를 클래스로(진행중업무, 완료업무, 취소업무…)" 설계했다. 어떤 문제가 있고 어떻게 바꾸겠는가?</summary>

**정답.** 상태가 바뀔 때마다 개체의 클래스를 바꿔야 하고, 이력과 변경 시각·출처를 표현하기 어렵다. 상태를 속성 값으로 두고, 상태 변경을 시각·출처가 있는 사건 개체로 남기며, 현재 상태는 최신 사건에서 구하도록 바꾼다.

**해설.** Preflight의 업무 단계 관리(ADR-05)와 같은 판단이다.

</details>

<details class="qa" data-type="applied"><summary>Q4. 새 도메인(예: 물류 창고)의 온톨로지를 2주 안에 처음 설계해야 한다. 어떤 순서로 하겠는가?</summary>

**정답.** ① 현장 인터뷰로 역량 질문 10~20개 수집, ② 기존 표준(장소·조직·제품) 재사용 검토, ③ 질문에서 용어를 뽑아 클래스·속성 초안, ④ 질문마다 SPARQL과 기대 결과를 쓰고 실제 데이터 표본으로 시험, ⑤ 답이 안 나오는 질문을 기준으로 수정, ⑥ 현장과 함께 용어 정의 검토.

**해설.** 질문 → 설계 → 시험 → 수정의 짧은 반복이 핵심이다.

</details>
