## 0. 한눈에 보기 (입문)

### 한 줄 요약
**데이터 파이프라인**은 데이터를 원천(ERP, API, 파일)에서 가져와(Extract) 다듬고(Transform) 쓸 곳에 넣는(Load) 자동화된 흐름이다. 좋은 파이프라인의 조건은 빠름보다 **다시 돌려도 안전하고(멱등), 틀렸을 때 되돌릴 수 있고, 조용히 틀리지 않는 것**이다.

### 쉬운 설명
식당의 식재료 흐름을 떠올리자.

- **Extract(받기):** 매일 아침 시장에서 재료가 들어온다.
- **Transform(손질):** 씻고, 썰고, 상한 것을 골라낸다.
- **Load(보관):** 바로 쓸 수 있게 정리해 냉장고 칸에 넣는다.

두 가지 방식이 있다. 손질한 것만 보관하는 방식(**ETL**)은 깔끔하지만, 나중에 다른 요리에 필요한 부위를 이미 버렸을 수 있다. 일단 **받은 그대로 보관**하고 필요할 때 손질하는 방식(**ELT**)은 공간을 더 쓰지만, 나중에 새 메뉴가 생겨도 원재료에서 다시 손질할 수 있다.

### 내 프로젝트에서는
- **Preflight는 ETL에서 "원본 보존"으로 바꿨다.** 처음에는 화면에 필요한 **12개 필드만** 저장했으나, 미결 업무 목록·준수율 집계에 빠진 정보가 필요해져 **ERP 원본 전체를 보존하고 필요한 값을 가공하는** 구조로 바꿨다(포트폴리오 기재). 예시의 "이미 버린 부위" 문제를 실제로 겪고 고친 것이다.
- **업로드를 전체 교체에서 누적 병합으로 바꿨다(08.16).** 매번 전부 지우고 새로 넣는 대신, 기존 데이터에 바뀐 것만 합친다. 이때부터 "같은 행을 어떻게 알아보나(행 식별)", "같은 파일을 두 번 넣으면?(멱등성)"이 핵심 문제가 되었고, Preflight는 원본 값 기반 행 식별과 재업로드 멱등성으로 답했다.
- **DeepVi는 매일 수집 파이프라인이었다.** 기업 뉴스를 매일 수집해 Pinecone에 벡터로 저장하고, 재무·주가·뉴스·ESG·거시지표를 PostgreSQL에 저장했다(포트폴리오·저장소 기재). 매일 돌아가는 파이프라인은 "어제 실패한 날을 어떻게 다시 채우나(재처리)"를 반드시 고민해야 한다.

### 먼저 알면 좋은 것
- 관계형 데이터 모델링(DE-MODEL-001): 테이블, 키
- 트랜잭션과 ACID(DE-DB-002): 멱등성, upsert, 업로드 단위 트랜잭션

## 1. 핵심 요약

- **ETL vs ELT:** 가공 후 적재 vs 원본 적재 후 가공. 저장 비용이 싸진 지금은 원본을 보존하는 ELT가 흔하다.
- **층 구조:** 원본(raw) → 정제(staging: 형식 통일, 중복 제거) → 업무용(mart: 집계, 지표). 각 층을 다시 만들 수 있어야 한다.
- **적재 방식:** 전체 교체(단순, 느림, 이력 없음) vs 증분 적재(빠름, 행 식별·삭제 처리 필요).
- **멱등성:** 재실행·재처리에 안전해야 한다. 키 기반 upsert/MERGE, 기간 단위 교체.
- **품질 검사:** 행 수, 필수 값, 키 중복, 합계 대조, 원천과의 대사. 실패하면 다음 단계로 넘기지 않는다.
- **상태 vs 이력:** "지금 상태" 테이블만 있으면 과거 집계가 나중에 바뀔 수 있다. 변경 이력(또는 날짜별 스냅숏)을 남긴다.

## 2. 개념과 등장 배경

1980~90년대 기업들은 운영 시스템(주문, 회계)의 데이터를 분석용 **데이터 웨어하우스**로 옮겨 보고서를 만들었다. 랠프 킴벌(Ralph Kimball)과 빌 인먼(Bill Inmon)이 웨어하우스 설계 방법론을 정리했고, 이 시기 데이터를 옮기는 과정이 ETL로 불렸다. 저장과 계산이 비쌌기 때문에 필요한 것만 다듬어 넣는 것이 합리적이었다.

2010년대 클라우드 저장소와 대규모 분석 DB가 싸지면서, 원본을 먼저 넣고 DB 안에서 SQL로 가공하는 **ELT**가 퍼졌다. 동시에 작업 의존 관계를 DAG로 정의해 스케줄링하는 워크플로 도구(Airflow 등)와, 가공 SQL을 버전 관리하고 테스트하는 도구(dbt 등)가 표준적인 구성 요소가 되었다. 요즘은 "데이터도 코드처럼 테스트하고 배포한다"는 관점이 일반적이다.

## 3. 직관적 설명 및 기초 이론

### 파이프라인의 단계

| 단계 | 하는 일 | 대표 실패 |
|---|---|---|
| 추출 | API 호출, 파일 수신, DB 조회 | 원천 장애, 형식 변경, 일부만 받음 |
| 검증 | 형식·필수 값·행 수 확인 | 검증 없이 넘어가 조용히 틀림 |
| 원본 적재 | 받은 그대로 저장 | 원본을 안 남겨 재처리 불가 |
| 가공 | 정규화, 조인, 중복 제거, 계산 | 잘못된 키로 중복 제거(정상 데이터 삭제) |
| 업무 적재 | 화면·집계용 테이블 갱신 | 중간 실패로 반쯤 갱신된 상태 노출 |

### 전체 교체 vs 증분

| | 전체 교체 | 증분(누적 병합) |
|---|---|---|
| 방법 | 매번 비우고 전부 넣음 | 바뀐 것만 추가·갱신 |
| 장점 | 단순, 원천과 항상 같음 | 빠름, 이력·사람 수정값 보존 가능 |
| 단점 | 느림, 사람이 고친 값이 날아감 | 행 식별, 삭제 감지, 멱등성 설계 필요 |
| 원천에서 행이 사라지면 | 자동으로 사라짐 | 직접 정해야 함(삭제? 보류? 단계 변경?) |

Preflight가 누적 병합으로 바꾸면서 "파일에서 빠진 행은 지우지 않고 업무 단계로 관리"(ADR-05)를 정한 것이 오른쪽 아래 칸에 대한 답이다.

## 4. 엄밀한 정의와 작동 원리

### 멱등한 적재

적재 함수 $L$을 같은 입력 $x$에 두 번 적용해도 결과가 같으면 멱등하다:

$$
L(L(S, x), x) = L(S, x)
$$

$S$는 현재 DB 상태다. 키 기반 upsert는 멱등하고, 단순 INSERT는 멱등하지 않다. PostgreSQL에서는 `INSERT ... ON CONFLICT` 또는 `MERGE`(조건에 따라 갱신·삽입·삭제를 한 문장으로)로 구현한다.

### 증분 추출과 워터마크

"마지막으로 가져온 시각 이후에 바뀐 행만" 가져오는 방식:

```sql
SELECT * FROM source WHERE updated_at > :last_watermark;
-- 성공하면 last_watermark = 이번에 가져온 행의 최대 updated_at
```

**함정:** ① 원천 시스템의 시계나 커밋 지연 때문에 워터마크 직전 시각으로 늦게 기록되는 행을 놓칠 수 있다 → 겹치는 구간(예: 10분 전부터)을 다시 가져오고 멱등 적재로 중복을 흡수한다. ② 삭제된 행은 `updated_at`으로 잡히지 않는다 → 원천의 삭제 표시나 전체 키 목록 비교가 필요하다.

### 상태 테이블 vs 이력

| 저장 방식 | "3주 전 미결 건수"를 지금 다시 계산하면 |
|---|---|
| 지금 상태만(덮어쓰기) | 그 사이 바뀐 행 때문에 **다른 값**이 나올 수 있음 |
| 변경 이력(유효 기간 행, 이벤트 로그) | 그 시점 기준으로 **같은 값** 재현 |
| 날짜별 스냅숏 | 같은 값, 저장 공간 많이 씀 |

킴벌의 "천천히 변하는 차원(SCD) 2형"은 행마다 유효 시작·끝 날짜를 두어 이력을 보존하는 대표적 방법이다.

### 대사(reconciliation)

파이프라인 끝에서 원천과 결과를 맞춰 본다:

$$
\text{원천 행 수} = \text{적재 행 수} + \text{거부 행 수} + \text{중복 제거 행 수}
$$

이 등식이 안 맞으면 어디선가 행이 조용히 사라진 것이다.

## 5. 수식 및 기호 설명

| 기호·용어 | 뜻 |
|---|---|
| $L(S, x)$ | 상태 $S$에 입력 $x$를 적재한 결과 |
| 워터마크 | 마지막으로 처리한 시각·번호 |
| upsert / MERGE | 있으면 갱신, 없으면 삽입 |
| 재처리(backfill) | 과거 기간을 다시 돌려 채우기 |
| SCD 2형 | 행마다 유효 기간을 두어 이력 보존 |

## 6. 단계별 계산 또는 동작 예제

### 예제 1. 전체 교체가 사람의 수정을 지우는 과정

| 시점 | 일 | ERP 값 | 화면 값 |
|---|---|---|---|
| 월 | ERP 파일 업로드 | 납기 12/01 | 12/01 |
| 화 | 담당자가 화면에서 납기를 12/05로 수정 | 12/01 | 12/05 |
| 수 | 새 ERP 파일 업로드(전체 교체) | 12/01 | **12/01** (사람 수정 사라짐) |

누적 병합 + 출처 우선순위(사람 > 파일 > 시스템)로 바꾸면 수요일에도 12/05가 유지되고, ERP 값이 바뀐 경우에만 검토로 보낸다. Preflight가 실제로 택한 방식이다(포트폴리오 기재: 출처 우선순위, "사람이 고친 칸을 ERP가 다른 값으로 바꾸면 덮지 않고 검토").

### 예제 2. 워터마크가 행을 놓치는 경우

워터마크 = 10:00:00. 10:05 실행에서 `updated_at > 10:00:00`인 행을 가져오고 최대값 10:04:58로 워터마크를 옮겼다. 그런데 10:04:30에 시작한 원천 트랜잭션이 10:05:30에 커밋되며 `updated_at = 10:04:30`으로 기록되었다. 다음 실행은 `> 10:04:58`만 보므로 이 행은 **영원히 누락**된다.

대책: 매 실행에서 `updated_at > 워터마크 − 15분`으로 겹쳐 가져오고, 키 기반 upsert로 중복을 흡수한다. 겹치는 행은 다시 적재되지만 결과는 같다(멱등).

### 예제 3. 행 수 대사

ERP 파일 1,240행 → 형식 오류 거부 12행, 완전 중복 제거 8행, 적재 1,220행. $1240 = 1220 + 12 + 8$ ✓.

만약 적재 1,200행이면 20행이 설명되지 않는다. 이런 불일치를 찾는 검사를 파이프라인에 넣어 두면, Preflight의 "품목 기준 중복 제거가 두 사출처의 정상 데이터를 지운" 문제(ADR-02) 같은 사고를 더 일찍 발견할 수 있다. 그 문제에서는 "중복 제거 행 수"가 예상보다 많아졌을 것이기 때문이다.

### 예제 4. 지금 상태만 세면 과거가 바뀐다

11월 첫 주 금요일에 "미결 업무 20건"을 보고했다. 둘째 주에 그중 3건이 파일에서 빠져 드롭 처리되었다. 지금 테이블만 보고 "첫 주 금요일 기준 미결"을 다시 세면, 드롭된 3건의 처리 방식에 따라 17건이 나올 수 있다. Preflight는 일부 실적 집계가 '지금 목록'만 세어 지난주 숫자가 바뀔 수 있음을 발견하고, 모든 산출식에 세는 범위(지금 목록·지난 기록·원본 누적 등)를 명시했다(포트폴리오 기재).

## 7. 시각화와 해석

파이프라인은 상자(단계)와 화살표(데이터 흐름)로 그린 DAG다(MATH-GRAPH-001). 각 화살표에 행 수를 적어 두면(1,240 → 1,228 → 1,220) 어디서 데이터가 줄었는지 한눈에 보인다. 매일 적재 행 수를 시간 순으로 그리면 원천 장애로 반토막 난 날이 튀어 보이고, 이것을 관리도로 감시할 수도 있다(STAT-SPC-001).

## 8. 기술 비교 및 선택 기준

| 상황 | 권장 |
|---|---|
| 데이터가 작고(수만 행) 원천이 기준이며 사람이 수정하지 않음 | 전체 교체(한 트랜잭션으로) |
| 사람 수정이 섞이거나 이력이 필요 | 누적 병합 + 출처 우선순위 + 변경 이력 |
| 원천이 변경 시각을 제공 | 워터마크 증분 + 겹치는 구간 + 멱등 적재 |
| 대용량 파일 적재 | PostgreSQL `COPY`로 임시 테이블에 넣고 `MERGE`/upsert |
| 실시간 반영 필요 | 변경 데이터 캡처(CDC), 스트림 처리 |
| 작업 간 의존이 많음 | DAG 기반 워크플로 도구 |

## 9. 실무 사례

- **일 배치:** 새벽에 전날 주문을 추출해 매출 집계 테이블을 갱신하고, 집계가 원천 합계와 맞는지 대사한 뒤 대시보드에 반영한다.
- **재처리:** 환율 원천이 사흘간 잘못된 값을 보냈다. 원본을 보존했기 때문에 고친 원천으로 해당 사흘만 다시 돌린다.
- **스키마 변경 감지:** 원천이 칸 이름을 바꾸면 추출 단계에서 실패시키고 알린다. 조용히 NULL로 채우면 몇 주 뒤에야 발견된다.

## 10. 기존 프로젝트와의 연결

아래 사실은 포트폴리오·저장소 원문(`content/profile.json`)에서 옮긴 것이다.

- **Preflight — 동기화 파이프라인:** 파일 지문 확인(같은 파일·더 오래된 파일은 반영 전에 멈춤) → 원본 값으로 행 식별 → 지난번 ERP 값 기준 칸 비교 → 위험도 판정 → 검토 대기열. 지문 확인은 멱등성, 행 식별은 증분 병합의 키, 칸 비교는 변경 감지, 위험도 판정은 품질 게이트다.
- **Preflight — 원본 보존과 정규화:** ERP 원본 전체를 보존하고 필요한 값을 가공한다. ExcelJS·SheetJS가 모두 읽지 못한 비표준 xlsx를 보정하는 정규화 모듈은 추출 단계의 형식 문제를 해결한 것이다.
- **Preflight — 되돌리기와 안전한 변경:** 업로드 단위로 되돌릴 수 있고, DB 변경은 더하기만 한다. 파이프라인이 틀렸을 때 복구할 수 있는 설계다.
- **Preflight — 대장 대조:** 표·칸·계산식 대장을 실제 DB와 칸 단위로 대조하고, 18개 칸 누락을 발견했다. 메타데이터 수준의 대사다.
- **DeepVi — 매일 수집:** 뉴스는 Pinecone(news-ns 네임스페이스), 재무·주가·뉴스·ESG·거시는 PostgreSQL. 점검 질문(기록 없음): 수집이 실패한 날을 재처리하는 방법이 있었는가? 같은 기사가 두 번 벡터화되지 않도록 키를 두었는가?

## 11. 가정·한계·흔한 오해·트레이드오프

- **오해: 파이프라인이 에러 없이 끝났으면 데이터가 맞다.** 가장 위험한 실패는 에러 없이 일부 행만 들어오거나 값이 틀리는 것이다. 대사와 품질 검사가 필요하다.
- **오해: 원본은 가공 후 버려도 된다.** 요구가 바뀌거나 가공 로직에 버그가 있을 때 원본이 없으면 재처리할 수 없다.
- **증분의 복잡도:** 삭제, 늦게 도착하는 데이터, 키 변경을 모두 처리해야 한다. 데이터가 작으면 전체 교체가 오히려 안전할 수 있다.
- **개인정보:** 원본 보존은 민감 정보도 보존한다는 뜻이다. 보존 기간과 접근 권한을 정한다. Preflight는 원본 파일을 브라우저에서 파싱하고 값만 저장했다.
- **시간대와 날짜:** "하루"의 경계(UTC vs KST)를 정하지 않으면 날짜별 집계가 어긋난다.

## 12. 이해 확인 및 면접 질문

<details class="qa" data-type="concept"><summary>Q1. ETL과 ELT의 차이와, 요즘 ELT가 흔해진 이유는?</summary>

**정답.** ETL은 가공한 뒤 적재하고, ELT는 원본을 먼저 적재한 뒤 저장소 안에서 가공한다. 저장 비용이 싸지고 분석 DB의 계산 능력이 커져, 원본을 보존해 재가공·재처리할 수 있는 이점이 비용보다 커졌기 때문이다.

**해설.** Preflight의 12개 필드 → 원본 보존 전환이 같은 이유다.

</details>

<details class="qa" data-type="concept"><summary>Q2. 워터마크 기반 증분 추출에서 행을 놓칠 수 있는 두 가지 경우와 대책은?</summary>

**정답.** ① 늦게 커밋되어 워터마크 이전 시각으로 기록된 행 → 겹치는 구간을 다시 읽고 멱등 적재. ② 원천에서 삭제된 행 → 삭제 표시 컬럼이나 주기적 전체 키 비교.

**해설.** 겹쳐 읽기는 멱등 적재가 있어야 안전하다.

</details>

<details class="qa" data-type="judgment"><summary>Q3. 매주 ERP 파일을 받아 전체 교체로 적재하는데, 현장 담당자가 화면에서 고친 값이 사라진다는 불만이 나왔다. 어떻게 바꾸겠는가?</summary>

**정답.** 누적 병합으로 바꾸고, 행을 안정적인 업무 키로 식별하며, 칸마다 출처(사람/파일/시스템)와 우선순위를 둔다. ERP 값이 사람 수정값과 다르게 바뀌면 덮지 않고 검토로 보낸다. 파일에서 빠진 행은 삭제하지 않고 상태로 관리하며, 업로드 단위로 되돌릴 수 있게 이력을 남긴다.

**해설.** Preflight가 실제로 택한 설계다(누적 병합 08.16, 출처 우선순위, ADR-05).

</details>

<details class="qa" data-type="applied"><summary>Q4. 매일 뉴스 수집 파이프라인이 사흘간 실패한 것을 오늘 알았다. 무엇을 하고, 재발을 어떻게 막겠는가?</summary>

**정답.** 사흘치를 기간 지정으로 재처리하되, 기사 URL 등 키 기반 upsert로 이미 들어온 일부와 중복되지 않게 한다. 재발 방지로 일별 적재 건수 감시(0건 또는 평소 대비 급감 시 알림), 실행 결과 기록, 실패 시 알림을 둔다.

**해설.** 실패 자체보다 "사흘 뒤에야 알았다"가 더 큰 문제다. 감시와 기록이 파이프라인의 일부다.

</details>
